# 매퍼 후보 판정

기준일: 2026-08-07

전체 한글화에는 원본의 256 KiB PRG와 128 KiB CHR 한계를 넘어서는 저장 공간이 필요하다. 동시에 배터리 SRAM, 16 KiB 가변 PRG 뱅크, 고정 마지막 뱅크와 MMC4의 타일 트리거 CHR 전환을 대체해야 한다. 헤더만 바꾸는 변환은 성립하지 않는다.

## 현재 후보

| 후보 | 맞는 점 | 남는 문제 | 판정 |
| --- | --- | --- | --- |
| MMC3, mapper 4 | 더 큰 PRG·CHR, 선택적 PRG RAM | MMC4의 타일별 FD/FE 래치가 없고 PRG 창도 8 KiB 중심 | 직접 변환 후보 아님 |
| UNROM512, mapper 30 | 512 KiB PRG, 최대 32 KiB 뱅크 CHR-RAM | 원본과 같은 배터리 PRG RAM이 없고 래치도 없음 | 제외 |
| MMC5, mapper 5 | 최대 1 MiB PRG·CHR, PRG RAM, 배경 타일별 4 KiB CHR 선택 | 모든 네임테이블·스크롤 상태를 새 소유자가 유지해야 하며 VBlank 시간 예산을 넘김 | 주 경로에서 제외 |
| J.Y. ASIC, mapper 209 | 16 KiB PRG 모드, 큰 CHR, MMC4식 래치 | Mesen 구현에서 16 KiB 모드 설정 뒤 `$6000` 배터리 RAM을 유지할 수 없음 | 제외 |
| MMC3+MMC2 hybrid, mapper 165 | MMC3식 PRG·SRAM과 MMC2식 FD/FE 래치, 최대 256 KiB CHR-ROM, 4 KiB CHR-RAM | MMC4와 FD 트리거 시점이 달라 일부 페이지 쌍의 트리거 비트플레인 보정 필요 | 우선 후보 |

근거 사양은 [MMC4](https://www.nesdev.org/wiki/MMC4), [MMC5](https://www.nesdev.org/wiki/MMC5), [mapper 165](https://www.nesdev.org/wiki/INES_Mapper_165), [J.Y. Company ASIC](https://www.nesdev.org/wiki/J.Y._Company_ASIC), [UNROM512](https://www.nesdev.org/wiki/INES_Mapper_030), [Nintendo 매퍼 비교](https://www.nesdev.org/wiki/Comparison_of_Nintendo_mappers)를 따른다.

mapper 165는 실제 비공식 Fire Emblem에도 쓰인 MMC2+MMC3 하이브리드다. CHR 레지스터 0은 CHR-RAM을 가리키므로 무번역 프로브는 원본 CHR 앞에 8 KiB를 예약하고 32개 원본 4 KiB 페이지를 +2 이동한다. 이 배치에서 원본 CHR SHA-1을 그대로 유지하면서 256 KiB 한계까지 30개 4 KiB 페이지를 추가로 쓸 수 있다.

MMC5 확장 속성 실험은 한 화면의 래치 결과를 표현할 수 있음을 보였지만, 일반화하려면 모든 네임테이블 쓰기와 스크롤을 새 런타임이 소유해야 했다. 바이트 훅과 큐 소비자 훅은 실제 VBlank 시간 예산을 넘겼고, 게시 경계만으로는 직접 전송을 닫지 못했다. 이 때문에 MMC5는 비교·재현 자료로 남기고 주 경로에서는 제외한다.

## mapper 165 현재 증거

무번역 프로브는 원본 PRG 256 KiB, 배터리 플래그, 재배치한 원본 CHR SHA-1을 유지한다. Mesen은 이 출력에 8 KiB Save RAM과 4 KiB CHR-RAM을 제공했다. 타이틀 프레임 1206, 자동 능력치 프레임 1928, 1장 인트로 대화 화면은 기존 원본 표본과 SHA-256이 정확히 같았다.

프레임 800의 오른쪽 FD/FE 쌍 `00/14`에서는 트리거 타일 두 칸의 한 비트플레인만 달라 16픽셀 차이가 났다. mapper 165는 FD 페이지를 `$xFD0`에서, MMC4는 `$xFD8`에서 전환하기 때문이다. 같은 FD `00`과 FE `18`을 쓰는 인트로 대화는 원본과 정확히 같아, 해결 대상은 네임테이블 전체가 아니라 FD/FE 페이지 쌍에 따른 트리거 타일 비트플레인이다.

관측 쌍에 따른 공급 규칙은 구현했고 전투의 직접 왼쪽 `02/06`, `06/06`과 오른쪽 `02/06`도 자연 페이지로 호환됨을 확인했다. 직접 CHR writer 31곳의 쌍 분류는 완료했다. 자연 중단 저장·재개와 검증된 턴 경계 게임 오버 표본은 원본과 동등하며, 현재 남은 G2 관문은 정규 장 완료 저장·불러오기와 장 전환의 진행 동등성이다.

## MMC5 실험 당시 통과 조건

1. `$A000`~`$F000` 직접 쓰기 후보를 실행 코드·데이터로 나누고 실제 실행 지점을 렌더 경로에 결속한다.
2. PRG 뱅크, SRAM, 미러링과 CHR 선택의 원본 상태 전이를 재현 가능한 보고서로 만든다.
3. 번역과 한글 자산 없이 MMC5 PRG 모드 1과 SRAM만 이식한 빌드를 만든다.
4. 타이틀과 처음부터 화면에서 원본 MMC4 래치 결과를 MMC5 확장 속성으로 재현한다.
5. 인트로 대화, 맵 대기, 능력치, 맵 메뉴를 오가며 화면과 진행이 원본과 의미상 같은지 확인한다.

4번까지 실패하면 MMC5를 채택하지 않는다. CHR-RAM 방식은 래치 의존 화면을 어떻게 재구성할지 별도 근거가 생길 때 다시 비교한다.

대표 1장 초반 경로에서는 `$B000`~`$E000` 쓰기가 모두 중앙 루틴을 통과했고, 부팅의 PRG·미러링 직접 쓰기도 원인 명령에 결속했다. 1번은 전투·상점·저장·장 전환·엔딩의 미적중 후보가 남아 있어 아직 통과하지 않았다.

## 현재 실험 상태

3번의 정적 빌드는 완료했다. 프로브는 원본과 같은 256 KiB PRG·128 KiB CHR을 유지하고 mapper 5, PRG 모드 1, PRG RAM 0번 뱅크와 쓰기 허용, 수평·수직 미러링 변환을 넣는다. 새 루틴은 마지막 뱅크의 `$FA00`~`$FA7F`에서 원본이 모두 `FF`이고 직접 `JSR`·`JMP` 바이트 패턴 대상이 없을 때만 배치한다. 원본 루틴·리셋 벡터·헤더도 예상 바이트가 맞을 때만 바꾼다.

Mesen 콜드 런치에서는 첫 명령 PC가 `$FA00`이었고, MMC5 초기화 다섯 건 뒤 프레임 0에 원본 리셋 `$C075`로 들어갔다. 부팅 중 원본 16 KiB 뱅크 `06 → 0E → 06` 선택은 `$5115` 값 `8C → 9C → 8C`로 바뀌었으며, raw 뱅크 래퍼 전후의 A와 상태 플래그도 같았다. 따라서 PRG 리셋·부팅 뱅크 계약은 실행으로 통과했다. PRG RAM은 매핑과 쓰기 허용 초기화까지만 확인했으며 실제 저장·불러오기는 아직 검증하지 않았다.

CHR 동등성은 통과하지 못했다. 브레이크포인트를 제거한 뒤 120프레임 제한 실행에서 CPU는 계속 진행했지만 화면은 거의 검게 깨졌다. 이는 원본 CHR 바이트만 보존해서는 MMC4의 FD/FE 래치 결과가 MMC5에서 재현되지 않는다는 예상된 실패다. 다음 실험은 타이틀·처음부터 화면에 필요한 CHR 상태를 먼저 재현한다.

첫 CHR 정적 실험은 MMC5 4 KiB 모드를 켜고 원본 네 중앙 공급 루틴을 `$5123/$5127`에 연결했다. 각 PPU 창의 FD/FE 값을 하나의 마지막 쓰기로 투영하므로 그림자 쌍이 같은 화면만 직접 표현할 수 있다. 이는 래치 재현안이 아니라 확실한 공급·실행 접점을 얻기 위한 하위 프로브다.

실행에서는 `$5101=01` 뒤 프레임 6에 `$5123=14,14`, `$5127=00,00`, 프레임 548에 `$5127=00,14`가 누락 없이 관측됐다. 무입력 콜드 실행의 프레임 1206 타이틀 애니메이션은 원본과 프로브의 화면 SHA-256이 `7653368704bf030f7dcbcbfb64cf0d3c3a4bd039b8cba11ef88d3d1d0e674c59`로 정확히 같았다. 반면 중앙 루틴만 옮긴 프로브의 프레임 1928 자동 능력치 화면은 원본 `e2893dd71c6f93d1a29e2bc40256e0563e75332c3d2f6eca98277435c06215a1`, 프로브 `a5c4d09e3bbd3bf2c12895c8e4f9ff73c031307991bec0001cf2282a7e8322f7`로 갈라졌다.

동일 프레임 덤프에서 두 실행의 네임테이블·팔레트·OAM·PRG RAM은 바이트 단위로 같았다. 원본은 제로 페이지 그림자 `14/14`, `00/14`를 유지하면서 실제 MMC4 뱅크를 `02/02`, `00/00`으로 바꿨고, 중앙 루틴만 옮긴 프로브는 `$5123/$5127=14/14`에 남았다. 실행 추적으로 뱅크 `0D:$8036/$8039`의 `$D000/$E000` 직접 쓰기와 `0D:$83AB/$83AE`의 `$B000/$C000` 직접 쓰기를 확인했다. 따라서 이 프레임의 실패 원인은 래치 공존이 아니라 누락된 직접 매퍼 쓰기였다.

직접 쓰기 네 곳을 같은 길이로 `$5127/$5123`에 옮긴 프로브는 프레임 1206 해시를 유지했고, 프레임 1928도 원본 해시 `e2893dd71c6f93d1a29e2bc40256e0563e75332c3d2f6eca98277435c06215a1`과 정확히 같아졌다. 이 결과는 두 표본 화면의 하위 관문만 닫으며 마지막-writer 방식의 전역 동등성은 뜻하지 않는다. 이후 대사 화면에서 FD/FE 값이 다른 페이지를 동시에 요구하는 실제 소비자를 확인했으며, 아래의 확장 속성 실험으로 이어졌다.

확장 저장 프로브에서는 원본 CHR을 그대로 상위 128 KiB에 복제하고 검증된 store가 페이지 번호에 `20`을 더하도록 했다. 하위 CHR SHA-1은 원본 그대로이고 상위 첫 페이지 뒤는 원본 복제와 일치한다. 무입력 프레임 1206 타이틀은 원본과 픽셀 단위로 같았고, 프레임 1928에서는 상위 첫 페이지에만 넣은 한글 PoC 타일이 실제로 표시되면서 기존 `STR`, `SKI`, `WLV`, `AGI`, `DEF`, `MOV`, `H.P`, `EXP`는 유지됐다.

동일 입력 프레임 3965에서 확장 프로브와 그 기반 CHR writer 프로브는 내부 RAM·네임테이블·팔레트·OAM·PRG RAM이 모두 바이트 단위로 같았다. 그러나 둘 다 원본의 인트로 대화 화면과 달랐다. 첫 확인 원인은 `$E6B2` 인덱스 포인터 표 루틴의 `$E6BA/$E6F1` 직접 `$A000` 쓰기였다. MMC5가 이 쓰기를 무시해 `$BFE0,Y`를 잘못된 PRG 뱅크에서 읽었고, `$E6D7` 덧셈이 넘쳐 원본에는 없는 `$E6DD INC $05`가 실행됐다.

두 쓰기를 A·상태 플래그 보존 PRG 래퍼로 옮긴 네 직접 쓰기 빌드에서 `$E6DB`의 carry-clear 분기와 `$E6DD` 건너뛰기는 원본과 같아졌다. 하지만 같은 입력의 프레임 3965 화면은 여전히 정지된 맵 해시 `fb077a6a8a7cff0ab89e82ae07b1d929b9fca67e5d8ac75b52df1d551563c511`에 남았다.

다음 차이는 `$E69C` 대사 바이트 읽기 루틴의 `$E6A1/$E6AB` 직접 `$A000` 쓰기였다. 원본은 `$77F2` 뱅크에서 `($76),Y`를 읽고 뱅크 `0A`로 복귀하지만, MMC5 프로브는 두 쓰기를 무시해 현재 뱅크의 다른 바이트를 반환했다. 두 쓰기를 같은 보존 래퍼로 옮긴 뒤 `$80AA` 비교 직전 A는 원본과 같은 `E5`였고 정지 맵에서도 벗어났다.

프레임 3965에서 새 프로브와 원본은 네임테이블·팔레트·OAM·PRG RAM, 프레임/사이클과 선택 PRG 뱅크가 일치했다. CPU PC는 한 바이트 차이였고 내부 RAM은 15바이트가 달랐다. 화면 해시 `0f8117ae8117025c3a38c00a9838442d57f417fc4a0543bd04d84d06d4897a4f`가 원본과 다른 주된 가시 원인은 CHR 공급이다. 남은 직접 `$A000` 후보 `$C99F`, `$E422/$E43E`, `$E71D/$E736`은 이 입력의 프레임 3965까지 실행 적중이 없었다. 따라서 PRG 진행 표본은 크게 좁혔지만 내부 RAM과 CHR 화면 동등성은 아직 통과하지 못했다.

같은 원본 프레임의 실제 MMC4 상태는 왼쪽 FD/FE가 `07/07`, 오른쪽이 `00/18`이고 오른쪽 FE 래치가 활성화돼 있었다. 네임테이블 1에는 `FD` 트리거 18개와 `FE` 트리거 81개가 있어, 마지막 쓰기 하나로는 오른쪽 두 페이지의 공존을 표현할 수 없다. 이를 제로 스크롤 행 우선 fetch로 투영한 1 KiB 확장 속성을 실행 중 MMC5 ExRAM에 넣자 원본과 비교한 61,440픽셀 가운데 본문 61,416픽셀이 같았다. 차이는 화면 개입 시점의 첫 스캔라인 왼쪽 24픽셀뿐이었다.

도구로 다시 생성한 확장 속성 SHA-256 `d725b2f05f43d7c793b5a243a21a38a52263a6018b2d4ec86c61132f18f86a62`는 그 실행 개입 입력과 정확히 같다. 이어서 오른쪽 FD·FE 공급 루틴 양쪽을 감시하고 쌍 `00/18`이 완성되면 `$5104=2`에서 1 KiB를 쓴 뒤 `$5104=1`로 표시하는 ROM 전용 프로브를 만들었다. 복사 루틴은 프레임 1706에 그림자 `00/18`로 적중했고, 외부 메모리 쓰기 없이 프레임 3970의 화면 SHA-256 `73b06fd52d64a8faced6ab3d2d22867558e1d86b3455cadd31bab0af7d61c62f`를 냈다. 원본 프레임 3965와의 차이는 수동 개입 때와 같은 첫 스캔라인 24픽셀뿐이다.

이는 MMC5 확장 속성이 확인된 대화 화면의 MMC4 래치 결과를 표현하고 ROM이 정적 속성 적재를 소유할 수 있다는 하위 증거다. 후속 네임테이블 쓰기를 함께 갱신하거나 스크롤·경계 fetch를 처리하는 일반 소유자는 아니므로 4번과 G2 전체는 아직 통과하지 않았다.

일반 소유자의 판정 기준으로 두 물리 네임테이블을 유지하는 호스트 측 그림자 모델을 추가했다. 모델은 논리 네임테이블 주소를 현재 수평·수직 미러링으로 물리 페이지에 결속하고, PPU 주소 증가 1·32와 `$3000` 미러를 적용한 뒤 선택한 제로 스크롤 화면의 FD/FE 래치와 팔레트 사분면을 1 KiB 확장 속성으로 다시 투영한다. 전체 페이지 전송 결과는 기존 정적 투영과 같고, 트리거·속성 쓰기와 미러링 변경도 행동 검사로 구분한다. 이는 ROM 안의 갱신 코드가 따라야 할 의미 기준이며 자체로 런타임 소유를 증명하지 않는다.

현재 MMC5 프로브를 Mesen에서 격리 실행한 결과 `$5113=1`은 `$6000` 창을 PRG RAM 오프셋 `$2000`에 매핑했고, 뱅크 1의 표식 쓰기는 뱅크 0을 바꾸지 않았다. 표식은 다시 지우고 `$5113=0`으로 복원했다. 이 관측은 네임테이블 그림자를 원본 저장 뱅크와 분리할 수 있는 후보 증거지만, 다른 실행 환경의 RAM 용량이나 실제 저장·불러오기 호환성을 아직 증명하지 않는다.

지원 원본의 직접 `STA $2006` 20곳과 `STA $2007` 7곳은 전수 목록에 결속했다. 모두를 바이트마다 가로채 PRG RAM 뱅크 1의 그림자를 갱신한 실행에서는 프레임 301까지 주소 상위·하위 49회씩과 데이터 6,714회가 적중했으나 실제 CIRAM과 128바이트가 달랐고 화면도 깨졌다. 레지스터 보존·뱅크 전환·주소 계산의 반복 비용이 VBlank 전송을 지연시켰으므로 이 설계는 기각한다. 다음 런타임 소유자는 같은 의미 모델을 PPU 큐와 직접 전송 루틴의 경계에서 일괄 적용해야 한다.
