# 렌더 경로 조사

기준일: 2026-08-07

이 문서는 G1에서 확인한 MMC4 CHR 공급 코드와 실제 화면별 작업 집합을 기록한다. 여기서 `확인`은 지원 일본판 SHA-1 `0179c550d424e0397496078789e7b116601d120c`에 귀속된다. 도입 화면만 연 후반 장을 이전 장 종료부터의 연속 전환이나 엔딩 경로까지 일반화하지 않는다.

## MMC4 CHR 공급 코드

고정 PRG 뱅크의 네 루틴은 입력값을 제로 페이지 그림자에 보존하고 `$52`를 OR한 뒤 MMC4 CHR 레지스터에 쓴다.

| CPU | 그림자 | MMC4 레지스터 | 래치 영역 | 원본 명령 바이트 |
| --- | --- | --- | --- | --- |
| `$C9AE` | `$59` | `$B000` | PPU `$0000`, FD | `85 59 05 52 8D 00 B0 60` |
| `$C9B6` | `$5A` | `$C000` | PPU `$0000`, FE | `85 5A 05 52 8D 00 C0 60` |
| `$C9BE` | `$5B` | `$D000` | PPU `$1000`, FD | `85 5B 05 52 8D 00 D0 60` |
| `$C9C6` | `$5C` | `$E000` | PPU `$1000`, FE | `85 5C 05 52 8D 00 E0 60` |

`analyze-font-supply` 보고서 스키마 3은 이 네 루틴의 바이트를 검사하고 직접 `JSR`·`JMP` 바이트 패턴 후보를 PRG 뱅크·PRG 오프셋·파일 오프셋·CPU 주소로 출력한다. 지원 원본의 `JSR` 후보는 차례로 12, 12, 11곳, 7곳이고 `$C9C6`을 가리키는 `JMP` 후보가 2곳 더 있다. 스키마 5는 `$A000`~`$F000` 직접 절대 쓰기 패턴도 각각 12, 31, 9, 9, 9, 5곳 기록한다. 스키마 6은 이 가운데 가까이 이어진 CHR 쓰기를 13개 후보 집단으로 묶어 실행 검증 우선순위를 제공한다. PRG 안의 코드와 데이터 경계를 아직 모두 확정하지 않았으므로 어느 목록이나 집단도 실행 호출자나 패치 지점으로 자동 승격하지 않는다.

글꼴 페이지의 코드 `FD`와 `FE`는 단순 공백이나 회수 슬롯이 아니라 PPU `$1000` 쪽 래치를 전환하는 보호 코드다. 다음 실측에서 일본어가 있는 화면은 `$5B=00`을 유지하면서 `$5C`에 화면별 그래픽 페이지를 짝지었다.

## 관리 실행의 매퍼 쓰기 실측

같은 Mesen 호스트의 첫 명령 전 경계에서 원본을 다시 시작하고 CPU `$A000`~`$FFFF` 쓰기를 감시했다. 부팅의 `$A000` 뱅크 쓰기는 이벤트 상한을 넘었으므로 양성 적중만 사용했다. 이후 `$A000`을 제외하고 처음부터 메뉴, 인트로 진입·대화, 맵 진입과 능력치까지 나눈 6개 관측 창은 모두 `dropped=0`이었다. 여섯 이벤트 파일을 그 순서로 결합한 SHA-256은 `bc0bc733e79b14e207a8988f9f068d851cc443726ce796125abab1f192b02c43`이다.

Mesen 쓰기 이벤트의 PC는 해당 3바이트 명령 다음 주소였다. 라이브 디스어셈블로 다음 원인 명령을 결속했다.

| 레지스터 | 이벤트 PC | 원인 명령 | 관측 범위 |
| --- | --- | --- | --- |
| `$A000` | `$C9AD`, `$C200`, `$C208` | `$C9AA`, `$C1FD`, `$C205`의 `STA $A000` | 부팅 양성 적중 |
| `$B000` | `$C9B5` | `$C9B2: STA $B000` | 무손실 6개 창 |
| `$C000` | `$C9BD` | `$C9BA: STA $C000` | 무손실 6개 창 |
| `$D000` | `$C9C5` | `$C9C2: STA $D000` | 무손실 6개 창 |
| `$E000` | `$C9CD` | `$C9CA: STA $E000` | 무손실 6개 창 |
| `$F000` | `$C9DD` | `$C9DA: STA $F000` | 부팅 양성 적중 |

대표 경로의 `$B000`~`$E000` 쓰기는 모두 중앙 공급 루틴을 통과했다. 이는 정적 직접 쓰기 후보 전체가 데이터라는 뜻이 아니다. 양도/폐기 결과의 미관측 CHR 쌍·후반 장 연속 전환·엔딩에서 적중하지 않은 후보는 계속 미확정이며, 매퍼 변환에서 삭제하거나 고칠 수 없다.

## 1장 초반에서 확인한 공급 호출자

`$C9BE/$C9C6` 실행 중단점에서 내부 RAM `$0000`~`$01FF`를 원자적으로 보존했다. 스택 반환 주소로 `JSR` 원점을 복원하고, 제로 페이지 `$51`로 `$8000`~`$BFFF`에 매핑된 PRG 뱅크를 식별했다. 고정 뱅크의 `$C1E0`은 반환 주소가 아니라 실제 명령 `4C C6 C9`를 디스어셈블해 꼬리 `JMP`로 확인했다.

| 역할 | 대상 | 확인한 전달 지점 | 입력 페이지 | 관측 경로 |
| --- | --- | --- | --- | --- |
| 처음부터 화면 초기화 | `$C9BE`, `$C9C6` | 뱅크 `02:$A685`, `02:$A688`의 직접 `JSR` | `00`, `00` | 타이틀 → 처음부터 |
| 장면 그래픽 쌍 초기화 | `$C9BE`, `$C9C6` | 뱅크 `06:$A7B9`, `06:$A7BC`의 직접 `JSR` | `18`, `18` | 슬롯 선택 → 인트로, 인트로 → 대화 |
| 문자 페이지 00 공급 | `$C9BE` | 뱅크 `0B:$928A`의 직접 `JSR` | `00` | 처음부터, 대화, 능력치, 맵 메뉴, 부대 목록 |
| FD 쪽 그래픽 페이지 준비 | `$C9BE` | 뱅크 `0B:$9324`의 직접 `JSR` | `15`, `18`, `19` | 대화·능력치 진입과 이탈 |
| 장면 애니메이션 쌍 교체 | `$C9BE`, `$C9C6` | 고정 뱅크 `$C1DD`의 `JSR`, `$C1E0`의 꼬리 `JMP` | `15`, `18`, `19` | 인트로와 맵의 애니메이션 구간 |

이 표는 해당 1장 초반 실행에서 실제로 적중한 지점만 확정한다. 나머지 정적 후보는 아이템·상점·후반 장 연속 전환·엔딩을 관측하기 전까지 미확정이다. 원시 중단점 이벤트는 `evidence/private/g1-caller-*.json`에 두며 Git에는 넣지 않는다.

## 자동 병종 설명 화면의 직접 CHR 쓰기

무입력 콜드 실행의 프레임 1928에서 나오는 화면은 맵의 입력 대기 `unit_status`가 아니라 병종명·능력치·설명문을 자동 표시하는 `class_profile`이다. 원본과 중앙 CHR writer만 옮긴 MMC5 프로브를 같은 경계로 덤프했을 때 네임테이블·팔레트·OAM·PRG RAM은 바이트 단위로 같았고, 내부 RAM은 2,048바이트 중 4바이트만 달랐다. 제로 페이지 그림자 `$59/$5A=14/14`, `$5B/$5C=00/14`도 같았지만 원본의 실제 MMC4 페이지는 `$0000` 쪽 `02/02`, `$1000` 쪽 `00/00`이었고, 프로브의 `$5123/$5127`은 `14/14`에 남았다. 네임테이블에는 `FD/FE` 트리거가 없으므로 이 화면의 실제 배경은 페이지 `00` 하나이며, 프레임 1929 OAM에는 페이지 `02`를 쓰는 가시 스프라이트 18개가 있다.

원본 `$B000`~`$E000` 쓰기 추적과 라이브 디스어셈블로 다음 직접 명령을 확인했다. 긴 관측 창은 반복 쓰기로 이벤트 128개가 누락됐으므로 전수성 근거로 쓰지 않고, 아래 양성 적중과 최종 매퍼 상태만 사용한다.

| PRG 위치 | 원본 명령 | 관측값 | 역할 |
| --- | --- | --- | --- |
| `0D:$8036` | `STA $D000` | `00` | 자동 화면 진입의 PPU `$1000` FD 페이지 |
| `0D:$8039` | `STA $E000` | `00` | 자동 화면 진입의 PPU `$1000` FE 페이지 |
| `0D:$83AB` | `STA $B000` | `00 → 02` | 자동 화면 애니메이션의 PPU `$0000` FD 페이지 |
| `0D:$83AE` | `STA $C000` | `00 → 02` | 자동 화면 애니메이션의 PPU `$0000` FE 페이지 |

네 명령을 같은 3바이트 길이로 `$5127/$5123`에 옮긴 프로브는 프레임 1206 타이틀과 프레임 1928 자동 병종 설명 화면을 각각 원본과 픽셀 단위로 재현했다. 따라서 기존 프레임 1928 실패는 MMC4 래치 공존 증거가 아니라 직접 쓰기 누락 증거로 교정한다. 다른 화면과 아직 실행 분류하지 않은 후보에는 이 결론을 일반화하지 않는다.

## 전투 애니메이션의 직접 CHR 쓰기

1장 맵에서 적 턴 전투 애니메이션으로 진입해 정적 분석에서 남긴 고정 뱅크 직접 쓰기를 관측했다. `$C1F2/$C1F7`는 제로 페이지 `$5E/$5F`의 `02/06`을 오른쪽 FD/FE에 매 프레임 공급했다. 30프레임 짧은 창에서 두 지점이 각각 30회 적중했고 이벤트 누락은 0건이었다. 두 페이지의 타일 `FD` 상위 비트플레인은 모두 0이므로 mapper 165에서도 별도 변형 없이 호환된다.

후속 전투에서는 왼쪽 FE·FD 공통 선택기에서 호출 스택과 매핑된 `$810E` 코드를 함께 보존했다. 같은 프레임의 반환 주소 `8110/8115`, 패치된 `JSR $FA40/$FA60`, `$5E/$5F=02/06`이 일치해 bank 05 `$810E/$8113` 쌍을 왼쪽 `02/06`으로 결속했다. 이후 FE 선택 없이 `$E414`가 `$0484+X`의 FD를 `06 → 02`로 바꿔 왼쪽 `06/06`, `02/06`이 실제로 이어졌다. 이 두 페이지의 타일 `FD` 상위 비트플레인도 모두 0이므로 추가 변형이 필요 없다.

이로써 직접 CHR writer 31곳은 같은 A를 연속 기록하는 26곳의 정적 동등 쌍, 고정 뱅크 오른쪽 2곳, bank 05 왼쪽 2곳, `$E414` 단독 1곳으로 전부 분류됐다. 장 완료 저장·콜드 로드·2장 전환은 별도 실행 증거로 확인했지만, 이 분류 자체는 전체 진행 동등성의 증거가 아니다.

## 현재 설계 판정

- 관측한 문자 화면은 모두 PPU `$1000` FD 쪽 공급값 `$5B=00`을 사용한다. 반대 래치 `$5C`는 문자 화면에 따라 `00`, `14`, `18`, `19`로 바뀐다.
- 문자창이 없는 인트로와 맵에서는 페이지 00이 빠지고 `$C1DD/$C1E0` 경로가 `15`, `18`, `19` 그래픽 쌍을 교체한다. 표의 `15/15`는 그 순환 중 한 표본이다. 문자 페이지의 수명은 게임 전체가 아니라 화면 진입과 이탈에 결속돼 있다.
- 따라서 동적 한글 글꼴의 첫 접점 후보는 `$C9BE`를 통과하는 페이지 00 공급 경로다. G2에서 mapper 165의 CHR-RAM을 사용할 수 있게 됐으므로 이제 이 경로의 페이지 수명에 글리프 적재를 결속한다.
- 기존 영어·숫자와 일본어가 같은 페이지 00을 소비한다. 한글 캐시는 영어 슬롯을 덮는 구조가 아니라 보호 고정 슬롯과 화면별 한글 슬롯을 함께 구성해야 한다.
- 확인된 보호 43코드와 합성 레이아웃의 `0F`, `1F`, `FF`를 예약하면 현재 한글 활성 슬롯 상한은 210개다. 전투 대사에서 쓰이는 `9D = !`는 보존 원문 문장부호이며 `8E = 。`, `AB/AC = 「/」`는 일본어 원문이다. 이는 화면별 활성 한글 슬롯 예산이 아니다. 코드 `00`~`FF`의 실제 소비 집합과 아직 관측하지 않은 렌더 경로를 모두 연결하면서 추가 예약 코드를 빼고 최종 예산을 확정한다.

## 화면 단위 글꼴 계약

동적 글꼴은 전역 페이지 번호가 아니라 화면 역할과 그 화면에서 동시에 살아 있어야 하는 요소를 기준으로 선택한다. 각 화면은 배경 FD 문자, 배경 FE 그래픽, 스프라이트, 기존 영문·숫자, 전환 상태를 따로 기록한다. 국소 소비자를 찾더라도 이 계약에서 빠진 요소가 있으면 페이지를 실행에 결속하지 않는다.

`analyze-screen-contracts`는 현재 분리된 실제 화면 45개를 여덟 관점—일본어 대상, 원본 영어·숫자, FD 문자, FE 그래픽, 스프라이트, 시간에 따라 변하는 UI, 입력·자동 전이, 글꼴 수명—으로 보고하며 전부 실행 관측했다. 원천 단계 수는 화면 수로 쓰지 않는다. 사운드 테스트의 6단계 전투 테스트는 공용 `battle_animation`의 여러 가시 수명으로 결속하고, 30단계 엔딩은 원본 영어 도입·캐스트, 일본어 장 기록, 원본 영어 스태프, 일본어 인물 후일담, 정적 종단 화면으로 나눈다. 자동 `class_profile`, 세 유닛 UI, 무기점 아홉 화면, 소지품 일곱 화면과 장 전환 여덟 화면도 각각 분리한다. 공용 전투의 다섯 경로 62개 표본은 전투 극성을 닫았다. 인물 후일담은 별도 분석기가 자연·전원 직접·전원 라우팅의 112개 보이는 엔트리를 다섯 불규칙 시점씩 검증해 왼쪽 CHR 13쌍과 오른쪽 `00/00`을 모았다. 직접 선택자 쓰기 이벤트는 희소 표본에서 빠진 확장 엔트리 `3F`까지 보완한다. 따라서 다음 글꼴 작업은 이 합집합과 검토된 번역문으로 실제 한글 작업 집합을 계산하며, 장별 종료 대사와 도입 화면 변형은 별도 실행 관문으로 남긴다.

첫 계약 대상은 1장 맵에서 관측한 설정 화면이다. 이 화면의 그림자는 `$52=00`, 왼쪽 `$59/$5A=1A/1A`, 오른쪽 `$5B/$5C=00/15`다. 이후 입력 흐름을 다시 확인한 결과 진행 메뉴 다섯째 `スイッチ`는 설정 진입이 아니라 `アイテム / エリア / ユニット` 하위 메뉴를 열었다. 따라서 기존의 "다섯째 항목으로 설정 진입" 경로 설명은 철회하며, 설정 화면의 실제 정상 진입 소유자는 별도로 다시 결속한다. 이미 캡처한 화면 계약과 `$93BF` 실행 소유 증거는 유지한다.

고급 메모리 덤프의 2 KiB 네임테이블 SHA-1은 `3b25421890ded5f92e9c350d2dbac4f15a66fd04`다. 두 번째 물리 페이지를 초기 FE, FD=`00`, FE=`15`로 투영하면 FD/FE 트리거는 `6/135`, 실제 타일 fetch 수는 `66/894`였다. 설정 첫째 행과 둘째 행 표본의 네임테이블은 바이트 단위로 같고, OAM 첫 바이트만 `1F → 2F`로 바뀌었다. 첫째 행에서 입력 없이 8프레임 간격과 30프레임 간격으로 총 152프레임을 표본화한 화면은 모두 SHA-256 `bf9e91ca3e4ace890dc66287be709beb9c8c7a45eceae8400be57f4ed6533e53`으로 같았다. 이는 그 관측 창 안에서 놓친 점멸 위상이 없다는 근거이며 다른 화면의 점멸 주기까지 일반화하지 않는다.

따라서 첫 `A → B → A` 후보는 설정 화면의 정확한 CHR 그림자 네 값과 `$0034=20/30`을 함께 검사하고, `Down`과 `Up`으로 페이지를 왕복시키는 구조다. 화면 밖에서는 원본 FD 페이지를 복구해야 한다. 다만 설정 화면 자체에는 기존 영문이 없으므로 이 왕복만으로 G3 전체를 통과했다고 판정하지 않는다.

행 이동 때 기존 CHR 공급 루틴이 다시 호출되는지도 별도로 추적했다. `$0034` 쓰기는 매 프레임 뱅크 `0B:$93BF`의 `STA $34`에서 적중했고, 히트 시점 `$51=0B`, 오른쪽 그림자 `00/15`가 결속됐다. 첫째 행에서 `Down`을 누른 41프레임 창에는 41회 쓰기가 있었으며 값이 `20 → 30`으로 바뀐 뒤에도 같은 지점이 매 프레임 새 상태를 기록했다.

반면 mapper 165 코드의 CHR 선택기 범위 `$FA80`~`$FB7F`가 원인인 `$8000/$8001` 쓰기를 감시한 `Up` 10프레임과 후속 30프레임에는 적중이 없었다. 행 이동은 OAM과 `$0034`를 바꿀 뿐 기존 CHR writer를 재호출하지 않는다. 그러므로 화면 쌍을 판정하는 중앙 FD 선택기만 수정해서는 A/B가 움직이지 않는다. 실행 훅은 설정 화면의 이 매 프레임 행 계산부에 결속하고, 원래 행 좌표 계산과 플래그·레지스터 결과를 보존한 뒤 오른쪽 FD 페이지를 선택해야 한다. 전역 NMI나 다른 화면의 입력 처리에는 결속하지 않는다.

화면 전용 훅을 넣은 콜드 실행에서 첫째·둘째·셋째 행의 `$0034`는 `20 → 30 → 40`, 오른쪽 FD mapper 값은 `88 → 8C → 88`로 움직였다. 세 화면 모두 `사운드`, `애니메이션`, `대기시간`과 지도·창·커서가 함께 유지됐다. 설정에서 이탈하면 오른쪽 FD/FE 그림자가 `15/15`, mapper 값이 자연 페이지 `5C`로 돌아갔다. 같은 이탈 상태를 훅 없는 패리티 ROM과 비교해 화면, 모드 `$24=0C`, 좌표와 CHR 그림자가 같음을 확인했으므로 이탈 직후 입력 비활성은 한글 훅 회귀가 아니다. 정상 재진입 경로는 다음 화면 전이 조사에서 별도로 닫는다.

### 부대 목록

깨끗한 맵 대기에서 `SELECT`로 진행 메뉴를 열고 첫 항목 `いちらん`을 `A`로 결정하면 부대 목록에 들어간다. 이 화면은 일본어 이름과 원본 `LV`, `HP`, 숫자, 오른쪽 인물 그래픽, 선택 커서를 동시에 표시한다.

물리 네임테이블 1을 투영한 결과 FD/FE 트리거는 `18/66`, fetch는 `306/654`, 고유 코드는 `29/33`이다. FD 쪽 29코드는 일본어 인코딩 17개, 원본 숫자 `0,1,2,6,8`의 `60,61,62,66,68`, 원본 영문 `H,L,P,V`의 `71,75,79,7F`, 구조 코드 `FE/FF`, 아직 문자·UI 경계를 닫지 않은 `A9`로 나뉜다. 보고서는 고유 코드뿐 아니라 코드별 fetch 횟수도 출력한다. 네임테이블 SHA-1은 `2c07a911705fbb836d4910e42f748526aaf44f04`다.

OAM에는 오른쪽 인물 그림을 이루는 28개 스프라이트와 타일 `F4`, X=`48`, Y=`5F`의 커서 1개가 살아 있다. 첫 조사에서 오른쪽 쌍 `00/15`와 이탈·재진입 뒤 `00/19`를 각각 8프레임 간격으로 152프레임 표본화했고, 두 변형의 네임테이블·OAM·팔레트가 바이트 단위로 같음을 확인했다. 새 한글 빌드의 콜드 진입에서는 추가 위상 `00/18`이 나타났다. 처음에는 미관측 쌍을 원문 페이지로 폴백했고, 이를 레지스트리에 추가한 재빌드에서는 전환 정착 뒤 152프레임 동안 화면·OAM·CHR 그림자가 각각 한 상태로 유지됐다.

`B`는 부대 목록을 닫아 맵으로 돌아가고, 맵에서는 오른쪽 그래픽 쌍이 `18/18 → 15/15 → 19/19`로 순환했다. 이어 `SELECT → いちらん → A`로 재진입하면 `$5B`가 현재 배경 페이지를 한 번 거친 뒤 `00`이 되고 `$5C`는 배경 페이지를 유지했다. 이는 기존에 확인한 뱅크 `0B:$9324`의 그래픽 공급과 `0B:$928A`의 문자 페이지 공급 계약에 맞는다.

부대 목록 머리말은 뱅크 `0B:$917C`의 `15 20 03 FF FF FF 75 7F FF 71 79 ED` 한 곳이며, 앞 세 코드만 `なまえ`다. 화면 FD 사용 집계에서 `15/20/03`은 각각 한 번뿐이므로 `15/20`을 `이/름` 타일로 바꾸고 `03`을 빈 칸으로 지웠다. `75/7F`의 `LV`, `71/79`의 `HP`와 숫자 타일은 원본 그대로다. 물리 페이지 `36/37`, mapper 값 `90/94`의 두 페이지는 `이/름`을 공유하고 화면의 다른 가시 코드를 원본 그대로 복사한다. 각 107자, 합집합 212자로 한 페이지 상한 210자를 실제로 넘는다.

외부 상태 `$24=0C`와 오른쪽 `00/(15|18|19)`만으로 화면을 판정하면 같은 값을 쓰는 진행 메뉴까지 부대 목록 페이지로 바뀌어 글자가 깨졌다. 반대로 머리말 리소스 호출 `$89F2`만 훅하면 그 뒤의 공용 CHR 갱신이 페이지를 다시 덮었다. 부대 목록 생성자 `0B:$89DB`가 만드는 `$05CF/$05D0=12/04`, `$70/$71=30/40` 네 바이트와 머리말 리소스 `2B`를 화면 소유 근거로 삼고, 최종 중앙 공급 `$C9C2`에서 이 수명을 다시 확인한다. 생성자의 18바이트 서명은 지원 원본 PRG에 한 번뿐이다.

최종 콜드 실행의 연속 재진입에서 FE `19 → 15 → 19`, mapper 값 `90 → 94 → 90`의 `A → B → A`가 나왔다. 세 상태 모두 한글 `이름`, 원본 `LV/HP`·숫자, 일본어 유닛명과 인물 그래픽을 함께 표시했다. 각 상태를 서로 다른 불규칙 간격으로 다시 캡처해 머리말과 문자 영역이 유지됨을 확인했고, 마지막 `B` 이탈 뒤 진행 메뉴는 진입 전과 같은 원본 일본어 화면으로 복구됐다.

### 유닛 요약·명령·상세

맵 커서 좌표 `$008E/$008F=08/18`과 아군 레코드의 시작 좌표 `08/18`이 일치하는 유닛에서 입력 흐름을 관측했다. 2프레임 탭은 방향키도 소비되지 않았고 10프레임 탭에서만 좌표와 화면 전이가 한 번씩 바뀌었다. 맵 유휴에서 `A`는 `unit_summary`, 같은 자리의 다음 `A`는 `unit_status`를 열었다. 상세에서 `B`는 이동 선택으로, 다시 `B`는 맵 유휴로 돌아간다. 이동 선택에서 같은 자리를 확정하면 `もちもの / たいき`의 `unit_command_menu`가 열리고 `B`는 요약으로 돌아간다.

`unit_summary`의 그림자는 왼쪽 `1A/1A`, 오른쪽 `00/15`, `00/18`, `00/19`를 관측했다. 물리 네임테이블 1의 `00/18` 표본에서 FD/FE 트리거는 `12/114`, fetch는 `140/820`, 고유 코드는 `26/72`다. FD 쪽 일본어 코드는 `06,0F,12,13,19,25,29,2A,30,31,44,45,4D,5A,5B`이며 이름·병종·레벨과 `てつのつるぎ` 같은 아이템명을 포함한다. 원본 `S`, `HP`, 콜론, 슬래시와 숫자는 `61,62,64,68,71,79,7C,8D,AD`로 보존한다. 152프레임 표본에는 선택 커서와 맵 애니메이션 때문에 화면 해시 3개가 있었고 창과 문자는 계속 표시됐다.

### 소지품 목록과 행동 메뉴

유닛 명령 결과 6은 뱅크 `06:$90B6`에서 주 상태를 `1A`로 바꾸고 합성 상태 `07`의 소지품 목록을 연다. 입력 대기 상태 `1B`에서 관측한 두 행은 `てつのつるぎ 42`, `てやり 22`였으며 일본어 아이템명만 번역 대상이고 내구도 숫자는 보존한다. 빈 칸용 고정 라벨 인덱스 17의 원본 `NO ITEM`도 번역하지 않는다. 화면은 왼쪽 `1A/1A`, 오른쪽 `00/15`를 152프레임 등간격과 168프레임 불규칙 간격 동안 유지했고, 문자와 아이템 행은 남은 채 커서·맵 스프라이트가 세 화면 위상으로 순환했다.

목록의 `A`는 선택 아이템과 슬롯을 `$77B0/$77B1`에 저장하고 사용 가능 행동을 계산한 뒤 합성 상태 `09`, 입력 상태 `1C`의 행동 메뉴를 연다. 첫 아이템은 정규화 마스크 `0D`로 `そうび / わたす / すてる`를 표시했고, 부모 목록과 숫자를 그대로 유지했다. 같은 시간 표본에서 CHR은 고정되고 화면은 세 위상으로 순환했다. 목록의 `B`는 유닛 명령 메뉴로, 행동 메뉴의 `B`는 소지품 목록으로 돌아갔으며 두 경로 모두 유닛 레코드를 바꾸지 않았다.

행동 메뉴의 `A`는 마스크상 선택 서수를 장비 0, 사용 1, 양도 2, 폐기 3으로 바꾸는 실제 변경 경계다. 결과 대사 인덱스 표 `$9516`은 `19/1A/1B/1C`다. 장비는 선택 슬롯과 첫 슬롯의 아이템·내구도를 교환한 뒤 상태 `1E`, 대사 `19`, 복귀 상태 `19`로 갔다. 둘째 슬롯 표본은 `02/2A,0F/16 → 0F/16,02/2A` 교환을 확인했다. 완성 대사는 77프레임부터 227프레임까지 입력 없이 남았고 CHR은 `1A/1A + 00/15`였다.

양도는 상태 `1D`의 텍스트 없는 `1A/1A + 15/15` 지도 오버레이에서 대상을 고른다. 211프레임 불규칙 표본 중 한 위상에서는 후보 표시가 빠졌으므로 단일 캡처를 완전한 UI로 보지 않는다. `B`는 소지품을 바꾸지 않고 상태 `1B` 목록으로 돌아갔다. `A`로 승인한 표본은 `$7715` 대상 버퍼의 빈칸에 아이템/내구도 `02/2A`를 넣고 원본을 지운 뒤 압축했으며, 상태 `1E`, 대사 `1B`, 복귀 상태 `1A`의 별도 결과 화면을 열었다.

### 무기점 화면 흐름과 사전 검사

`ぶきや` 진입은 명령 결과 7 뒤 뱅크 06의 시설 분기에서 `$77F1=00`, `$77F4=B1`을 만들고, 대사 초기화가 `$77F2=0B`로 뱅크를 고른다. 고정 `$E6B2`는 디렉터리 `$BFE2`의 `$A766` 88포인터 표에서 첫 엔트리 `$A816`을 해석한다. 기존 `shop-and-item-dialogue` 구조 분석을 재사용하며 원문 대사 덤프는 추가하지 않는다.

첫 품목 목록은 여섯 일본어 아이템명과 가격, `2000G`, 초상화, 인사 대사, 선택 표식, 뒤쪽 맵과 유닛을 동시에 표시했다. 번역 대상은 아이템명과 일본어 대사이고 숫자와 `G`는 보존한다. CHR 그림자는 왼쪽 `1E/1E`, 오른쪽 `00/15`였고 19프레임 간격 8회, 총 152프레임 동안 화면 SHA-256 `301892a990362f0b5fca399bd4b9ee939a83c46fdce9d6f705b0ee0fc6046c6f`와 CHR이 고정됐다. 품목명·가격 생산자와 선택 표식의 배경/스프라이트 소유는 아직 분리하지 않았다.

공용 메뉴 입력 처리기 `0B:$9333`은 마스크 `3F`의 선택 서수를 결과 1~6으로 바꾼다. 위·아래는 선택만 순환하고 `B`는 결과 0으로 이탈 대사를 고른다. 외부 상태 4의 `06:$9A0E`는 `A` 결과를 받은 뒤 빈 소지품 칸, 저장 단위가 표시 G의 1/10인 금액, 아이템별 조건을 검사한다. 정상 분기만 대사 인덱스 1과 상태 5로 진행하고 이 시점에는 금액·소지품을 바꾸지 않는다.

구매 확인은 기존 품목·가격·금액·초상화 위에 일본어 질문과 두 선택지를 더한다. 관측 커서는 OAM `9F F2 00 18`의 스프라이트다. 같은 `1E/1E + 00/15`에서 152프레임 등간격과 168프레임 불규칙 간격 표본 모두 화면 SHA-256 `0bce2fe4bd13e470ad4a4c29a9a2e19b05102e6155a3b1fcde0eab447488318f`로 같았다. 외부 상태 7의 `06:$9B86`은 메뉴 결과 1만 `$9BA4`의 금액 차감과 아이템·내구도 삽입으로 보내며 결과 0과 2는 같은 비변경 거절 경로로 보낸다.

실제 첫 품목 구매는 저장 금액 `$7678/$7679`를 `00C8 → 00A8`, 표시를 `2000G → 1680G`로 바꿨고, 첫 빈 소지품 `$7709`에 `02`, 대응 내구도 `$770D`에 `2A`를 같은 프레임에 썼다. 구매 결과 화면은 품목 목록을 닫은 채 갱신 금액, 초상화, 일본어 결과와 계속 구매 질문, 두 선택지, 커서, 맵과 유닛을 표시했다. 외부 상태 12의 `06:$9C1A`은 결과 1을 상태 3의 품목 목록 재구축으로 보내고 결과 0/2를 이탈 대사로 보낸다. 화면 SHA-256 `c16554e171b10bf6c212b2a01e0754180ffc0e2a937eee7468423d7fdb00f106`과 `1E/1E + 00/15`는 152프레임 등간격과 168프레임 불규칙 표본에서 고정됐다.

결과 화면의 `B`는 대사 인덱스 6, 외부 상태 8을 선택했고 추가 금액·소지품 쓰기는 없었다. 이탈 화면에는 갱신 금액, 초상화, 일본어 작별 대사, 맵과 유닛만 남고 품목 목록·두 선택지·커서는 사라졌다. 화면 SHA-256 `15d1d0adf1fd2a56863bc87a56df7aeff10c022948128de9ef3cb045ea403b6f`와 같은 CHR 쌍도 두 시간 표본에서 고정됐다. 여기서 `A`는 `$7803=01`을 만든 뒤 `06:$A122`가 `$05DB=00`으로 초기화하고 맵 `1A/1A + 18/18`로 돌아가 시설 행동을 완료했다. 이 마지막 입력은 금액·소지품을 더 바꾸지는 않지만 유닛 행동을 끝내므로 단순 화면 닫기로 취급하지 않는다.

소지품 가득 참 분기는 되돌릴 수 있는 실행 상태에서 세 번째 아이템·내구도 `02/2A`를 네 번째 빈칸 `$770A/$770E`에 복사해 만들었다. 네 아이템 `02/0F/02/02`에서 품목 `A`는 같은 프레임에 외부 상태를 `04→07→08`, 대사 인덱스를 `03`으로 바꿨고, 대사 엔진은 입력 없이 인덱스 `06`의 이탈 문구까지 이어 붙였다. 안정 화면은 여섯 품목·가격, `1680G`, 초상화, 일본어 소지품 오류와 이탈 대사, 맵·유닛을 함께 표시하며 화면 SHA-256 `90f436083be6ff4e0af8ac3f88d8c70061abec9aff664995cc0be7c09c96d0ea`와 `1E/1E + 00/15`가 152프레임 등간격·168프레임 불규칙 표본에서 고정됐다. 금액 `00A8`, 아이템과 내구도에는 실행 쓰기가 없었다. 여기서 `A`는 `$7803=01`, `$05DB=00`을 거쳐 맵으로 돌아가므로 이 화면도 비구매 거절이면서 시설 행동을 끝내는 하류 화면이다. 이 결과는 선언한 RAM 개입으로 얻은 분기 도달 증거이며 자연 플레이 재현은 아니다.

금액 부족 분기는 같은 품목 목록에서 네 번째 빈칸을 유지한 채 저장 금액 `$7678/$7679`만 `00A8→0000`으로 낮춰 만들었다. 품목 `A`는 외부 상태 `04→08→09→0A→0B→0C`, 대사 인덱스 `02→36`을 거쳐 품목 목록과 초상화를 닫고 `0G`, 일본어 부족 안내와 계속 구매 질문, 두 선택지, 커서, 맵·유닛을 표시했다. 화면 SHA-256 `d74c34516389161786e8dc4dc93cabd07807b0bdd7baafbfa6d9731ed93b2c9a`와 `1E/1E + 00/15`는 152프레임 등간격·168프레임 불규칙 표본에서 고정됐다. 분기와 상태 `0C`의 “예” 모두 금액·아이템·내구도를 쓰지 않았으며, “예”는 상태 `03→04`로 품목 목록을 다시 만들었다. 이 역시 선언한 RAM 개입의 분기 도달 증거다.

### 전투 CHR-RAM 캐시 업로드 창

1장 전투 조합은 네임테이블 코드만 보존했을 때 일부 스프라이트 그래픽을 놓쳤다. 시간 표본의 네임테이블과 가시 OAM을 합친 활성 코드 119개를 원본 그대로 두고 남은 91칸에 86글리프 코드북을 배치하자 배경과 스프라이트를 함께 보존할 수 있었다. 한 프레임의 네임테이블만으로 전투 페이지 보호 집합을 정하지 않는다.

업로드 창은 NMI의 렌더 마스크 쓰기 뒤 `$C191`이다. 플레이어 선공 주 상태 `$84=16`과 적 선공 `32` 모두 전투 위상 `$047C=00`, 마스크 그림자 `$CC=06`에서 이 창을 지난다. 카인/가르다병 페이지는 전투 준비 레코드 `$76F4/$7715`의 정체성 바이트가 `[04,85]` 쌍이고, 병종 바이트 `$76F5/$7716` 각각이 `[01,08]`, 장착 무기 `$7707/$7728` 각각이 `[0C,1B]`, 지형 원천 인덱스 `$0322/$0323` 각각이 `[00,0B]` 집합에 들 때 선택한다. 이 값들은 별도 상수가 아니라 조합의 번역 원천 인덱스에서 생성된다. 더 앞선 `$C188`에서는 `$CC=1E`, 전투 위상 `01`이어서 안전한 대체점이 아니다. 4 KiB 전송 전에 `$2002`를 읽어 PPU 주소 래치를 초기화하고 `$2000` 증가 방향을 순차 쓰기로 고정하며, 전송 뒤에는 보류 VBlank를 지우고 NMI와 원래 스크롤 복구 경로로 돌아간다.

정규 전투 원천은 `$9E5D`가 제로 페이지 `$9F/$A0` 포인터의 27바이트 라이브 유닛 레코드를 `$76F4` 슬롯으로 복사하는 경로다. 정체성·병종·장착 아이템은 슬롯 오프셋 `00/01/13`이고, `$9E84/$9E92`가 `$76F4/$7715` 두 슬롯 사이를 양방향으로 복사한다. `$A5CE`의 장비 교체가 라이브 레코드를 변경하므로 정적 장별 표만으로 모든 전투 조합을 고정할 수 없다. 사운드 테스트의 `$9271` 압축 레코드 생성기는 별도 경로다. 전투 대사 selector `3E`는 `$0334/$0479/$0335`가 비0이고 `$05DF`가 0인 분기에서 `$7936`에 기록되며, 동시에 `$7A4B=($0479 OR 0x60)`, `$7A4C=EF`를 만든다. 이 정적 결속은 selector 62의 자연 화면 관측을 대신하지 않는다.

결속한 전투 진입 상태는 저장 시점부터 네임테이블 아래 두 행에 교차 패턴이 있었고, 첫 업로드 직후 네임테이블 차이는 0바이트였다. 따라서 그 패턴을 업로드가 새로 만든 손상으로 보지 않는다. 최초 구현은 안전 조건이 여러 NMI에 걸쳐 유지되어 프레임 2·4·6·8·10에 다섯 번 업로드했고 논리 진행을 늦췄다.

원본 전투 활성 바이트 `$047D`는 뱅크 05의 `$8000` 한 곳에서 0/비0만 판정하고, 다섯 초기화·종료 지점이 `STA`로 전체 바이트를 다시 쓴다. 안전 업로드 뒤 상위 비트 `80`을 세우면 원본에는 계속 활성으로 보이면서 후속 NMI만 건너뛸 수 있다. 플레이어 선공과 적 선공의 첫 전투는 지형 `00/0B`, 같은 적 턴의 두 번째 전투는 `00/00`이었다. 합의 정확 일치 판정은 두 번째 전투를 거부해 글리치를 만들었으므로 폐기했고, 캐시가 가진 원천 집합의 부분집합 판정으로 바꾼 뒤 두 전투가 각각 한 번 업로드했다. 각 전투의 `$047D`는 `01→81→00`, CHR-RAM은 PRG 원천과 4,096/4,096바이트 같았고 한글 `가르다병의 공격`과 원본 `HIT`·숫자·그래픽이 유지됐다. 병종·장비·지형을 집합 밖 값으로 하나씩 바꾼 세 합성 반례에서는 각 5프레임 동안 필드 판별기 7회, 업로드 진입 0회를 기록했다. 단일 페이지의 수용 범위와 전체 적 턴 지도 복귀는 통과했지만, 여러 페이지 사이의 안정적인 글리프 코드와 대사 selector 62 표시는 별도 관문이다.

## 남은 G1 조사

1. 닫힌 인물 후일담 합집합과 검토된 번역문으로 화면별 실제 한글 글리프 작업 집합을 계산한다. 나머지 장별 종료 대사·초상화·CHR·제목 바 변형은 같은 형식의 실행 회귀 관문으로 유지한다.
2. 남은 직접 `JSR`·`JMP` 후보를 해당 화면의 실행 적중과 디스어셈블로 판정한다.
3. 대사·이름·아이템·지형 등 후보 포인터 표를 일본판의 실제 디코더까지 추적한다.
4. 사용 아이템별 대사·효과 생산자와 양도 대상의 소지품 가득 참 피드백을 결속한다. 동시에 `unit_summary`·`unit_command_menu`·`unit_status`의 검토된 번역 후보가 요구하는 한글 합집합과 페이지 예산을 계산한다. 자동 `class_profile`의 여덟 능력치 약어 계약은 별도로 닫는다.
