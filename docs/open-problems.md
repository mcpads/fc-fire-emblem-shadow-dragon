# 열려 있는 문제

기준일: 2026-08-13

이 문서는 «지금 무엇이 막혀 있고, 무엇을 알아야 풀리는가»만 적는다. 무엇을 했는지는 `status.md`, 왜 그렇게 했는지는 `decisions.md`, 앞으로의 순서는 `roadmap.md`에 있다.

판정 기준은 하나다 — **크래시 0건, 일본어 잔존 0건, 진행 불가 0건인 플레이 가능한 ROM.** 아래 항목은 그 기준에서 아직 «아니오»인 것들이다.

---

## 1. 장 인트로의 제목과 실행 생성 표식이 전역 대사 코드북과 공존하지 않는다 (막힘)

**증상.** 현재 전역 대사 탐침은 맵·창·초상화와 대사 본문 한글을 함께 표시한다. 그러나 같은 화면의 장 제목은 깨지고, 첫 줄 앞에서 `{EA}`가 만드는 원본 표식 `9E AB`는 한글처럼 보이는 잘못된 두 글리프로 바뀐다.

**닫힌 원인.** 첫 산출물은 표시 selector가 mapper165의 오른쪽 FD 레지스터 2와 FE 레지스터 4를 모두 같은 CHR RAM 페이지로 바꿨다. FD 글꼴과 FE 맵 배경은 같은 타일 코드 공간을 서로 다른 패턴으로 쓰므로 한 페이지로 합칠 수 없다. FD만 RAM으로 고르는 구조로 바꿨고 배경 손상은 닫혔다. 반복 E4 생산자가 `ready` 직후 같은 요청을 다시 냉합성하던 문제도 게시 원문 정체성 비교로 닫혔다.

**셋째 실행에서 닫힌 원인.** 탐침 `A4AE24B8DE40F2930FDC799C48A6D2C3E6E2894D`은 새 런타임 코드북을 만들면서 정규 대사 저장소는 이전 누적 후보의 국소 코드북 바이트로 남겼다. 300프레임 안정성은 수명만 증명했으며 표시 정확성은 증명하지 않았다. 현재 빌드는 저장소 11구간과 포인터 517개를 같은 코드북에서 설치하고 최종 이미지에서 다시 검증한다.

**현재 실행 결과.** 탐침 `018EDE4D6E6E500D025CBCC5279194BB142161ED`의 1장 프레임 2937은 `ready`를 쓰는 NMI 내부에서 멈춘 상태여서 새 CHR이 아직 프레임버퍼에 나타나지 않았다. 한 프레임 뒤 2938에서 대사 본문은 읽혔다. 그때 네임테이블 코드, 현재 그룹 23 코드북, 참조 CHR 타일의 16바이트 전체와 PPU `$1000..$1FFF`가 일치했다. 따라서 런타임 2bpp 전송이나 PPU 소비는 현재 막힘이 아니다.

**통과한 것.** `ready` 게시, 같은 원문 0페이지의 300프레임 재사용, FD RAM/FE 원본 분리, 현재 대사 저장소와 현재 코드북의 정적·실행 코드 일치, 1장 첫 본문의 가독성은 통과했다.

**정적 해결.** `{EA}`가 논리 줄 안에 있을 때도 출력 코드 `9E AB`를 그 페이지의 보존 집합에 넣었다. 장 제목 글리프는 해당 장의 전체 인트로 전이 사슬 페이지에 넣고, 제목 저장소를 한 번만 인코딩해도 모든 해당 페이지에서 같은 글리프 코드가 유지되도록 고정 배정을 찾는다. 25개 장·관련 가시 페이지 129개·제목 글리프 88개가 결속됐고, 제목 저장소 25개를 동일한 Expected Write 이미지에 설치한다. 최대 합성 페이지 수요는 `210/210`이다.

**필요한 것.** 새 탐침 `0A0571125A619FA2E27AB1D6C903334C0CBE00A8`의 정확한 콜드 1장 경로에서 장 제목, 원본 `EA` 표식, 한글 본문, 맵·창·초상화를 같은 표시 프레임으로 확인한다. 그 뒤에만 7장 최대 15페이지와 자연 이탈로 넓힌다.

## 2. 콜드 합성이 4초 가까이 걸린다 (품질)

한 페이지를 새로 올리는 데 복원 128프레임 + 덮기 최대 103프레임 = **231프레임, 약 3.9초**다. 그동안 디스패처 게이트가 대사를 붙잡고 있으므로 깨지지는 않고 멈춰 있는다.

내역은 이렇다. vblank 여유가 프레임당 1,259사이클이고, 복원은 32바이트 덩어리 하나(약 460사이클), 덮기는 타일 두 개(약 700사이클)가 한 프레임에 들어가는 한계다.

**줄일 여지.**

- 같은 정적 그룹의 레코드 전환은 resolver 뒤 그룹 비교로 닫았다. E6 상태 `10`은 상주권을 유지하며 1장 실행에서 이전의 즉시 재합성이 사라졌다.
- E7 재진입은 아직 외부 호출 전에 상주권을 버린다. 관측한 1장 호출 전후 CHR-RAM 4,096바이트는 같았지만, 호출별 예외로 일반화하지 않는다. 전투 합성기와 대사 합성기를 포함한 CHR-RAM 작성자 전수가 공유 소유권을 무효화하도록 만든 뒤에만 같은 그룹을 재사용한다.
- 복원의 바이트당 비용이 12사이클이다. `LDA (zp),Y`가 6, `STA $2007`이 4, `INY`가 2. 원본 주소를 언롤해 `LDA abs,X`(5)로 바꾸면 바이트당 11이 되지만 코드가 길어진다.
- CHR 뱅크 복원이 프레임마다 최대 292사이클을 쓴다(`$FA80`·`$FAA0` callee 각 140 + 호출자 `JSR` 각 6). 이것을 프레임마다 하지 않아도 되는 조건이 있는지 아직 안 봤다.
- `continuous` 경로(항목 3에 있음)가 붙으면 페이지 전환은 66타일 이하라 훨씬 짧다. 콜드는 대사 수명이 새로 시작될 때만 든다.

**하지 않을 것.** 예산을 늘려 vblank를 넘기는 것. 속도는 품질 지표이고 예산 초과는 정확성 위반이다.

## 3. 대사 런타임 제어 흐름 뒤의 두 소비 경로가 남았다

원본 상태 머신에 필요한 제어 역할은 **9 / 9**가 설치됐다. 초기 진입, `E4/E6` 전이, `E7` 복귀, 페이지 완료·종료, `E7` 외부 인계 무효화, 소비자(`$C179`), 디스패처 게이트(`0A:$8000`), CHR selector(`$FF40`)가 모두 Expected Write에 들어간다.

`$FA80/$FAA0` 관측 훅은 설치하지 않는다. 둘은 직접 CHR 기록기가 쓰는 stateless helper이고, 여기서 `$5B/$5C`를 갱신하면 mapper165가 의도적으로 나눈 중앙 상태와 일시적 직접 기록을 섞는다. 대사 소비자는 후보의 중앙 기록기 `$C9BE/$C9C6`가 소유하는 `$5B/$5C`를 읽기만 하며, 이 두 생산자와 두 helper의 바이트를 설치 선행 조건으로 묶었다. 이전 임시 그림자 `$07EB`는 기존 전투 런타임의 `$07E0..$07EF`와 충돌하므로 폐기했다.

**빠진 `continuous` 경로.** 같은 원문 0페이지 재사용과 같은 정적 그룹의 레코드 전환은 CHR 쓰기 없이 처리한다. 다만 직전 그룹과 새 그룹이 다를 때 차이 타일만 덮는 경로는 여전히 빠져 있으며, 실제로 달라진 전이와 다음 페이지 성공 요청은 콜드 복원이다. E7은 외부 작성자 소유권을 확인하기 전까지 이 재사용 대상에 넣지 않는다.

**빠진 동적 remap 투영.** `{EC:xx}` 자리에 들어가는 아군명·아이템명·수량의 글리프를 출력 시점에 CHR RAM 색인으로 바꾸는 부분. 재료(`dynamic_remap`, 547바이트)는 이미 설치돼 있고 읽는 코드가 없다.

## 4. 나머지 12개 도메인이 소비자에 연결되지 않았다

전체 설치가 요구하는 도메인은 13개이고, 저장·주소 쓰기를 기여하는 것은 `main_dialogue` 하나뿐이다. 글꼴 공급 쓰기는 **0 / 13**이다.

관문 보고서가 그대로 말한다 — `cross_domain_consumer_writes_planned: false`, `integrated_candidate_ready: false`.

CHR 페이지 34..63의 30장은 대사가 CHR RAM 합성으로 가면서 비었고 나머지 도메인 몫이다. 어느 도메인이 몇 장을 쓰는지는 아직 배분되지 않았다.

## 5. 번역 승인이 0줄이다

의미 있는 일본어 2,548줄이 모두 한국어로 채워져 있고 미번역은 0이지만 **사람 승인은 0줄**이다. 파일별로는 `recruitment-dialogue` 1,337, `village-and-outro-dialogue` 1,983, `chapter-intro-dialogue` 931, `house-dialogue` 723, `epilogue-dialogue` 367줄이다.

승인 전에는 `release_eligible`이 false다.

## 6. 실기 지원이 선언만 되어 있다

배포 이미지는 NES 2.0으로 매퍼 165, CHR 256 KiB 정렬, CHR RAM 4 KiB와 배터리 작업 RAM 8 KiB를 정확히 선언한다. 소비자도 vblank 안에서만 `$2007`에 쓴다는 것을 실측으로 확인했다(`$C3A5` 인계 시점 scanline 257, 남은 431사이클).

**확인되지 않은 것.** 실기 플래시 카트가 매퍼 165를 지원하는가. 지원 목록을 아직 확인하지 않았다. 지원하지 않으면 배포 형태 자체를 다시 정해야 하므로, 코드가 더 쌓이기 전에 닫는 편이 싸다.

## 7. 새 외부 호출은 사이클 CFG를 함께 확장해야 한다

`worst_case_cycles`는 «비용을 모르는 `JSR`»를 거부한다. `$FA80`·`$FAA0`의 공용 131사이클 상수도 제거했다. 후보 고정 뱅크를 typed RP2A03으로 해석해 분기·직접 점프·중첩 호출·복귀의 최장 경로를 계산한 현재 callee 상한은 둘 다 140사이클이고, 호출자의 `JSR` 6사이클은 방출 명령 쪽에서 별도로 센다. 이전 예산은 helper마다 9사이클을 작게 셌지만 현재 프레임 예산은 수정된 값으로도 통과한다.

분기 조건의 실제 도달 가능성은 좁히지 않고 양쪽 중 큰 값을 택하므로 안전한 상한이다. 선언 코드 범위 밖 전이, 간접 점프, 루프·재귀, 아직 모델링하지 않은 명령 형식은 전부 설치를 거부한다. 따라서 남은 규칙은 새 외부 호출을 추가할 때 그 callee의 허용 범위와 CFG 상한을 같은 작업 단위에서 결속하는 것이다.

## 되풀이되는 실패 방식

같은 유형이 이 작업에서 네 번 나왔다. 새 코드를 쓸 때 확인할 목록으로 남긴다.

**자기 상수를 자기 테스트로 확인하기.** CHR selector가 `encode_chr_page_register(0)`과 같은지를 단언하고 통과했는데, 그 함수는 물리 페이지 0용이라 1을 돌려주고 CHR RAM은 0이었다. 테스트는 **하드웨어 계약**을 단언해야 한다.

**기존 훅이 성립하던 조건을 안 물려받기.** 전투 합성이 `$C191`에서 동작한다는 사실이 대사에도 맞는다는 뜻이 아니었다. 전투는 렌더링을 끄고 돌아 면제를 받고 있었다.

**끼어드는 자리가 나르던 것을 안 돌려주기.** CHR selector가 사슬의 누산기를 덮어 화면 전체를 깨뜨렸다. 사슬은 페이지 번호를 A로 나른다.

**«나중에 해도 되는 것»을 잘못 고르기.** 원본 페이지 복원을 «첫 페이지에는 필요 없다»며 미뤘는데, 맵 타일과 글꼴이 같은 4 KiB 페이지에 있어 첫 페이지의 전제였다.

넷 다 단위 시험은 전부 통과한 상태에서 **실행**이 잡았다.
