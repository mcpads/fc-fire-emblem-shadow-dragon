# 한글 표시 경로 소유권

이 문서는 리팩터링의 현재 진행 기록이 아니라 코드가 지켜야 하는 구조 계약이다. 현재 위치는 `status.md`, 남은 제품 문제는 `open-problems.md`, 판단 이력은 `decisions.md`를 따른다.

## 의존 방향

한글 표시 경로는 다음 방향으로만 흐른다.

`지원 원본 결속 + 번역 재료 → 화면·수명 계획 → typed 런타임 방출 → 설치 → 최종 이미지 재검증 → exact-ROM 실행 증거`

- 원본 결속은 주소, 상태 생산자, 소비자와 저장소를 확인한다. 번역 페이지를 선택하지 않는다.
- 번역 재료는 문자열, 글리프, 페이지와 레시피를 만든다. 화면 상태를 다시 해석하지 않는다.
- 화면·수명 계획은 동시에 보여야 하는 재료와 페이지 소유자를 결정한다.
- 런타임 방출은 이미 결정된 계획을 typed RP2A03 코드로 옮긴다.
- 설치 검증은 완성 이미지에서 Expected Write, 페이지, 훅과 소비 경로를 다시 읽는다.
- 실행 증거는 정확한 ROM·SaveRAM·입력 계보에서 진입, 변형, 취소, 결과와 이탈을 확인한다.

뒷단이 앞단의 정책을 재추측하거나, 앞단이 실행 성공을 대신 선언해서는 안 된다.

## 소유자

| 계약 | 단일 소유자 | 소비자 |
| --- | --- | --- |
| 전투 원본 ABI와 합성 수명 | `battle_runtime_state.rs` | 전투 분석, 합성 코드, 설치 감사, 시간축 검증 |
| 주 대사 원본 상태와 정체성 | `dialogue_runtime_state.rs` | 대사 인벤토리, 시설·엔딩 생산자, 전역 대사 런타임, 실행 증거 |
| 전투 recipe field 순서와 변환 | `BattleRuntimeStateLayout::recipe_fields` | 선택 색 수집기와 실제 타일 적용기 |
| 전투 합성 실행 코드 | `mapper165/battle_composition_runtime/` | 누적 설치와 독립 런타임 검증 |
| 전투 재료 배치 | `mapper165/battle_text_material.rs` | 전투 base, 합성기, 최종 carried-domain 감사 |
| 공용 글꼴 페이지 생성 | `mapper165/dialogue_font_page.rs` | 대사·유닛·시설·최종 소비자 코드북 |
| 설정·명단 UI 페이지 설치 | `mapper165/ui_page_install.rs` | 누적 빌드와 해당 진단 CLI |
| 최종 화면 상주 정책 | `full_translation_install/screen_font_residency/` | 런타임 방출, 설치 검증, 보고서 |
| CLI와 파일 출력 | `command_line/` | 사용자 명령 진입점 |

화면별 모듈은 역할명 alias를 둘 수 있지만 숫자 주소와 변환 규칙을 다시 선언할 수 없다. 원본 바이트 digest나 합성 시험의 예상값은 증거이므로 허용하지만 제품 정책의 두 번째 소유자가 되어서는 안 된다.

## 제품과 프로브 경계

제품 빌드는 이름이 `_probe`인 모듈을 의존하지 않는다. 채택된 구현은 역할 기반 제품 모듈로 이동한다. 프로브 명령이 계속 필요하면 제품 API를 호출하고 별도 출력·보고서만 만드는 얇은 어댑터로 둔다.

다음은 제품 코드가 아니다.

- 한 화면이나 한 전투 조합만 고정한 ROM 생성기
- 관측값을 허용 목록으로 만든 임시 캐시
- 현재 설치 경로가 소비하지 않는 옛 CLI와 보고서
- 대체된 계획과 그 계획만 보호하는 테스트

실제 제품 소비자가 없고 조사 결과도 현재 소유자에 옮겨졌다면 같은 변경에서 제거한다. Git 이력이 보존하므로 “혹시 필요할 수 있음”만으로 죽은 경로를 유지하지 않는다.

## 이름과 상수

- 이름은 `probe`, 커밋 번호, 당시 증상보다 현재 역할을 나타낸다.
- RAM 주소, 레코드 폭, 필드 순서, selector 투영과 수명 writer는 typed 상태 계약에서 파생한다.
- 같은 숫자가 서로 다른 의미면 이름도 분리한다. 예: 전투 대사 엔트리 선택자와 대사 글꼴 페이지 선택 루틴.
- 코드 생성과 검증은 같은 주소 목록을 각각 복사하지 않고 동일 계약을 읽는다.
- 제품용 실행 바이트는 typed ISA와 checked assembler에서 만든다. 원본 바이트 배열은 읽기 전용 source contract로만 쓴다.

## 테스트 경계

테스트는 구현 파일의 길이나 상수 개수를 고정하지 않고 공유 행동을 보호한다.

- 상태 계약 시험: 알려진 지원 원본 주소와 역할이 일치하고 범위가 겹치지 않는지 확인한다.
- 코드 생성 시험: 수집기와 적용기가 같은 recipe field 계획을 쓰는지 확인한다.
- 수명 시험: 새 전투 시작 writer와 같은 전투의 다음 라운드 writer를 구분한다.
- 설치 시험: 최종 이미지의 실제 루틴, 저장소와 페이지를 다시 읽는다.
- 실행 검증: 설치된 dispatch에서 실제 진입·반환 역할을 유도하고 독립 재합성과 CHR-RAM 전체를 비교한다.

삭제한 구현만 통과시키던 테스트는 함께 지운다. 재현된 결함이 여전히 제품 계약이면 새 공용 소유자 수준의 행동 시험으로 옮긴다.

## 도구 책임

- Rust 라이브러리는 원본 결속, 계획, typed 코드 생성, Expected Write, 최종 검증과 합격 판정을 소유한다.
- Rust CLI는 경로와 인자를 라이브러리에 전달하고 검증된 산출물을 쓴다.
- Python은 비공개 집계·비교나 선택적 후보 계산만 한다. ROM 수정, 주소 지식, 페이지 정책과 출시 판정을 소유하지 않는다.
- emucap은 exact ROM과 파일로 보존한 SaveRAM을 받아 묶음 실행 증거를 만든다. 정적 분모를 대신하지 않는다.

확정 에셋의 반복 빌드는 원본 연구나 whole-program 분석을 다시 실행하지 않는다. 원본 ABI·매퍼 코드·소유 계약이 바뀌거나 반례가 생길 때만 해당 분석을 다시 연다.

## 변경 단위

1. 먼저 소유자와 소비자 목록을 정한다.
2. 공용 계약을 추가하고 모든 생산·검증 소비자를 같은 변경에서 이관한다.
3. 대체된 alias, 프로브, CLI, 보고서와 테스트를 제거한다.
4. 포맷, 경고 없는 `cargo check`, 전체 시험과 exact 재빌드로 행동과 출력의 동일성을 확인한다.
5. ROM 바이트가 바뀌면 구조 이동과 의미 변경을 분리한다.
6. 문서는 현재 상태, 안정 계약, 실행 이력을 서로 다른 파일에 기록한다.

## 종료 조건

리팩터링은 파일 수가 줄었다고 끝나지 않는다.

- 제품 경로에 프로브 모듈 의존이 없다.
- 공유 ABI와 화면 정책의 숫자 복제본이 없다.
- 코드 생성과 검증이 같은 typed 계약을 소비한다.
- 대체된 구현과 그 전용 테스트가 남지 않는다.
- 누적·통합 ROM이 의미 변경 없이 기준선과 byte-identical이다.
- 현재 상태 문서는 한 기준선과 한 다음 관문만 가리킨다.
