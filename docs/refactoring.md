# 전수 리팩터링 계획

이 문서는 증상별 패치를 더하는 대신 전체 한글 표시 경로의 소유권을 한 방향으로 정리하는 현재 계획이다. 현재 상태와 실행 결과는 `status.md`, 남은 제품 문제는 `open-problems.md`, 개별 판단의 근거는 `decisions.md`가 맡는다.

## 목표

최종 목표는 화면 하나가 열릴 때 필요한 번역 문자열·글리프·CHR 페이지·매퍼 경로·닫기 경계가 한 계획에서 결정되고, 다른 모듈은 그 결정을 방출하거나 검증만 하게 만드는 것이다. 어떤 화면도 직전 화면의 우연한 페이지나 서로 다른 선택기의 실행 순서에 의존해서는 안 된다.

다음 불변 조건을 지킨다.

- 화면 상태와 동시에 보이는 표면의 집합은 한 곳에서만 선언한다.
- 각 상태는 명시적인 페이지 경로, 이름에 의해 결정되는 경로, 또는 번역 페이지 해제 가운데 하나를 갖는다. `현재 페이지 유지`는 상위 수명이 증명된 경우가 아니면 허용하지 않는다.
- 글리프 배치와 페이지 선택은 같은 계획을 읽는다. 메뉴에는 있는데 선택 페이지에는 없는 글리프를 런타임 조건문으로 보완하지 않는다.
- 원천 결속, 계획, 실행 코드 방출, 최종 산출물 재검증, 에뮬레이터 관측을 서로 다른 단계로 유지한다.
- 국소 화면 통과는 전체 통합 통과가 아니다. 정확한 최종 ROM에서 관련 전이 묶음을 다시 실행한다.

## 목표 구조

전체 경로를 아래 여섯 층으로 나눈다.

1. **원천 결속**은 지원 원본의 상태 생산자·문자열 저장소·소비자·진입과 이탈을 검사한다. 번역 페이지를 고르지 않는다.
2. **번역 재료**는 논리 문자열, 글리프 코드, CHR 페이지와 실행용 문자열 재료를 만든다. 화면 상태를 읽지 않는다.
3. **화면 상주 계획**은 화면 상태마다 동시에 보여야 하는 표면과 필요한 재료를 합쳐 유일한 페이지 경로를 고른다. 화면별 선택의 단일 출처다.
4. **런타임 투영**은 상주 계획을 typed RP2A03 루틴과 훅으로 방출한다. 상태·글리프 정책을 다시 판단하지 않는다.
5. **설치 검증**은 최종 ROM에서 페이지 바이트, 경로, 훅, 소유 범위와 Expected Write를 다시 읽어 계획과 일치시킨다.
6. **실행 증거**는 정확한 ROM SHA와 SaveRAM 계보에 묶인 화면 전이 묶음을 관측한다. 정적 검증을 대신하지 않고, 정적 검증도 이를 대신하지 않는다.

의존 방향은 `원천 결속 + 번역 재료 -> 화면 상주 계획 -> 런타임 투영 -> 설치 검증 -> 실행 증거` 한 방향뿐이다. 누적 빌드의 옛 선택기는 최종 상주 계획의 입력이 아니며, 이관이 끝난 도메인에서는 재료 설치용 어댑터로만 남긴다.

## 이관 순서

현재 진행 상태는 다음과 같다.

- 프런트엔드, 유닛·아이템·고정 메뉴, 장 저장·엔딩 기록, 메인 대사의 글리프 수명은 중앙 계획으로 이관했다. 메인 대사는 초안과 완성 계획을 타입으로 나눠, 928개 최종 작업집합과 코드북을 결속하지 않으면 런타임 경로를 꺼낼 수 없다.
- 전투는 네 텍스트 도메인의 공유 코드북·합성기·렌더러에 더해 지형 미니어처 1곳과 효과 스프라이트 21곳의 CHR 공급, 공통 선택 루틴, 원본 CHR 7페이지를 정확한 최종 산출물에서 함께 재검증한다. 전체 실행 경로와 직접 writer의 동적 공존 수명은 아직 실행 관문이다.
- 프런트엔드 상태 `0D/0E/21/22`는 중앙 계획이 전부 소유한다. 최종 산출물의 옛 `$FC60..$FC98` 상태 선택기는 같은 크기의 `$FBD4` 포워더로 바뀌며, 누적 후보의 정확한 이전 바이트와 유일한 직접 진입을 먼저 결속하지 못하면 설치하지 않는다. 전투 런타임 보존 범위도 이 교차 도메인 소유 구간 앞뒤로 나누어, 한 도메인의 넓은 보존 검사가 다른 도메인의 의도적 교체를 삼키지 않게 했다.
- 유닛 요약·상태 화면은 더 이상 같은 모호한 동적 정책으로 묶지 않는다. 요약 상태 `04`는 이전 route를 지운 뒤 이름 appender가 실제 카탈로그 페이지를 게시하고, 상태 `0F`는 같은 화면 수명 안에서 그 route를 변경 없이 유지한다. 지원 원본의 요약 이름 appender 1회와 상태의 독립 게시 부재를 결속하고, 방출된 6502 코드를 실행하는 시험으로 `publish -> retain` 전이를 고정했다.
- 이 중앙 수명을 근거로 유닛 누적 선택기 `$F700..$F747`도 제거했다. 누적 후보의 전체 72바이트 생성 구조, 명단 선택기의 유일한 직접 진입 `$FBD1 → $F700`, 다음 미이관 소유자 `$F748`을 먼저 결속한 뒤 같은 범위를 순수 포워더로 바꾼다. 직접 합성 상태 `02..26`의 37개 정책은 이제 중앙 소유 17개, 검증된 상위 소유자 위임 6개, 미해결 14개로 나뉜다. 설정·명단처럼 실제 입력에 따라 페이지를 고르는 선택기는 유지하고, 중앙 쓰기가 없다는 사실만 확인한 상태를 안전한 상속으로 승격하지 않는다. 다음 의미 이관은 14개 미해결 상태를 생산자 가족별로 결속하는 것이고, 큰 파일의 물리적 분할은 이 의미 소유권이 정리된 뒤 진행한다.
- 누적 선택 경로는 단순 사슬이 아니었다. 전투 중앙 경로와 설정 화면 경로가 각각 최대 대사와 설정 선택기를 거쳐 명단 선택기로 합류한다. 이를 8개 선택기 노드와 11개 진입·fallback 경로의 타입화된 그래프로 바꾸고, 생성 바이트와 활성 고정 뱅크의 직접 진입 후보 9개, 설정 owner gate의 조건 분기 1개, 원래 pair-aware 선택기로 나가는 말단 1개를 함께 결속했다. 최종 계획은 이 같은 그래프에서 유닛·프런트엔드 2개만 중앙 포워더로 분류하고, 설정·명단·상점·장 대사 4개는 동적 선택기로 유지하며, 전투·최대 대사 2개는 통합 런타임의 별도 재결속 대상으로 명시한다. 누적 보고서와 최종 보고서가 같은 그래프를 직렬화하므로 이후 선택기 제거가 다른 단계의 분기를 모른 채 진행될 수 없다.
- 유지 중인 네 선택기를 다시 대조했다. 설정은 현재 행에 따라 두 페이지를 고르고, 명단도 표시 구간에 따라 두 페이지를 고르며, 상점은 상점 대사 수명 식별자, 장 대사는 장 번호를 입력으로 쓴다. 따라서 정적 중앙 포워더로 바꾸는 것은 잘못이다. 대신 8개 노드의 최종 소유자를 `중앙 상주`, `동적 선택 유지`, `통합 런타임 재결속`의 typed 분할 하나로 만들고, 설치 검증·보고서 개수·노드 보고가 모두 이 분할을 사용하게 했다.

### 1. 프런트엔드 기록 화면

상태 `0D`, `0E`, `21`, `22`의 페이지 결정을 한 계획으로 옮긴다. 기록 작업 상태 `22`는 메뉴, 주인공 이름, 병종, 수치와 결과 대사가 공존하는 수명이다. 주인공 이름이 배치된 카탈로그 페이지가 설치된 메뉴 코드와 병종 코드도 모두 갖는지 계획 단계에서 검사하고, 그 페이지를 FD와 FE에 명시적으로 게시한다. 빈 페이지에서 진입해도 같은 결과여야 한다.

### 2. 유닛·아이템·고정 메뉴

요약, 상태, 명령, 소지품 목록, 장비·사용 결과, 전달·버리기·취소, 게임 속도, 저장소 메뉴를 같은 상태 레지스트리로 옮긴다. 고정 메뉴 appender와 이름 appender는 페이지를 새로 결정하지 않고 계획된 경로를 재게시한다. 성공·취소·가득 참·용량 안내를 하나의 전이 묶음으로 시험한다.

### 3. 장 전환·대사·엔딩

장 제목, 본문, 화자, 선택지, 저장 안내, 인물·지명 후일담을 가시 수명 단위로 옮긴다. 대사 페이지 레시피와 정적 UI 페이지가 서로의 CHR 소유권을 무효화하는 경계를 한 레지스트리에서 파생한다.

### 4. 전투·지형·예측

전투 이름·병종·장비·지형·짧은 메시지와 스프라이트 CHR 공급을 한 전투 수명 계획으로 합친다. 텍스트 경로와 직접 CHR writer 인벤토리는 별도 증거지만 최종 화면 소유 계획에서 함께 소비한다.

### 5. 중복 선택기 제거

각 도메인 이관 뒤 누적 선택기와 최종 선택기의 중복 상태 분기를 제거한다. 누적 단계는 페이지 재료와 원천 결속만 보고하고, 최종 실행 선택은 화면 상주 계획 하나가 소유한다. 보고서와 번역 커버리지도 같은 레지스트리에서 화면 역할을 파생한다.

### 6. 큰 모듈 분해

행동 소유가 분리된 뒤에만 파일을 나눈다. 우선 대상은 CLI 진입점, 누적 패치 조립기, 전체 설치 조립기, 런타임 코드 조립기, 소비자 페이지 게시자, 통합 쓰기 집합이다. 줄 수를 줄이는 것이 목적이 아니라 입력 계획, 방출 결과, 검증 결과가 타입으로 구분되는 것이 종료 조건이다.

첫 분해로 누적 빌드, 전체 설치, 빌드 후 커버리지의 인자와 출력만 `command_line` 어댑터로 옮겼다. `main`은 세 명령을 파싱해 `execute`에 넘기고, 어댑터는 경로를 기존 라이브러리 입력 타입으로 변환한다. 원천 주소·페이지 정책·ROM 쓰기·합격 판정은 이동하지 않았다. 세 명령의 공개 이름, 기본 경로, 호환 별칭을 파서 행동 시험으로 고정하고, 분해 전후 누적 ROM·최종 ROM·세 JSON 보고서 SHA-1이 모두 같음을 exact 빌드로 확인했다.

뒤이어 모든 하위 명령의 실행 디스패치를 `command_line/dispatch.rs`로 옮겼다. crate 진입점은 clap 선언과 `command_line::execute` 호출만 남기며, 분석·추출·프로브·빌드 명령의 출력은 CLI 어댑터 밖으로 새지 않는다. 이 이동 뒤에도 전체 시험과 누적·최종·커버리지 세 명령을 실제로 다시 실행해 산출물 SHA-1이 같음을 확인했다.

누적 조립기는 번역 입력 준비, 단계별 ROM 설치, 보고서 투영을 분리했다. 입력 준비 모듈은 지원 원본과 모든 작업공간을 한 번 검증해 타입화된 계획만 돌려주고, 본 조립기는 그 계획으로 Expected Write 단계를 순서대로 설치한다. 보고서 조립은 단계 계보, 대사 수명, 화면별 결과, 선택기 그래프의 하위 모듈이 담당한다. JSON 모듈은 ROM을 쓰거나 원천 파일을 다시 읽지 않으며, 설치 조립기는 보고서 문구나 직렬화 구조를 직접 만들지 않는다.

전체 설치 조립기도 같은 경계를 적용하기 시작했다. 직렬화 보고서 스키마는 `full_translation_install/report.rs`가 소유하고, 설치 계획 함수는 검증된 계획과 설치 결과를 그 스키마에 투영하기만 한다. 이 분리는 JSON 형식이나 ROM 바이트를 바꾸지 않으며, 다음 단계에서 통합 쓰기 집합을 재료 설치·런타임 설치·최종 재검증으로 나눌 수 있는 선행 경계다.

통합 쓰기 집합은 이제 498줄 오케스트레이터와 글꼴 페이지, 교차 도메인 재료, 장 제목 저장소, 본문·포인터 저장소, 고정 화면 투영, 런타임 재료, 도메인별 쓰기 기여, 행동 시험의 소유 모듈로 나뉜다. 각 설치 함수와 최종 바이트 검증 함수는 같은 모듈이 소유하며, 오케스트레이터는 적용 순서·전체 변경 추적·최종 기술 관문만 맡는다. 따라서 한 모듈이 바이트를 쓰고 다른 모듈이 그 사실을 모른 채 별도 규칙으로 검사하는 구조를 만들지 않는다.

전체 설치 라이브러리는 더 이상 출력 경로나 보고서 경로에 쓰지 않는다. 검증된 통합 ROM 바이트, 결정적 JSON 바이트, 요약만 반환하고, CLI의 `artifact_output` 어댑터가 보호 입력과의 경로 충돌을 검사한 뒤 두 파일을 쓰고 다시 읽어 동일성을 확인한다. 라이브러리 합격 판정과 파일 시스템 성공 여부가 한 함수에 섞이지 않으며, Python이 이 사이에 ROM을 고치거나 보고서 합격 상태를 바꿀 자리는 없다.

전체 설치 보고서의 파생 계산도 `report/projection.rs`로 옮겼다. 대사 코드북·장 도입 상주·페이지 풀·런타임 합성·대사 저장소·설치 관문은 이미 검증된 계획을 JSON 값으로 투영할 뿐, ROM을 읽거나 쓰지 않는다. 특히 런타임 프레임 수와 PPU 쓰기량 계산이 설치 조립기에서 떨어져 나와, 설치 정책 변경과 보고서 계산 변경을 같은 긴 함수에서 섞지 않는다.

대사 런타임 조립기는 실행 조각의 배치·사이클 계산과 생성 코드의 매퍼 쓰기 검증을 각각 `runtime_code/assembly.rs`, `runtime_code/mapper_write_verification.rs`로 분리했다. 조립 규칙의 겹침·용량 시험과 매퍼 쓰기 규칙의 typed-ISA 행동 시험도 각 소유 모듈로 함께 이동했다. 이 검증은 생성한 조각의 직접·절대 인덱스 쓰기만 다루며, 아직 닫히지 않은 whole-program 실행 분모나 간접 주소 범위를 완료로 승격하지 않는다.

분리 과정에서 기존 동굴 검사가 끝 주소와 조각 간 겹침만 확인하고 시작 주소는 확인하지 않는 잘못된 판정을 찾았다. 공용 검사를 시작·끝 범위 계약으로 바꾸고, 동굴 앞에서 시작하는 조각과 뒤집힌 범위를 거부하는 행동 시험을 추가했다. 디스패처·트램폴린·페이지 선택기·동적 생산자·소비자 카탈로그는 이제 각자 결속한 정확한 동굴 양끝을 모두 넘긴다.

복합 UI 글꼴 수명도 공개 façade, 지원 원본의 생산자·호출·동굴 결속, typed RP2A03 런타임 방출, 합성 실행 행동 시험으로 나눴다. `$05E8` 상태와 열기·닫기·게임플레이 인계 주소는 façade의 공용 계약으로 남기고, 원천 결속은 ROM을 읽기만 하며 런타임 방출은 검증된 페이지 계획만 소비한다. 같은 최종 ROM의 콜드 실행에서는 프런트엔드와 첫 대사 뒤 설정·저장소·유닛 요약·상태·명령·소지품, 전달 취소와 실제 전달·버리기 결과를 한 실행 계보에서 연속 확인했다. 이 관측은 아직 보고서에 결속하지 않았으므로 `runtime-bound` 완료 수치로 승격하지 않는다.

전체 설치의 다음 관문 계산도 `installation_readiness`로 분리했다. 기존 판정은 사람 검토가 끝나지 않은 초안 산출물에도 최종 산출물용 대표·최악 실행 증거를 먼저 요구했다. 이후 번역 검토가 바이트를 바꾸면 ROM 해시와 실행 증거를 함께 다시 만들어야 하므로 잘못된 순서였다. 이제 선언 소비자와 기술 설치를 먼저 닫고, 사람 검토와 재빌드가 끝난 뒤에만 최종 실행 증거 결속을 다음 관문으로 낸다. 검토 전 에뮬레이터 실행은 결함 발견용 진단으로는 계속 쓰되 최종 실행 완료로 승격하지 않는다.

오디오 동시 접근 검사도 잘못된 완료 판정을 바로잡았다. 이전 CFG는 bank `0E:$8A7C`의 `JMP ($F4)`에서 조용히 추적을 끝내 959개 명령만 보고도 간접 접근 분모가 닫혔다고 기록했다. 이제 간접 제어 이전을 미해결 사이트로 보존하고, `$882D..$88ED`의 96개 handler 포인터·88개 고유 대상을 보수적 루트로 추가한다. 확장된 2,037개 명령에서 새로 드러난 APU 레지스터 복사와 인덱스 표 조회도 생산자·유효 주소 범위에 결속한다. 따라서 간접 점프를 놓친 작은 CFG로 휘발 저장소가 안전하다고 판정할 수 없다.

매퍼 쓰기 음성 공간은 원본 PRG의 모든 매핑 투영에서 가능한 명령 시작점을 뿌리와 무관하게 먼저 만든다. 기존 전투·주 대사·NMI·오디오 양성 실행 그래프의 주소는 원본 바이트로 다시 디코드해 실제 명령 범위와 내부 바이트를 유도하며, 그 내부에 놓인 후보만 미해결 집합에서 옮긴다. 다른 추적 시작점과 겹치는 내부, 바이트가 모자란 경계, 실행 바이트와 겹치는 자료 소유는 분류하지 않고 실패하거나 미해결로 남긴다. 후보 수·실행 명령 수·digest는 현재 분석을 설명하는 보고 값일 뿐 합격 상수가 아니다. 검증은 전체 후보의 분할이 빠짐없고 겹치지 않는지, 양성 그래프 적용 전후의 집합 차이가 바이트에서 유도한 명령 내부 집합과 같은지, 남은 미해결 집합이 임의로 줄지 않았는지를 검사한다. whole-program 실행 뿌리가 아직 닫히지 않았으므로 전역 완료 값은 계속 거짓이다.

하드웨어 NMI·reset·IRQ 벡터 세 슬롯도 이제 원본 바이트에서 직접 읽어 고정 PRG의 typed 직접 제어 흐름에 넣는다. 이 그래프가 처음 드러낸 reset의 `$C09E: STA ($00),Y`는 주소만 허용하지 않고, `$00/$01`을 `$0000/$0700`으로 초기화한 뒤 Y 전체와 high byte `7..0`을 순회해 정확히 `$0000..$07FF`만 지우는 원본 루프 전체에 결속했다. 동적 switchable 호출과 `$C34C`의 inline pointer dispatch 선택값 범위는 아직 열린 edge로 남긴다. 따라서 벡터에서 출발했다는 사실만으로 whole-program 완료나 그 이후 자료 영역의 실행을 선언하지 않는다.

고정 뱅크 `$C1FB`의 오디오 호출은 이 열린 경계 가운데 하나를 실제 기존 소유자와 연결한다. 원본의 `bank 0E 선택 → $8000 호출 → $29 그림자 복원` 전체 14바이트와 호출 edge가 동시에 있어야만 기존 오디오 실행 그래프의 `0E:$8000` 루트로 넘긴다. 코드만 있고 edge가 없거나 edge만 있고 코드가 바뀌면 실패한다.

`$C34C`는 더 이상 네 추적기가 제각각 건너뛰는 주소 상수가 아니다. 공용 binder가 JSR이 스택에 남기는 마지막 operand 주소, `ASL; TAY; INY`의 8비트 wrap, low/high 포인터 읽기, `$C367: JMP ($000C)` tail 전체를 원본과 typed ISA에 묶는다. 전투 phase처럼 소유자가 selector 범위를 가진 표는 그 범위만 확정한다. 반면 고정 스케줄러 `$F2A2`는 아직 `$25` 값 범위가 닫히지 않았으므로 `00..FF` 256개를 전부 평가한 69개 고유 target을 열린 증거로 유지한다. exact 보고서의 현재 미해결은 동적 bank의 `$F29A → $8400`과 이 selector-domain dispatch 두 개다.

## 도구별 책임

| 주체 | 반드시 해야 하는 일 | 해서는 안 되는 일 |
| --- | --- | --- |
| Rust 라이브러리 | 원본 해시와 구조 결속, 번역 계획, 글리프·페이지 배치, typed ISA 조립, Expected Write, 최종 ROM 생성과 재검증, 직렬화할 보고서 값 계산 | CLI 인자나 로컬 경로를 의미 계약으로 사용, 관측되지 않은 실행 성공 선언 |
| Rust 단위 테스트 | 합성 입력으로 상태 전이, 페이지 선택, 용량 초과, 중복 소유, 누락 경로와 재현된 결함을 행동으로 고정 | 원본 ROM 경로가 있을 때만 도는 테스트, 내부 벡터 길이만 고정하는 테스트 |
| Rust 빌드 통합 게이트 | 사용자가 명시한 exact source와 모든 번역 입력을 받아 결정적 산출물을 만들고, 설치 이미지를 다시 읽어 전체 쓰기·페이지·경로를 검사 | 일부 도메인만 성공한 ROM 방출, 이전 산출물 실행 증거 승계 |
| Rust CLI | 명령행 인자와 파일 입출력을 라이브러리 호출로 연결하고 JSON 보고서와 종료 상태를 전달 | ROM 주소, 글리프 배치, 상태 분기, 합격 조건을 `main.rs`에서 다시 구현 |
| Python | JSON 표준입출력의 선택적 최적화 계산, 사람이 보는 비공개 비교·집계처럼 Rust 의미 모델 밖의 보조 작업 | ROM 수정, 주소 지식, 인코딩, 페이지 선택의 단일 출처, 빌드·출시 합격 판정 |
| 에뮬레이터 관측 | exact ROM·SaveRAM·입력 계보에 묶인 실제 전이와 화면·메모리 소비 확인 | 정적 분모나 설치 검증 대체, 다른 SHA 산출물의 성공 승계 |

현재 Python 프로그램 `tools/solve_dialogue_page_capacity.py`는 JSON 요청을 받아 배치 후보만 반환한다. Rust가 입력 유효성, 후보의 전수 재검증, 결정적 정규화와 실패 판정을 계속 소유한다. 향후 Python 도구도 같은 경계를 넘지 않는다.

현재 exact 전체 빌드는 Rust의 결정적 best-fit 배치만으로 완료되며 Python을 호출하지 않는다. 제한된 물리 페이지 수를 탐색해야 할 때만 Python/HiGHS 또는 Z3를 후보 생성기로 쓸 수 있고, 어느 결과든 Rust의 같은 검증기를 통과해야 한다.

## 테스트와 빌드 뒤의 작업 구분

1. `cargo test`는 합성 행동 회귀와 라이브러리 불변 조건을 검사한다.
2. 빌드 CLI는 exact source와 번역 입력으로 누적·통합 ROM을 만들고 최종 바이트를 재결속한다.
3. 분석 CLI는 방금 만든 ROM과 보고서를 다시 읽어 번역 커버리지, 소비자 설치, 미해결 실행 역할을 계산한다.
4. Python은 필요한 경우에만 CLI JSON을 입력으로 받아 최적화 또는 비공개 시각 비교를 수행한다. 그 결과는 Rust가 다시 검증하기 전까지 제안이다.
5. emucap은 같은 ROM과 SaveRAM 파일로 관련 전이를 묶어 실행한다. 캡처 하나가 아니라 진입·변형·취소·결과·이탈을 같은 실행 계보에서 확인한다.

## 커밋 경계

- 계획·화면 상주 타입·화면군별 생산자와 소비자 결속은 이미 독립 커밋으로 나눴다.
- 프런트엔드 네 상태의 중복 선택기 제거와 교차 도메인 보존 범위 분할은 독립 커밋으로 닫았다.
- 유닛 요약·상태의 수명 의미를 소비해 누적 유닛 선택기를 제거하는 커밋과, 누적 선택기들을 8노드·11경로의 분기 그래프로 묶는 커밋을 각각 닫았다. 그래프 커밋은 ROM 바이트를 바꾸지 않고 누적·최종 보고서와 최종 설치 검증이 같은 경로 분모를 소비하게 한다.
- 선택기 그래프는 공개 모델·원천 바이트 결속·직접 진입 센서스·합성 행동 시험의 네 모듈로 나눴다. 뒤이은 누적 조립기 분해는 입력 계획과 보고서 투영을 설치 코드에서 떼고, 보고서도 단계 계보·대사·화면·선택기 그래프로 다시 나눈다. 두 분해 모두 의미와 직렬화 결과를 바꾸지 않는다.
- 전체 설치 조립기의 직렬화 스키마도 별도 보고서 모듈로 분리한다. 이 커밋은 계획·쓰기·검증 순서와 최종 ROM·보고서 바이트를 바꾸지 않으며, 통합 쓰기 집합의 책임 분할과 섞지 않는다.
- 통합 쓰기 집합의 다음 커밋은 설치 대상별 `install`과 `verify_installed`를 같은 하위 모듈로 옮기고, 최상위에는 쓰기 순서·전체 변경 추적·기술 설치 판정만 남긴다. 원천 주소, Expected Write, 출력 보고서 값은 그대로 유지한다.
- 전체 설치의 다음 커밋은 라이브러리가 메모리 안의 ROM·JSON 산출물만 반환하게 하고, 실제 경로 보호·쓰기·read-back은 CLI 어댑터로 옮긴다. 단위 테스트는 합성 경로 충돌과 두 산출물 read-back을 검증하며, exact 빌드는 분리 전후 해시 동일성을 확인한다.
- 전체 설치 보고서 투영 커밋은 계획 타입에서 파생되는 코드북·페이지·런타임·저장소·관문 값을 `report/projection.rs`로 옮긴다. 조립기는 계획값을 넘기고 완성된 하위 보고서를 조합하며, JSON 키·값·순서는 exact 보고서 SHA-1로 고정한다.
- 다음 의미 커밋은 14개 미해결 합성 상태를 고정 문자열 appender, 동적 선택기, 주 대사 overlay, 원본 전용 그래픽의 생산자 가족으로 나눠 상주 레지스트리에 결속한다. 중앙 계획이 실제로 페이지를 게시하거나 유지하는 상태만 포워더로 바꾸고, 정적으로 닫히지 않는 경로는 미해결로 유지한 채 exact-artifact 묶음 실행으로 넘긴다.
- 대형 파일 분리는 소유 결정 변경과 섞지 않는다. 같은 행동을 유지한 채 CLI 어댑터, 계획, 실행 코드 방출, 설치 검증을 파일과 타입으로 나누는 별도 커밋으로 만든다. 첫 별도 커밋은 세 최종 파이프라인 명령의 CLI 어댑터만 옮기며 산출물 바이트를 바꾸지 않는다.

각 커밋은 `cargo fmt --check`, 관련 행동 테스트, 전체 crate 테스트, `git diff --check`를 통과한다. ROM과 비공개 작업공간, 캡처, SaveRAM은 커밋하지 않는다.

## 완료 조건

리팩터링 완료는 파일을 나눈 시점이 아니다. 다음 조건을 모두 만족해야 한다.

- 모든 번역 대상 화면 상태가 한 화면 상주 레지스트리에 속한다.
- 런타임 코드에 별도의 상태별 페이지 정책이 없다.
- 누적 패치와 최종 패치가 서로 다른 선택 결정을 하지 않는다.
- 최종 설치 검증과 번역 커버리지가 같은 레지스트리를 소비한다.
- Python 없이도 정답을 검증하고 ROM을 만들 수 있다. Python 최적화가 없으면 더 느린 Rust 대안이나 명시적 미해결로 실패한다.
- 대표·최악·성공·취소·이탈을 묶은 exact-artifact 실행 회귀가 남은 화면 역할을 명시한다.
