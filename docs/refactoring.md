# 전수 리팩터링 계획

이 문서는 증상별 패치를 더하는 대신 전체 한글 표시 경로의 소유권을 한 방향으로 정리하는 현재 계획이다. 현재 상태와 실행 결과는 `status.md`, 남은 제품 문제는 `open-problems.md`, 개별 판단의 근거는 `decisions.md`가 맡는다.

## 목표

최종 목표는 화면 하나가 열릴 때 필요한 번역 문자열·글리프·CHR 페이지·매퍼 경로·닫기 경계가 한 계획에서 결정되고, 다른 모듈은 그 결정을 방출하거나 검증만 하게 만드는 것이다. 어떤 화면도 직전 화면의 우연한 페이지나 서로 다른 선택기의 실행 순서에 의존해서는 안 된다.

다음 불변 조건을 지킨다.

- 화면 상태와 동시에 보이는 표면의 집합은 한 곳에서만 선언한다.
- 각 상태는 명시적인 페이지 경로, 이름에 의해 결정되는 경로, 또는 번역 페이지 해제 가운데 하나를 갖는다. `현재 페이지 유지`는 상위 수명이 증명된 경우가 아니면 허용하지 않는다.
- 글리프 배치와 페이지 선택은 같은 계획을 읽는다. 메뉴에는 있는데 선택 페이지에는 없는 글리프를 런타임 조건문으로 보완하지 않는다.
- 원천 결속, 계획, 실행 코드 방출, 최종 산출물 재검증, 에뮬레이터 관측을 서로 다른 단계로 유지한다.
- 국소 화면 통과는 전체 통합 통과가 아니다. 정확한 최종 ROM에서 관련 전이 묶음을 다시 실행한다.

## 목표 구조

전체 경로를 아래 여섯 층으로 나눈다.

1. **원천 결속**은 지원 원본의 상태 생산자·문자열 저장소·소비자·진입과 이탈을 검사한다. 번역 페이지를 고르지 않는다.
2. **번역 재료**는 논리 문자열, 글리프 코드, CHR 페이지와 실행용 문자열 재료를 만든다. 화면 상태를 읽지 않는다.
3. **화면 상주 계획**은 화면 상태마다 동시에 보여야 하는 표면과 필요한 재료를 합쳐 유일한 페이지 경로를 고른다. 화면별 선택의 단일 출처다.
4. **런타임 투영**은 상주 계획을 typed RP2A03 루틴과 훅으로 방출한다. 상태·글리프 정책을 다시 판단하지 않는다.
5. **설치 검증**은 최종 ROM에서 페이지 바이트, 경로, 훅, 소유 범위와 Expected Write를 다시 읽어 계획과 일치시킨다.
6. **실행 증거**는 정확한 ROM SHA와 SaveRAM 계보에 묶인 화면 전이 묶음을 관측한다. 정적 검증을 대신하지 않고, 정적 검증도 이를 대신하지 않는다.

의존 방향은 `원천 결속 + 번역 재료 -> 화면 상주 계획 -> 런타임 투영 -> 설치 검증 -> 실행 증거` 한 방향뿐이다. 누적 빌드의 옛 선택기는 최종 상주 계획의 입력이 아니며, 이관이 끝난 도메인에서는 재료 설치용 어댑터로만 남긴다.

## 이관 순서

현재 진행 상태는 다음과 같다.

- 프런트엔드, 유닛·아이템·고정 메뉴, 장 저장·엔딩 기록, 메인 대사의 글리프 수명은 중앙 계획으로 이관했다. 메인 대사는 초안과 완성 계획을 타입으로 나눠, 928개 최종 작업집합과 코드북을 결속하지 않으면 런타임 경로를 꺼낼 수 없다.
- 전투는 네 텍스트 도메인의 공유 코드북·합성기·렌더러에 더해 지형 미니어처 1곳과 효과 스프라이트 21곳의 CHR 공급, 공통 선택 루틴, 원본 CHR 7페이지를 정확한 최종 산출물에서 함께 재검증한다. 전체 실행 경로와 직접 writer의 동적 공존 수명은 아직 실행 관문이다.
- 프런트엔드 상태 `0D/0E/21/22`는 중앙 계획이 전부 소유한다. 최종 산출물의 옛 `$FC60..$FC98` 상태 선택기는 같은 크기의 `$FBD4` 포워더로 바뀌며, 누적 후보의 정확한 이전 바이트와 유일한 직접 진입을 먼저 결속하지 못하면 설치하지 않는다. 전투 런타임 보존 범위도 이 교차 도메인 소유 구간 앞뒤로 나누어, 한 도메인의 넓은 보존 검사가 다른 도메인의 의도적 교체를 삼키지 않게 했다.
- 유닛 요약·상태 화면은 더 이상 같은 모호한 동적 정책으로 묶지 않는다. 요약 상태 `04`는 이전 route를 지운 뒤 이름 appender가 실제 카탈로그 페이지를 게시하고, 상태 `0F`는 같은 화면 수명 안에서 그 route를 변경 없이 유지한다. 지원 원본의 요약 이름 appender 1회와 상태의 독립 게시 부재를 결속하고, 방출된 6502 코드를 실행하는 시험으로 `publish -> retain` 전이를 고정했다.
- 이 중앙 수명을 근거로 유닛 누적 선택기 `$F700..$F747`도 제거했다. 누적 후보의 전체 72바이트 생성 구조, 명단 선택기의 유일한 직접 진입 `$FBD1 → $F700`, 다음 미이관 소유자 `$F748`을 먼저 결속한 뒤 같은 범위를 순수 포워더로 바꾼다. 상주 경로가 아직 초기값 `0`일 수 있는 다른 도메인은 포워더로 성급히 바꾸지 않는다. 다음 의미 이관은 남은 아이템·상점·명단 선택기의 화면 상태 분모를 중앙 레지스트리와 대조하는 것이고, 큰 파일의 물리적 분할은 이 의미 소유권이 정리된 뒤 진행한다.
- 누적 선택 경로는 단순 사슬이 아니었다. 전투 중앙 경로와 설정 화면 경로가 각각 최대 대사와 설정 선택기를 거쳐 명단 선택기로 합류한다. 이를 8개 선택기 노드와 11개 진입·fallback 경로의 타입화된 그래프로 바꾸고, 생성 바이트와 활성 고정 뱅크의 직접 진입 후보 9개, 설정 owner gate의 조건 분기 1개, 원래 pair-aware 선택기로 나가는 말단 1개를 함께 결속했다. 최종 계획은 이 같은 그래프에서 유닛·프런트엔드 2개만 중앙 포워더로 분류하고, 설정·명단·상점·장 대사 4개는 동적 선택기로 유지하며, 전투·최대 대사 2개는 통합 런타임의 별도 재결속 대상으로 명시한다. 누적 보고서와 최종 보고서가 같은 그래프를 직렬화하므로 이후 선택기 제거가 다른 단계의 분기를 모른 채 진행될 수 없다.

### 1. 프런트엔드 기록 화면

상태 `0D`, `0E`, `21`, `22`의 페이지 결정을 한 계획으로 옮긴다. 기록 작업 상태 `22`는 메뉴, 주인공 이름, 병종, 수치와 결과 대사가 공존하는 수명이다. 주인공 이름이 배치된 카탈로그 페이지가 설치된 메뉴 코드와 병종 코드도 모두 갖는지 계획 단계에서 검사하고, 그 페이지를 FD와 FE에 명시적으로 게시한다. 빈 페이지에서 진입해도 같은 결과여야 한다.

### 2. 유닛·아이템·고정 메뉴

요약, 상태, 명령, 소지품 목록, 장비·사용 결과, 전달·버리기·취소, 게임 속도, 저장소 메뉴를 같은 상태 레지스트리로 옮긴다. 고정 메뉴 appender와 이름 appender는 페이지를 새로 결정하지 않고 계획된 경로를 재게시한다. 성공·취소·가득 참·용량 안내를 하나의 전이 묶음으로 시험한다.

### 3. 장 전환·대사·엔딩

장 제목, 본문, 화자, 선택지, 저장 안내, 인물·지명 후일담을 가시 수명 단위로 옮긴다. 대사 페이지 레시피와 정적 UI 페이지가 서로의 CHR 소유권을 무효화하는 경계를 한 레지스트리에서 파생한다.

### 4. 전투·지형·예측

전투 이름·병종·장비·지형·짧은 메시지와 스프라이트 CHR 공급을 한 전투 수명 계획으로 합친다. 텍스트 경로와 직접 CHR writer 인벤토리는 별도 증거지만 최종 화면 소유 계획에서 함께 소비한다.

### 5. 중복 선택기 제거

각 도메인 이관 뒤 누적 선택기와 최종 선택기의 중복 상태 분기를 제거한다. 누적 단계는 페이지 재료와 원천 결속만 보고하고, 최종 실행 선택은 화면 상주 계획 하나가 소유한다. 보고서와 번역 커버리지도 같은 레지스트리에서 화면 역할을 파생한다.

### 6. 큰 모듈 분해

행동 소유가 분리된 뒤에만 파일을 나눈다. 우선 대상은 CLI 진입점, 누적 패치 조립기, 전체 설치 조립기, 런타임 코드 조립기, 소비자 페이지 게시자, 통합 쓰기 집합이다. 줄 수를 줄이는 것이 목적이 아니라 입력 계획, 방출 결과, 검증 결과가 타입으로 구분되는 것이 종료 조건이다.

첫 분해로 누적 빌드, 전체 설치, 빌드 후 커버리지의 인자와 출력만 `command_line` 어댑터로 옮겼다. `main`은 세 명령을 파싱해 `execute`에 넘기고, 어댑터는 경로를 기존 라이브러리 입력 타입으로 변환한다. 원천 주소·페이지 정책·ROM 쓰기·합격 판정은 이동하지 않았다. 세 명령의 공개 이름, 기본 경로, 호환 별칭을 파서 행동 시험으로 고정하고, 분해 전후 누적 ROM·최종 ROM·세 JSON 보고서 SHA-1이 모두 같음을 exact 빌드로 확인했다.

## 도구별 책임

| 주체 | 반드시 해야 하는 일 | 해서는 안 되는 일 |
| --- | --- | --- |
| Rust 라이브러리 | 원본 해시와 구조 결속, 번역 계획, 글리프·페이지 배치, typed ISA 조립, Expected Write, 최종 ROM 생성과 재검증, 직렬화할 보고서 값 계산 | CLI 인자나 로컬 경로를 의미 계약으로 사용, 관측되지 않은 실행 성공 선언 |
| Rust 단위 테스트 | 합성 입력으로 상태 전이, 페이지 선택, 용량 초과, 중복 소유, 누락 경로와 재현된 결함을 행동으로 고정 | 원본 ROM 경로가 있을 때만 도는 테스트, 내부 벡터 길이만 고정하는 테스트 |
| Rust 빌드 통합 게이트 | 사용자가 명시한 exact source와 모든 번역 입력을 받아 결정적 산출물을 만들고, 설치 이미지를 다시 읽어 전체 쓰기·페이지·경로를 검사 | 일부 도메인만 성공한 ROM 방출, 이전 산출물 실행 증거 승계 |
| Rust CLI | 명령행 인자와 파일 입출력을 라이브러리 호출로 연결하고 JSON 보고서와 종료 상태를 전달 | ROM 주소, 글리프 배치, 상태 분기, 합격 조건을 `main.rs`에서 다시 구현 |
| Python | JSON 표준입출력의 선택적 최적화 계산, 사람이 보는 비공개 비교·집계처럼 Rust 의미 모델 밖의 보조 작업 | ROM 수정, 주소 지식, 인코딩, 페이지 선택의 단일 출처, 빌드·출시 합격 판정 |
| 에뮬레이터 관측 | exact ROM·SaveRAM·입력 계보에 묶인 실제 전이와 화면·메모리 소비 확인 | 정적 분모나 설치 검증 대체, 다른 SHA 산출물의 성공 승계 |

현재 Python 프로그램 `tools/solve_dialogue_page_capacity.py`는 JSON 요청을 받아 배치 후보만 반환한다. Rust가 입력 유효성, 후보의 전수 재검증, 결정적 정규화와 실패 판정을 계속 소유한다. 향후 Python 도구도 같은 경계를 넘지 않는다.

현재 exact 전체 빌드는 Rust의 결정적 best-fit 배치만으로 완료되며 Python을 호출하지 않는다. 제한된 물리 페이지 수를 탐색해야 할 때만 Python/HiGHS 또는 Z3를 후보 생성기로 쓸 수 있고, 어느 결과든 Rust의 같은 검증기를 통과해야 한다.

## 테스트와 빌드 뒤의 작업 구분

1. `cargo test`는 합성 행동 회귀와 라이브러리 불변 조건을 검사한다.
2. 빌드 CLI는 exact source와 번역 입력으로 누적·통합 ROM을 만들고 최종 바이트를 재결속한다.
3. 분석 CLI는 방금 만든 ROM과 보고서를 다시 읽어 번역 커버리지, 소비자 설치, 미해결 실행 역할을 계산한다.
4. Python은 필요한 경우에만 CLI JSON을 입력으로 받아 최적화 또는 비공개 시각 비교를 수행한다. 그 결과는 Rust가 다시 검증하기 전까지 제안이다.
5. emucap은 같은 ROM과 SaveRAM 파일로 관련 전이를 묶어 실행한다. 캡처 하나가 아니라 진입·변형·취소·결과·이탈을 같은 실행 계보에서 확인한다.

## 커밋 경계

- 계획·화면 상주 타입·화면군별 생산자와 소비자 결속은 이미 독립 커밋으로 나눴다.
- 프런트엔드 네 상태의 중복 선택기 제거와 교차 도메인 보존 범위 분할은 독립 커밋으로 닫았다.
- 유닛 요약·상태의 수명 의미를 소비해 누적 유닛 선택기를 제거하는 커밋과, 누적 선택기들을 8노드·11경로의 분기 그래프로 묶는 커밋을 각각 닫았다. 그래프 커밋은 ROM 바이트를 바꾸지 않고 누적·최종 보고서와 최종 설치 검증이 같은 경로 분모를 소비하게 한다.
- 현재 물리 분해 커밋은 이 그래프를 공개 모델·원천 바이트 결속·직접 진입 센서스·합성 행동 시험의 네 모듈로 나눈다. 의미와 직렬화 결과를 바꾸지 않으며, 이후 선택기 정책 변경이 700줄이 넘는 한 파일에 다시 섞이지 않게 한다.
- 다음 의미 커밋은 그래프에서 동적 선택기로 남긴 설정·명단·상점·장 대사의 화면 상태 분모를 중앙 상주 레지스트리와 대조한다. 중앙 계획이 실제로 페이지를 게시하거나 유지하는 상태만 포워더로 바꾸고, 아직 소유가 닫히지 않은 경로는 동적으로 유지한다.
- 대형 파일 분리는 소유 결정 변경과 섞지 않는다. 같은 행동을 유지한 채 CLI 어댑터, 계획, 실행 코드 방출, 설치 검증을 파일과 타입으로 나누는 별도 커밋으로 만든다. 첫 별도 커밋은 세 최종 파이프라인 명령의 CLI 어댑터만 옮기며 산출물 바이트를 바꾸지 않는다.

각 커밋은 `cargo fmt --check`, 관련 행동 테스트, 전체 crate 테스트, `git diff --check`를 통과한다. ROM과 비공개 작업공간, 캡처, SaveRAM은 커밋하지 않는다.

## 완료 조건

리팩터링 완료는 파일을 나눈 시점이 아니다. 다음 조건을 모두 만족해야 한다.

- 모든 번역 대상 화면 상태가 한 화면 상주 레지스트리에 속한다.
- 런타임 코드에 별도의 상태별 페이지 정책이 없다.
- 누적 패치와 최종 패치가 서로 다른 선택 결정을 하지 않는다.
- 최종 설치 검증과 번역 커버리지가 같은 레지스트리를 소비한다.
- Python 없이도 정답을 검증하고 ROM을 만들 수 있다. Python 최적화가 없으면 더 느린 Rust 대안이나 명시적 미해결로 실패한다.
- 대표·최악·성공·취소·이탈을 묶은 exact-artifact 실행 회귀가 남은 화면 역할을 명시한다.
