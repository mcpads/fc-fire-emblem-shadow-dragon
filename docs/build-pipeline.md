# 빌드 파이프라인

제품 빌드는 다음 순서로 실패 폐쇄형으로 동작한다.

1. 일본판 원본 전체·PRG·CHR 해시와 iNES/매퍼 구조를 검사한다.
2. 번역 자료가 `ja`에서 `ko`로 가며 `preserve_existing_english: true`인지 검사한다.
3. 한글 타일 코드가 첫 일본어 설정 문자열에서 실제로 쓰인 가나 코드인지 검사한다.
4. Dalmoori를 8x8 NES 저비트플레인 타일로 래스터화한다.
5. 설정 표와 각 CHR 타일의 원본 바이트가 기대값과 정확히 일치할 때만 같은 길이로 쓴다.
6. 최종 ROM의 모든 변경 바이트가 등록된 쓰기 범위 안인지 감사한다.
7. 모든 검사가 끝난 뒤에만 무시된 `out/` 아래에 ROM과 미리보기를 쓴다.

영문 패치나 조사 산출물은 이 경로의 입력이 아니다. 설정 PoC는 실행 코드를 수정하지 않고 고정 길이 자료와 일본어 타일만 바꾼다.

## 화면 계약 조사

`analyze-screen-contracts`는 국소 주소를 패치하기 전에 화면 역할별로 일본어 대상, 보존할 원본 영어·숫자, FD 문자, FE 그래픽, 스프라이트 UI, 점멸·애니메이션, 입력 대기·자동 전이, 글꼴 페이지 진입·이탈·재진입을 함께 점검한다. 분리된 실제 화면 46개는 모두 실행으로 관측했고 43개는 CHR 쌍까지 결속했다. 새 게임 선택과 저장 슬롯 선택은 같은 페이지를 쓰더라도 합성 상태와 가시 요소가 달라 별도 수명이다. 사운드 테스트의 `START`는 6단계 테스트를 별도 여섯 화면으로 세지 않고 공용 `battle_animation`의 유닛 정보·예측·공격·피해·결과 수명으로 결속한다. `SELECT`의 30단계 엔딩은 같은 상태 `01` 안에서도 번역 경계가 다른 원본 영어 도입·캐스트와 일본어 장 기록을 나누고, 원본 영어 스태프, 일본어 인물 후일담, 정적 종단 화면도 별도 역할로 둬 미분할 화면군이 남지 않았다. 소지품 목록·행동 메뉴·장비·사용 결과는 `1A/1A + 00/15`, 텍스트 없는 양도 대상 선택은 `1A/1A + 15/15`였다. 공용 전투 엔진의 이름·병종·아이템·별도 전투 대사 원천과 28개 대사 레코드, 엔딩 장 기록 스트림과 인물 후일담 두 표까지 소스에 결속했다. 정규 전투의 유리·불리·패배 경로 극성과 인물 후일담의 직접·라우팅 렌더링 합집합을 닫았으며, 다음 구현 관문은 검토된 번역문에서 실제 한글 글리프 작업 집합을 계산하는 것이다.

`analyze-temporal-surfaces`는 비공개 frozen-frame 증거 manifest를 받아 각 표본의 스크린샷·생산자 상태·내부 RAM·PRG RAM·2 KiB 네임테이블·OAM·팔레트를 함께 검증한다. 선언 프레임 차와 생산자 프레임 차가 정확히 같고, 표본마다 소스에서 예상한 상태 바이트가 맞을 때만 화면·CHR 쌍·두 물리 네임테이블의 타일 코드·가시 스프라이트 타일 합집합을 만든다. 가시 스프라이트는 OAM의 Y 좌표가 `00..EE`인 항목으로 한정한다. 스키마 2부터는 각 표본의 배경·스프라이트 패턴 테이블 주소도 기록해 같은 타일 번호가 실제로 어느 4 KiB 페이지를 소비하는지 구분한다. 스키마 3은 게임 오버 표본마다 대사 선택자 `$77F4:$77F1`의 실제 값을 기록하고, 원본 `0B:$A09F..$A100`이 생산할 수 있는 `B0:06/07/08/09/0A` 가족에 속하는지 검사한다. 현재 무저장 1장 표본의 실제 값은 모두 `B0:0A`다. 원본 MMC4의 상태 키와 mapper 165의 1 KiB 레지스터 값을 각각 읽고, mapper 165 값은 예약한 8 KiB 접두부를 뺀 원본 상대 4 KiB 페이지로 정규화한다. 예약 접두부나 정렬되지 않은 레지스터는 거부한다. 공개 코드와 보고서에는 증거 경로나 대사 원문을 넣지 않는다. 현재 사운드 테스트 공용 전투 11개, 자동 엔딩 18개, 턴 경계 게임 오버 12개, 적 선공 정규 전투 11개, 플레이어 선공 정규 전투 10개, 합계 62개 불규칙 표본에서 CHR 쌍 16개·네임테이블 타일 코드 219개·가시 스프라이트 타일 코드 160개를 모았다. 게임 오버 완성 문구는 890프레임 동안 입력 대기로 유지됐고, 두 정규 전투는 예측·공격·피격·반격·성장·결과 수명을 포함했으며, 엔딩 종단은 `$7731=1D`, `$7732=00`, no-op 처리기와 12,000프레임 동일 표본으로 정적임을 확인했다. 현재 보고서 SHA-1은 `d1390d192c071ee6e1cc5e7bcf2ecaa19774165b`다.

`analyze-epilogue-variants`는 자연 부대, 전원 직접, 전원 라우팅의 고정된 엔트리 집합과 7·19·43·82·171프레임 표본을 실패-폐쇄로 검사한다. 각 표본은 여덟 산출물과 고정 메모리 크기, 생산자 프레임 차, 첫 선택자·엔트리가 모두 맞아야 한다. 현재 112개 보이는 엔트리의 560개 표본에서 13개 CHR 쌍을 얻었으며, 라우팅 `41:01`의 장기 빈 화면은 보이는 엔트리에서 제외한다. 보고서는 원문·번역문·입력 경로 대신 구조 수치와 해시만 기록한다.

`analyze-chapter-transitions`는 장 종료부터 다음 장 도입까지의 기본 여섯 수명과 저장 완료 “아니오”의 종료 안내·사운드 테스트 두 수명을 분리한다. 장 인트로 `E5` 문맥 25개가 `$781D=00..18`을 공급하고, 장 제목 표 `$EE08`도 25개 포인터를 가지며 마지막 문자열이 다음 장소 이름 표 `3EFC7` 직전에서 끝나는지 검사한다. `NEXT STORY` 인덱스 `3E`와 저장 질문 인덱스 `32`의 포인터·원본 바이트·합성 소비자도 고정한다. 정규 파일 1의 장 번호 `$6519`, `$6000..$6542` 16비트 가산 체크섬, 기록·검증 코드도 결속한다. 11장 성 명령부터 이어진 기본 실행과 두 “아니오” 분기는 각각의 상태·입력 효과·CHR 수명에 결속했다. 사운드 테스트에서는 위·아래·`A`·`B`의 원천 효과와 `START`의 공용 전투 엔진, `SELECT`의 자동 엔딩을 결속한다. 전투는 32개 내부 단계, 이름·병종·아이템·지형의 다섯 고정 표, 22개 짧은 메시지 템플릿, 인라인 예측 라벨과 별도 상태기의 대사 28레코드를 검사한다. 엔딩은 113개 장 기록 스트림·동적 턴 삽입과 두 인물 후일담 표를 구조적으로 검사한다. 다섯 고정 표의 107개 고유 코드는 일본어 100·보존 원문 6·레이아웃 1개로 나뉜다. 전투 대사 834바이트는 일본어 620·보존 원문 167·레이아웃 47바이트, 엔딩 장 기록 439바이트는 349·47·43바이트, 인물 후일담 1,649바이트는 1,529·9·111바이트로 정확히 분할되며 세 표면 모두 미해결 코드는 없다.

인물 후일담은 상태 `0E`가 `$773B=35`를 만든 뒤 상태 `0F`가 후보 ID `35..01`을 역순으로 훑는다. `$6A90`의 54개 부대 레코드는 각 27바이트이고, 오프셋 `00`의 ID가 후보와 같은 레코드가 없으면 화면을 만들지 않고 다음 후보로 넘어간다. 선택자와 장별 이력 생산자는 각각 포인터의 하위 바이트 `90`, 상위 바이트 `6A`를 저장해 이 주소를 만든다. 일치 레코드의 행동 바이트 `12`가 `FF`이면 표 `41`과 그 레코드의 오프셋 `0E` 장소 이름을, 아니면 표 `40`을 고르며 엔트리 번호는 후보 ID와 같다. 장 전환 상태 `06:$B5C8`은 `06:$B67B`를 호출해 행동 바이트가 `FF`인 비활성·격파 레코드의 `0E`에 현재 장 `$7674`를 기록하므로, 장소 이름 소비와 생산 경로가 이어진다. 표 `41`의 스크립트 엔트리 `02..35` 52개는 모두 표 `40`의 엔트리 `00`으로 전이한다. 합성한 `41:01`은 상태 `10`의 장기 빈 화면이고 보이는 엔트리가 아니다. 표 `40`의 추가 엔트리 `36..41`은 외부 후보 선택자가 아니라 대사 제어 전이로만 들어가며, 쓰기 이벤트에서 `36..39`, `3B..3D`, `3F..41`을 관측했다. `FF`가 모든 경우에 인물 사망만 뜻한다고 좁히지는 않는다. 보고서는 장 종료·저장 완료·전투·후일담의 원문을 출력하지 않으며, 진행 가속이나 합성 분기 도달을 자연 난이도·실패·운명 증거로 일반화하지 않는다.

`analyze-chapter-victory`는 11장 지도 포인터와 25×32 타일 구조를 검사해 성 타일 `4B` 두 개를 행 8, 열 5·6에 결속한다. `しろ` 라벨 인덱스 `38`, 명령 비트 3의 `06:$907B`, 주 상태 `3C`, `06:$9390 → 0F:$C027 → 03:$8006`과 외부 화면 상태 `0C`의 4단계 처리기 표를 한 경로로 묶는다. 코드 구간은 고정 원본 바이트뿐 아니라 고정된 `retro-rp2a03`의 typed decoder로 명령 경계를 다시 확인한다. 런타임 계약은 초기 성 점유자, 행동 바이트 `FF`의 비활성 규칙, 실제 이동으로 열린 성, 네 줄 메뉴, 네 에필로그 페이지와 12장까지의 7개 화면을 기록한다. 보고서는 지도 전체나 대사 원문을 출력하지 않으며, 좌표·행동 상태·승리 단계 직접 쓰기를 완료 증거로 허용하지 않는다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-screen-contracts \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"

cargo run -p fc-fire-emblem-patch -- analyze-chapter-transitions \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"

cargo run -p fc-fire-emblem-patch -- analyze-temporal-surfaces \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes" \
  evidence/private/temporal-surfaces/manifest.json

cargo run -p fc-fire-emblem-patch -- analyze-chapter-victory \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

보고서는 원문이나 캡처를 포함하지 않고 화면 역할, 구조 상태와 다음 관문만 기록한다. 실행 관측이 없는 화면은 추측으로 채우지 않으며, CHR 쌍 목록도 같은 레지스트리에서 생성해 화면 목록과 매퍼 분석이 어긋나면 실패한다.

`analyze-translation-coverage`는 화면 계약을 번역 원천·입력 상태·현재 누적 ROM의 설치 소비자에 연결한다. 단위가 다른 대사 줄, 이름, 프로필, 라벨을 하나의 숫자로 더하지 않고 23개 도메인별로 센다. 전체 53개 화면 중 일본어 대상 44개는 모두 적어도 한 도메인에 속해야 하며, 미등록 화면·도메인·설치 소비자, 작업공간 결속 불일치, 현재 ROM과 빌드 보고서 SHA-1 불일치는 즉시 실패한다. 공개 보고서에는 원문·번역문·글리프 문자·입력 경로를 넣지 않는다. 시작 메뉴의 일곱 라벨은 `new_game_choice`와 `save_slot_selection` 두 소비자에 설치되고, 용량 보고서도 두 수명을 별도로 낸다. 저장 후속 선택은 대사 레코드 `45`와 공용 `예/아니오` 배정을 한 역할 `storage_follow_up_choice`로 측정한다. 레코드 프리픽스를 실제 배치대로 읽은 뒤 새로 드러난 일본어도 별도 전체 설치 게이트에서 한국어 입력을 모두 채웠다. 기존 화면의 최악 `209/210`과 제목 그래픽 `117/121`은 이 입력을 실제 작업집합에 합친 뒤 다시 전역 판정한다. `--defer-runtime-evidence` 빌드도 정적 용량과 설치 보고서는 갱신하며, 실행 증거가 없는 도메인은 `runtime_bound_screen_roles`를 빈 집합으로 두고 런타임 완료를 거짓으로 보고한다.

`plan-full-translation-installation`은 주 대사와 나머지 13개 도메인의 입력을 한 번에 읽고 일부 도메인만 설치하는 후보를 만들지 않는다. 원천 504레코드는 각각 표시 단위 하나다. 전체 분모는 504개 표시 단위·928개 가시 페이지 작업집합이며, 리터럴 글리프는 715개다. 동적 문자열과 장 제목 공존 수명을 포함한 개별 작업집합의 최대 수요는 `195/210`, 합쳐진 물리 페이지의 최대 수요는 `210/210`이다. 결정적 best-fit 묶음의 정적 상한은 36페이지라 현재 후보가 회수·추가할 수 있는 14페이지에 들어가지 않는다. 14페이지 정확 해의 존재 여부는 아직 결정하지 않았으며, 시간 제한에 걸린 solver 실행을 불가능 증명으로 취급하지 않는다. 전역 런타임은 이 정적 페이지 묶음을 직접 싣지 않고 atlas에서 CHR RAM을 합성하므로, 36은 합성 재료의 정적 상한이지 ROM의 CHR 페이지 요구량이 아니다. 공용 선택지 주민 모집단 전체의 최대는 `195/210`이지만, 저장 후속 선택창 자체의 설치 작업집합은 대사 글리프 11개와 보존 활성 코드 15개를 합친 `26/210`이다. 두 수치를 혼용하지 않는다.

같은 명령은 각 대사 줄의 표시 폭도 감사한다. 고정 창 기술자에서 폭을 읽고 원천 전이 그래프로 이어진 레코드에만 전파하며, `EC` 동적 문자열은 생산자별 정확 길이 또는 번역 모집단의 최대 길이를 더한다. 일본어 `0F/1F`는 합성 텍스트 렌더러와 같은 규칙으로 폭 0 결합부호로 센다. 절대 창 폭을 모르는 줄은 같은 항목별 `한국어 폭 - 일본어 폭`의 최댓값만 더하고, 원문 그대로인 숫자 생산자는 양변에서 상쇄한다. 번역 쪽 상한이 원문 쪽보다 크지 않을 때만 원본 적합성을 승계한다. 어느 경계로도 닫히지 않으면 전체 설치가 미해결을 보고하며, 검토자가 기존 줄 안에서 문장을 압축하거나 의미 단위로 재배치한다. 문장·제어 코드·선택지·페이지 경계를 모르는 기계적 줄바꿈은 하지 않는다.

정식 우선안은 대사를 페이지 코드북으로 인코딩하고 실행 중 CHR RAM에 합성하는 것이다. `EC` 142회를 생산자 의미에 따라 보존 숫자·아이템명·아군명·장소명 네 도메인으로 전수 분류했다. 가능한 동적 이름 합집합은 최대 175자이고, 리터럴·보존 코드를 합친 실제 작업집합 상한은 `195/210`이다. 대사 코드북 715자와 다른 필수 도메인의 10자를 합친 공유 atlas는 725타일·5,800바이트다. 동적 글리프 187개는 각자가 나타날 수 있는 모든 페이지의 보존 코드와 충돌하지 않는 canonical 물리 코드를 이분 매칭으로 하나씩 받는다. 소비 수요 142개는 모두 원본 생산 경로에 이었고, 공유 전투 표의 비단사 바이트를 대사 코드로 재사용하지 않는다.

합성 단위는 개별 페이지가 아니라 35개 상주 그룹이다. 그룹 레시피는 그 그룹의 전체 글리프를 싣고, 928개 페이지 참조 중 같은 레코드의 직전 페이지와 동일한 레시피는 `FFFF`로 표시한다. 연결 레코드 전이 637개도 현재 상주 그룹 색인과 새 그룹 색인을 비교하며, 현재 원천 그래프에서는 변경 0개·재사용 637개다. 같은 그룹이면 resolver가 즉시 `ready`를 게시하므로 원본 페이지 복원과 오버레이 전송, 동기 합성기 호출을 모두 건너뛴다. 그룹이 바뀌거나 독립 수명으로 들어올 때만 합성한다. 첫 콜드 그룹은 clean vblank에서 렌더링을 끄고 완성하므로 짧은 blackout이 남는다. 지원 원본의 마지막 공통 화면-off 경계는 대사 정체성 게시보다 먼저 끝나므로 화면별 훅으로 억지로 합치지 않는다. 실제 화면 확인 전에는 전체 설치 완료로 보지 않는다.

압축과 회피책은 같은 비용 기준으로 유지한다. 36개 완성 CHR 페이지는 147,456바이트라 현재 가능한 14페이지·57,344바이트에 들지 않는다. 4×4 block dictionary는 atlas를 4,085바이트로 줄여 1,619바이트를 아끼지만 둘 다 한 8 KiB PRG 페이지에 들어가므로 복원 루틴을 먼저 추가할 이유가 없다. 소비자 remap은 canonical 물리 코드 고정이 전체 모집단에서 성립해 기각했다. 10비트 의미 글리프 스트림이나 다중 바이트 escape는 물리 코드 결박을 없앨 수 있지만 디코더 전체를 바꾸므로 현재 고정 배정이 성립하지 않을 때만 다시 계산한다. 매퍼 추가 확장과 의미 보존형 글리프 축소는 그 뒤의 최후 수단이다.

레코드 프리픽스는 한 가지 순서가 아니다. 창 기술자가 없는 레코드가 504개 중 206개다. 선두가 `E8`인 39개, 선두가 다른 제어 코드인 129개, 기술자 자리가 표시 글자인 38개이며 나머지 298개는 기술자를 갖는다. 예전 파서는 이 셋 모두에서 네 바이트를 무조건 뺐고, 그래서 같은 저장 바이트가 진입 방향에 따라 다르게 읽혀 `E4/E6` 대상 139레코드가 두 모드를 가진 것처럼 보였다. 실행이 어느 쪽이 맞는지 정했다. `chapter-intro-dialogue:002`·`:004`와 `shop-and-item-dialogue:036` 세 표본이 세 형태를 모두 덮고 셋 다 기술자를 빼지 않는 쪽과 일치한다. 파서를 배치에 맞춘 뒤 139레코드의 두 프리픽스는 전부 같아졌다. 따라서 직접·전이 payload를 따로 두던 확장 미러 뱅크, 전이 resolver와 reader 선택기, 두 모드를 나누던 정규화는 모두 폐기했다. 의사결정 57·59번을 따른다.

`E4/E6` 피연산자는 16비트 주소가 아니라 원천 pointer table의 `selector + entry index`이며 213개를 그대로 보존한다. 레코드마다 payload가 하나뿐이므로 저장은 원천 소유 구간 안에서 끝난다. 이 정확 배치는 `29,792/39,425`바이트로 11개 구간을 모두 통과하고 9,633바이트가 남는다.

전체 설치 배치도는 기존 전투 재료 PRG 뱅크 `10`과 대사 합성 재료·실행 코드용 MMC3 8 KiB 페이지 `2C..30`을 서로 겹치지 않게 고정한다. 다섯 페이지는 항상 40,960바이트 전체를 한 컨테이너로 쓰므로 뒤에 코드가 추가돼도 다른 도메인의 시작점은 움직이지 않는다. 나머지 `31..3D` 13페이지·106,496바이트는 다른 도메인의 공용 재료 풀이다. 현재 이 풀은 비대사 13개 도메인의 338엔트리 4,082바이트, 20,645바이트 대사 페이지 레시피, 1,585바이트 최종 소비자 카탈로그를 가진다. payload는 합계 26,312바이트, 16바이트 정렬을 포함한 범위는 34,353바이트라 정확 `FF` 범위에 든다. 고정 뱅크에서는 예약을 두지 않고 정확한 `FF` cave 전부를 후속 코드 후보로 보고한다. 전이 reader 예약은 미러 뱅크와 함께 폐기했다. CHR은 교체 가능한 물리 페이지 `50`부터 14페이지다.

합성 재료는 더 이상 크기 추정치가 아니다. 5,800바이트 1bpp 공유 atlas, 36개 그룹과 928개 페이지 선택자·504레코드 디렉터리를 담은 5,212바이트 스캔 자료, 1,350바이트 런타임 식별표, 1,067바이트 동적 생산자 저장소를 결정적으로 직렬화했다. 식별표는 8개 디렉터리·523슬롯을 모두 가지며 517개 유효 대사 엔트리와 6개 핸들러 빈칸을 닫는다. 16바이트 머리와 5개 섹션 디렉터리가 각 자료의 위치를 소유한다. 용기는 MMC3 페이지 `2C..30` 다섯 장·40,960바이트로 고정하며 마지막 페이지 8,192바이트 전체를 실행 코드에 예약한다. 비대사 13개 도메인 섹션은 원문 바이트와 atlas 색인을 구분하는 16비트 셀, 엔트리 디렉터리, 입력·정체성·내용 digest를 가지며 별도 Expected Write로 설치한다. 보고서에는 글리프와 번역문을 내보내지 않는다. 현재 14개 선언 도메인 모두 실행 재료 쓰기에 기여하고 정적 소비자 결속도 **14 / 14**다. `저장·주소 / 실행 재료 / 글꼴 공급 / 전체 소비자 / exact-ROM 실행`을 각각 구분하며, 정적 소비 결속만으로 실제 화면 검증을 완료로 올리지 않는다.

대사 런타임은 화면별 예외 목록이 아니라 원본 대사 상태 머신 전체에 결속한다. 초기 진입 `0A:$809B`, 두 전이 `0A:$85F8/$865F`, 외부 호출 복귀 `0A:$871C`, 페이지 완료·종료 `0A:$85C9`, 외부 호출 이탈 `0A:$8556`이 요청을 생산하거나 무효화한다. 소비자는 조용한 프레임 조건이 성립하는 원본 NMI `$C179`에 끼어들며, 대기열 표시가 하나라도 서면 PPU를 건드리지 않는다. 현재 제어 역할 10개와 동적 문자열 생산자 역할 5개는 모두 통합 쓰기 계획에 설치됐다. 초기·전이·다음 페이지 요청은 아직 모두 콜드 복원이고, 직전 `ready` 정체성을 이용하는 delta 경로는 후속 최적화다. 코드 실행 구간은 마지막 페이지 `30`의 `$A000..$BFFF`이고, 고정 trampoline은 정확한 `FF` cave `$F400..$F4B0`, 동적 생산자 브리지는 `$F79A..$F806`에 결속했다. 과거 최대 대사 한 건을 위한 `$85C9`, `$F341`, `$F990`의 샘플 코드는 전체 digest를 확인한 뒤 전역 수명·게이트로 교체한다.

CHR 복원 상태는 mapper165 생산자가 이미 가진 것을 소비한다. 중앙 오른쪽 FD/FE 기록기 `$C9BE/$C9C6`는 원천 페이지를 `$5B/$5C`에 각각 보존하고 `$52`를 합쳐 selector 사슬을 부른다. 직접 CHR 기록기가 쓰는 `$FA80/$FAA0`은 stateless이므로 관측 훅으로 이 상태를 갱신하지 않는다. 전송 중에는 현재 래치와 관계없이 `$2007` 쓰기가 RAM에 닿도록 FD/FE를 모두 CHR RAM으로 고르고, 이탈은 `$5B/$5C | $52`를 각각 원래 helper에 넘겨 두 래치를 독립 복원한다. 표시 단계는 다르다. PRG 페이지 `21`의 4 KiB는 대사 FD 원천 페이지 `00`과 같으므로 마지막 전송 프레임이 FE 복원 뒤 FD만 RAM으로 직접 게시하고, 하드웨어 선택 뒤에 `ready`를 쓴다. 이후 중앙 FD 재공급은 `ready`, 원본 대사 상태 `00..0E`, 원천 FD `00`을 확인해 같은 선택을 유지한다. `$29`는 NMI의 PRG 복원 그림자이므로 대사 수명 판정에 쓰지 않는다. FE 배경은 원본 CHR ROM에 둔다. FD/FE를 한 RAM 페이지에 합치는 안은 실제 코드 패턴 충돌 때문에 폐기했다. 임시 저장소 `$07EB`도 전투 런타임 `$07E0..$07EF`와 겹쳐 쓰지 않는다.

복원 helper 비용은 고정 상수가 아니다. 후보의 `$FA80/$FAA0` 진입부터 `$FE90`의 공용 판정과 각 최상위 `RTS`까지 typed RP2A03 CFG를 따라 분기 양쪽의 큰 값, 직접 점프와 중첩 호출을 센다. 현재 callee 상한은 FD/FE 각각 140사이클이고 호출자 `JSR`는 별도 6사이클이다. 선언 범위를 벗어나거나 간접 전이·루프·재귀·미모델 명령을 만나면 전체 설치 계획이 실패한다.

레코드 색인 2바이트·가시 페이지·그룹·상태의 휘발 저장소는 `$07F0..$07F4`로 선택한다. 18개 원본 처리기에서 도달하는 1,173개 typed RP2A03 명령의 직접 충돌은 0곳이다. 후보와 겹칠 수 있었던 `$0781,X` 3곳은 공용 appender의 `CPX #$5F`와 overflow abort, 직렬화 종단을 원본 코드에 결속해 최고 주소 `$07DF`로 닫았다. 간접 접근 32곳은 10개 포인터 역할로 완전 분할하며, 새 접근이 어느 역할에도 정확히 속하지 않으면 계획을 실패시킨다. 캐릭터 스프라이트의 두 단계 포인터도 bank 0A의 선택자 `00..FE` 255개, 포인터 510개를 전수 읽어 모두 switchable PRG 안임을 확인한다. 여기에 16개 PRG 뱅크 262,144바이트 전체를 직접 주소 피연산자로 스캔한다. 발견되는 세 후보는 모두 실제 명령 시작이 아니라 앞 명령의 내부 바이트임을 원천 바이트와 typed decode로 결속한다. 동시에 실행되는 고정 NMI 277개 명령과 그 NMI가 bank 0E에서 부르는 오디오 그래프 2,037개 명령도 따로 추적한다. 오디오 `$8A7C JMP ($F4)`는 더 이상 분석을 조용히 끝내지 않는다. `$882D..$88ED`의 96개 포인터와 88개 고유 대상을 보수적 실행 뿌리로 결속한 뒤 간접 읽기 30곳과 간접 쓰기 1곳을 역할별로 분할한다. 새로 드러난 `$87F6 STA ($F2),Y`의 목적지는 `$4000..$400F` APU 레지스터로 제한되고, `$8C1F` 인덱스 읽기는 13개 typed 포인터 생산자와 `$8C3C..$8F0E` 범위에 결속한다. 이는 NMI·오디오 양성 실행 그래프를 닫은 것이며 whole-program 실행 명령 분모를 닫았다는 뜻은 아니다. mapper 165의 기존 전투 상태는 `$07DF..$07EF`까지만 소유한다. 이 주소는 영구 전용 RAM이 아니라 주 대사 활성 수명에만 소유한다. 모든 진입과 `E7` 복귀는 사용 전 5바이트 전체를 콜드 초기화하고, `E4/E6`·페이지 전이는 원본 활성 상태가 유지될 때만 연속 소유하며, `E7` 이탈·종료·reset·save/load·비활성 선택은 무효화한다. 전송 중 커서인 `$07F5/$07F6`은 `ready` 게시 직전에 완성 페이지의 원문 `$77F4/$77F1` 정체성으로 바뀐다. 연속 페이지와 명시적 레코드 전이는 291개 표시 수명으로 묶으며, 가장 큰 수명도 53레코드·53작업집합·활성 슬롯 `198/210`에 들어간다. 637개 상주 전이는 모두 같은 코드북을 재사용한다. 반복 생산자는 `ready + 같은 게시 정체성`이면 완료 훅이 정한 현재 가시 페이지와 코드북을 재사용하되, 훅이 밀어낸 원본 resolver는 항상 실행한다. 다른 원문이나 무효화된 수명만 다시 합성한다. 이 판정이 커진 요청 발행기는 트램폴린과 `$F400..$F4B0`을 공유하고, 표시 selector는 별도 exact-`FF` 동굴 `$F558..$F700`을 쓴다. 동적 `EC` 문자열의 187개 canonical 코드는 관련 페이지의 물리 코드와 같도록 전역 배정했으므로 공용 글리프 reader `$E57F`는 건드리지 않고, 원본 영어·라틴 문자·숫자도 항등 매핑을 유지한다. 현재 설치 계획은 정규 대사 저장소 11구간·포인터 517개, 제어 역할 훅 10개, 동적 생산자 훅 5개, 고정 지원 루틴과 실행 페이지 루틴을 하나의 추적 이미지에 방출하고 최종 이미지에서 현재 인코딩과 다시 비교한다. 필수 냉합성 동안에는 물리 CHR 페이지 `50`·mapper 값 `C8`의 전용 표시 페이지가 보호 46코드를 유지하고 한글 활성 슬롯 210개만 비운다. 요청 게시 전·중앙 selector·각 전송 프레임 이탈의 세 지점이 FD만 이 페이지로 고른다. 정확 탐침 `30C5406ED6724ADBBCA2B124D626129587C0D22D`은 복원·덮기 구간의 빈 슬롯과 보존 UI, 완료 뒤 장 제목·원본 표식·한글 본문·맵·창·초상화를 함께 확인했다. v25 `26A8D6587D23EDBF06964FF175C4285F05DBE9BE`는 첫 레코드 전이에서 보조 버퍼 길이 `06`을 소비 전에 기록하고, `$053E=02`를 유지한 채 다음 한글 대사 화면까지 진행했다. 다음 검증 관문은 정확 최신 출력에서 실제 동적 아이템·인물·지명과 보존 숫자, 나머지 장·외부 호출 경로를 함께 회귀하는 것이다.

`build-release-image`은 누적 이미지를 배포용으로 다시 포장한다. PRG와 CHR 내용은 한 바이트도 바꾸지 않는다. 헤더를 NES 2.0으로 다시 쓰고 CHR ROM을 매퍼 상한과 같은 256 KiB까지 0으로 채운다. 채우는 자리는 아직 아무도 고르지 않는 물리 페이지라 뱅크 번호는 그대로다.

바꾸는 이유는 실기다. iNES 1.0에는 «CHR ROM이 있으면서 CHR RAM도 따로 있다»를 적을 자리가 없어서, 누적 이미지는 실행 환경이 매퍼 165를 알아서 맞춰 주기를 기대하는 상태였다. NES 2.0은 바이트 11 하위 니블로 CHR RAM 4 KiB, 바이트 10 상위 니블로 배터리 작업 RAM 8 KiB를 명시한다. CHR 216 KiB가 2의 거듭제곱이 아니었던 것도 함께 없앤다. 의사결정 62번을 따른다.

승격이 동작을 바꾸지 않는다는 것은 실행으로 확인했다. 누적 iNES 1.0 이미지와 배포 NES 2.0 이미지를 같은 조건에서 콜드 부팅해 프레임 600과 1300의 화면 SHA-256이 `c5495239f6dbeb2e3c04649df7cacd68e827c026e0114e26a7fe48e980da74aa`와 `446f2c6b0c882d01135c9c1473f3cd5dbea4db38e4be31f78e7099789614a24e`로 양쪽 같았다. 배포 이미지의 노출 메모리 영역은 CHR RAM 4,096바이트, CHR ROM 262,144바이트, PRG 524,288바이트, 배터리 SRAM 8,192바이트로 선언과 일치한다.

`build-title-logo-asset`은 원본 제목 스트림과 CHR 페이지의 강한 해시를 확인한 뒤, 외부 ImageGen 후보와 그 해시·자르기 범위를 선언한 manifest를 `216×40` 2bpp 로고로 정규화한다. 원본의 `TM`은 마지막 행 `BA+BB` 두 셀을 함께 쓰므로 둘 다 보존하고, 나머지 134셀의 일본어 로고 전용 코드 121개만 재사용한다. 후보의 마지막 행이 `TM` 영역을 침범하거나 고유 비공백 타일이 121개를 넘으면 실패한다. 현재 자산은 200픽셀 폭·고유 타일 `117/121`이며 원본 CHR을 복제하지 않고 셀 코드와 새 패턴만 담는다. 누적 설치는 제목 스트림의 보존 셀과 미배정 CHR 패턴이 그대로인지 다시 확인한다. 완성 연출의 별도 PPU 전송은 `$2182`의 상단 장식 26셀을 빈 타일로 만들고 `$21A8/$21CD/$21ED`의 본체 11셀을 같은 한국어 로고로 재고정하되 명령·속성 바이트는 보존한다. 과거 누적 후보 `87176c60d9ebb3cfd28e9cc44c58954113863d0e`의 무입력 실행에서 프레임 1206·1331·1458·1912의 초기·완성 점멸, 상단 공백, 칼, 두 셀 `TM`, 저작권 줄과 자동 병종 소개 이탈을 확인했다. 이 실행은 현재 누적 후보 `0b507b7c9d0d97a483a04a27bf2821a82b1a9a14`에 승계하지 않으며 사람 승인과 패배 뒤 제목 복귀도 별도 관문이다.

`analyze-item-flow`는 유닛 명령 결과 6부터 소지품 목록, 조건부 행동 메뉴, 텍스트 없는 양도 대상 선택, 장비·사용·양도·폐기 결과를 별도 화면으로 결속한다. 목록의 `A`는 선택 아이템과 슬롯을 저장한 뒤 행동 가능 조건만 계산하며 아직 소지품을 바꾸지 않는다. 행동 메뉴의 `A`는 가용 마스크를 행동 코드 0~3으로 바꿔 실제 변경 경계를 넘는다. 결과 대사 인덱스는 `19/1A/1B/1C`다. 장비는 첫 슬롯과 선택 슬롯을 교환하고, 양도는 승인한 대상 버퍼로 아이템과 내구도를 옮기며, 폐기는 지운 뒤 목록을 압축한다. 사용은 진행 상태 2에서 아이템 계열 효과를 자동 적용하고 일반 결과는 상태 3에서 입력을 기다린다. 행동 플래그 표의 91개 항목 전체를 검사해 `사용` 비트가 있는 26개를 8개 효과 계열로 분류하고, 직접 선택되는 결과 대사 `1D..27/2F..33/50`을 원천에 결속한다. 성공 승급은 레벨 10 이상과 아이템 `50..54`별 허용 병종 표를 모두 통과해야 하며, 실패하면 결과 `30`으로 간다. 성공하면 병종을 바꾸고 공통 결과 대사를 우회한 채 하위 상태 `04→05→06`에서 공용 전투 표시기를 실행한다. 상태 `05` 안의 중첩 전투 대사 `$7937=04`는 완료 조건 `$76ED=0`, `$794A≠0`에서만 `A`를 요구하고, 승인 뒤 공유 전투 정리와 지도 복귀는 자동이다. 대지의 오브 `55`는 이 상태기를 쓰지 않고 상태 2 안에서 동기적인 32단계 화면 변위와 아군·적군 레코드 처리를 끝낸 뒤 결과 `33`, 상태 3으로 간다. 두 경로의 코드와 자료를 41개 원천 구간으로 나누고 typed RP2A03 명령 258개를 검사했다. 실행은 승급의 초기 사용문과 별도 전투 수명, 중첩 승인, 지도 복귀 및 대지의 오브 전 단계에서 유지되는 사용문·CHR, 결과 `33`을 닫았다. 표본 아이템 `40`은 회복 성공 때만 내구도를 줄였고, 최대 HP에서는 무효 결과로 사용 횟수를 보존했으며, 마지막 사용은 슬롯을 지웠다. 고정 라벨 `NO ITEM`, 전투의 `LV/HIT`, 내구도 숫자는 일본판 원본 영어·숫자이므로 보존한다. 보고서 스키마 4의 현재 SHA-1은 `4bd2cd523911112207909735c72d2190cd34da76`다.

```sh
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

`analyze-unit-ui-text`는 `unit_summary`, `unit_command_menu`, `unit_status`를 국소 writer에 결속한다. `$05E8` 합성 상태 `04/05/07/0F`를 각각 요약 상단, 명령 목록, 요약 아이템 목록, 상세 능력치 조립기로 검증하고, 유닛명·병종·아이템·고정 문자열·숫자·합성 파서의 공유 호출부를 보고한다. 상태 `05`는 유닛 능력·지형·인접 대화·인벤토리·시설에 따른 명령 라벨 15개를 정적으로 결속하며, 실행 표시는 `こうげき/もちもの/たいき/たずねる/ぶきや/しろ` 6개를 확인했다. `こうげき`는 무기 선택으로, `しろ`는 승리 처리로 들어가는 입력 효과도 별도 보고서에 결속했다. 공격·지팡이·변신·지형·대화·소지품·시설·대기의 판정 순서와 `$05EB` 비트 0~7, 지형 타일 5종과 시설 인덱스 5종의 라벨 대응도 보고한다. 시설 생산자는 뱅크 `0B:$A291`, 장별 포인터 표는 `$A4FF`이며 1장 `$A531`의 `03 1A 01 00 F0`가 좌표 `$03/$1A`를 시설 인덱스 1 `ぶきや`에 결속한다. 요약·명령·상세의 오른쪽 `00/(15|18|19)`를 모두 관측했다. 원본 `HP`와 숫자·구두점은 번역 대상에서 제외하며 자동 `class_profile` 계약은 섞지 않는다. 현재 번역 입력을 결속한 보고서 SHA-1은 `db20e0cca1ee3d2e52dc56e0ab32419d8b80df56`이다. 전체 합집합은 229자, 요약·상태 공유군은 218자라 정적 단일 페이지가 불가능하고 명령군 30자는 별도 페이지에 들어간다. 독립 최대를 더한 화면 상한은 요약 36, 상태 30, 명령 30이다.

같은 명령은 기존 텍스트 표 명세를 다시 사용해 병종·아이템·아군명·적군명 4개 표의 소비자와 전송 코드를 먼저 검증한다. 이 범위는 포인터 235개, 고유 문자열 234개, 참조 바이트 1,255개, 고유 저장 바이트 1,250개다. 작은 가타카나 `A6..AA = ァ/ィ/ゥ/ェ/ォ`까지 공용 디코더에 포함하면 고유 원문 코드 107개 중 일본어는 100개이고 나머지는 모두 기존 보호·레이아웃 집합에 들어가므로 잠정 한글 슬롯 상한은 210개다. 이 수치는 원문 레퍼토리일 뿐 번역문 한글 수가 아니다. 검토된 번역문이 없으므로 단일 공용 페이지 적합 여부는 계속 미확정으로 보고한다. 요약·상세는 한 이름·한 병종·현재 소지품 최대 네 개를 한 페이지 수명에서 공유하고 소지품이 바뀔 수 있으며, 명령 메뉴는 진입 때 별도 페이지를 다시 공급한다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-unit-ui-text \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

이 명령은 보이는 한 유닛의 문자열을 직접 고치는 패치를 만들지 않는다. 네 조립 역할과 공유 원천 표가 모두 맞아야 하며, 모든 관측 배경 위상과 15개 명령 라벨을 포함한 공용 한글 페이지 설계의 입력으로만 쓸 수 있다. 번역문 합집합이 210칸을 넘으면 유닛별 예외가 아니라 내용 조합별 페이지나 실행 중 글리프 공급을 비교한다.

## 공개 저장소 자료 경계

추출·재삽입 로직과 구조 메타데이터, 설정처럼 작은 메뉴·UI 번역은 추적할 수 있다. 대사 중심의 대규모 원문 추출본, 대사 번역본과 번역 작업용 중간 자산은 Git에 넣지 않는다. 그런 자료는 `private/dialogue/`, `out/` 또는 `evidence/private/` 아래에서만 생성한다. 공개 문서에는 원문 덤프 대신 범위·개수·해시·주소와 소비 경로를 기록한다.

## mapper 165 무번역 패리티 프로브

`build-mapper165-parity-probe`는 지원 일본판을 MMC2식 CHR 래치와 MMC3식 PRG·SRAM을 함께 쓰는 mapper 165로 변환한다. 원본 CHR 앞에 빈 8 KiB를 두고 원본 32개 4 KiB 페이지를 +2 이동하므로, mapper 165의 CHR-RAM 선택값 0과 원본 CHR page 0이 충돌하지 않는다. 재배치한 원본 CHR SHA-1, PRG 크기와 배터리 플래그가 바뀌면 빌드가 실패한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mapper165-parity-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

이 명령은 매퍼 변환 계획을 검토하는 분석 관문이다. 원본의 가능한 매퍼 쓰기와 실행 그래프, writer 분모, 인덱스 별칭, NMI 선택자 안전 계약을 전수 검사한 뒤 같은 계획을 설치한다. 지원 원본이나 매퍼 변환 코드·소유 계약이 바뀌면 이 명령을 다시 실행한다.

일반 `build-kr-patch`는 이미 확정된 매퍼 설치 계획만 적용한다. 지원 원본의 강한 해시를 확인하고 각 원본 바이트에 Expected Write를 적용한 뒤, 추적하지 않은 변경과 최종 설치 계약을 다시 검사하지만 전역 실행 그래프를 매 제품 빌드마다 재계산하지 않는다. 번역문·글꼴·고정 에셋 변경은 이 빠른 생산 경로를 쓰며, 배포 전 검증은 별도의 매퍼 분석 관문과 누적·최종·커버리지 빌드를 모두 통과해야 한다. 분석 관문의 생략을 최종 매퍼 동등성 완료로 해석하지 않는다.

PRG writer 12곳과 명령 경계가 확인된 CHR writer를 같은 길이의 호출로 바꾼다. 새 루틴은 공유 RP2A03 ISA로 조립·역검산하고, 원본이 `FF`이며 직접 `JSR`·`JMP` 대상이 아닌 고정 뱅크 범위에만 배치한다. 출력 보고서는 CHR 재배치, 코드 배치, writer 수, 모든 추적 쓰기와 남은 실행 경계를 기록한다.

이 프로브는 번역이나 한글 자산을 넣지 않는다. 타이틀·자동 병종 설명·1장 인트로 대화, 자연 중단 저장·재개, 검증된 턴 경계 게임 오버, 실제 전투를 거친 1장 완료, 정규 저장, native power cycle 뒤 불러오기와 2장 전환 표본은 원본과 동등하다. 직접 CHR writer 31곳의 트리거 쌍도 모두 분류해 G2를 통과했다. 다만 이는 전체 장·상점·아이템·엔딩의 전수 회귀가 아니며 한글도 아직 공급하지 않으므로 `release_eligible`은 거짓이다.

`analyze-mapper165-trigger-planes`는 화면 실측으로 확인한 FD/FE 쌍에서 타일 `FD`의 상위 비트플레인 8바이트를 비교한다. MMC4는 `$xFD8`, mapper 165는 `$xFD0`에서 FD 전환을 시작하므로, mapper 165의 FD 페이지 상위 비트플레인이 직전에 선택된 FE 페이지와 같아야 트리거 타일이 보존된다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-mapper165-trigger-planes \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

현재 설정·부대 목록, 맵 애니메이션, 세 유닛 UI, 무기점 아홉 화면, 소지품 메뉴·장비 결과·양도 대상을 포함한 29개 화면의 고유 쌍 18개 가운데 오른쪽 `00/14` 한 쌍만 별도 변형 페이지가 필요하다. 설정·부대 목록·유닛 UI·무기점·소지품 화면의 `00/15`, `00/18`, `00/19`와 양도 대상의 `15/15`는 원본 트리거 평면과 같아 자연 페이지를 쓴다. 그러나 같은 FD `00`은 `00/00`, `00/15`, `00/18`, `00/19`에서 원본 비트플레인을 요구하므로 페이지 00을 전역 수정할 수 없다. 빌더는 예약 CHR의 물리 4 KiB 페이지 1에 변형을 합성하고, 중앙 오른쪽 공급자가 FD/FE 그림자 쌍에 따라 자연 페이지와 변형 페이지를 고르게 한다. 직접 writer는 상태를 추측하지 않고 기존 단순 매핑을 유지한다.

`analyze-mapper165-direct-chr-pairs`는 직접 CHR writer 31곳의 명령 경계와 값 공급 방식을 원본 바이트로 검사한다. 연속 `STA`가 같은 A를 소비하는 26곳은 FD=FE 또는 같은 값의 전체 창 초기화로 닫는다. 전투 실행에서 고정 뱅크 오른쪽 쌍과 bank 05 왼쪽 쌍은 모두 `$5E/$5F=02/06`으로 결속했다. bank 05 FE=`06` 뒤 `$E414` 단독 FD가 `06 → 02`로 바뀌어 실제 왼쪽 쌍 `06/06`, `02/06`도 확인했다. 세 쌍의 트리거 비트플레인은 모두 같아 추가 변형이 필요 없다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-mapper165-direct-chr-pairs \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

## 동적 한글 페이지 계획

`plan-hangul-page-proof`는 원본 글꼴 페이지를 기준으로 확장 CHR-ROM에 들어갈 4 KiB 한글 페이지 두 개를 만든다. 현재 보호가 확정된 영어·숫자·부속 문장부호·제어·래치 43코드와 합성 레이아웃 3코드는 원본 타일을 그대로 유지한다. 나머지 210코드만 한글 활성 슬롯으로 배정하며, 한 페이지의 중복 글리프·210자 초과·보호 타일 변경·mapper 165의 256 KiB CHR 범위 초과를 거부한다.

```sh
cargo run -p fc-fire-emblem-patch -- plan-hangul-page-proof \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

현재 합성 표본은 설정 화면에 실제로 표시할 한글 12자를 A와 B의 같은 코드에 공유하고, 그 밖의 같은 100코드에는 페이지마다 다른 합성 글리프를 넣는다. 각 페이지는 112자로 예산 안에 있고 합집합은 `12 + 100 + 100 = 212`자로 한 페이지 한계를 넘는다. 페이지가 바뀌어도 화면 공유 글리프 12개의 코드·문자·타일은 같다. 물리 페이지는 `34/35`, mapper 레지스터 값은 `88/8C`이고, 기존 무번역 프로브 뒤에는 최대 30페이지가 남아 페이지별 배정 총량 상한은 6,300칸이다. 이는 화면별 중복과 실제 번역 코퍼스를 반영한 최종 수용량이 아니다. 산출물의 `runtime_bound`는 거짓이며, ROM 삽입·화면 선택·`A → B → A` 실행 전환을 통과하기 전에는 G3 완료 증거로 쓰지 않는다.

`build-mapper165-hangul-page-probe`는 검증된 mapper 165 무번역 이미지를 메모리에서 재생성한 뒤 설정용 두 4 KiB 페이지를 물리 페이지 `34/35`, 부대 목록용 두 페이지를 `36/37`에 붙인다. 설정 페이지는 공유 12자와 페이지별 100자로 각각 112자, 합집합 212자다. 부대 목록 페이지는 공유 `이/름` 2자와 화면에 보이지 않는 페이지별 증명 105자로 각각 107자, 합집합 212자다. 화면에 보이는 나머지 27코드는 두 페이지 모두 원본 타일과 같아야 한다. 화면마다 같은 코드가 다른 일본어에 쓰일 수 있으므로 두 페이지 집합은 화면 수명을 넘어 합치지 않는다. 출력 CHR은 19뱅크·152 KiB다. 설정 표와 뱅크 `0B:$917C`의 `なまえ   LV HP` 머리말은 각각 검증된 소규모 한글 자료로 바꾸며, `LV/HP` 바이트와 해당 글꼴 타일은 Expected Write와 페이지 전수 비교로 보존한다.

설정 루틴은 `$52=00`, `$59/$5A=1A/1A`, `$5B/$5C=00/15`를 모두 만족할 때만 개입한다. `$0034=20/40`은 A의 `88`, `30`은 B의 `8C`를 오른쪽 FD 레지스터에 쓰며, 화면 계약이 다르면 기존 `$FAC0` 쌍 인식 선택기로 돌아간다.

부대 목록 생성자 `0B:$89DB`는 창 기술자 `$05CF/$05D0=12/04`와 위치 `$70/$71=30/40`을 만든 뒤 `$89F2`에서 머리말 리소스 `2B`를 읽는다. 이 18바이트 생성자 서명은 지원 원본 PRG에 한 번만 있어야 한다. 머리말 호출에서 한 번만 CHR을 쓰면 뒤의 공용 갱신이 덮으므로, 중앙 오른쪽 FD 호출 `$C9C2`를 `$FB80`의 typed RP2A03 선택기로 보낸다. 선택기는 이 네 수명 바이트, 왼쪽 `18/18`, 오른쪽 FD `00`을 모두 확인한 뒤 FE `18/19`에는 페이지 `36`의 값 `90`, FE `15`에는 페이지 `37`의 값 `94`를 쓴다. 다른 화면이나 위상은 기존 `$FAC0`으로 돌아간다. 진행 메뉴는 외부 상태와 CHR 쌍 일부를 공유하지만 생성자 기술자가 달라 원본 페이지를 유지한다. 두 루틴 모두 입력 레지스터·플래그를 보존하며 원본에 선행 직접 `JSR/JMP`가 없고 전부 `FF`인 구간에만 설치된다. 보고서의 `runtime_verified`는 빌드만으로 실행을 주장하지 않도록 거짓으로 유지하고 별도 콜드 실행 결과는 [현재 상태](status.md)에 기록한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mapper165-hangul-page-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

## MMC5 PRG 정적 프로브

`build-mmc5-prg-probe`는 번역·한글 자산 없이 지원 일본판을 mapper 5 헤더로 바꾸고, 원본 마지막 16 KiB PRG 뱅크의 확인된 `FF` 구간 `$FA00`~`$FA7F`에 최소 초기화·뱅크·미러링 루틴을 배치한다. 새 실행 코드는 허용된 RP2A03 명령과 주소 지정 형식만 받는 checked assembler로 생성한다. 이 구간을 대상으로 하는 직접 `JSR`·`JMP` 3바이트 패턴이 PRG 전체에서 하나라도 나오면 쓰지 않는다.

리셋 초기화는 MMC5 PRG 모드 1, 마지막 16 KiB ROM, PRG RAM 0번 뱅크와 쓰기 허용 레지스터를 설정한 뒤 원본 `$C075`로 간다. 원본 중앙 PRG 선택 루틴은 16 KiB 뱅크 번호를 MMC5의 8 KiB 번호로 바꾸고, 미러링 선택은 `$5105`의 수평 `50`·수직 `44` 값으로 바꾼다. 부팅 경로 두 곳, `$E69C` 대사 바이트 읽기 경로 `$E6A1/$E6AB`, `$E6B2` 인덱스 포인터 표 경로 `$E6BA/$E6F1`에서 실행을 확인한 여섯 `$A000` 직접 쓰기는 원본 `$29/$51` 그림자를 손상하지 않는 raw 뱅크 루틴으로 보낸다. 변환 계산 전후에 A와 상태 플래그를 복원하고, 미러링 루틴도 원본 반환 A값 `0/1`을 유지한다.

헤더, 코드 구간, 원본 루틴과 리셋 벡터는 모두 Expected Write로 보호하며 마지막에 변경 전수를 감사한다. 산출물은 mapper 5, PRG/CHR 크기, 원본 CHR SHA-1과 배터리 플래그를 다시 검사한다. `out/mmc5-prg-probe.json`은 루틴 주소와 추적 쓰기만 기록한다. MMC4 CHR 래치, 아직 분류하지 않은 매퍼 쓰기 후보, 코드 구간의 간접 참조, 실행 동등성은 미해결로 명시하며 `release_eligible`은 항상 거짓이다.

`build-mmc5-chr-writer-probe`는 같은 메모리 내에서 위 PRG 프로브를 먼저 생성·검증한 뒤 MMC5 CHR 모드 1을 설정한다. 원본 중앙 CHR 공급 루틴 네 곳은 그림자와 `$52` 계산을 유지하면서 `$B000/$C000 → $5123`, `$D000/$E000 → $5127`로 같은 8바이트 안에서 바꾼다. 자동 병종 설명 화면에서 실행을 확인한 뱅크 `0D:$8036/$8039`, `0D:$83AB/$83AE`의 직접 쓰기 네 곳도 같은 3바이트 길이로 옮긴다. 이 추가 단계는 PRG 프로브 바이트를 기준으로 10개 Expected Write와 변경 전수 감사를 거친다.

이 매핑은 각 PPU 4 KiB 창에서 마지막으로 실행된 공급값 하나만 남긴다. FD/FE 값이 같은 직접 쓰기 쌍은 그대로 표현하지만 값이 다른 중앙 공급 쌍의 래치 공존은 재현하지 않는다. 보고서의 `fd_fe_latch_equivalent`와 `release_eligible`은 항상 거짓이고, 각 화면의 실행 동등성은 별도 관문이다. 아직 실행 분류하지 않은 직접 쓰기 후보는 자동으로 고치지 않는다.

`build-mmc5-expanded-chr-options-probe`는 검증된 CHR writer 프로브를 기준으로 원본 128 KiB CHR을 상위 절반에 한 번 더 복제하고 iNES CHR 크기를 256 KiB로 늘린다. 하위 CHR은 원본 SHA-1을 그대로 유지하고, 상위 복제본의 첫 4 KiB에서 일본어 설정용 12타일만 한글 PoC 글리프로 바꾼다. 기존 영어·숫자 타일은 수정하지 않는다.

검증된 여덟 CHR store는 같은 3바이트 길이의 `JSR`로 바꾸고, `$FA68/$FA74`의 checked RP2A03 래퍼가 A와 상태 플래그를 보존하면서 뱅크에 `20`을 OR한 뒤 `$5123/$5127`에 쓴다. 헤더·래퍼·store·설정 표·상위 글리프를 합친 24개 Expected Write를 감사하고, 상위 첫 페이지 뒤의 124 KiB가 원본 CHR과 같은지도 검사한다. 이 프로브는 확장 저장·공급 경로만 검증하며 최종 글꼴 배치나 전체 진행 동등성을 선언하지 않는다.

## MMC4 래치 네임테이블 투영

`project-mmc4-latch-nametable`은 실행에서 덤프한 정확히 1 KiB 또는 2 KiB 네임테이블을 받아 한 페이지의 32×30 배경 타일을 제로 스크롤 행 우선 순서로 순회한다. 각 타일에는 현재 FD/FE 래치의 6비트 CHR 뱅크와 원본 속성표의 팔레트 2비트를 결합한다. `FD`·`FE` 트리거 타일 자체는 이전 래치 뱅크를 사용하고, 전환은 다음 타일부터 적용한다. 마지막 64바이트는 화면 개입과 같은 결정적 1 KiB 입력을 만들기 위해 초기 래치 뱅크로 채운다.

같은 순회에서 각 타일이 FD와 FE 가운데 어느 쪽으로 fetch되는지도 집계한다. 보고서는 양쪽의 실제 타일 수와 정렬된 고유 코드 집합을 함께 내므로, 문자·창·배경을 한 네임테이블에 섞어 세지 않고 화면별 한글 작업 집합을 분리할 수 있다. 스프라이트는 이 투영에 포함되지 않으므로 OAM과 PPU `$0000` 공급 페이지를 화면 계약에서 별도로 확인한다.

```sh
cargo run -p fc-fire-emblem-patch -- project-mmc4-latch-nametable \
  path/to/nametable.bin \
  --nametable-index 1 \
  --fd-bank 0 \
  --fe-bank 24 \
  --initial-latch fe \
  --output out/mmc5-exram-attributes.bin \
  --report out/mmc4-latch-nametable.json
```

입력 크기·페이지 인덱스·6비트 뱅크 범위가 맞지 않으면 산출물을 만들지 않는다. 보고서는 원본 바이트 대신 입력·출력 해시, 트리거 개수와 초기·종료 래치만 기록하며 `release_eligible`은 항상 거짓이다. 이 도구는 미세 스크롤, PPU의 선행 타일 fetch, 네임테이블 경계, MMC5 ExRAM의 한 화면 미러링과 스프라이트 CHR을 모델링하지 않는다. 따라서 결과는 런타임 소유·갱신 구현의 입력을 검증하는 개발용 프로브일 뿐 ROM 삽입 자산이 아니다.

`replay-mmc4-latch-ppu-transfers`는 로컬 JSON에 기록한 PPU 전송을 두 물리 네임테이블에 순서대로 적용한다. 입력은 스키마 1, 초기 채움 바이트, 수평·수직 미러링, 선택할 논리 네임테이블, FD/FE 뱅크와 초기 래치, 그리고 각 전송의 14비트 시작 주소·`across`/`down` 증가 방향·16진 데이터로 구성한다. `$3000`~`$3EFF` 미러는 대응 네임테이블로 보내고 패턴·팔레트 주소 쓰기는 투영 입력에서 제외한다.

```sh
cargo run -p fc-fire-emblem-patch -- replay-mmc4-latch-ppu-transfers \
  path/to/ppu-transfers.json \
  --output out/mmc5-exram-transfer-replay.bin \
  --report out/mmc4-latch-transfer-replay.json
```

보고서는 원문 전송 바이트를 복제하지 않고 입력 SHA-1, 전송·데이터·네임테이블 적용 수와 출력 SHA-1만 기록한다. 이 명령은 ROM 갱신 코드와 비교할 호스트 측 의미 기준이며, 제로 스크롤 선택 화면만 투영하므로 자체로 런타임 소유나 스크롤 동등성을 증명하지 않는다.

## MMC5 네임테이블 바이트 훅 기각 프로브

`build-mmc5-nametable-shadow-probe`는 지원 원본의 직접 `STA $2006` 20곳과 `STA $2007` 7곳이 선언한 주소와 정확히 일치할 때만 CHR writer 프로브 위에 훅을 설치한다. PPU 쓰기를 먼저 실행한 뒤 A·X·Y·상태 플래그를 보존하면서 MMC5 PRG RAM 뱅크 1의 `$6800`~`$6FFF`에 두 물리 네임테이블을 모사한다. 새 코드는 typed RP2A03 조립과 Expected Write 감사를 거치며 간접 PPU 쓰기는 닫았다고 선언하지 않는다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mmc5-nametable-shadow-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

이 명령은 채택할 런타임 소유자가 아니라 기각된 시간 설계를 재현하는 개발용 프로브다. 콜드 실행 프레임 301에서 주소 상위·하위 훅은 각각 49회, 데이터 훅은 6,714회 적중했지만 실제 CIRAM과 그림자가 128바이트 갈렸고 화면도 깨졌다. 바이트마다 PRG RAM 뱅크를 바꾸고 상태를 보존하는 비용이 VBlank 전송을 지연시켰으므로 `per_byte_hook_design_eligible`과 `release_eligible`은 항상 거짓이다. 후속 구현은 PPU 큐와 직접 전송 루틴의 경계에서 데이터를 일괄 반영해야 한다.

## MMC5 PPU 큐 일괄 그림자 프로브

`build-mmc5-queue-shadow-probe`는 콜드 실행에서 `$21=1`을 실제 게시한 `0D:$A6B9`, `0D:$AD52`와 기존 합성 텍스트 게시자 `$C8C8`을 원본 바이트에 결속한다. 각 게시자가 준비 플래그를 올리기 전에 `$0781` 큐를 한 번만 순회해 PRG RAM 뱅크 1의 두 물리 네임테이블에 반영한다. 기술자 bit 6은 `$C3D5/$C3D8`의 분기와 인덱스 진행을 따라 한 입력 바이트 반복으로 처리한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mmc5-queue-shadow-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

공통 소비자 `$C3E7` 안에서 같은 처리를 한 실험은 큐 26회·504바이트를 잡았지만 NMI 시간을 늘려 화면을 더 깨뜨렸으므로 기각했다. 게시 경계 프로브는 프레임 800에서 같은 26회, 명령 31개, 출력·네임테이블 504바이트를 반영하면서 기반 CHR writer 화면 해시를 유지했다. 이때 실제 CIRAM과의 차이는 168바이트였다.

다음 직접 전송 경계는 `0D:$848E`의 물리 네임테이블 0 초기화다. 원본은 타일 960바이트를 `FF`, 속성 64바이트를 `00`으로 지우므로 별도 `direct_clear` 모듈이 같은 네 바이트 진입 구간을 checked RP2A03 `JSR`로 바꾸고 PRG RAM 뱅크 1의 그림자를 한 번에 갱신한 뒤 원본 루틴을 계속 실행한다. 프레임 800에는 훅이 아직 0회라 초기값 차이만 보였고, 최초 래퍼 실행은 프레임 1731이었다. 프레임 1732에는 베이스의 CIRAM 차이 213바이트가 0으로 닫혔고 화면 SHA-256 `788d6984576bb13490a00df106ec8ec4a1c2f966e544debd99f7ffce8d65c029`도 같았다. 프레임 1928에는 훅 2회 뒤 차이가 베이스 495바이트에서 234바이트로 줄었고 화면 SHA-256 `e2893dd71c6f93d1a29e2bc40256e0563e75332c3d2f6eca98277435c06215a1`을 유지했다. 따라서 이 경계는 유효하지만 뒤의 직접 합성 전송 234바이트가 아직 그림자를 우회하므로 ExRAM 표시나 릴리스 적합성을 주장하지 않는다.

`build-mmc5-dialogue-exram-probe`는 위에서 생성한 정확히 1 KiB 입력 가운데 확인된 오른쪽 FD/FE 뱅크 `00/18`만 허용한다. CHR writer 프로브 위에서 오른쪽 FD·FE 공급 루틴을 같은 길이의 공통 검사 호출로 바꾸고, 두 그림자가 `00/18`이 되는 순간 고정 PRG의 `$FB00`~`$FEFF`에서 MMC5 ExRAM `$5C00`~`$5FFF`로 복사한다. 복사 동안 `$5104=2`, 표시 전에는 `$5104=1`을 쓰며 A·X·상태 플래그를 복원한다. 새 상대 분기는 절대 목표 주소를 받아 signed 8비트 도달 범위를 checked assembler에서 검산한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mmc5-dialogue-exram-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes" \
  out/mmc5-exram-attributes.bin
```

새 코드 두 구간은 원본의 직접 `JSR`·`JMP` 패턴이 0건이고 기대 바이트가 모두 `FF`일 때만 쓴다. 데이터 구간을 가리키는 PRG 전체의 3바이트 패턴 후보는 보고하되 명령 경계로 오인하지 않는다. 이 ROM은 목표 대화 화면의 외부 메모리 주입을 제거하는 전용 프로브다. 정적 1 KiB를 조건 일치 때 다시 적재할 뿐 후속 네임테이블 쓰기, 다른 래치 쌍, 스크롤과 경계 fetch를 갱신하지 않으므로 `release_eligible`은 거짓이다.

## 글꼴 공급 조사

`analyze-font-supply`는 지원 일본판만 입력으로 받아 4 KiB CHR 페이지별 통계, 첫 글꼴 페이지의 256개 코드별 타일 특성, 보호 판정과 확인된 참조를 JSON으로 쓴다. 스키마 3부터 고정 PRG 뱅크의 MMC4 CHR 공급 루틴 4개를 원본 바이트로 검사하고, 각 루틴을 가리키는 직접 `JSR`·`JMP` 바이트 패턴 후보를 PRG 뱅크·PRG 오프셋·파일 오프셋·CPU 주소로 함께 기록한다. 후보는 명령 경계와 실행 적중을 별도로 확인하기 전에는 호출자로 간주하지 않는다. 스키마 4는 확인된 보호 코드 43개와 합성 레이아웃 예약 코드 `0F`, `1F`, `FF`를 제외한 현재 한글 활성 슬롯 상한 210개를 기록한다. 전투 대사에서 쓰이는 `9D = !`는 번역하지 않을 원본 문장부호로 보호하며, `8E = 、`, `8F = 。`, `AB/AC = 「/」`는 일본어 원문 코드로 분류한다. 이는 미확정 소비자를 모두 닫은 화면별 최종 예산이 아니다. 같은 입력에서 각 코드가 표시된 PNG 타일 시트도 만든다. 두 산출물은 무시된 `out/` 아래에 생성하며 원본 CHR 바이트는 JSON에 복제하지 않는다.

스키마 5는 PRG 뱅크 선택 `$C9A6`과 미러링 비트 선택 `$C9CE/$C9D6`의 원본 바이트를 추가로 검사한다. 또한 PRG 전체에서 `$A000`~`$F000`에 직접 쓰는 `STA`·`STX`·`STY` 3바이트 패턴을 좌표와 함께 열거한다. 이 목록은 매퍼 변환 누락 방지용 후보 상한이며, 데이터 우연 일치가 섞일 수 있으므로 실행 적중이나 디스어셈블 없이 패치 대상으로 삼지 않는다.

스키마 6은 `$B000`~`$E000` 후보 가운데 같은 PRG 뱅크에서 명령 시작 사이가 3~8바이트인 연속 집단을 별도로 묶는다. 이는 반복 레지스터 설정처럼 보이는 위치의 실행 검증 순서를 정하기 위한 하한이며, 단독 후보와 더 멀리 떨어진 실제 코드는 포함하지 않는다. 각 집단은 항상 `candidate_only_runtime_execution_or_disassembly_required`로 남고 자동 패치 입력이 아니다.

조사기는 설정 일본어 표와 상태 능력치 약어 표의 원본 바이트가 기대값과 같을 때만 보고서를 만든다. 숫자 `0`~`9`, 대문자 `A`~`Z`, 상태 표에서 함께 쓰는 `:`·`.`는 원본 표시 보호 대상으로 분류한다. `ED`·`EF`는 확인된 텍스트 제어 코드, `FD`·`FE`는 MMC4 래치 코드로 보호한다.

비어 보이거나 현재 확인된 참조가 없는 타일은 사용 가능으로 분류하지 않는다. 모든 소비 경로를 배제하기 전까지 `unresolved`로 유지하며, 보고서의 `available_font_code_count`는 현재 항상 0이다.

실제 화면별 CHR 그림자 값과 MMC4 공급 경로의 해석은 [렌더 경로 조사](render-paths.md)에 기록한다. 런타임 관측값을 정적 보고서가 임의로 추론하지 않는다.

## 텍스트 표 조사

`analyze-text-tables`는 지원 일본판에서 소비 코드가 확인된 클래스·아이템·아군·적·지형·장소·장 제목 포인터 표 7개를 JSON으로 쓴다. 각 표의 포인터 수, 종료 코드, 공유 포인터, 문자열 범위와 원본 바이트를 보존하고, 정확한 indexed `LDA` 쌍이 해당 표의 하위·상위 포인터 바이트를 읽는지 검사한다.

숫자·대문자는 전역 `protected_original`로 분리한다. 문장부호는 `M.`처럼 기존 라틴 토큰에 붙은 정확한 위치를 원본 바이트로 확인한 경우에만 같은 분류로 보호한다. 나머지 코드는 일본어·제어·레이아웃 판정이 끝날 때까지 `unresolved`이며 자동 번역하지 않는다. 자세한 범위와 현재 증거 한계는 [일본판 텍스트 표 조사](text-tables.md)에 둔다.

스키마 2부터 포인터를 받은 뒤의 복사 루프도 원본 바이트로 검사한다. 보고서의 `transfer`는 원본 포인터, 목적 버퍼, 인식하는 종료 코드, 목적 버퍼에 남는 끝 코드와 그 코드가 원문 복사인지 소비자 합성인지를 구분한다. 아이템 이름처럼 복사 코드에 명시적인 16바이트 상한이 있으면 모든 현재 엔트리가 종료자를 포함해 그 안에 들어오는지도 검사한다.

스키마 3은 사용 코드별 출현 수와 첫 글꼴 페이지의 16바이트 타일 SHA-1·전부 0 여부를 기록한다. 보호하지 않은 바이트는 비공백 타일 또는 공백 타일 후보로 나누되, 다운스트림 렌더러가 코드값을 실제 타일 번호로 소비한다는 증거가 추가되기 전에는 둘 다 `unresolved`를 유지한다. 이 집계는 원문 문자열 덤프를 공개 자료로 승격하지 않는다.

스키마 4는 뱅크 `0B`의 합성 텍스트 파서에서 `0F`·`1F`를 폭 0 결합부호로 처리하는 두 패스와 출력 칸 증가 루틴을 원본 바이트로 검사한다. 전체 7개 표의 출현 수는 참고 집계일 뿐이며, 아직 연결하지 않은 다른 소비자에서도 같은 동작을 한다고 간주하지 않는다.

스키마 5는 합성 텍스트 파서 `$8F39`를 직접 가리키는 절대 `JSR`·`JMP` 바이트 패턴을 PRG 뱅크·PRG 오프셋·파일 오프셋·CPU 주소로 기록한다. CHR 공급 조사와 같은 스캐너를 사용하며, 명령 경계와 호출자 역할을 확인하기 전에는 대사·메뉴 소비자로 승격하지 않는다.

스키마 6은 같은 파서가 `$0451`의 `ED` 종료 세그먼트를 두 번 읽어 `$0311`에 결합부호 오버레이와 기본 문자 출력 세그먼트를 차례로 만드는 구조를 기록한다. 첫 패스가 일반 문자 칸에 생성하는 `FF`는 이 경로의 빈 오버레이이고, `0F`·`1F`는 앞 칸을 대체하는 폭 0 결합부호다. 이 의미를 다른 텍스트 소비자의 원문 `FF`까지 일반화하지 않는다.

스키마 7은 `$0311`을 가리키는 `$06/$07`, 공유 커서 `$0310`, 두 번 호출되는 `$961C` 출력 단계와 `ED`를 `FF`로 바꾸어 `$0701,X`에 쓰는 `$96E7` 루프를 원본 바이트로 검사한다. 이 연결은 2패스 순서가 후속 출력에서 실제로 소비됨을 보이지만, 최종 PPU 전송이나 아직 확인하지 않은 다른 호출자까지 일반화하지 않는다.

스키마 8은 `$0700` 단계 기술자를 `$0781` 명령 큐로 직렬화하는 `$C84E`, 큐 준비 플래그 `$21`을 소비하는 `$C3A5`, `$2006/$2007`에 주소와 코드를 쓰는 `$C3E7` 경로를 원본 바이트로 검사한다. 따라서 확인된 합성 텍스트 경로는 PPU 쓰기까지 연결되지만, 아직 실행 적중을 확인하지 않은 `$8F39` 진입 후보의 화면 역할은 계속 미확정이다.

스키마 9는 직접 `JSR $8F39` 두 곳이 모두 `JMP $8163`으로 이어지는 별도 후처리 계열임을 기록한다. `$8163`은 `$0311`에서 첫 `ED`의 위치를 폭으로 삼고, 그 다음의 기본 문자 평면을 고정 뱅크 복사 루틴 `$C209`로 한 칸 왼쪽에 옮겨 결합부호 평면 바로 뒤에 붙인다. 호출자의 실제 화면 역할은 실행 적중 전까지 붙이지 않는다.

스키마 10은 실제 대사 본문을 뱅크 `0B:$8F39` 메뉴·제목 합성 경로와 분리한다. 뱅크 `0A:$8208` 디스패처와 고정 뱅크 `$E69C` 읽기 루틴, 32바이트 간격인 6개의 SRAM 줄 버퍼 시작 주소, `ED` 줄 종료, 확인된 제어 코드 분기, `$83BA`의 점진적 2평면 렌더링과 `$C842 → $0781` 화면 경로를 원본 바이트로 검사한다. 1장 실행에서 확인한 뱅크 `08:$9FCE → $78B2` 원문 공급과 폭 18의 단계 기술자 `52`도 원문 덤프 없이 구조 관측값으로 기록한다. 제어 코드별 길이와 전체 대사 모집단은 계속 미확정이므로 조사기는 아직 대사 추출 완료를 선언하지 않는다.

스키마 11은 대사 제어 15개의 현재 포인터 진행, 인라인 피연산자 수, 뒤 두 바이트 읽기, 줄 종료 여부와 상태 주소 효과를 고정한다. `E4`·`E6`가 다음 두 바이트를 읽어도 현재 포인터는 제어 하나만 지나가는 경계를 별도로 기록하고, `EC`의 네 SRAM 문자열 선택 표와 `DF`의 니블 기반 상태 비트 선택 루틴까지 원본 바이트로 검사한다. 게임상 의미와 전체 모집단의 유효 값은 구조 증거와 분리해 계속 미확정으로 둔다.

스키마 12는 `E4`·`E6`의 뒤 두 바이트가 다음 줄 문자가 아니라 전환 대상 인자라는 저장 계약을 분리한다. 보고서는 두 제어의 저장 길이 3바이트, 현재 포인터 진행 1바이트, 전환 대상 2바이트를 함께 기록한다. 구조 스캐너와 재삽입기는 현재 실행 포인터의 증가량만 보고 두 인자를 버려서는 안 된다.

스키마 13은 `$C3E7` PPU 큐 소비자의 명령 경계를 기록한다. `$00/$01` 포인터에서 `PPU 주소 상위·하위 바이트`, 기술자, 데이터가 이어지고 첫 바이트 `00`은 종료자다. 기술자의 하위 6비트는 `$C3DD`의 `$2007` 출력 길이이고 비트 7은 PPU 주소 증가 방향을 고른다. 비트 6이 꺼지면 출력마다 입력을 진행하고, 켜지면 한 입력 바이트를 선언 길이만큼 반복한다. 미러링·스크롤·팔레트 사분면 정책은 일반 ExRAM 갱신기에서 별도로 검증한다.

## 대사 진입 표 조사

`analyze-dialogue-structure`는 지원 일본판만 받아 장 인트로·마을/아웃트로·영입·승패·상점/아이템·민가·전투·에필로그 본문·에필로그 라우팅의 대사 진입 표 9개를 검사한다. 보고서는 표 주소·포인터 수·표 SHA-1·진입 주소·별칭만 기록하며 대사 원문 바이트나 번역문은 기록하지 않는다.

각 포인터 표가 선언한 PRG 뱅크 안에 완전히 들어가는지, 각 일반 진입점이 같은 뱅크의 선언된 데이터 시작 이후를 가리키는지 검사한다. 주 대사 디렉터리에 연결된 8개 표는 선택자의 상위 니블을 원문 뱅크로, 하위 니블을 `$BFE0` 디렉터리 그룹으로 해석해 실제 루트 포인터까지 확인한다. 에필로그 라우팅 표는 `04:$BFE2 → $B96C` 루트뿐 아니라 `04:$A17E`의 선택자 `41`·엔트리 선택 코드도 함께 고정한다. 별도 경로인 전투 대사 표는 뱅크 `04:$8000` 로더가 `$7935/$7936`으로 표 집합과 엔트리를 고르고 `$802D` 루트에서 `$845B` 표를 찾아 `$76/$77`에 넣는 명령까지 별도로 검사한다.

고정 뱅크 처리 루틴을 가리키는 값이 필요해지면 주소와 원본 명령 바이트를 표별 허용 목록에 함께 선언해야 한다. 선언하지 않은 교차 뱅크 포인터, 달라진 처리 루틴, 표 범위 이탈은 모두 거부한다. 이 단계는 진입점 모집단을 확정하는 조사이며, 외부 레코드 상태 기계와 각 엔트리의 끝을 확인하기 전에는 대사 길이·내용 해시·번역 준비 상태를 추정하지 않는다.

스키마 2는 뱅크 `0A:$8000`이 `$77F7` 상태값으로 18개 처리자를 고르는 디스패처를 원본 명령과 처리자 표 SHA-1로 고정한다. 대사 원문 앞부분은 선택적인 6바이트 `E5` 프리픽스, 선택적인 4바이트 창 기술자, 선택적인 6바이트 `E8` 프리픽스 순서다. 셋 다 없는 레코드도 있다. 주 디렉터리의 고유 대사 진입점 504개마다 이 세 구간과 첫 줄 시작 파일 오프셋을 기록한다. 영입 표의 네 엔트리가 공유하는 `$AA2B`와 에필로그 라우팅 표의 두 엔트리가 공유하는 `$C73D`는 원본 실행 코드가 정확히 일치할 때만 비대사 처리자로 분리한다. 상태 처리자 10개의 상세 의미와 엔트리 종료 규칙은 계속 미확정이며, 보고서는 원문을 출력하지 않는다.

스키마 3은 504개 주 대사 진입점의 첫 줄을 공통 15개 제어 계약으로 전수 검사한다. 리터럴·제어·인라인 피연산자·`E4/E6` 전환 대상의 길이를 분리하고, `EC` 피연산자는 `0`~`3`, `DF` 하위 니블은 `0`~`7`만 허용한다. `E4/E6`의 선택자와 인덱스는 선언된 주 대사 표 범위에 들어가야 한다. 보고서에는 첫 줄 위치·저장 길이·현재 포인터 진행·제어 개수·SHA-1만 기록하고 원문 바이트는 기록하지 않는다. 리터럴에서 확인된 숫자·대문자 코드도 번역하지 않는 원문 보호 수량으로 별도 집계한다.

스키마 4는 각 진입점에서 `ED`·`EE`·`EB` 뒤의 다음 줄을 계속 읽고, `EF` 종료, `E7` 호출자 인계, `E4/E6` 명시 전이 중 하나를 처음 만날 때 선형 구간을 닫는다. 구간은 최대 64줄 안에 경계를 만나야 하며 `E4/E6` 대상은 선언된 주 대사 표와 인덱스 범위를 다시 검사한다. 공개 보고서에는 줄별 위치·길이·해시·제어 통계와 구간 경계만 기록하고 원문 바이트는 넣지 않는다. 이 단계는 경계까지의 연속 저장을 증명할 뿐, `E7/E4/E6` 뒤의 전체 제어 흐름이나 도달 가능성을 증명하지 않는다.

스키마 5는 별칭을 같은 저장 노드로 정규화하고 `E4/E6` 대상 인덱스를 실제 대사 진입점에 결속한다. 코드 처리자를 향하거나 존재하지 않는 노드로 가는 간선, 대상 없는 전이, 지원하지 않는 경계와 순환은 모두 보고서 생성을 거부한다. 각 노드가 `EF` 종료 또는 `E7` 호출자 인계 경계에 도달하는지 검사하고 최대 전이 단계도 기록한다. 간선 보고서는 표·엔트리·포인터·파일 오프셋만 포함하며 원문은 포함하지 않는다.

스키마 6은 `E7`의 일반 구조를 특정 게임상 선택지와 분리한다. 디코더가 `$7808`을 올리면 후속 상태가 `$7809` 호출자 플래그를 올리고 상태 17로 간다. 상태 17은 고정 뱅크 `$E6B2`로 현재 `$77F4/$77F1` 선택을 다시 결속하고 `$7808/$7809`를 지운 뒤 상태 9에서 재개한다. PRG 전체의 정확한 `LDA $7809` 패턴 5곳도 좌표로 고정한다. 각 호출자가 이를 선택지·에필로그 진행 등 어떤 결과에 쓰는지는 이 공통 구조 계약에 섞지 않는다.

스키마 7은 에필로그 호출자가 조건에 따라 선택자 `40`과 `41`을 나누는 원본 명령, `04:$BFE2 → $B96C` 디렉터리 루트와 54개 포인터를 결속한다. 선택자 `41` 표의 고유 스크립트 52개는 모두 `E8` 프리픽스를 거쳐 한 줄의 `E4` 전환으로 선택자 `40` 엔트리 0에 합류한다. 두 엔트리가 가리키는 `$C73D`는 한 바이트 `RTS` 처리자로 분리한다. 이 구조만으로 각 조건의 게임상 의미를 이름 붙이지 않는다.

스키마 8은 `$7809`를 읽는 처리자가 외부 `$C34C` 상태 디스패처에서 직접 선택되는 경우를 분리한다. 다섯 관측 처리자 중 네 개가 11개 처리자 표의 22개 상태 슬롯에 결속되며, 각 디스패처 명령·상태 주소·처리자 표 전체를 검사한다. 뱅크 `04:$A20F` 처리자는 직접 결속을 아직 찾지 못했고, 이 목록은 간접 포인터나 동적 호출이 없음을 증명하지 않는다. 따라서 코드 관측 지점 5개를 게임상 선택지 5개로 환산하지 않는다.

스키마 9는 주 대사 고유 엔트리 504개마다 포인터가 가리키는 레코드 시작부터 프리픽스와 첫 `EF/E7/E4/E6` 경계까지 실제로 소비되는 저장 범위를 닫는다. `E4/E6`의 대상 두 바이트도 범위와 해시에 포함한다. 레코드별 소비량 합계는 39,642바이트지만 실제 고유 저장은 39,425바이트이며, 6쌍이 217바이트를 공유하고 최대 중첩 깊이는 2다. 따라서 포인터 엔트리를 곧바로 독립 재삽입 단위로 보지 않고, 공유 구간을 한 번만 소유하는 배치 계약을 먼저 만들어야 한다. 전투 대사는 별도 형식이므로 이 범위 계산에서 제외한다.

`extract-main-dialogue-source`는 겹치거나 맞닿은 주 대사 범위를 PRG 뱅크별 단일 소유 구간으로 정규화해 무시된 `private/dialogue/main-source.json`에 쓴다. 현재 원본에서는 504개 레코드가 겹치지 않는 11개 구간, 39,425바이트로 정규화된다. 형식 3은 별칭을 포함한 포인터 쓰기 위치 517곳과 전이 대상 소비 프리픽스를 각 레코드에 결속한다. `verify-main-dialogue-source-roundtrip`은 이 자산이 지원 일본판에서 다시 계산한 구조·바이트와 완전히 같은지 검사하고, 11개 구간을 중복 쓰기 없이 재구성한 ROM이 원본 SHA-1과 일치할 때만 `out/`에 기록한다. 이 자산의 목적은 `exact_source_roundtrip_only`이며 번역 바이트 입력은 허용하지 않는다.

스키마 12는 레코드 프리픽스를 실제 배치대로 읽는다. 창 기술자는 모든 레코드에 있지 않다. 그 자리가 제어 코드로 시작하거나 네 바이트 뒤가 다시 표시 글자면 기술자가 없는 것이며, 전체 504개 중 206개가 그렇다. 명시적 `E4/E6` 간선이 가리키는 고유 대상 139개도 같은 규칙으로 읽으면 진입 방향과 무관하게 같은 프리픽스가 나온다. 이 규칙으로 다시 읽었을 때 기존에 입증한 저장 끝·그래프 경계·그래프 목적지가 모두 같아야만 보고서를 만든다. 선형 구간은 2,814줄, 번역 뷰도 2,814줄·안전 일본어 28,367바이트다. 전이 시 소비되는 제어 전용 줄도 보호 토큰으로 유지하되 일본어가 없으므로 번역하지 않는다.

스키마 10은 일본판 글꼴과 확인된 설정·단위 UI·전투·엔딩 문자열을 기준으로 `00`~`5F`의 가나·결합부호·일본어 문장부호, `84`~`8B`의 작은 가나, `A6`~`AA`의 작은 가타카나 모음과 `8E = 、`, `8F = 。`, `AB/AC = 「/」`를 일본어 리터럴로 분류한다. 숫자·대문자 `60`~`83`, 보존 문장부호 `9D = !`와 그 밖의 기호는 비일본어 리터럴로 유지한다. 선형 구간의 참조 수는 일본어 28,519바이트·비일본어 2,790바이트이고, 공유를 한 번만 센 고유 저장은 각각 28,367바이트·2,770바이트다. 같은 바이트를 한 엔트리는 일본어 리터럴, 다른 엔트리는 구조로 읽던 충돌 16바이트는 프리픽스를 실제 배치대로 읽은 뒤 0바이트가 됐다.

스키마 11은 뱅크 `04:$7937`의 9상태 전투 대사 처리기를 별도 문법으로 결속한다. 상태 1은 4바이트 헤더를 소비하고 상태 2는 `EC` 뒤 선택자 한 바이트 `00..03`을 동적 값으로 확장하며 첫 `EF`에서 레코드를 끝낸다. 65포인터의 고유 대상 28개는 1,152바이트의 겹치지 않는 범위다. 물리 데이터 구간에는 포인터가 없는 16바이트 레코드가 하나 더 있으므로 이를 번역 대상으로 추정하지 않고 원형 보존한다. 코드 구간은 고정 SHA-1과 typed RP2A03 명령 경계로 함께 검사한다.

`extract-main-dialogue-workspace`는 번역 소비 뷰를 이용해 무시된 `private/dialogue/main-workspace.json`에 504개 레코드·2,814줄의 번역 골격을 만든다. 레코드와 줄에는 원본 위치가 바뀌어도 유지할 안정 ID를 붙인다. 일본어 코드는 문자로 풀고 숫자·대문자는 원문 그대로 두며, 공백·미확정 기호·제어와 피연산자는 수정되지 않도록 중괄호 토큰으로 표시한다. 각 줄에는 원문 저장 SHA-1, `untranslated` 상태와 빈 `korean` 필드가 있다. 구조와 겹치는 원천이 포함된 3개 줄은 `requires_relocation: true`로 표시하며 재배치 계약 전에는 재삽입할 수 없다. 기존 작업공간이 있으면 안정 줄 ID와 원문 마크업이 모두 같은 번역만 상태와 함께 새 골격으로 옮긴다. 번역한 원문이 바뀌거나 번역 줄이 사라진 경우에는 기존 파일을 쓰기 전에 전체 갱신을 거부하며, 검증된 결과만 같은 디렉터리의 임시 파일을 거쳐 원자적으로 교체한다. 이 작업 자산 자체는 공개 보고서나 Git에 넣지 않는다.

`validate-main-dialogue-workspace`는 작업 골격을 지원 일본판에서 다시 추출한 값과 대조한다. 원본 결속 필드가 달라지거나, 상태와 `korean` 필드가 모순되거나, 제어 토큰·피연산자·기존 영문·숫자가 추가·삭제·변경되거나, 번역 필드에 일본어가 남으면 실패한다. 자연 소비가 확인되지 않은 원문 잔편은 안정 줄 ID로 명시한 원문 보존 목록에서만 허용하며, 번역이나 일반 미번역 줄로 가장할 수 없다. 이 단계는 한글 문자열을 논리 글리프로 검사할 뿐 코드 배정이나 ROM 쓰기는 하지 않는다.

주 대사 이중 진입 작업공간을 만들던 세 명령 `extract-main-dialogue-entry-mode-workspace`·`validate-main-dialogue-entry-mode-workspace`·`import-main-dialogue-entry-mode-draft`는 폐기했다. 두 모드의 차이는 레코드 프리픽스 파서 결함이 만든 것이어서 나눌 파트가 없다. 자산은 `private/dialogue/retired/`로 옮겼다. 의사결정 59번을 따른다.

`extract-battle-dialogue-workspace`는 주 대사와 형식이 다른 전투 대사 28레코드를 `private/dialogue/battle-workspace.json`에 만든다. 포인터 별칭 65개와 정확한 저장 범위 1,152바이트를 다시 검사하고, 4바이트 헤더는 본문 밖 결속 필드로 두며, `EC` 피연산자와 `AB/AC/ED/EE/EF` 제어를 보호 토큰으로 기록한다. 결과는 100줄·일본어 620바이트다. 기존 파일이 있으면 원문과 모든 결속 필드가 같은 번역 줄만 병합하고 달라진 입력은 덮어쓰지 않는다. `validate-battle-dialogue-workspace`는 한국어 필드에 일본어가 남거나 동적 선택자·기존 영문·숫자·제어 순서가 바뀌면 실패한다.

`import-battle-dialogue-draft`는 비공개 TSV의 `line_id<TAB>korean_markup`을 작업공간에 병합한다. TSV는 일본어가 있는 줄을 빠짐없이 정확히 한 번씩 포함해야 하고, 병합 결과가 보호 토큰 검증을 통과해야만 작업공간을 원자적으로 교체한다. 현재 일본어 포함 70줄을 모두 `needs_human_review` 초벌로 채웠으며 제어 전용 30줄은 원문 상태를 유지한다.

전투 초벌의 4바이트 헤더·본문·제어 토큰을 글리프당 1바이트 논리열로 다시 세면 포인터 참조 28레코드는 1,114바이트다. 여기에 포인터가 가리키지 않더라도 삭제하지 않을 원본 레코드 16바이트를 더한 실제 계획은 1,130/1,168바이트이며 38바이트를 남긴다. `plan-battle-dialogue-reinsertion`은 미참조 레코드의 정확한 원래 위치와 SHA-1을 다시 확인하고, 그 앞뒤 두 소유 구간에 28개 레코드를 자르지 않고 채운다. 배치 결과에서 별칭을 포함한 포인터 65개의 새 CPU 주소를 계산하며 상세 보고서에는 대사·글리프 문자·로컬 경로를 싣지 않는다. 현재 보고서 SHA-1은 `b6fb8dd55ae95ced551d72326358112dac6e60a1`이다. 이 단계는 실제 ROM 쓰기·글꼴 페이지·실행 표시를 아직 닫지 않는다.

```sh
cargo run -p fc-fire-emblem-patch -- extract-battle-dialogue-workspace \
  'roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes'

cargo run -p fc-fire-emblem-patch -- plan-battle-dialogue-reinsertion \
  'roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes'

cargo run -p fc-fire-emblem-patch -- build-battle-dialogue-probe \
```

`analyze-battle-text-workset`은 272개 고정 번역을 글리프당 한 바이트 논리열로 만들고 각 문자열이 원래 소유 길이 안에 드는지 검사한 뒤, 전투 대사와 예측창 라벨을 합친 수치만 공개한다. 고정 251글리프와 대사 152글리프의 전체 합집합은 319글리프로 정적 한 페이지에 들어가지 않는다. 이 도구가 낸 114/210은 메시지 템플릿 하나만 넣은 초기 조합식이므로, 전투 동안 한 번 올린 캐시가 메시지 템플릿 22개 전부를 지원해야 하는 전체 수명 상한으로 쓰지 않는다. 보고서 SHA-1은 `07ecd93eb1947fe699d4dee5ac3733c5a153b47c`이며 글리프 문자·원문·번역문은 싣지 않는다.

`analyze-battle-codebook-plan`은 캐시 페이지가 달라도 같은 글리프가 같은 바이트 코드를 쓸 수 있는지 공존 그래프로 검사한다. 모든 전투 메시지 템플릿과 예측 라벨은 공용 기반으로 두고, 한 참가자의 이름·병종·장비를 실제 장착 필요조건 안에서만 한 가족으로 묶는다. 현재 아군 참가자 상위집합은 10,413개다. 적군은 뱅크 08의 장별 초기 471레코드와 뱅크 03의 증원 93레코드에서 만든 지도·증원 후보 2,132개에 bank `0B:$A32D` 투기장 생성기의 후보 39개를 합쳐 2,171개다. 투기장 쪽은 22개 장 포인터·88개 병종 선택·병종별 기본 장비·6개 대체 병종과 각 네 장비 변형을 결속한다. 이 집합은 생성기 출력의 필요조건 상위집합이며 각 난수 결과의 정확 도달성을 주장하지 않는다. 정규 입력 생산자 `06:$91F1/$AD46`는 라이브 레코드를 전투 필드로 투영하고, 장비 ID `40` 이상은 표시 원천 `44`로 접는다. 정상 지형 표 15개와 특수 전투 인덱스 `0E`를 합쳐 16개 지형 원천 전체를 이룬다. 현재 모델은 294정점·40,879간선이며 클리크 하한과 최소 색 수는 213이다. 한 전투의 텍스트 수요는 교차 가족 중복을 공제하지 않은 보수 상한 134개, 정확 모델 최대 131개다. selector `0x3E`(62)는 원본 조건과 자연 실행에서 모두 결속했다. 추상 안정 배정 SHA-1은 `13fd42d14700491ff3dabdfe1561bd30925440f9`, 스키마 4 보고서 SHA-1은 `ddcc4562019ef5fa9e96834bc9cae77b442d7ca0`이다.

같은 분석은 완성 페이지 카탈로그 대신 런타임 합성 레시피도 만든다. 보수 모델의 참가자·지형·대사 곱은 162,044,273,664개로 실제 도달 수를 뜻하지 않지만 조합별 완성 페이지 설계를 기각하기에는 충분하다. 고정 디렉터리는 아군명 53·적군명 56·병종 24·장비 64·지형 16·대사 28개를 가리키며, 없는 항목은 `FFFF`로 실패 닫힘 처리한다. 항상 선택되는 공용 글리프는 가족별 payload에서 다시 싣지 않는다. 242개 추상 레시피의 786개 글리프 참조는 194개 고유 payload로 중복 제거되고, 32바이트 머리말을 포함한 바이너리는 3,031바이트다. 294타일 아틀라스는 4,704바이트이고 원본 페이지 4,096바이트와 레시피를 같은 자료 배치에 넣어도 1,065바이트가 남는다. 원본 페이지를 복원한 뒤 현재 조합의 글리프를 최대 2,144바이트 덮는 보수적 합성 상한은 6,240바이트다.

`analyze-battle-surface-constraints`는 이 레시피 바이너리를 실제 런타임 소비자처럼 다시 읽는다. 전투 표본의 `$0304..$0323`에서 양측 이름·병종·장비·지형 원천을 얻고 `$7936`의 현재 대사 선택자를 읽되, 원본 `$85DE` 생산자 조건이면 장래 선택자 `3E`를 미리 투영한다. 32개 불규칙 표본은 다섯 유효 런타임 튜플이고 관측 최대는 선택 색 90개·재배치 3쌍이다. 배경은 `$1000`, 스프라이트는 `$0000` 패턴 테이블을 쓰므로 CHR-RAM 물리 제약에는 실제 소비하는 네임테이블만 들어간다. 공용 렌더러와 전투 대사·이름·병종·장비·지형 호출 경계, 182개 전투 뿌리에서 도달하는 큐 게시자, 직접·인덱스·간접 RAM 접근 분류는 계속 원본에 결속한다. 현재 추상색 213개 가운데 활성 물리 코드는 210개이므로 보존 표시 코드 세 개를 논리 코드로 빌린다. 보호 물리 코드 39개에 빌린 세 색을 합친 보호 추상색 42개를 항상 살아 있는 공용 색 밖에 두고, 참가자·적·두 지형·대사 가족의 충돌을 분산한다. 교차 가족 중복을 공제하지 않은 최악은 7쌍이어서 기존 8쌍 표에 든다. canonical 배정 SHA-1은 `15f2231363f059e1b956dbee3c3072978b4a8b48`, 스키마 14 보고서 SHA-1은 `cfd4ea8665c807c1425438c639da73148d0b25d3`이다.

가족별 최대 합 134가 실제 한 튜플에서 동시에 가능한지는 별도 정확 탐색으로 판정한다. 대사·두 지형의 고유 문맥 마스크를 만든 뒤 아군·적 참가자 후보를 분기 한정으로 전수 비교하며, 원문·번역문이나 글리프 문자를 보고서에 싣지 않는다. 현재 가능한 모델의 정확 최대는 131개이고, 증인 입력을 원천 후보에 다시 결속했다. 134는 거짓 값이 아니라 교차 가족 중복을 공제하지 않은 안전 상한이며, 전역 보호 물리 코드 39개를 더하면 각각 정확 최대 `170/210`, 보수 상한 `173/210`이다.

첫 입력 일반형 실행에서 `$047D`의 원본 전체 바이트 writer가 합성 다음 프레임에 값을 0으로 되돌려 재배치 투영 수명까지 끊는 반례가 나왔다. 원본 `$047D`는 게임의 0/1 의미만 유지하고, 최대 8개의 정규→대체 쌍은 `$07E0..$07EF`, 준비 비트와 쌍 수는 `$07FE`에 둔다. `$07FE`의 준비 마스크 `80`과 쌍 수 마스크 `1E`는 겹치지 않는다. 쌍 표는 `$0781` 큐 시작에서 95바이트 떨어져 최대 67바이트 큐 뒤에도 28바이트가 남고, `$07FE`까지 포함한 직접·인덱스·간접 쓰기 분류는 전투 원본과 주 대사 런타임 양쪽에서 충돌이 없을 때만 통과한다.

`build-battle-text-cache-base`는 mapper 165 패리티 이미지를 512 KiB PRG로 확장한다. 추가 PRG의 MMC3 8 KiB 페이지 `20`에는 전역 코드북 순서의 294개 글리프·4,704바이트 타일 아틀라스를 넣는다. 페이지 `21`의 앞 4,096바이트에는 mapper 패리티 CHR의 원본 글꼴·그래픽 페이지를, 뒤에는 3,031바이트 레시피를 넣어 기반 자산을 두 페이지에 닫는다. 원래 256 KiB PRG 접두부와 활성 고정 뱅크, CHR은 보존한다. 이 기반은 아직 실행 중 원본 페이지를 복원하거나 레시피를 적용하지 않으며 배포 후보가 아니다.

`build-battle-text-runtime-base`는 위 자산을 실제 번역 바이트와 처음 결합한다. 전투 레시피 카탈로그에 든 고정 원천 233개, 전투 대사 28레코드와 포인터 65개, 예측창 라벨을 재인코딩한다. 레시피 디렉터리에서 결측인 고정 작업공간은 전투에 쓰인다고 추정하지 않고 원문 바이트를 유지한다. MMC3 페이지 `20`의 `$9400`에는 213바이트 canonical 코드표를 두고 그 뒤에 보호 추상색 42개, 안전 추상색 171개, 8개 비트 마스크를 둔다. 현재 누적 빌드는 이 단계 보고서 SHA-1 `2ec85d003f4f7dbb9656b6499c6d7ecd219990b7`을 exact 전투 단계 입력으로 결속한다. 별도 실행 증거가 없으면 이 기반만으로 `runtime_verified`를 참으로 만들지 않는다.

`build-battle-composition-loader-probe`는 이 개발 기반에 입력 일반형 합성 로더를 설치한다. 열 레시피에서 선택된 추상색을 27바이트 비트맵으로 모으고, canonical 코드가 보호 물리 코드와 충돌한 항목만 안전한 미선택 코드로 옮긴다. 최대 8개의 정규→대체 쌍은 `$07E0..$07EF`, 쌍 수와 준비 표식은 `$07FE`에 저장하고 원본 `$047D`의 0/1 의미는 바꾸지 않는다. 활성 판정은 바깥 주 상태 목록이 아니라 공용 전투 위상 `$047C < 20`을 사용한다. 따라서 일반 전투·사운드 테스트·투기장이 같은 엔진 수명을 공유하고, `$047C >= 20`이면 재배치 상태를 지운다. 사운드 테스트 반복 시작의 원본 writer 래퍼는 다음 조합 재합성을 위해 유지하되 원래 `A`·플래그·`$047D=1` 효과를 보존한다. 원본 4,096바이트 페이지 복원과 오버레이 업로드, 공용 텍스트 렌더러 `$E57F`는 모두 이 한 위상 판정과 `$07FE` 준비 표식을 사용한다. 배정 실패는 CHR-RAM 선택 전에 복귀한다. 현재 누적 전투 단계는 21개 typed RP2A03 루틴 1,156바이트이고 보고서 SHA-1은 `3e40527786c691fb85e3a148e4f7a150f0fb9561`이다. 관측한 다섯 튜플은 허용 목록이 아니라 회귀 표본이다.

`verify-battle-composition-runtime`은 합성 반환 지점에서 수집한 내부 RAM·CHR-RAM과 `$7936` 스냅샷을 읽는다. 원본 생산자 조건이면 장래 선택자 `62`를 투영하고, 아니면 관측 선택자를 쓴다. 사용자가 선택자를 따로 입력하지 않는다. 실행 ROM의 아틀라스·canonical 코드표·보호색 목록·원본 페이지·레시피를 Rust에서 독립적으로 다시 계산해 예상 4 KiB 페이지와 실제 CHR-RAM을 모든 바이트와 타일 단위로 비교하고, `$07FE`의 준비·쌍 수와 `$07E0`의 정규→대체 쌍도 정확히 대조한다. 한 반환 스냅샷의 합성만으로 시간 표시·이탈 복구·전체 시각 변형을 대신하지 않는다. 투기장 회귀는 별도로 실제 `$07FE=82` 게시, 한글 결과, `$047C=FF` 이탈과 `$07FE=00` 정리를 같은 실행에서 확인했다.

`plan-main-dialogue-reinsertion`은 검증된 작업 골격의 채워진 줄을 글리프당 1바이트인 논리열로 만들고, 원본에서 소유가 증명된 11개 구간 안에서만 레코드를 다시 배치한다. 바뀌지 않은 공유 꼬리는 한 번만 두고, 번역으로 달라진 공유 레코드는 분리한다. 각 레코드의 새 뱅크 내 포인터와 원본 포인터 표 쓰기 위치를 `out/main-dialogue-layout.json`에 기록하며, 어느 구간이든 용량을 넘으면 보고서를 쓰기 전에 실패한다. 현재 전체 배치는 원천 소유 39,425바이트 중 32,101바이트를 사용하고 7,324바이트를 남긴다. 사람 승인·코드 배정·화면별 글리프 예산·실행 표시는 별도 관문이며, 줄 폭은 위의 전체 설치 감사에서 확정 범위와 미해결 범위를 나눠 판정한다. 보고서에는 원문이나 번역문을 넣지 않는다.

`build-main-dialogue-slice-probe`는 완전히 채운 단일 레코드만 골라 같은 안정 ID와 원문 결속을 다시 확인한다. 다른 레코드와 저장 공간을 공유하거나 재배치가 필요하거나 원래 소유 바이트보다 길면 ROM을 쓰기 전에 실패한다. 화면 증거는 서로 다른 에뮬레이터 프레임의 상태·2 KiB 네임테이블 SHA-1을 다시 검사하고, 오른쪽 배경 패턴 표에서 대사창 내부를 제외한 활성 코드와 해당 레코드 뒤의 명시 전이 사슬 원문 코드를 보존 집합으로 만든다. 한글은 그 합집합 밖에만 배정한다. 원본 CHR은 그대로 두고 한 8 KiB 뱅크를 추가해 물리 페이지 `34`에 원본 글꼴 페이지 복제본과 한글을 넣으며, 중앙 `$C9C2` 공급 호출은 정확한 1장 도입부 계약에서만 mapper 값 `88`을 고른다. 나머지 호출은 원래 쌍 인식 선택기로 돌아간다. 보고서는 대사·글리프 문자·증거 경로를 싣지 않고 `release_eligible: false`를 유지한다.

첫 레코드 표본은 3줄·19글리프·45바이트이며 원래 54바이트에서 9바이트를 남겼다. 전이 사슬은 첫 레코드를 포함해 4개이고, 시간 표본 4개의 네임테이블은 같은 안정 화면이었으며 동시 화면 76개·원문 사슬 58개의 활성 코드 합집합 109개를 보존했다. ROM SHA-1은 `c9a86f1c20691dfc60921ff3c2f9601c69a96fc3`, 스키마 2 보고서 SHA-1은 `29b830b951f88a2b2d6de4d2611464b9d9dc161b`다. 콜드 실행에서 타이틀 `START`, 기본 새 게임 `A`, 슬롯 1 `A`의 결속된 경로만 사용했다. 일본어 시작 메뉴와 장 제목, 원본 `MAP`·숫자, 한글 첫 대사, 뒤의 일본어 다섯 화면, 초상화·맵·창이 함께 정상 표시됐고 여섯 번째 완료 페이지 `A` 뒤 자연 맵 페이지로 복구됐다. 완료 표식과 맵 스프라이트는 7·19·43프레임 표본에서 위상만 바뀌었다. 이 결과는 첫 `chapter_intro_title_dialogue_composite` 수명만 닫으며 다른 장과 1장 전체를 대신하지 않는다.

## 누적 한글 패치 빌드

`build-kr-patch`는 이전 개발 ROM을 입력으로 받지 않고, 지원 일본판 원본에서 모든 단계를 결정적으로 다시 만든다. 첫 단계는 mapper 165 설정·부대 목록 페이지와 선택자를 만들고, 둘째 단계는 1장 제목과 도입부 전이 사슬 4레코드·18줄, 물리 CHR 페이지 `38`, mapper 값 `98`을 추가한다. 셋째 단계는 2장 제목과 도입부 1레코드·11줄, 물리 페이지 `40`, mapper 값 `A0`을 더한다. 넷째 단계는 시작·기록 메뉴 7개와 물리 페이지 `42`, mapper 값 `A8`을 추가한다. 이 단계의 선택기는 시작 메뉴 상태 `0D/0E`와 저장 슬롯 상태 `21`, 왼쪽 그림자 `1A/1A`, `$5B | $52`의 하위 5비트로 계산한 실효 FD 원천 `00`이 모두 맞을 때만 페이지를 고른다. 선택기가 바꾸지 않는 FE 배경 그림자는 조건에 넣지 않는다. 다섯째 단계는 아군명 52개를 부대 목록과 맵 유닛 UI의 서로 다른 코드북으로 투영하고, 물리 페이지 `44/45`와 mapper 값 `B0`을 추가한다. 여섯째 단계는 자동 병종 소개 22개·설명 75줄의 한글 216자를 프로필 `0..10`과 `11..21`로 나누어 물리 페이지 `46/47`, mapper 값 `B8/BC`에 넣는다. 일곱째 단계는 무기점 대사 8레코드·12줄을 물리 페이지 `48`, mapper 값 `C0`에 넣는다. 여덟째 단계는 품목명 6개와 `예/아니오`를 같은 페이지에 추가하고, 목록·선택 품목·선택지 소비자를 무기점 수명에서만 전용 포인터로 연결한다. 아홉째 단계는 전투 고정 문자열 231개와 대사 28레코드·70번역 줄을 적용하고, 전투 재료 페이지와 동적 합성 로더를 추가하면서 PRG를 512 KiB로 확장한다. 열째 단계는 7장 `C0:18` 최대 대사 1레코드·57번역 줄을 15페이지·세 글꼴 묶음으로 인코딩하고, 초기 진입과 완료 페이지 진행 때 물리 페이지 `50/51/52`, mapper 값 `C8/CC/D0`을 고른다. 공용 typed RP2A03 선택자들은 전투, 부대 목록, 유닛 요약·상태, 무기점 대사, 시작 메뉴, 장 대사와 최대 대사를 순서대로 판정하고 불일치하면 원래 쌍 인식 선택기로 돌아간다. 자동 병종 소개는 별도 typed 제목 훅에서 프로필 인덱스로 전용 페이지를 고른다.

장 제목 작업공간은 25개, 작은 메뉴 작업공간은 7개, 현재 아군명 정본은 53개, 지명 작업공간은 24개 원문 인덱스에 각각 결속한다. SHA-1 `1ddc435b5e678c214c2273ce7a665ba4bf0ade13`인 기존 누적 후보는 아군명 52개 시점의 역사적 기반이므로 현재 53개 입력의 완료 산출물이 아니다. 아군명 번역은 한 의미 자산에서 소비자별 바이트 투영을 만들기 때문에 부대 목록과 유닛 UI의 물리 코드가 달라도 번역은 중복하지 않는다. 포인터 선택기는 합성 상태 `$02`에서 부대 목록 표, `$04`에서 유닛 UI 표를 쓰고 나머지는 고정 뱅크 `$DE2B`의 원본 표로 돌아간다.

53명 정본의 전투 그래프는 212색 clique 하한을 유지한다. 이를 210색으로 축소하지 않고 논리 코드북 212개와 활성 물리 코드 210개를 분리한다. 모든 보존 전투 리터럴에 없는 표시 코드 2개만 논리 원천으로 빌리며, 선택된 전투의 보수적 텍스트 134개와 보호 그래픽 39개는 `173/210`, 정확 모델 최대는 `170/210`이다. 보호 충돌의 보수적 재배치는 `7/8`이라 기존 쌍 저장소에 든다. 현재 깨끗한 빌드는 전투 기반 SHA-1 `260e2924c354264e48c2eb7b2dc9ff0438c87dfa`와 합성 로더 SHA-1 `45fc71a76084a7ca41e3bf0b7bf80cf2bd8cb882`를 생성한다.

7장 완료 페이지 증거는 전체 대사 파일이 아니라 대상 레코드의 페이지 경계 topology에 결속한다. 아래 첫 명령은 번역문을 출력하지 않고 포인터·글리프/제어 구분·줄 경계 digest만 낸다. 둘째 명령은 과거 출력의 제어 topology와 현재 출력의 실제 한글 래스터를 같은 15개 포인터에 대조한다. 현재 topology SHA-1은 `5ee3b66823c66070447a180a63058a2e1277b75a`이고 현재 최대 대사 단계 SHA-1은 `80f63bc4cb6afa977ade127af60aafd4f17275b0`이다.

현재 개발 빌드는 실행 증거를 명시적으로 유예한 채 11단계를 완료해 누적 후보 `0b507b7c9d0d97a483a04a27bf2821a82b1a9a14`를 만든다. 이 모드는 오래된 실행 증거를 승계하지 않으며, 누적 보고서의 해당 런타임 역할을 미결로 남긴다. 과거 누적 후보에서 확인한 제목의 네 무입력 위상과 7장 15페이지 실행도 현재 후보에 승계하지 않는다.

`plan-full-translation-installation`은 역사적 입력 후보와 보고서 해시를 먼저 확인하고, 후보에 명시적으로 16 KiB를 확장한 뒤 선언된 14개 도메인의 Expected Write를 적용한다. 마지막에는 같은 순서로 최종 이미지를 재구성하고, 역할·오프셋·예상 바이트·교체 바이트·유도 근거가 같은 정확한 변경 집합인지 검사한다. 이 기술 설치 관문은 현재 통과했지만 화면 레지스트리 23개 번역 도메인의 소비 경로 전수 조사와는 별도다. 소비자 근거 상태는 알려진 경로만 결속, 전수 조사 완료, 미해결로 상호 배타적으로 세며 현재 각각 5 / 23, 0 / 23, 18 / 23다. `terrain_names`는 16개 원천 레코드와 확인한 `battle_animation` 경로를 결속했지만 사운드 테스트를 포함한 전체 생산자와 계산·간접 참조 분모는 남아 있다. 이 수치는 설치·실행 표시·사람 검토를 대신하지 않는다. 장 제목 저장소는 원본 고정 뱅크와 512 KiB 확장 뒤 CPU가 실제로 읽는 활성 고정 뱅크 복사본에 각각 25개씩 설치한다.

유닛 요약·상태 고정 라벨은 물리 저장 바이트 수와 합성기의 표시 셀 수를 따로 검증한다. `0F/1F`는 0폭 결합부호이고 그 밖의 종단 전 바이트는 한 칸이므로, 아홉 상태 라벨은 콜론까지 원본 8칸, 요약 `레벨`은 4칸을 유지해야 한다. 번역문은 이 폭 안에서 오른쪽 정렬하고 남는 물리 저장소는 `EF` 뒤에만 채운다. 유닛 UI 코드가 화면용 버퍼에 직접 쓰는 `AD/AF/BF`는 번역 논리열에 없어도 카탈로그 배정에서 제외하고 모든 생성 페이지의 타일이 원본과 같은지 검사한다. 현재 `마법방어` 입력을 포함한 카탈로그는 두 페이지, 최대 `210/210`, 이름 정체성 122개를 모두 수용한다. 개발 출력 SHA-1은 `5fda755073d41b56b1c9b695374151703a22a5f4`, SHA-256은 `3ab4eb7e2adabd22bfbed7271bc9a7d3a061a06da2c3cac312ded91af0328729`, 전체 설치 보고서 SHA-1은 `31c48849792238b52d3d7dfd07b118e11d7fc42d`다.

선택 인수 `--final-runtime-evidence`는 생성된 통합 이미지와 정확히 같은 SHA-1을 선언한 외부 실행 증거 manifest만 받는다. 안정 화면의 시간 관측은 등록된 화면 역할, 대표·최악 구분, 콜드 부팅, 세이브스테이트 미사용, 일본어 대상 0·보호 원문 유지·시간 표본의 가시 글리치 0을 선언하고, 최소 세 개의 불규칙 시간 표본과 실제 이미지 SHA-256을 제공해야 한다. 과거 후보의 실행 역할은 승계하지 않는다. 주 대사 결합 역할은 여기에 더해 서로 다른 가시 페이지 둘 이상의 표본, 그보다 뒤의 다음 레코드 표본, 다시 그보다 뒤의 역할 이탈 표본을 같은 manifest 이미지 목록에 결속해야 한다. `chapter_clear_epilogue_dialogue`의 최악 관측은 이미지 digest가 서로 다른 완료 페이지 표본이 정확히 15개이고 그 뒤 이탈 표본이 있어야 하며, 14개 이하 또는 같은 화면 반복은 빌드에서 거부한다.

한 실행에서 잠깐씩만 나타나는 여러 화면은 각 화면을 다시 세 번 찍어 별도 실행처럼 꾸미지 않는다. 알려진 route 형식이 체크포인트 종류와 순서를 소유하고, manifest는 한 콜드·세이브스테이트 미사용 실행의 증가하는 frame offset과 각 한 장짜리 가시 결과를 결속한다. 한 장의 체크포인트는 그 프레임의 한글 가독성·일본어 대상 부재·보호 원문·가시 결함만 판정하며 시간 안정성을 주장하지 않는다. 장 완료에서 다음 장 지도까지의 route는 서로 다른 완료 대사 15페이지, 원본 `NEXT STORY`, 저장 질문·완료, 서로 다른 도입 네 페이지, 지도 정착, 부대명단과 지도 복귀를 정확히 그 순서로 요구한다. 누락·재정렬·반복 페이지·다른 이미지 digest는 실패한다. 이 실행 결속은 선언한 기술 설치, 사람 검토, 배포 판정과 각각 별도이며, 사람 검토로 번역 바이트가 바뀌면 새 exact artifact에서 다시 결속한다.

병종 소개 작업공간은 인덱스 `$0559`의 22개 제목과 75개 설명 줄을 원본 포인터·저장 바이트에 결속한다. 빌드는 원본 영문 능력치 약어와 숫자를 보호하고 일본어 제목·설명만 바꾸며, 모든 줄이 원래 저장 길이 안에 드는지 검사한다. 자동 경로의 첫·중간·페이지 경계·마지막 소개, 검은 전환과 뒤의 영어 화면을 해당 단계 출력 SHA-1에 결속한 7개 무입력 표본이 없으면 빌드가 실패한다.

무기점 대사는 공유·중첩된 레코드가 있으므로 대상 8개만 제자리 덮어쓰지 않는다. 대상이 닿는 원본 소유 구간의 모든 레코드를 다시 포장하되 비대상 레코드는 원본 논리 바이트를 그대로 보존하고, 그 구간의 모든 포인터를 Expected Write로 함께 갱신한다. 화면 선택기는 외부 상태 `01..0C`, 시설 `01`, 대사 뱅크·디렉터리 `0B/B1`, CHR 쌍 `1E/1E + 00/(15|18|19)`가 모두 맞을 때만 `C0`을 공급한다. 품목 목록과 선택 품목은 각각의 실제 소비 지점에서 전용 표를 고르고, `예/아니오`는 같은 수명에서만 전용 문자열로 전환한다. 공용 페이지는 한글 60자와 보존 코드 90개, 합계 `150/210`이며 아홉 화면 역할의 용량을 함께 닫는다. 실행 증거는 이 용량 결속과 분리한다. 여덟째 단계 출력 SHA-1 `4758d15b9beb9b075be6976508b90e17ef1ea54d`의 비구매 경로에서 선택 확인·계속 질문·품목 목록 복귀·종료 문구·지도 복귀의 17개 불규칙 표본, 선택자 실행, 원본 선택 품목 표 우회와 금액·소지품 무변경을 결속했다. 뒤 단계의 Expected Write 검증은 이 페이지와 선택기를 보존하지만, 최종 누적 출력의 실제 구매·사전 검사 분기까지 실행으로 대신하지 않는다.

아홉째 전투 단계는 전투 단독 기반과 지원 원본의 mapper 165 패리티 접두부를 비교해 329개 연속 변경 구간만 이전 누적 ROM에 Expected Write로 적용한다. 그런 뒤 전투 재료 페이지와 현재 고정 뱅크 복제본을 포함하도록 PRG를 256 KiB에서 512 KiB로 확장하고, 누적 전용 주소 `$FC20..$FF8F`에 21개 typed RP2A03 루틴 1,176바이트를 설치한다. 열째 최대 대사 단계는 앞 선택자와 CHR 25뱅크를 보존한 채 CHR 두 뱅크를 추가하고, 15페이지의 세 글꼴 묶음과 초기·진행 선택기를 Expected Write로 설치한다. 이 열째 단계 ROM SHA-1은 `17911417a91fc8190e68d5e032107e97ca939dfe`, 보고서 SHA-1은 `80dca08005ddfe17f5a0abd9b784e73e8d7f73b5`이며 10단계·42대사 레코드·168번역 줄·1,148글리프 슬롯·추적 쓰기 545개를 보고한다.

같은 누적 ROM의 콜드 실행은 `처음부터`, 슬롯 화면, 1장 제목·도입 여섯 페이지, 지도와 부대 목록을 거쳐 세 번째 턴의 자연 전투에 도달했다. 첫 두 적 턴은 전투 없이 상태 `00`으로 복귀했고, 세 번째 턴의 두 합성은 프레임 13,230과 14,195의 새 주소 `$FC99`에서 시작했다. 둘 다 +43프레임의 CHR-RAM과 PPU `$1000`가 4,096/4,096바이트 같았고, `가르다병`·`해적 :도끼`·`카인`, `가르다병의 공격`, `카인의 반격`, `카인은(는) 11의 경험치를 얻었다`와 원본 `LV/HIT/EXP`·숫자·그래픽이 함께 유지됐다. 프레임 15,997에는 상태 `00`, `$07DF=00`으로 지도에 복귀했다. 최대 대사 실행 manifest를 명시하면 빌드는 초기 선택기 원시 이벤트, 15페이지의 `0E/4줄` 상태·포인터·`C8/CC/D0`, 90개 화면 표본과 여섯 점멸 접촉표, 마지막 `0E→0F` 기록과 `NEXT STORY` 상태를 현재 출력 SHA-1에 결속한다. 이 증거는 상태를 연결한 7장 성 명령 경로이며, 콜드 부팅부터 해당 장면까지의 연속 회귀나 아직 설치하지 않은 화면을 대신하지 않는다.
