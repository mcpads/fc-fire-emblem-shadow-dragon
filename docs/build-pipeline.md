# 빌드 파이프라인

제품 빌드는 다음 순서로 실패 폐쇄형으로 동작한다.

1. 일본판 원본 전체·PRG·CHR 해시와 iNES/매퍼 구조를 검사한다.
2. 번역 자료가 `ja`에서 `ko`로 가며 `preserve_existing_english: true`인지 검사한다.
3. 한글 타일 코드가 첫 일본어 설정 문자열에서 실제로 쓰인 가나 코드인지 검사한다.
4. Dalmoori를 8x8 NES 저비트플레인 타일로 래스터화한다.
5. 설정 표와 각 CHR 타일의 원본 바이트가 기대값과 정확히 일치할 때만 같은 길이로 쓴다.
6. 최종 ROM의 모든 변경 바이트가 등록된 쓰기 범위 안인지 감사한다.
7. 모든 검사가 끝난 뒤에만 무시된 `out/` 아래에 ROM과 미리보기를 쓴다.

영문 패치나 조사 산출물은 이 경로의 입력이 아니다. 설정 PoC는 실행 코드를 수정하지 않고 고정 길이 자료와 일본어 타일만 바꾼다.

## 화면 계약 조사

`analyze-screen-contracts`는 국소 주소를 패치하기 전에 화면 역할별로 일본어 대상, 보존할 원본 영어·숫자, FD 문자, FE 그래픽, 스프라이트 UI, 점멸·애니메이션, 입력 대기·자동 전이, 글꼴 페이지 진입·이탈·재진입을 함께 점검한다. 분리된 실제 화면 45개는 모두 실행으로 관측했고 42개는 CHR 쌍까지 결속했다. 사운드 테스트의 `START`는 6단계 테스트를 별도 여섯 화면으로 세지 않고 공용 `battle_animation`의 유닛 정보·예측·공격·피해·결과 수명으로 결속한다. `SELECT`의 30단계 엔딩은 같은 상태 `01` 안에서도 번역 경계가 다른 원본 영어 도입·캐스트와 일본어 장 기록을 나누고, 원본 영어 스태프, 일본어 인물 후일담, 정적 종단 화면도 별도 역할로 둬 미분할 화면군이 남지 않았다. 소지품 목록·행동 메뉴·장비·사용 결과는 `1A/1A + 00/15`, 텍스트 없는 양도 대상 선택은 `1A/1A + 15/15`였다. 공용 전투 엔진의 이름·병종·아이템·별도 전투 대사 원천과 28개 대사 레코드, 엔딩 장 기록 스트림과 인물 후일담 두 표까지 소스에 결속했다. 정규 전투의 유리·불리·패배 경로 극성은 모두 시간 표면으로 닫았고, 다음 상위 관문은 남은 인물 후일담의 글리프·초상화·스프라이트 변형 합집합이다.

`analyze-temporal-surfaces`는 비공개 frozen-frame 증거 manifest를 받아 각 표본의 스크린샷·생산자 상태·내부 RAM·PRG RAM·2 KiB 네임테이블·OAM·팔레트를 함께 검증한다. 선언 프레임 차와 생산자 프레임 차가 정확히 같고, 표본마다 소스에서 예상한 상태 바이트가 맞을 때만 화면·CHR 쌍·두 물리 네임테이블의 타일 코드·가시 스프라이트 타일 합집합을 만든다. 가시 스프라이트는 OAM의 Y 좌표가 `00..EE`인 항목으로 한정한다. 원본 MMC4의 상태 키와 mapper 165의 1 KiB 레지스터 값을 각각 읽고, mapper 165 값은 예약한 8 KiB 접두부를 뺀 원본 상대 4 KiB 페이지로 정규화한다. 예약 접두부나 정렬되지 않은 레지스터는 거부한다. 공개 코드와 보고서에는 증거 경로나 대사 원문을 넣지 않는다. 현재 사운드 테스트 공용 전투 11개, 자동 엔딩 18개, 턴 경계 게임 오버 12개, 적 선공 정규 전투 11개, 플레이어 선공 정규 전투 10개, 합계 62개 불규칙 표본에서 CHR 쌍 16개·네임테이블 타일 코드 219개·가시 스프라이트 타일 코드 160개를 모았다. 요구한 전투 경로 극성은 모두 닫혔고 남은 인물 후일담 변형은 아직 관문 밖이다. 게임 오버 완성 문구는 890프레임 동안 입력 대기로 유지됐고, 두 정규 전투는 예측·공격·피격·반격·성장·결과 수명을 포함했으며, 엔딩 종단은 `$7731=1D`, `$7732=00`, no-op 처리기와 12,000프레임 동일 표본으로 정적임을 확인했다.

`analyze-chapter-transitions`는 장 종료부터 다음 장 도입까지의 기본 여섯 수명과 저장 완료 “아니오”의 종료 안내·사운드 테스트 두 수명을 분리한다. 장 인트로 `E5` 문맥 25개가 `$781D=00..18`을 공급하고, 장 제목 표 `$EE08`도 25개 포인터를 가지며 마지막 문자열이 다음 장소 이름 표 `3EFC7` 직전에서 끝나는지 검사한다. `NEXT STORY` 인덱스 `3E`와 저장 질문 인덱스 `32`의 포인터·원본 바이트·합성 소비자도 고정한다. 정규 파일 1의 장 번호 `$6519`, `$6000..$6542` 16비트 가산 체크섬, 기록·검증 코드도 결속한다. 11장 성 명령부터 이어진 기본 실행과 두 “아니오” 분기는 각각의 상태·입력 효과·CHR 수명에 결속했다. 사운드 테스트에서는 위·아래·`A`·`B`의 원천 효과와 `START`의 공용 전투 엔진, `SELECT`의 자동 엔딩을 결속한다. 전투는 32개 내부 단계와 네 고정 문자열 표, 별도 상태기와 28개 포인터 참조 대사 레코드를, 엔딩은 113개 장 기록 스트림·동적 턴 삽입과 두 인물 후일담 표를 구조적으로 검사한다. 전투 고정 표의 107개 고유 코드는 일본어 100·보존 원문 6·레이아웃 1개로 나뉜다. 전투 대사 834바이트는 일본어 620·보존 원문 167·레이아웃 47바이트, 엔딩 장 기록 439바이트는 349·47·43바이트, 인물 후일담 1,649바이트는 1,529·9·111바이트로 정확히 분할되며 세 표면 모두 미해결 코드는 없다.

인물 후일담은 상태 `0E`가 `$773B=35`를 만든 뒤 상태 `0F`가 후보 ID `35..01`을 역순으로 훑는다. `$906A`의 54개 부대 레코드는 각 27바이트이고, 오프셋 `00`의 ID가 후보와 같은 레코드가 없으면 화면을 만들지 않고 다음 후보로 넘어간다. 일치 레코드의 오프셋 `12`가 `FF`이면 표 `41`과 그 레코드의 오프셋 `0E` 장소 이름을, 아니면 표 `40`을 고르며 엔트리 번호는 후보 ID와 같다. 표 `41`의 스크립트 엔트리 `02..35` 52개는 모두 표 `40`의 엔트리 `00`으로 전이하고 `00/01`은 고정 no-op 처리자다. 표 `40`의 추가 엔트리 `36..41`은 외부 후보 선택자가 아니라 대사 제어 전이로만 들어간다. 이 구조만으로 오프셋 `12`의 두 값을 생존·사망으로 이름 붙이지 않으며, 생산자 또는 실행 근거를 다음 관문에서 따로 결속한다. 보고서는 장 종료·저장 완료·전투·후일담의 원문을 출력하지 않으며, 진행 가속 도달을 기준 난이도나 실패 경로로 일반화하지 않는다.

`analyze-chapter-victory`는 11장 지도 포인터와 25×32 타일 구조를 검사해 성 타일 `4B` 두 개를 행 8, 열 5·6에 결속한다. `しろ` 라벨 인덱스 `38`, 명령 비트 3의 `06:$907B`, 주 상태 `3C`, `06:$9390 → 0F:$C027 → 03:$8006`과 외부 화면 상태 `0C`의 4단계 처리기 표를 한 경로로 묶는다. 코드 구간은 고정 원본 바이트뿐 아니라 고정된 `retro-rp2a03`의 typed decoder로 명령 경계를 다시 확인한다. 런타임 계약은 초기 성 점유자, 행동 바이트 `FF`의 비활성 규칙, 실제 이동으로 열린 성, 네 줄 메뉴, 네 에필로그 페이지와 12장까지의 7개 화면을 기록한다. 보고서는 지도 전체나 대사 원문을 출력하지 않으며, 좌표·행동 상태·승리 단계 직접 쓰기를 완료 증거로 허용하지 않는다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-screen-contracts \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"

cargo run -p fc-fire-emblem-patch -- analyze-chapter-transitions \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"

cargo run -p fc-fire-emblem-patch -- analyze-temporal-surfaces \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes" \
  evidence/private/temporal-surfaces/manifest.json

cargo run -p fc-fire-emblem-patch -- analyze-chapter-victory \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

보고서는 원문이나 캡처를 포함하지 않고 화면 역할, 구조 상태와 다음 관문만 기록한다. 실행 관측이 없는 화면은 추측으로 채우지 않으며, CHR 쌍 목록도 같은 레지스트리에서 생성해 화면 목록과 매퍼 분석이 어긋나면 실패한다.

`analyze-item-flow`는 유닛 명령 결과 6부터 소지품 목록, 조건부 행동 메뉴, 텍스트 없는 양도 대상 선택, 장비·사용·양도·폐기 결과를 별도 화면으로 결속한다. 목록의 `A`는 선택 아이템과 슬롯을 저장한 뒤 행동 가능 조건만 계산하며 아직 소지품을 바꾸지 않는다. 행동 메뉴의 `A`는 가용 마스크를 행동 코드 0~3으로 바꿔 실제 변경 경계를 넘는다. 결과 대사 인덱스는 `19/1A/1B/1C`다. 장비는 첫 슬롯과 선택 슬롯을 교환하고, 양도는 승인한 대상 버퍼로 아이템과 내구도를 옮기며, 폐기는 지운 뒤 목록을 압축한다. 사용은 진행 상태 2에서 아이템 계열 효과를 자동 적용하고 상태 3에서 입력을 기다린다. 표본 아이템 `40`은 회복 성공 때만 내구도를 줄였고, 최대 HP에서는 무효 결과로 사용 횟수를 보존했으며, 마지막 사용은 슬롯을 지웠다. 고정 라벨 `NO ITEM`과 내구도 숫자는 일본판 원본 영어·숫자이므로 보존한다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-item-flow \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

보고서는 원문 대사나 ROM 변경 없이 상태 디스패처, 합성 상태, 고정 라벨 포인터, 행동별 변경 경계와 실행 표본만 기록한다. 목록·행동 메뉴·양도 대상의 `B`는 각각 상위 화면으로 돌아가는 비변경 경로다. 양도 대상은 점멸 주기 중 한 프레임에서 후보 표시가 빠질 수 있으므로 불규칙 다중 표본을 요구한다. 장비·양도·폐기 확정은 독립 세이브 분기에서 데이터 변경과 결과 화면을 함께 검증했으며, 사용은 자연스럽게 쓸 수 있는 아이템의 표적과 실패 효과를 먼저 결속해야 한다.

`analyze-shop-flow`는 `ぶきや` 명령 결과 7에서 무기점 상태 디스패처 `06:$99AC`, 품목 선택 상태 4, 구매 확인 상태 7, 결과 상태 12, 이탈 상태 8과 공용 메뉴 입력 처리기 `0B:$9333`을 하나의 화면 전이로 결속한다. 품목 목록의 `A`는 소지품 빈칸·금액·아이템별 조건을 검사할 뿐 구매하지 않고, 확인 메뉴 결과 1만 `06:$9BA4`의 금액 차감과 아이템·내구도 삽입으로 들어간다. 아이템 조건 실패는 상태 7의 구매 경고로 정착하며, “예”는 실제 구매하고 `B`/“아니오”는 비변경 계속 구매 질문으로 간다. 구매가 마지막 빈칸을 채우면 일반 결과 질문 대신 상태 8의 자동 이탈 화면으로 간다. 메뉴 선택은 `$7FF3` 단일값이 아니라 `$05CE` 인덱스를 쓰는 기준 주소로 보고한다. 기존 `shop-and-item-dialogue` 88포인터 표와 디렉터리 `B1:$BFE2 → $A766`을 재사용하며 대사 원문은 보고서에 출력하지 않는다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-shop-flow \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

`analyze-unit-ui-text`는 `unit_summary`, `unit_command_menu`, `unit_status`를 국소 writer에 결속한다. `$05E8` 합성 상태 `04/05/07/0F`를 각각 요약 상단, 명령 목록, 요약 아이템 목록, 상세 능력치 조립기로 검증하고, 유닛명·병종·아이템·고정 문자열·숫자·합성 파서의 공유 호출부를 보고한다. 상태 `05`는 유닛 능력·지형·인접 대화·인벤토리·시설에 따른 명령 라벨 15개를 정적으로 결속하며, 실행 표시는 `こうげき/もちもの/たいき/たずねる/ぶきや/しろ` 6개를 확인했다. `こうげき`는 무기 선택으로, `しろ`는 승리 처리로 들어가는 입력 효과도 별도 보고서에 결속했다. 공격·지팡이·변신·지형·대화·소지품·시설·대기의 판정 순서와 `$05EB` 비트 0~7, 지형 타일 5종과 시설 인덱스 5종의 라벨 대응도 보고한다. 시설 생산자는 뱅크 `0B:$A291`, 장별 포인터 표는 `$A4FF`이며 1장 `$A531`의 `03 1A 01 00 F0`가 좌표 `$03/$1A`를 시설 인덱스 1 `ぶきや`에 결속한다. 요약·명령·상세의 오른쪽 `00/(15|18|19)`를 모두 관측했다. 원본 `HP`와 숫자·구두점은 번역 대상에서 제외하며 자동 `class_profile` 계약은 섞지 않는다.

같은 명령은 기존 텍스트 표 명세를 다시 사용해 병종·아이템·아군명·적군명 4개 표의 소비자와 전송 코드를 먼저 검증한다. 이 범위는 포인터 234개, 고유 문자열 233개, 참조 바이트 1,250개, 고유 저장 바이트 1,245개다. 작은 가타카나 `A6..AA = ァ/ィ/ゥ/ェ/ォ`까지 공용 디코더에 포함하면 고유 원문 코드 107개 중 일본어는 100개이고 나머지는 모두 기존 보호·레이아웃 집합에 들어가므로 잠정 한글 슬롯 상한은 210개다. 이 수치는 원문 레퍼토리일 뿐 번역문 한글 수가 아니다. 검토된 번역문이 없으므로 단일 공용 페이지 적합 여부는 계속 미확정으로 보고한다. 요약·상세는 한 이름·한 병종·현재 소지품 최대 네 개를 한 페이지 수명에서 공유하고 소지품이 바뀔 수 있으며, 명령 메뉴는 진입 때 별도 페이지를 다시 공급한다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-unit-ui-text \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

이 명령은 보이는 한 유닛의 문자열을 직접 고치는 패치를 만들지 않는다. 네 조립 역할과 공유 원천 표가 모두 맞아야 하며, 모든 관측 배경 위상과 15개 명령 라벨을 포함한 공용 한글 페이지 설계의 입력으로만 쓸 수 있다. 번역문 합집합이 210칸을 넘으면 유닛별 예외가 아니라 내용 조합별 페이지나 실행 중 글리프 공급을 비교한다.

## 공개 저장소 자료 경계

추출·재삽입 로직과 구조 메타데이터, 설정처럼 작은 메뉴·UI 번역은 추적할 수 있다. 대사 중심의 대규모 원문 추출본, 대사 번역본과 번역 작업용 중간 자산은 Git에 넣지 않는다. 그런 자료는 `private/dialogue/`, `out/` 또는 `evidence/private/` 아래에서만 생성한다. 공개 문서에는 원문 덤프 대신 범위·개수·해시·주소와 소비 경로를 기록한다.

## mapper 165 무번역 패리티 프로브

`build-mapper165-parity-probe`는 지원 일본판을 MMC2식 CHR 래치와 MMC3식 PRG·SRAM을 함께 쓰는 mapper 165로 변환한다. 원본 CHR 앞에 빈 8 KiB를 두고 원본 32개 4 KiB 페이지를 +2 이동하므로, mapper 165의 CHR-RAM 선택값 0과 원본 CHR page 0이 충돌하지 않는다. 재배치한 원본 CHR SHA-1, PRG 크기와 배터리 플래그가 바뀌면 빌드가 실패한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mapper165-parity-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

PRG writer 12곳과 명령 경계가 확인된 CHR writer를 같은 길이의 호출로 바꾼다. 새 루틴은 공유 RP2A03 ISA로 조립·역검산하고, 원본이 `FF`이며 직접 `JSR`·`JMP` 대상이 아닌 고정 뱅크 범위에만 배치한다. 출력 보고서는 CHR 재배치, 코드 배치, writer 수, 모든 추적 쓰기와 남은 실행 경계를 기록한다.

이 프로브는 번역이나 한글 자산을 넣지 않는다. 타이틀·자동 병종 설명·1장 인트로 대화, 자연 중단 저장·재개, 검증된 턴 경계 게임 오버, 실제 전투를 거친 1장 완료, 정규 저장, native power cycle 뒤 불러오기와 2장 전환 표본은 원본과 동등하다. 직접 CHR writer 31곳의 트리거 쌍도 모두 분류해 G2를 통과했다. 다만 이는 전체 장·상점·아이템·엔딩의 전수 회귀가 아니며 한글도 아직 공급하지 않으므로 `release_eligible`은 거짓이다.

`analyze-mapper165-trigger-planes`는 화면 실측으로 확인한 FD/FE 쌍에서 타일 `FD`의 상위 비트플레인 8바이트를 비교한다. MMC4는 `$xFD8`, mapper 165는 `$xFD0`에서 FD 전환을 시작하므로, mapper 165의 FD 페이지 상위 비트플레인이 직전에 선택된 FE 페이지와 같아야 트리거 타일이 보존된다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-mapper165-trigger-planes \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

현재 설정·부대 목록, 맵 애니메이션, 세 유닛 UI, 무기점 아홉 화면, 소지품 메뉴·장비 결과·양도 대상을 포함한 29개 화면의 고유 쌍 18개 가운데 오른쪽 `00/14` 한 쌍만 별도 변형 페이지가 필요하다. 설정·부대 목록·유닛 UI·무기점·소지품 화면의 `00/15`, `00/18`, `00/19`와 양도 대상의 `15/15`는 원본 트리거 평면과 같아 자연 페이지를 쓴다. 그러나 같은 FD `00`은 `00/00`, `00/15`, `00/18`, `00/19`에서 원본 비트플레인을 요구하므로 페이지 00을 전역 수정할 수 없다. 빌더는 예약 CHR의 물리 4 KiB 페이지 1에 변형을 합성하고, 중앙 오른쪽 공급자가 FD/FE 그림자 쌍에 따라 자연 페이지와 변형 페이지를 고르게 한다. 직접 writer는 상태를 추측하지 않고 기존 단순 매핑을 유지한다.

`analyze-mapper165-direct-chr-pairs`는 직접 CHR writer 31곳의 명령 경계와 값 공급 방식을 원본 바이트로 검사한다. 연속 `STA`가 같은 A를 소비하는 26곳은 FD=FE 또는 같은 값의 전체 창 초기화로 닫는다. 전투 실행에서 고정 뱅크 오른쪽 쌍과 bank 05 왼쪽 쌍은 모두 `$5E/$5F=02/06`으로 결속했다. bank 05 FE=`06` 뒤 `$E414` 단독 FD가 `06 → 02`로 바뀌어 실제 왼쪽 쌍 `06/06`, `02/06`도 확인했다. 세 쌍의 트리거 비트플레인은 모두 같아 추가 변형이 필요 없다.

```sh
cargo run -p fc-fire-emblem-patch -- analyze-mapper165-direct-chr-pairs \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

## 동적 한글 페이지 계획

`plan-hangul-page-proof`는 원본 글꼴 페이지를 기준으로 확장 CHR-ROM에 들어갈 4 KiB 한글 페이지 두 개를 만든다. 현재 보호가 확정된 영어·숫자·부속 문장부호·제어·래치 43코드와 합성 레이아웃 3코드는 원본 타일을 그대로 유지한다. 나머지 210코드만 한글 활성 슬롯으로 배정하며, 한 페이지의 중복 글리프·210자 초과·보호 타일 변경·mapper 165의 256 KiB CHR 범위 초과를 거부한다.

```sh
cargo run -p fc-fire-emblem-patch -- plan-hangul-page-proof \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

현재 합성 표본은 설정 화면에 실제로 표시할 한글 12자를 A와 B의 같은 코드에 공유하고, 그 밖의 같은 100코드에는 페이지마다 다른 합성 글리프를 넣는다. 각 페이지는 112자로 예산 안에 있고 합집합은 `12 + 100 + 100 = 212`자로 한 페이지 한계를 넘는다. 페이지가 바뀌어도 화면 공유 글리프 12개의 코드·문자·타일은 같다. 물리 페이지는 `34/35`, mapper 레지스터 값은 `88/8C`이고, 기존 무번역 프로브 뒤에는 최대 30페이지가 남아 페이지별 배정 총량 상한은 6,300칸이다. 이는 화면별 중복과 실제 번역 코퍼스를 반영한 최종 수용량이 아니다. 산출물의 `runtime_bound`는 거짓이며, ROM 삽입·화면 선택·`A → B → A` 실행 전환을 통과하기 전에는 G3 완료 증거로 쓰지 않는다.

`build-mapper165-hangul-page-probe`는 검증된 mapper 165 무번역 이미지를 메모리에서 재생성한 뒤 설정용 두 4 KiB 페이지를 물리 페이지 `34/35`, 부대 목록용 두 페이지를 `36/37`에 붙인다. 설정 페이지는 공유 12자와 페이지별 100자로 각각 112자, 합집합 212자다. 부대 목록 페이지는 공유 `이/름` 2자와 화면에 보이지 않는 페이지별 증명 105자로 각각 107자, 합집합 212자다. 화면에 보이는 나머지 27코드는 두 페이지 모두 원본 타일과 같아야 한다. 화면마다 같은 코드가 다른 일본어에 쓰일 수 있으므로 두 페이지 집합은 화면 수명을 넘어 합치지 않는다. 출력 CHR은 19뱅크·152 KiB다. 설정 표와 뱅크 `0B:$917C`의 `なまえ   LV HP` 머리말은 각각 검증된 소규모 한글 자료로 바꾸며, `LV/HP` 바이트와 해당 글꼴 타일은 Expected Write와 페이지 전수 비교로 보존한다.

설정 루틴은 `$52=00`, `$59/$5A=1A/1A`, `$5B/$5C=00/15`를 모두 만족할 때만 개입한다. `$0034=20/40`은 A의 `88`, `30`은 B의 `8C`를 오른쪽 FD 레지스터에 쓰며, 화면 계약이 다르면 기존 `$FAC0` 쌍 인식 선택기로 돌아간다.

부대 목록 생성자 `0B:$89DB`는 창 기술자 `$05CF/$05D0=12/04`와 위치 `$70/$71=30/40`을 만든 뒤 `$89F2`에서 머리말 리소스 `2B`를 읽는다. 이 18바이트 생성자 서명은 지원 원본 PRG에 한 번만 있어야 한다. 머리말 호출에서 한 번만 CHR을 쓰면 뒤의 공용 갱신이 덮으므로, 중앙 오른쪽 FD 호출 `$C9C2`를 `$FB80`의 typed RP2A03 선택기로 보낸다. 선택기는 이 네 수명 바이트, 왼쪽 `18/18`, 오른쪽 FD `00`을 모두 확인한 뒤 FE `18/19`에는 페이지 `36`의 값 `90`, FE `15`에는 페이지 `37`의 값 `94`를 쓴다. 다른 화면이나 위상은 기존 `$FAC0`으로 돌아간다. 진행 메뉴는 외부 상태와 CHR 쌍 일부를 공유하지만 생성자 기술자가 달라 원본 페이지를 유지한다. 두 루틴 모두 입력 레지스터·플래그를 보존하며 원본에 선행 직접 `JSR/JMP`가 없고 전부 `FF`인 구간에만 설치된다. 보고서의 `runtime_verified`는 빌드만으로 실행을 주장하지 않도록 거짓으로 유지하고 별도 콜드 실행 결과는 [현재 상태](status.md)에 기록한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mapper165-hangul-page-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

## MMC5 PRG 정적 프로브

`build-mmc5-prg-probe`는 번역·한글 자산 없이 지원 일본판을 mapper 5 헤더로 바꾸고, 원본 마지막 16 KiB PRG 뱅크의 확인된 `FF` 구간 `$FA00`~`$FA7F`에 최소 초기화·뱅크·미러링 루틴을 배치한다. 새 실행 코드는 허용된 RP2A03 명령과 주소 지정 형식만 받는 checked assembler로 생성한다. 이 구간을 대상으로 하는 직접 `JSR`·`JMP` 3바이트 패턴이 PRG 전체에서 하나라도 나오면 쓰지 않는다.

리셋 초기화는 MMC5 PRG 모드 1, 마지막 16 KiB ROM, PRG RAM 0번 뱅크와 쓰기 허용 레지스터를 설정한 뒤 원본 `$C075`로 간다. 원본 중앙 PRG 선택 루틴은 16 KiB 뱅크 번호를 MMC5의 8 KiB 번호로 바꾸고, 미러링 선택은 `$5105`의 수평 `50`·수직 `44` 값으로 바꾼다. 부팅 경로 두 곳, `$E69C` 대사 바이트 읽기 경로 `$E6A1/$E6AB`, `$E6B2` 인덱스 포인터 표 경로 `$E6BA/$E6F1`에서 실행을 확인한 여섯 `$A000` 직접 쓰기는 원본 `$29/$51` 그림자를 손상하지 않는 raw 뱅크 루틴으로 보낸다. 변환 계산 전후에 A와 상태 플래그를 복원하고, 미러링 루틴도 원본 반환 A값 `0/1`을 유지한다.

헤더, 코드 구간, 원본 루틴과 리셋 벡터는 모두 Expected Write로 보호하며 마지막에 변경 전수를 감사한다. 산출물은 mapper 5, PRG/CHR 크기, 원본 CHR SHA-1과 배터리 플래그를 다시 검사한다. `out/mmc5-prg-probe.json`은 루틴 주소와 추적 쓰기만 기록한다. MMC4 CHR 래치, 아직 분류하지 않은 매퍼 쓰기 후보, 코드 구간의 간접 참조, 실행 동등성은 미해결로 명시하며 `release_eligible`은 항상 거짓이다.

`build-mmc5-chr-writer-probe`는 같은 메모리 내에서 위 PRG 프로브를 먼저 생성·검증한 뒤 MMC5 CHR 모드 1을 설정한다. 원본 중앙 CHR 공급 루틴 네 곳은 그림자와 `$52` 계산을 유지하면서 `$B000/$C000 → $5123`, `$D000/$E000 → $5127`로 같은 8바이트 안에서 바꾼다. 자동 병종 설명 화면에서 실행을 확인한 뱅크 `0D:$8036/$8039`, `0D:$83AB/$83AE`의 직접 쓰기 네 곳도 같은 3바이트 길이로 옮긴다. 이 추가 단계는 PRG 프로브 바이트를 기준으로 10개 Expected Write와 변경 전수 감사를 거친다.

이 매핑은 각 PPU 4 KiB 창에서 마지막으로 실행된 공급값 하나만 남긴다. FD/FE 값이 같은 직접 쓰기 쌍은 그대로 표현하지만 값이 다른 중앙 공급 쌍의 래치 공존은 재현하지 않는다. 보고서의 `fd_fe_latch_equivalent`와 `release_eligible`은 항상 거짓이고, 각 화면의 실행 동등성은 별도 관문이다. 아직 실행 분류하지 않은 직접 쓰기 후보는 자동으로 고치지 않는다.

`build-mmc5-expanded-chr-options-probe`는 검증된 CHR writer 프로브를 기준으로 원본 128 KiB CHR을 상위 절반에 한 번 더 복제하고 iNES CHR 크기를 256 KiB로 늘린다. 하위 CHR은 원본 SHA-1을 그대로 유지하고, 상위 복제본의 첫 4 KiB에서 일본어 설정용 12타일만 한글 PoC 글리프로 바꾼다. 기존 영어·숫자 타일은 수정하지 않는다.

검증된 여덟 CHR store는 같은 3바이트 길이의 `JSR`로 바꾸고, `$FA68/$FA74`의 checked RP2A03 래퍼가 A와 상태 플래그를 보존하면서 뱅크에 `20`을 OR한 뒤 `$5123/$5127`에 쓴다. 헤더·래퍼·store·설정 표·상위 글리프를 합친 24개 Expected Write를 감사하고, 상위 첫 페이지 뒤의 124 KiB가 원본 CHR과 같은지도 검사한다. 이 프로브는 확장 저장·공급 경로만 검증하며 최종 글꼴 배치나 전체 진행 동등성을 선언하지 않는다.

## MMC4 래치 네임테이블 투영

`project-mmc4-latch-nametable`은 실행에서 덤프한 정확히 1 KiB 또는 2 KiB 네임테이블을 받아 한 페이지의 32×30 배경 타일을 제로 스크롤 행 우선 순서로 순회한다. 각 타일에는 현재 FD/FE 래치의 6비트 CHR 뱅크와 원본 속성표의 팔레트 2비트를 결합한다. `FD`·`FE` 트리거 타일 자체는 이전 래치 뱅크를 사용하고, 전환은 다음 타일부터 적용한다. 마지막 64바이트는 화면 개입과 같은 결정적 1 KiB 입력을 만들기 위해 초기 래치 뱅크로 채운다.

같은 순회에서 각 타일이 FD와 FE 가운데 어느 쪽으로 fetch되는지도 집계한다. 보고서는 양쪽의 실제 타일 수와 정렬된 고유 코드 집합을 함께 내므로, 문자·창·배경을 한 네임테이블에 섞어 세지 않고 화면별 한글 작업 집합을 분리할 수 있다. 스프라이트는 이 투영에 포함되지 않으므로 OAM과 PPU `$0000` 공급 페이지를 화면 계약에서 별도로 확인한다.

```sh
cargo run -p fc-fire-emblem-patch -- project-mmc4-latch-nametable \
  path/to/nametable.bin \
  --nametable-index 1 \
  --fd-bank 0 \
  --fe-bank 24 \
  --initial-latch fe \
  --output out/mmc5-exram-attributes.bin \
  --report out/mmc4-latch-nametable.json
```

입력 크기·페이지 인덱스·6비트 뱅크 범위가 맞지 않으면 산출물을 만들지 않는다. 보고서는 원본 바이트 대신 입력·출력 해시, 트리거 개수와 초기·종료 래치만 기록하며 `release_eligible`은 항상 거짓이다. 이 도구는 미세 스크롤, PPU의 선행 타일 fetch, 네임테이블 경계, MMC5 ExRAM의 한 화면 미러링과 스프라이트 CHR을 모델링하지 않는다. 따라서 결과는 런타임 소유·갱신 구현의 입력을 검증하는 개발용 프로브일 뿐 ROM 삽입 자산이 아니다.

`replay-mmc4-latch-ppu-transfers`는 로컬 JSON에 기록한 PPU 전송을 두 물리 네임테이블에 순서대로 적용한다. 입력은 스키마 1, 초기 채움 바이트, 수평·수직 미러링, 선택할 논리 네임테이블, FD/FE 뱅크와 초기 래치, 그리고 각 전송의 14비트 시작 주소·`across`/`down` 증가 방향·16진 데이터로 구성한다. `$3000`~`$3EFF` 미러는 대응 네임테이블로 보내고 패턴·팔레트 주소 쓰기는 투영 입력에서 제외한다.

```sh
cargo run -p fc-fire-emblem-patch -- replay-mmc4-latch-ppu-transfers \
  path/to/ppu-transfers.json \
  --output out/mmc5-exram-transfer-replay.bin \
  --report out/mmc4-latch-transfer-replay.json
```

보고서는 원문 전송 바이트를 복제하지 않고 입력 SHA-1, 전송·데이터·네임테이블 적용 수와 출력 SHA-1만 기록한다. 이 명령은 ROM 갱신 코드와 비교할 호스트 측 의미 기준이며, 제로 스크롤 선택 화면만 투영하므로 자체로 런타임 소유나 스크롤 동등성을 증명하지 않는다.

## MMC5 네임테이블 바이트 훅 기각 프로브

`build-mmc5-nametable-shadow-probe`는 지원 원본의 직접 `STA $2006` 20곳과 `STA $2007` 7곳이 선언한 주소와 정확히 일치할 때만 CHR writer 프로브 위에 훅을 설치한다. PPU 쓰기를 먼저 실행한 뒤 A·X·Y·상태 플래그를 보존하면서 MMC5 PRG RAM 뱅크 1의 `$6800`~`$6FFF`에 두 물리 네임테이블을 모사한다. 새 코드는 typed RP2A03 조립과 Expected Write 감사를 거치며 간접 PPU 쓰기는 닫았다고 선언하지 않는다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mmc5-nametable-shadow-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

이 명령은 채택할 런타임 소유자가 아니라 기각된 시간 설계를 재현하는 개발용 프로브다. 콜드 실행 프레임 301에서 주소 상위·하위 훅은 각각 49회, 데이터 훅은 6,714회 적중했지만 실제 CIRAM과 그림자가 128바이트 갈렸고 화면도 깨졌다. 바이트마다 PRG RAM 뱅크를 바꾸고 상태를 보존하는 비용이 VBlank 전송을 지연시켰으므로 `per_byte_hook_design_eligible`과 `release_eligible`은 항상 거짓이다. 후속 구현은 PPU 큐와 직접 전송 루틴의 경계에서 데이터를 일괄 반영해야 한다.

## MMC5 PPU 큐 일괄 그림자 프로브

`build-mmc5-queue-shadow-probe`는 콜드 실행에서 `$21=1`을 실제 게시한 `0D:$A6B9`, `0D:$AD52`와 기존 합성 텍스트 게시자 `$C8C8`을 원본 바이트에 결속한다. 각 게시자가 준비 플래그를 올리기 전에 `$0781` 큐를 한 번만 순회해 PRG RAM 뱅크 1의 두 물리 네임테이블에 반영한다. 기술자 bit 6은 `$C3D5/$C3D8`의 분기와 인덱스 진행을 따라 한 입력 바이트 반복으로 처리한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mmc5-queue-shadow-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes"
```

공통 소비자 `$C3E7` 안에서 같은 처리를 한 실험은 큐 26회·504바이트를 잡았지만 NMI 시간을 늘려 화면을 더 깨뜨렸으므로 기각했다. 게시 경계 프로브는 프레임 800에서 같은 26회, 명령 31개, 출력·네임테이블 504바이트를 반영하면서 기반 CHR writer 화면 해시를 유지했다. 실제 CIRAM과의 차이는 168바이트이며, 큐를 거치지 않은 직접 화면 초기화·합성 전송이 남았기 때문에 아직 ExRAM 표시나 릴리스 적합성을 주장하지 않는다.

`build-mmc5-dialogue-exram-probe`는 위에서 생성한 정확히 1 KiB 입력 가운데 확인된 오른쪽 FD/FE 뱅크 `00/18`만 허용한다. CHR writer 프로브 위에서 오른쪽 FD·FE 공급 루틴을 같은 길이의 공통 검사 호출로 바꾸고, 두 그림자가 `00/18`이 되는 순간 고정 PRG의 `$FB00`~`$FEFF`에서 MMC5 ExRAM `$5C00`~`$5FFF`로 복사한다. 복사 동안 `$5104=2`, 표시 전에는 `$5104=1`을 쓰며 A·X·상태 플래그를 복원한다. 새 상대 분기는 절대 목표 주소를 받아 signed 8비트 도달 범위를 checked assembler에서 검산한다.

```sh
cargo run -p fc-fire-emblem-patch -- build-mmc5-dialogue-exram-probe \
  "roms/Fire Emblem - Ankoku Ryuu to Hikari no Tsurugi (Japan).nes" \
  out/mmc5-exram-attributes.bin
```

새 코드 두 구간은 원본의 직접 `JSR`·`JMP` 패턴이 0건이고 기대 바이트가 모두 `FF`일 때만 쓴다. 데이터 구간을 가리키는 PRG 전체의 3바이트 패턴 후보는 보고하되 명령 경계로 오인하지 않는다. 이 ROM은 목표 대화 화면의 외부 메모리 주입을 제거하는 전용 프로브다. 정적 1 KiB를 조건 일치 때 다시 적재할 뿐 후속 네임테이블 쓰기, 다른 래치 쌍, 스크롤과 경계 fetch를 갱신하지 않으므로 `release_eligible`은 거짓이다.

## 글꼴 공급 조사

`analyze-font-supply`는 지원 일본판만 입력으로 받아 4 KiB CHR 페이지별 통계, 첫 글꼴 페이지의 256개 코드별 타일 특성, 보호 판정과 확인된 참조를 JSON으로 쓴다. 스키마 3부터 고정 PRG 뱅크의 MMC4 CHR 공급 루틴 4개를 원본 바이트로 검사하고, 각 루틴을 가리키는 직접 `JSR`·`JMP` 바이트 패턴 후보를 PRG 뱅크·PRG 오프셋·파일 오프셋·CPU 주소로 함께 기록한다. 후보는 명령 경계와 실행 적중을 별도로 확인하기 전에는 호출자로 간주하지 않는다. 스키마 4는 확인된 보호 코드 43개와 합성 레이아웃 예약 코드 `0F`, `1F`, `FF`를 제외한 현재 한글 활성 슬롯 상한 210개를 기록한다. 전투 대사에서 쓰이는 `9D = !`는 번역하지 않을 원본 문장부호로 보호하며, `8E = 。`, `AB/AC = 「/」`는 일본어 원문 코드로 분류한다. 이는 미확정 소비자를 모두 닫은 화면별 최종 예산이 아니다. 같은 입력에서 각 코드가 표시된 PNG 타일 시트도 만든다. 두 산출물은 무시된 `out/` 아래에 생성하며 원본 CHR 바이트는 JSON에 복제하지 않는다.

스키마 5는 PRG 뱅크 선택 `$C9A6`과 미러링 비트 선택 `$C9CE/$C9D6`의 원본 바이트를 추가로 검사한다. 또한 PRG 전체에서 `$A000`~`$F000`에 직접 쓰는 `STA`·`STX`·`STY` 3바이트 패턴을 좌표와 함께 열거한다. 이 목록은 매퍼 변환 누락 방지용 후보 상한이며, 데이터 우연 일치가 섞일 수 있으므로 실행 적중이나 디스어셈블 없이 패치 대상으로 삼지 않는다.

스키마 6은 `$B000`~`$E000` 후보 가운데 같은 PRG 뱅크에서 명령 시작 사이가 3~8바이트인 연속 집단을 별도로 묶는다. 이는 반복 레지스터 설정처럼 보이는 위치의 실행 검증 순서를 정하기 위한 하한이며, 단독 후보와 더 멀리 떨어진 실제 코드는 포함하지 않는다. 각 집단은 항상 `candidate_only_runtime_execution_or_disassembly_required`로 남고 자동 패치 입력이 아니다.

조사기는 설정 일본어 표와 상태 능력치 약어 표의 원본 바이트가 기대값과 같을 때만 보고서를 만든다. 숫자 `0`~`9`, 대문자 `A`~`Z`, 상태 표에서 함께 쓰는 `:`·`.`는 원본 표시 보호 대상으로 분류한다. `ED`·`EF`는 확인된 텍스트 제어 코드, `FD`·`FE`는 MMC4 래치 코드로 보호한다.

비어 보이거나 현재 확인된 참조가 없는 타일은 사용 가능으로 분류하지 않는다. 모든 소비 경로를 배제하기 전까지 `unresolved`로 유지하며, 보고서의 `available_font_code_count`는 현재 항상 0이다.

실제 화면별 CHR 그림자 값과 MMC4 공급 경로의 해석은 [렌더 경로 조사](render-paths.md)에 기록한다. 런타임 관측값을 정적 보고서가 임의로 추론하지 않는다.

## 텍스트 표 조사

`analyze-text-tables`는 지원 일본판에서 소비 코드가 확인된 클래스·아이템·아군·적·지형·장소·장 제목 포인터 표 7개를 JSON으로 쓴다. 각 표의 포인터 수, 종료 코드, 공유 포인터, 문자열 범위와 원본 바이트를 보존하고, 정확한 indexed `LDA` 쌍이 해당 표의 하위·상위 포인터 바이트를 읽는지 검사한다.

숫자·대문자는 전역 `protected_original`로 분리한다. 문장부호는 `M.`처럼 기존 라틴 토큰에 붙은 정확한 위치를 원본 바이트로 확인한 경우에만 같은 분류로 보호한다. 나머지 코드는 일본어·제어·레이아웃 판정이 끝날 때까지 `unresolved`이며 자동 번역하지 않는다. 자세한 범위와 현재 증거 한계는 [일본판 텍스트 표 조사](text-tables.md)에 둔다.

스키마 2부터 포인터를 받은 뒤의 복사 루프도 원본 바이트로 검사한다. 보고서의 `transfer`는 원본 포인터, 목적 버퍼, 인식하는 종료 코드, 목적 버퍼에 남는 끝 코드와 그 코드가 원문 복사인지 소비자 합성인지를 구분한다. 아이템 이름처럼 복사 코드에 명시적인 16바이트 상한이 있으면 모든 현재 엔트리가 종료자를 포함해 그 안에 들어오는지도 검사한다.

스키마 3은 사용 코드별 출현 수와 첫 글꼴 페이지의 16바이트 타일 SHA-1·전부 0 여부를 기록한다. 보호하지 않은 바이트는 비공백 타일 또는 공백 타일 후보로 나누되, 다운스트림 렌더러가 코드값을 실제 타일 번호로 소비한다는 증거가 추가되기 전에는 둘 다 `unresolved`를 유지한다. 이 집계는 원문 문자열 덤프를 공개 자료로 승격하지 않는다.

스키마 4는 뱅크 `0B`의 합성 텍스트 파서에서 `0F`·`1F`를 폭 0 결합부호로 처리하는 두 패스와 출력 칸 증가 루틴을 원본 바이트로 검사한다. 전체 7개 표의 출현 수는 참고 집계일 뿐이며, 아직 연결하지 않은 다른 소비자에서도 같은 동작을 한다고 간주하지 않는다.

스키마 5는 합성 텍스트 파서 `$8F39`를 직접 가리키는 절대 `JSR`·`JMP` 바이트 패턴을 PRG 뱅크·PRG 오프셋·파일 오프셋·CPU 주소로 기록한다. CHR 공급 조사와 같은 스캐너를 사용하며, 명령 경계와 호출자 역할을 확인하기 전에는 대사·메뉴 소비자로 승격하지 않는다.

스키마 6은 같은 파서가 `$0451`의 `ED` 종료 세그먼트를 두 번 읽어 `$0311`에 결합부호 오버레이와 기본 문자 출력 세그먼트를 차례로 만드는 구조를 기록한다. 첫 패스가 일반 문자 칸에 생성하는 `FF`는 이 경로의 빈 오버레이이고, `0F`·`1F`는 앞 칸을 대체하는 폭 0 결합부호다. 이 의미를 다른 텍스트 소비자의 원문 `FF`까지 일반화하지 않는다.

스키마 7은 `$0311`을 가리키는 `$06/$07`, 공유 커서 `$0310`, 두 번 호출되는 `$961C` 출력 단계와 `ED`를 `FF`로 바꾸어 `$0701,X`에 쓰는 `$96E7` 루프를 원본 바이트로 검사한다. 이 연결은 2패스 순서가 후속 출력에서 실제로 소비됨을 보이지만, 최종 PPU 전송이나 아직 확인하지 않은 다른 호출자까지 일반화하지 않는다.

스키마 8은 `$0700` 단계 기술자를 `$0781` 명령 큐로 직렬화하는 `$C84E`, 큐 준비 플래그 `$21`을 소비하는 `$C3A5`, `$2006/$2007`에 주소와 코드를 쓰는 `$C3E7` 경로를 원본 바이트로 검사한다. 따라서 확인된 합성 텍스트 경로는 PPU 쓰기까지 연결되지만, 아직 실행 적중을 확인하지 않은 `$8F39` 진입 후보의 화면 역할은 계속 미확정이다.

스키마 9는 직접 `JSR $8F39` 두 곳이 모두 `JMP $8163`으로 이어지는 별도 후처리 계열임을 기록한다. `$8163`은 `$0311`에서 첫 `ED`의 위치를 폭으로 삼고, 그 다음의 기본 문자 평면을 고정 뱅크 복사 루틴 `$C209`로 한 칸 왼쪽에 옮겨 결합부호 평면 바로 뒤에 붙인다. 호출자의 실제 화면 역할은 실행 적중 전까지 붙이지 않는다.

스키마 10은 실제 대사 본문을 뱅크 `0B:$8F39` 메뉴·제목 합성 경로와 분리한다. 뱅크 `0A:$8208` 디스패처와 고정 뱅크 `$E69C` 읽기 루틴, 32바이트 간격인 6개의 SRAM 줄 버퍼 시작 주소, `ED` 줄 종료, 확인된 제어 코드 분기, `$83BA`의 점진적 2평면 렌더링과 `$C842 → $0781` 화면 경로를 원본 바이트로 검사한다. 1장 실행에서 확인한 뱅크 `08:$9FCE → $78B2` 원문 공급과 폭 18의 단계 기술자 `52`도 원문 덤프 없이 구조 관측값으로 기록한다. 제어 코드별 길이와 전체 대사 모집단은 계속 미확정이므로 조사기는 아직 대사 추출 완료를 선언하지 않는다.

스키마 11은 대사 제어 15개의 현재 포인터 진행, 인라인 피연산자 수, 뒤 두 바이트 읽기, 줄 종료 여부와 상태 주소 효과를 고정한다. `E4`·`E6`가 다음 두 바이트를 읽어도 현재 포인터는 제어 하나만 지나가는 경계를 별도로 기록하고, `EC`의 네 SRAM 문자열 선택 표와 `DF`의 니블 기반 상태 비트 선택 루틴까지 원본 바이트로 검사한다. 게임상 의미와 전체 모집단의 유효 값은 구조 증거와 분리해 계속 미확정으로 둔다.

스키마 12는 `E4`·`E6`의 뒤 두 바이트가 다음 줄 문자가 아니라 전환 대상 인자라는 저장 계약을 분리한다. 보고서는 두 제어의 저장 길이 3바이트, 현재 포인터 진행 1바이트, 전환 대상 2바이트를 함께 기록한다. 구조 스캐너와 재삽입기는 현재 실행 포인터의 증가량만 보고 두 인자를 버려서는 안 된다.

스키마 13은 `$C3E7` PPU 큐 소비자의 명령 경계를 기록한다. `$00/$01` 포인터에서 `PPU 주소 상위·하위 바이트`, 기술자, 데이터가 이어지고 첫 바이트 `00`은 종료자다. 기술자의 하위 6비트는 `$C3DD`의 `$2007` 출력 길이이고 비트 7은 PPU 주소 증가 방향을 고른다. 비트 6이 꺼지면 출력마다 입력을 진행하고, 켜지면 한 입력 바이트를 선언 길이만큼 반복한다. 미러링·스크롤·팔레트 사분면 정책은 일반 ExRAM 갱신기에서 별도로 검증한다.

## 대사 진입 표 조사

`analyze-dialogue-structure`는 지원 일본판만 받아 장 인트로·마을/아웃트로·영입·승패·상점/아이템·민가·전투·에필로그 본문·에필로그 라우팅의 대사 진입 표 9개를 검사한다. 보고서는 표 주소·포인터 수·표 SHA-1·진입 주소·별칭만 기록하며 대사 원문 바이트나 번역문은 기록하지 않는다.

각 포인터 표가 선언한 PRG 뱅크 안에 완전히 들어가는지, 각 일반 진입점이 같은 뱅크의 선언된 데이터 시작 이후를 가리키는지 검사한다. 주 대사 디렉터리에 연결된 8개 표는 선택자의 상위 니블을 원문 뱅크로, 하위 니블을 `$BFE0` 디렉터리 그룹으로 해석해 실제 루트 포인터까지 확인한다. 에필로그 라우팅 표는 `04:$BFE2 → $B96C` 루트뿐 아니라 `04:$A17E`의 선택자 `41`·엔트리 선택 코드도 함께 고정한다. 별도 경로인 전투 대사 표는 뱅크 `04:$8000` 로더가 `$7935/$7936`으로 표 집합과 엔트리를 고르고 `$802D` 루트에서 `$845B` 표를 찾아 `$76/$77`에 넣는 명령까지 별도로 검사한다.

고정 뱅크 처리 루틴을 가리키는 값이 필요해지면 주소와 원본 명령 바이트를 표별 허용 목록에 함께 선언해야 한다. 선언하지 않은 교차 뱅크 포인터, 달라진 처리 루틴, 표 범위 이탈은 모두 거부한다. 이 단계는 진입점 모집단을 확정하는 조사이며, 외부 레코드 상태 기계와 각 엔트리의 끝을 확인하기 전에는 대사 길이·내용 해시·번역 준비 상태를 추정하지 않는다.

스키마 2는 뱅크 `0A:$8000`이 `$77F7` 상태값으로 18개 처리자를 고르는 디스패처를 원본 명령과 처리자 표 SHA-1로 고정한다. 그중 대사 원문 진입부는 선택적인 6바이트 `E5` 프리픽스, 항상 존재하는 4바이트 레코드 헤더, 선택적인 6바이트 `E8` 프리픽스 순서다. 주 디렉터리의 고유 대사 진입점 504개마다 이 세 구간과 첫 줄 시작 파일 오프셋을 기록한다. 영입 표의 네 엔트리가 공유하는 `$AA2B`와 에필로그 라우팅 표의 두 엔트리가 공유하는 `$C73D`는 원본 실행 코드가 정확히 일치할 때만 비대사 처리자로 분리한다. 상태 처리자 10개의 상세 의미와 엔트리 종료 규칙은 계속 미확정이며, 보고서는 첫 줄 이후의 원문을 읽거나 출력하지 않는다.

스키마 3은 504개 주 대사 진입점의 첫 줄을 공통 15개 제어 계약으로 전수 검사한다. 리터럴·제어·인라인 피연산자·`E4/E6` 전환 대상의 길이를 분리하고, `EC` 피연산자는 `0`~`3`, `DF` 하위 니블은 `0`~`7`만 허용한다. `E4/E6`의 선택자와 인덱스는 선언된 주 대사 표 범위에 들어가야 한다. 보고서에는 첫 줄 위치·저장 길이·현재 포인터 진행·제어 개수·SHA-1만 기록하고 원문 바이트는 기록하지 않는다. 리터럴에서 확인된 숫자·대문자 코드도 번역하지 않는 원문 보호 수량으로 별도 집계한다.

스키마 4는 각 진입점에서 `ED`·`EE`·`EB` 뒤의 다음 줄을 계속 읽고, `EF` 종료, `E7` 호출자 인계, `E4/E6` 명시 전이 중 하나를 처음 만날 때 선형 구간을 닫는다. 구간은 최대 64줄 안에 경계를 만나야 하며 `E4/E6` 대상은 선언된 주 대사 표와 인덱스 범위를 다시 검사한다. 공개 보고서에는 줄별 위치·길이·해시·제어 통계와 구간 경계만 기록하고 원문 바이트는 넣지 않는다. 이 단계는 경계까지의 연속 저장을 증명할 뿐, `E7/E4/E6` 뒤의 전체 제어 흐름이나 도달 가능성을 증명하지 않는다.

스키마 5는 별칭을 같은 저장 노드로 정규화하고 `E4/E6` 대상 인덱스를 실제 대사 진입점에 결속한다. 코드 처리자를 향하거나 존재하지 않는 노드로 가는 간선, 대상 없는 전이, 지원하지 않는 경계와 순환은 모두 보고서 생성을 거부한다. 각 노드가 `EF` 종료 또는 `E7` 호출자 인계 경계에 도달하는지 검사하고 최대 전이 단계도 기록한다. 간선 보고서는 표·엔트리·포인터·파일 오프셋만 포함하며 원문은 포함하지 않는다.

스키마 6은 `E7`의 일반 구조를 특정 게임상 선택지와 분리한다. 디코더가 `$7808`을 올리면 후속 상태가 `$7809` 호출자 플래그를 올리고 상태 17로 간다. 상태 17은 고정 뱅크 `$E6B2`로 현재 `$77F4/$77F1` 선택을 다시 결속하고 `$7808/$7809`를 지운 뒤 상태 9에서 재개한다. PRG 전체의 정확한 `LDA $7809` 패턴 5곳도 좌표로 고정한다. 각 호출자가 이를 선택지·에필로그 진행 등 어떤 결과에 쓰는지는 이 공통 구조 계약에 섞지 않는다.

스키마 7은 에필로그 호출자가 조건에 따라 선택자 `40`과 `41`을 나누는 원본 명령, `04:$BFE2 → $B96C` 디렉터리 루트와 54개 포인터를 결속한다. 선택자 `41` 표의 고유 스크립트 52개는 모두 `E8` 프리픽스를 거쳐 한 줄의 `E4` 전환으로 선택자 `40` 엔트리 0에 합류한다. 두 엔트리가 가리키는 `$C73D`는 한 바이트 `RTS` 처리자로 분리한다. 이 구조만으로 각 조건의 게임상 의미를 이름 붙이지 않는다.

스키마 8은 `$7809`를 읽는 처리자가 외부 `$C34C` 상태 디스패처에서 직접 선택되는 경우를 분리한다. 다섯 관측 처리자 중 네 개가 11개 처리자 표의 22개 상태 슬롯에 결속되며, 각 디스패처 명령·상태 주소·처리자 표 전체를 검사한다. 뱅크 `04:$A20F` 처리자는 직접 결속을 아직 찾지 못했고, 이 목록은 간접 포인터나 동적 호출이 없음을 증명하지 않는다. 따라서 코드 관측 지점 5개를 게임상 선택지 5개로 환산하지 않는다.

스키마 9는 주 대사 고유 엔트리 504개마다 포인터가 가리키는 레코드 시작부터 프리픽스와 첫 `EF/E7/E4/E6` 경계까지 실제로 소비되는 저장 범위를 닫는다. `E4/E6`의 대상 두 바이트도 범위와 해시에 포함한다. 레코드별 소비량 합계는 39,642바이트지만 실제 고유 저장은 39,425바이트이며, 6쌍이 217바이트를 공유하고 최대 중첩 깊이는 2다. 따라서 포인터 엔트리를 곧바로 독립 재삽입 단위로 보지 않고, 공유 구간을 한 번만 소유하는 배치 계약을 먼저 만들어야 한다. 전투 대사는 별도 형식이므로 이 범위 계산에서 제외한다.

`extract-main-dialogue-source`는 겹치거나 맞닿은 주 대사 범위를 PRG 뱅크별 단일 소유 구간으로 정규화해 무시된 `private/dialogue/main-source.json`에 쓴다. 현재 원본에서는 504개 레코드가 겹치지 않는 11개 구간, 39,425바이트로 정규화된다. 형식 2는 별칭을 포함한 포인터 쓰기 위치 517곳도 각 레코드에 결속한다. `verify-main-dialogue-source-roundtrip`은 이 자산이 지원 일본판에서 다시 계산한 구조·바이트와 완전히 같은지 검사하고, 11개 구간을 중복 쓰기 없이 재구성한 ROM이 원본 SHA-1과 일치할 때만 `out/`에 기록한다. 이 자산의 목적은 `exact_source_roundtrip_only`이며 번역 바이트 입력은 허용하지 않는다.

스키마 10은 일본판 글꼴과 확인된 설정·단위 UI·전투·엔딩 문자열을 기준으로 `00`~`5F`의 가나·결합부호·일본어 문장부호, `84`~`8B`의 작은 가나, `A6`~`AA`의 작은 가타카나 모음과 `8E = 。`, `AB/AC = 「/」`를 일본어 리터럴로 분류한다. 숫자·대문자 `60`~`83`, 보존 문장부호 `9D = !`와 그 밖의 기호는 비일본어 리터럴로 유지한다. 주 대사 선형 구간의 참조 수는 일본어 28,196바이트·비일본어 2,766바이트이고, 공유를 한 번만 센 고유 저장은 각각 28,048바이트·2,745바이트다. 같은 바이트를 한 엔트리는 일본어 리터럴, 다른 엔트리는 구조로 읽는 충돌 16바이트를 제외하면 안전한 일본어 번역 원천은 28,032바이트다. 리터럴 종류 충돌은 0개다. 작업공간 생성기는 이 수를 별도 상수로 복제하지 않고 대사 구조 분석 결과와 교차검증한다.

스키마 11은 뱅크 `04:$7937`의 9상태 전투 대사 처리기를 별도 문법으로 결속한다. 상태 1은 4바이트 헤더를 소비하고 상태 2는 `EC` 뒤 선택자 한 바이트 `00..03`을 동적 값으로 확장하며 첫 `EF`에서 레코드를 끝낸다. 65포인터의 고유 대상 28개는 1,152바이트의 겹치지 않는 범위다. 물리 데이터 구간에는 포인터가 없는 16바이트 레코드가 하나 더 있으므로 이를 번역 대상으로 추정하지 않고 원형 보존한다. 코드 구간은 고정 SHA-1과 typed RP2A03 명령 경계로 함께 검사한다.

`extract-main-dialogue-workspace`는 이 분류를 이용해 무시된 `private/dialogue/main-workspace.json`에 504개 레코드·2,732줄의 번역 골격을 만든다. 레코드와 줄에는 원본 위치가 바뀌어도 유지할 안정 ID를 붙인다. 일본어 코드는 문자로 풀고 숫자·대문자는 원문 그대로 두며, 공백·미확정 기호·제어와 피연산자는 수정되지 않도록 중괄호 토큰으로 표시한다. 각 줄에는 원문 저장 SHA-1, `untranslated` 상태와 빈 `korean` 필드가 있다. 구조와 겹치는 16바이트가 포함된 6개 줄은 `requires_relocation: true`로 표시하며 재배치 계약 전에는 재삽입할 수 없다. 이 작업 자산 자체는 공개 보고서나 Git에 넣지 않는다.

`validate-main-dialogue-workspace`는 작업 골격을 지원 일본판에서 다시 추출한 값과 대조한다. 원본 결속 필드가 달라지거나, 상태와 `korean` 필드가 모순되거나, 제어 토큰·피연산자·기존 영문·숫자가 추가·삭제·변경되거나, 번역 필드에 일본어가 남으면 실패한다. 이 단계는 한글 문자열을 논리 글리프로 검사할 뿐 코드 배정이나 ROM 쓰기는 하지 않는다.

`plan-main-dialogue-reinsertion`은 검증된 작업 골격의 채워진 줄을 글리프당 1바이트인 논리열로 만들고, 원본에서 소유가 증명된 11개 구간 안에서만 레코드를 다시 배치한다. 바뀌지 않은 공유 꼬리는 한 번만 두고, 번역으로 달라진 공유 레코드는 분리한다. 각 레코드의 새 뱅크 내 포인터와 원본 포인터 표 쓰기 위치를 `out/main-dialogue-layout.json`에 기록하며, 어느 구간이든 용량을 넘으면 보고서를 쓰기 전에 실패한다. 미완료 줄을 포함한 계획은 개발용이며, 모든 줄이 완료돼도 한글 코드 배정·줄 폭·화면별 글리프 예산·매퍼 변환·실행 표시를 아직 통과하지 않았으므로 배포 가능 판정은 항상 거짓이다. 보고서에는 원문이나 번역문을 넣지 않는다.
