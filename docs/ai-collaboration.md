# AI 협업으로 이 패치를 만든 방식

원래 제작 자료가 없는 오래된 게임을 분석해 한글패치를 만드는 동안, 사람은 어떤 문제를 전체 작업의 걸림돌로 보았고 어떤 지시로 흐름을 바꿨을까. 이 문서는 그 판단을 기록한다.

개발 작업을 이어가기 위한 안내서가 아니라, 프로젝트를 모르는 독자도 사람과 코딩 에이전트가 긴 작업을 어떻게 나눴는지 읽을 수 있게 쓴 공개 사례 기록이다.

세부 기술 결정과 당시의 개발 상태는 별도 기록에 남아 있다. 여기서는 이 글만으로도 흐름을 이해하도록 각 결정이 어떤 사람의 개입에서 나왔는지에 초점을 맞춘다.

작업은 두 시기로 나뉜다. 8월 15일까지는 번역 범위와 검증 원칙을 세우고 기술적으로 가능한 길을 찾았다. 그 뒤 급격히 불어난 코드와 반복되는 화면 결함을 정리한 다음 하나의 결과물을 끝까지 검증해 8월 24일 `0.1.0` 패치를 배포했다. 앞 시기의 기록과 인용은 당시 범위를 유지하고 후반부에는 배포까지의 별도 국면을 이었다.

## 핵심

사람은 구현 방법을 세세하게 지시하지 않았다. 대신 전체 결과를 바꾸거나 되돌리기 어려운 판단을 맡았다. 에이전트는 그 판단 안에서 조사·설계·구현·검증을 진행했다.

최종 결과는 실제로 적용 가능한 한글 패치였다. 에이전트가 많은 코드를 썼다는 사실만으로 이 결론에 이른 것은 아니다. 사람은 작은 성공을 전체 성공으로 부르지 못하게 했다. 잘못된 증거를 버리고 어디까지 확인했는지도 거듭 정했다. 이런 판단도 같은 비중으로 작용했다.

작업은 대체로 다음 순서로 굴러갔다.

1. 사람이 목표, 번역 범위, 보존 대상, 완료 조건을 정했다.
2. 에이전트가 당시 프로그램, 작업 기록, 만들어진 패치 파일, 실제 실행 결과를 확인했다.
3. 전체 완료를 막는 가장 가까운 조건을 골라 설계하고 구현했다.
4. 같은 패치 파일이 실제 게임 화면과 동작까지 제대로 이어지는지, 어디까지 확인했는지를 검증했다.
5. 사람은 의미·화면·우선순위를 판단하고 틀린 전제가 드러나면 그 위의 결과를 폐기했다.

“사람의 입력이 적었다”는 사실 자체는 성공 조건이 아니다. 범위, 완료 기준, 작업 순서, 폐기 판단처럼 결과 전체를 바꾸는 지점에 개입했는지가 중요했다.

### 사람이 끝까지 맡은 네 가지

사람이 끝까지 놓지 않은 것은 넷이다.

1. **번역 범위의 정의** — 무엇을 번역하고 무엇을 원본 그대로 두는가
2. **완료의 기준** — 무엇을 증명해야 "됐다"고 부를 수 있는가
3. **작업 순서** — 지금 무엇부터 깨야 하는가
4. **폐기 판단** — 틀린 경로를 언제 버리는가

게임 데이터가 어디에서 어떻게 쓰이는지 찾는 일은 에이전트의 몫이었다. 제한된 저장 공간을 나누고 한글을 저장 값과 연결하며 결과를 검사하는 일도 마찬가지였다.

사람은 게임 데이터의 정확한 위치나 게임기가 실행할 명령까지 지정하지 않았다. 세부 구현은 에이전트가 제안했고 사람은 목표에 맞는지, 그 결과를 받아들일지 판단했다. 이를 확인한 집계는 글 끝에 따로 둔다.

## 기술 용어를 몰라도 읽는 법

| 용어 | 이 글에서의 뜻 |
|---|---|
| ROM | 게임 데이터 전체를 담은 파일 |
| 뱅크·페이지 | 오래된 게임기가 필요한 데이터만 골라 불러오기 위해 나눈 구역 |
| 매퍼·MMC5 | 카트리지가 그 데이터 구역을 전환하는 방식 |
| 글리프·코드북 | 화면에 보이는 글자 모양과, 글자를 저장 값에 연결하는 대응표 |
| 정적 분석·동적 분석 | 게임을 실행하지 않고 코드와 데이터를 조사하는 방법, 실제로 실행해 확인하는 방법 |
| 런타임 검증 | 패치를 실제로 실행해 화면과 동작을 확인하는 과정 |
| 빌드·산출물 | 원본 게임에 변경 사항을 적용해 패치된 파일을 만드는 과정, 그렇게 만들어진 결과물 |
| 동결 후보 | 조사하는 동안 내용이 바뀌지 않도록 고정한 하나의 패치 결과물 |
| SaveRAM·세이브 스테이트 | 게임이 정상적으로 저장한 진행 기록, 게임기 전체 상태를 한순간에 복사한 기록 |
| BPS | 원본 게임 파일 없이 변경분만 전달하는 패치 파일 형식 |
| 실용 배포·형식적 완료 | 보통의 플레이와 배포에 필요한 범위를 통과한 상태, 가능한 모든 경로를 빠짐없이 증명한 상태 |
| 커밋·`.gitignore` | 작업 단위를 버전 기록에 남기는 것, 공개 기록에서 제외할 파일을 지정하는 목록 |
| 갓파일 | 서로 다른 역할이 한 파일에 너무 많이 몰린 상태 |
| 드리프트 | 새 사실이 나올 때마다 처음 정한 방향이나 설계가 흔들리는 현상 |

도구 이름과 파일명, 수치는 당시 판단의 근거라서 전문에 그대로 남겼다. 정확한 작동 원리를 몰라도 괜찮다. 각 사례에서 무엇이 문제였는지, 사람이 왜 개입했는지, 그 뒤 무엇이 달라졌는지만 따라가면 된다.

## 전반부: 범위와 원칙을 세우다

앞의 여섯 국면에서는 번역 범위, 관찰 방법, 도구와 공개 자료의 경계를 세웠다. 7~10번에서는 작은 성공에 머무르지 않고 가장 어려운 경우와 전체 완료 기준을 붙잡았다. 마지막 세 국면에서는 번역 품질, 검증 방법, 에이전트의 자율 범위를 조정했다.

### 2. 버튼을 누르기 전에 무엇을 확인할지 정하다 (08-07)

에이전트가 에뮬레이터에서 버튼을 눌러가며 화면 변화를 관찰하고 있었다. 진행은 되지만 무엇을 확인 중인지가 불명확했다.

결과가 나와도 이유를 모르는 시행착오는 다시 재현되지 않는다. 이 게임에는 깜빡이는 화면 요소도 있어서 확인할 순간을 잘못 잡으면 없는 결함을 보고하거나 있는 결함을 놓친다.

> **08-07 09:16** 조작과 관련해서 알게된 사실 등은 계속 지속적으로 문서화하면서 쭉 해

### 3. 쓰는 쪽의 편의 때문에 원본 도구를 함부로 고치지 않다 (08-07)

> **08-07 09:58** 지금 저 사이드이펙트가 뭘 일으킬줄알고 저 수정을 일으킨거야? 우선 대기해
>
> **08-07 10:02** emucap은 여기가 원천으로 관리되는 프로젝트인데 소비자가 드리프트가 걸린다고 생산자의 철학 이해 없이 수정해버리면 어떻게함? 일단 지금 수정분 리뷰를 진행중이니 액션은 말고

### 19. 도달한 화면과 정상 플레이를 같은 증거로 부르지 않다 (08-23)

대신 현재 후보를 처음부터 실행하고 게임이 읽을 수 있는 SaveRAM을 불러온 뒤, 왕좌까지 가는 좌표처럼 도달에 필요한 조건만 제한해서 바꿨다. 그 뒤의 승리 명령, 저장, 전원 종료 안내, 사운드 테스트와 엔딩 진행은 게임 자체가 만들게 했다. 확인 결과 영문 오프닝과 제작진 표기는 보존됐고 한국어 장 기록과 인물 후일담은 마지막 화면까지 이어졌다.

증명 범위도 좁게 적었다. 엔딩 화면과 그 소비 경로는 확인했지만 11장을 자연스럽게 완료했다거나 게임 난이도가 정상이라는 증거는 아니었다. 사망 장면 역시 체력과 위치를 조정해 도달했으므로 대사, 게임 오버, 명단 이탈과 저장 뒤 지속성만 확인한 것으로 남겼다.

저장도 만드는 쪽과 읽는 쪽을 따로 확인했다. 게임 명령으로 다음 장의 SaveRAM을 만든 뒤 게임을 완전히 껐다 켠 별도 실행에서 그 파일만 넣어 일반 불러오기 화면과 다음 장 진입을 확인했다. “저장 화면을 봤다”와 “그 저장을 나중에 읽을 수 있다”를 다른 사실로 취급했다.

### 20. 전수 증명과 실제 배포를 분리하다 (08-24)

기술적으로 더 확인할 수 있는 항목은 남아 있었다. 게임 안에서 가능한 모든 희귀 분기와 모든 데이터 전환 경로를 빠짐없이 증명하려면 작업은 훨씬 더 길어질 수 있었다. 사람은 이 지점에서 제품의 완료 기준을 다시 정했다.

> **08-24 02:08** 게임 플레이에 문제가 없는게 충분하지 우리는 학술을 하려는것까진 아니니 과검증은 안해도 됨

검증 자체를 그만둔 것은 아니었다. 보통의 플레이, 저장과 진행, 알려진 불리한 경계, 패치 적용 결과는 배포 전 필수로 남겼다. 모든 희귀 사망·영입 분기, 프로그램 전체의 형식적 분석, 실제 기기 시험은 “완료하지 않았지만 현재 배포를 막지는 않는 범위”로 따로 적었다.

배포 방식에도 사람이 직접 개입했다.

> **08-24 02:22** README는 사람이 보는 쪽이니까 bps 파일 업로드 하고 롬 해시랑 패치적용방법 공유하자. 형태는 publication쪽 참고하고 버전은 0.1.0
>
> **08-24 02:29** 헤더 미포함도 우리가 지원가능하지 않아? no intro 기준으로 해서
>

>
> **08-24 02:32** 그리고 Mesen을 강요할 필요는 없다고 봄. 그냥 저건 사용자가 알아서 할 문제고 너무 TMI야

그래서 원본 파일의 두 흔한 형태에 맞춘 BPS 두 개가 만들어졌다. 입력 형식은 다르지만 적용 뒤에는 같은 한글판이 된다. 제작 도구는 패치를 만든 뒤 스스로 다시 적용해 승인한 결과물과 한 바이트도 다르지 않은지 확인했다. 공개 자료에는 패치 적용법과 원본 확인값, 몇 장의 화면만 남기고 특정 에뮬레이터를 강요하는 긴 설명은 뺐다.

큰 방향이 일관됐다고 모든 선택이 처음부터 같았던 것은 아니다. 소스 코드 라이선스는 GPL 3 계열에서 GPL 2 계열을 거쳐 최종적으로 MIT로 바뀌었다. 번역 검토의 승인선도 작업 도중 더 구체화됐다. 이런 변경은 처음부터 그랬던 것처럼 덮지 않고 사람이 실제로 바꾼 제품 결정과 계속 유지된 원칙을 구분했다.

## 끝까지 갔을 때의 결과

프로젝트는 2026년 8월 6일 시작해 8월 24일 `0.1.0` 배포에 도달했다. Git에는 551개 커밋이 남았고 최종 조사 시점의 Rust 코드는 495개 파일, 약 17만 줄이었다. 자동 검사는 1,092개가 통과했고 에뮬레이터 실행 기록은 260개였다.

숫자는 규모를 보여 줄 뿐 성공 횟수를 뜻하지 않는다. 1,092개의 빠른 검사는 게임을 실제로 끝까지 플레이한 증거가 아니며 260개의 실행도 260개 기능이 통과했다는 뜻이 아니다. 이 프로젝트는 끝까지 제작 검사, 실제 실행, 사람의 화면 판단과 공개 배포를 서로 다른 결과로 기록했다.

최종 제작 과정은 14개 영역에서 미리 선언한 변경 821개를 한 결과물에 모았다. 원본 값, 변경 범위와 겹침을 확인한 뒤에만 패치 파일을 만들었다. 시작과 저장, 유닛과 시설, 전투와 사망, 후반과 엔딩의 네 실용 묶음도 같은 최종 후보에서 통과했다. 원본 ROM과 완성 ROM, 대규모 번역 자료, SaveRAM과 내부 검증 화면은 공개하지 않고 BPS와 사용 설명만 배포했다.

남은 한계도 있다. 가능한 39개 역할을 모두 묶은 실행 기록, 프로그램 전체의 데이터 전환 경로 증명, 모든 희귀 분기의 자연 도달과 실제 패미컴 기기 시험은 완료하지 않았다. 최종 배포 화면을 확인한 두 실행은 대화 기록과 이미지에는 남았지만 현재 실행 원장에서는 다시 찾지 못했다. 배포 결과 자체와 별개로 증거 기록의 연결은 더 나아질 여지가 있다.

별도 회고 자료에 전문을 실은 사용자 발화는 이 412건 가운데 방향을 잘 보여 주는 106건이다. 자동으로 끼어든 내용과 중복을 제외하고 시각과 본문을 원문 그대로 대조한 선별본이다. 106건은 전체 발화와 별도의 숫자가 아니라 412건에 포함되는 일부다.

## 사람이 실제로 한 일

약 18일간 412번의 입력과 551개 커밋이 남았다. 이 과정에서 사람은 다섯 가지를 맡았다.

1. **범위와 완료 기준을 정했다.** 무엇을 번역하고 무엇을 남길지, 무엇을 증명해야 "됐다"고 부를지 결정했다.
2. **눈앞의 문제만 고치는 흐름을 끊었다.** 같은 증상을 계속 손보게 되면 전체 설계로 돌려보냈다.
3. **가장 어려운 조건부터 확인하게 했다.** 쉬운 성공을 쌓는 것만으로 전체가 성공하지는 않는다고 계속 상기시켰다.
4. **원작에서 얻은 정보를 보탰다.** 정상 화면이 무엇인지, 어떤 용어가 공식인지는 사람만 알았다.
5. **틀린 경로를 버리게 했다.** 이미 들인 시간을 이유로 잘못된 전제를 남기지 않았다.

하지 않은 일도 분명하다. 412건 어디에도 게임 내부의 16진 주소, 구체적인 뱅크 번호, 어셈블리 명령이나 함수명을 지정해 고치라고 한 지시는 없다. 게임 내부를 고치는 방법은 전부 에이전트가 설계했다. 사람은 그 설계를 받아들일지 되돌릴지만 정했다.

다섯 역할은 배포까지 유지됐다. 후반부에는 같은 기준이 복잡해진 코드와 반복 결함 속에서 구체적인 작업 방식으로 굳어졌다.

커밋도 같은 기간의 저장소 전체 기록을 셌다. 게임을 고친 커밋뿐 아니라 공개 범위 점검과 이 글을 처음 작성한 커밋도 들어 있다.

- 사람이 직접 입력한 발화: **412건**
- 기간: 2026-08-06 20:24 ~ 2026-08-24 02:35 (KST, 약 18일)
- 같은 기간 저장소 커밋: **551개**

인용은 원문을 유지했다. 다만 공개를 전제로 표현이 거친 몇 곳만 뜻을 바꾸지 않는 선에서 다듬고 `(표현 완화)`로 표시했다. 시각은 KST다. 대화 기록의 UTC 시각을 변환했기 때문에 커밋 시각과 직접 대조된다.

### 게임 내부 구현을 지정한 지시는 0건이었다

입력 412건 전체를 패턴으로 훑고 문맥을 다시 확인한 결과다.

| 무엇을 찾았나 | 건수 |
|---|---:|
| 게임 내부의 16진 주소 (`$XXXX`, `0x…`) 지정 | **0** |
| 구체적인 뱅크·페이지 선택값 지정 | **0** |
| 게임기가 실행하는 명령 이름 (`LDA`, `STA`, `JSR` …) 지정 | **0** |
| 게임 내부 소스의 파일명·함수명·타입명 지목 | **0** |
| 게임 내부 자료구조·비트·버퍼 설계 지시 | **0** |

사람은 ROM의 어느 주소에 무엇을 쓸지, 뱅크를 어떻게 나눌지, 코드북을 어떤 자료구조로 만들지를 한 번도 지시하지 않았다. 관련 논의는 있었지만 구체적인 방법은 에이전트가 제안했고 사람은 방향과 수용 여부를 판단했다.

가장 구체적인 기술 지시는 도구 사용법에 관한 것이었다.

- 도구 선택 — `emucap으로 원본롬 한번 띄워봐`, `imagen 써서 진행`, `filter-repo 정도면 충분해`
- 관측 파라미터 — `800프레임정도 돌려봐`, `200스텝 더`
- 작업 구조 — 조사와 빌드, 테스트, CLI와 Python의 책임을 나눌 것
- 412건 중 바이트 수가 등장하는 유일한 발화 (08-15 11:03) — `파일에 저장해두고 write memory를 그 파일을 전달하는게 맞지 않아? 매번 8192바이트를 갖다 쌩으로 집어넣기보단?`

후반에는 바이너리 서치와 파이프라이닝을 예로 들거나, 중복 상수와 모듈 소유권을 문제 삼는 기술적 제안도 있었다. 그러나 어느 것도 게임 내부 주소·명령·함수의 해답을 지정하지 않았다. 마지막 바이트 발화 역시 8 KiB 저장 데이터를 도구에 더 효율적으로 넘기자는 지적이다.

`MMC5`는 두 번 나오지만 둘 다 파일을 어디에 둘지에 관한 말이었다. 14페이지라는 수치는 에이전트가 설명한 문제를 사람이 자기 말로 확인한 질문에 등장한다. 기술 내용을 언급하기는 했어도 내부 구현 지시로 세지는 않았다. “기술 지시 0건”은 기술 이야기가 없었다는 뜻이 아니라, 게임 내부의 구체적인 해법을 사람이 대신 설계하지 않았다는 뜻이다.

## 이 사례가 남긴 협업 방식

이 프로젝트에서 사람은 게임 내부의 주소나 명령을 설계하지 않았다. 대신 무엇을 번역할지, 어떤 실패를 전체 문제로 볼지, 잘못된 증거를 언제 버릴지, 어느 범위를 통과하면 실제 사용자에게 내놓을지를 결정했다. 에이전트는 그 기준 안에서 원본을 조사하고 코드를 만들고 반복 검사를 수행했다.

효과가 컸던 것은 답을 알려 준 말보다 작업의 단위를 바꾼 말이었다. 한 화면에 매달리지 않고 같은 원인을 찾기, 한 결과물에서 실패를 먼저 모으기, 조사와 생산을 나누기, 잘못된 입력은 시스템이 거부하게 만들기가 실제 제작 방식을 바꿨다.

그렇다고 사람의 개입이 적어도 된다는 뜻은 아니다. 짧은 승인 사이에도 전체 목표를 다시 세우는 판단이 계속 필요했다. 좋은 분업에서는 사람이 맡을 판단과 에이전트가 맡을 실행이 분명하고 두 역할이 같은 결과물을 근거로 서로를 교정한다.
