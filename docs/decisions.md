# 의사결정 흐름

이 문서는 세부 구현 이력이 아니라 한글화의 대전략이 어떻게 바뀌었는지를 기록한다. 현재 진행 상황은 [현재 상태](status.md), 기술 근거는 [초기 조사](initial-survey.md)와 [텍스트 표 조사](text-tables.md), 앞으로의 통과 조건은 [작업 로드맵](roadmap.md)에 둔다.

## 1. 일본판을 기준으로 일본어만 번역한다

처음부터 제품 기준은 지원 해시가 확인된 일본판 한 리비전으로 정했다. 일본판에 원래 들어 있는 영어·숫자·로마자 약어는 번역하지 않고 보존한다. 영문 패치는 구조를 교차 확인하는 참고 자료일 뿐 번역 원문이나 빌드 입력이 아니다.

## 2. 작은 한글 표시 PoC로 가능성을 먼저 확인했다

설정 항목 3개와 일부 가나 타일만 바꾸는 PoC로 NES 화면에 한글을 넣을 수 있음을 확인했다. 기존 영어 타일은 정적으로 보존했지만 설정 화면 자체에는 영어가 없으므로 한글과 원본 영어의 동시 실행 표시는 아직 별도 관문이다. 이 방식은 기술 확인용이며 전체 번역 방식으로 확대하지 않기로 했다.

## 3. 고정 타일 치환에서 동적 글꼴 구조로 방향을 바꿨다

원본 CHR-ROM은 대부분 사용 중이고, 화면마다 글꼴과 그래픽 페이지의 조합도 달랐다. 따라서 가나 타일을 계속 덮어쓰거나 완성형 한글을 한 페이지에 상주시키는 전략을 포기했다.

현재의 주 전략은 확장 ROM에 한글 글리프를 저장하고 화면별로 필요한 글리프만 CHR-RAM에 적재하는 것이다. 이를 위해 원본 그래픽과 진행을 그대로 보존하는 매퍼 변환을 먼저 증명해야 한다.

## 4. 번역 확대보다 텍스트·렌더 구조 확정을 앞세웠다

전체 대사를 바로 추출·번역하기보다, 먼저 어떤 문자열이 어떤 소비자·종료 코드·조판 규칙·글꼴 공급 경로를 쓰는지 조사하기로 했다. 원문 바이트 수와 화면 폭이 같지 않고 같은 제어 코드도 경로마다 동작이 다르다는 사실이 확인됐기 때문이다.

따라서 현재는 보호할 기존 영어와 화면별 한글 슬롯 예산을 확정하는 단계다. 이 관문과 동적 글꼴 실증을 통과하기 전에는 PoC 번역 범위를 넓히지 않는다.

## 5. CHR-RAM 고정안에서 확장 CHR 공급 비교로 넓혔다

MMC5 실험에서 원본 CHR을 보존한 채 확장 영역의 글리프를 실제 화면에 공급할 수 있음을 확인했다. 따라서 정식 글꼴을 반드시 CHR-RAM 업로드로만 구현한다고 미리 고정하지 않고, 확장 CHR-ROM 페이지 선택과 함께 비교하기로 했다.

다만 매퍼 쓰기 경로가 아직 모두 보존되지 않아 전체 진행 동등성은 통과하지 않았다. 먼저 원본 그래픽·진행을 닫고, 실제 화면 전환과 글리프 작업 집합에 더 잘 맞는 공급 방식을 그 뒤에 선택한다.

## 6. 바이트별 네임테이블 동기화에서 전송 단위 일괄 반영으로 바꿨다

모든 직접 PPU 주소·데이터 쓰기를 가로채 그림자를 한 바이트씩 갱신하는 경로를 실행해 보니, 훅 자체는 적중했지만 추가 사이클이 VBlank 전송 시간을 넘겨 화면과 실제 네임테이블을 깨뜨렸다. 따라서 바이트별 동기화는 채택하지 않는다.

앞으로는 원본이 이미 묶어서 처리하는 PPU 큐와 화면별 전송 루틴의 경계에서 그림자와 ExRAM 갱신을 일괄 수행한다. 의미 기준은 기존의 두 물리 네임테이블 모델을 유지하되, 실행 코드는 프레임 시간 예산을 함께 통과해야 한다.

## 7. 화면 상태를 재구성하기보다 원본 래치를 보존하는 매퍼로 옮겼다

MMC5는 한글 저장 공간을 늘릴 수 있었지만, 원본 래치 결과를 유지하려면 모든 화면 갱신과 스크롤을 새 구조가 소유해야 했다. 실행 경로가 커질수록 원본 시간 예산과 화면 동등성을 함께 지키기 어려웠다.

그래서 원본의 래치 동작과 저장 구조를 더 직접 보존하는 매퍼를 우선하기로 했다. 이 판단이 mapper 165의 화면·저장·진행 동등성 비교로 이어졌다.

## 8. mapper 165 동등성을 닫고 동적 한글로 넘어간다

mapper 165에서 화면별 래치, 전투와 패배, 중단 저장, 1장 완료 저장, 전원 재인가 뒤 불러오기와 2장 전환을 원본과 비교했다. 이 범위의 변환 동등성이 통과했으므로 mapper 165를 주 경로로 채택한다.

이제 매퍼 후보를 더 넓히지 않고, 전체 글리프는 확장 ROM에 두되 화면별 작업 집합만 교체하는 구조를 실증한다. 첫 관문은 기존 영어를 보호하면서 활성 슬롯 예산을 실제로 넘는 두 한글 페이지를 `A → B → A`로 바꾸는 것이다.

## 9. 첫 동적 글꼴 공급은 확장 CHR-ROM 페이지로 정한다

mapper 165의 CHR-RAM은 한 화면의 작업 페이지가 될 수 있지만, CPU가 확장 CHR-ROM을 복사 원천으로 직접 읽지 못하고 원본 PRG 256 KiB도 이미 가득 차 있다. 반면 무번역 변환 뒤 CHR에는 4 KiB 페이지 30개가 남는다.

따라서 첫 제품 경로는 보호 타일을 포함한 화면별 완성 페이지를 확장 CHR-ROM에 두고 직접 선택하는 방식으로 정한다. CHR-RAM 업로드는 별도 PRG 저장 원천이나 런타임 합성이 필요해지는 경우에만 다시 비교한다.

## 10. 국소 추적을 화면 계약의 빈칸을 닫는 방식으로 바꾼다

설정 화면의 페이지 전환은 국소 실행 소유자를 찾아 해결했지만, 같은 방식만 반복하면 화면별 영어·그래픽·스프라이트·점멸 UI와 이탈 수명을 빠뜨릴 수 있다. 따라서 화면 역할 목록을 먼저 두고 일본어 대상, 보존 영어·숫자, FD/FE 배경, 스프라이트, 시간 변화, 입력·자동 전이, 페이지 수명을 함께 관리한다.

앞으로의 주소·소비자 추적은 이 화면 계약의 미확정 항목을 닫는 데 사용한다. 첫 혼합 문자 대상인 부대 목록에서 한글 `이름`과 원본 `LV`·`HP`의 공존을 확인했으므로, 같은 방식으로 다음 능력치 화면 계약을 닫는다.

## 11. 화면 안의 표면뿐 아니라 화면 사이 흐름도 먼저 나눈다

장 전환을 조사하며 한 장면으로 보이던 구간이 종료 대사, `NEXT STORY`, 저장 제안, 저장 완료, 장 제목과 대사의 합성 화면으로 나뉜다는 점을 확인했다. 같은 배경을 공유해도 입력 부작용과 글꼴 수명이 다르면 별도 화면 역할로 관리한다.

앞으로는 상위 흐름에서 진입·겹치는 표면·입력 대기·이탈을 먼저 선언하고, 각 화면에서 텍스트·보존 영어·초상화·창·점멸·입력 부작용 가운데 무엇을 집중해서 볼지 정한다. 국소 주소 추적은 그 역할의 생산자와 미확정 항목을 닫는 데 쓴다. 같은 상태와 CHR 쌍을 유지해도 저장 완료 질문, 종료 안내, 원본 영어 사운드 테스트처럼 수명과 입력 의미가 다르면 별도 화면이다. 한 장의 대표 화면이나 한 장의 장 전환을 전체 게임에 일반화하지 않는다.

연속 경로 자체를 가상의 화면 역할로 세지는 않는다. 실제 화면은 각자 계약을 유지하고, 후반 장 연속 전환 같은 상위 관문은 관련 화면 역할을 묶어 순서·분기·위상 누락을 검사한다.

정적 상태 단계도 곧바로 화면 수로 세지 않는다. 사운드 테스트의 `START`·`SELECT`가 각각 6단계 전투 테스트와 30단계 엔딩 상태기로 이어진다는 사실은 상위 화면군의 존재만 확정한다. 실제 화면 역할은 무입력 자동 전이, 메시지 대기, 초상화·크레딧 합성 같은 가시 수명을 관측한 뒤 나눈다.

실행 결과도 이 원칙을 확인했다. `START`의 여섯 바깥 단계는 공용 전투 화면의 여러 수명으로 펼쳐졌고, `SELECT`의 서른 단계는 원본 영어를 보존할 구간과 일본어만 번역할 장 기록·인물 후일담, 정적 종단 화면으로 다시 나뉘었다. 앞으로도 상위 상태 수가 아니라 시간에 걸친 가시 요소와 번역 경계를 기준으로 화면을 센다. 처음에는 종단 진입 전 검은 전환 프레임을 서명 점멸로 보았지만, 단계 `1D`의 no-op 처리기와 `$7732=00`, 12,000프레임 장기 표본이 정적 서명을 증명해 계약을 수정했다.

## 12. 글꼴 페이지는 CHR 쌍이 아니라 화면 소유 수명에 결속한다

같은 외부 상태와 CHR 쌍을 진행 메뉴와 부대 목록이 공유하므로, 전역 쌍만 보고 부대 목록 페이지를 고르면 다른 화면이 깨진다. 화면별 글꼴 페이지는 해당 화면의 생성자가 만든 고유 수명 상태에 결속하고, 화면을 벗어나면 기존 자연 페이지 선택으로 돌아가게 한다. 서로 다른 화면에서 같은 문자 코드를 다른 한글로 써도 페이지 자산은 합치지 않는다.

## 13. 전체 번역 완료를 개발의 선행 조건으로 두지 않는다

전체 대사를 먼저 번역한 뒤 재삽입과 글꼴 공급을 개발하면 뒤늦게 발견한 구조 문제로 번역 작업을 다시 맞춰야 한다. 반대로 번역이 없으면 실제 글리프 집합·길이·화면 표시 문제를 검증할 수 없다.

따라서 안정 ID와 원문 결속으로 기존 번역을 보존하면서, 검토 가능한 작은 대사 묶음을 번역·재삽입·글리프 공급·실행 표시까지 먼저 연결한다. 이 수직 슬라이스에서 드러난 공용 규칙을 구현에 반영하고, 전체 번역과 화면별 개발을 병행해 범위를 넓힌다. 최종 글리프 집합과 전체 수용 판정만 모든 번역의 검토 완료 뒤 확정한다.

## 14. 전투 글꼴은 조합별 PRG 캐시를 CHR-RAM에 올리는 것으로 시작했다

전투 전체 번역은 한 정적 페이지에 들어가지 않지만, 실제 한 전투에서 동시에 필요한 조합은 들어간다. 따라서 전투에서는 조합별 완성 페이지를 확장 PRG에 두고 렌더가 꺼진 NMI 창에서 CHR-RAM으로 올리는 경로를 채택한다. 보호 집합은 배경뿐 아니라 시간에 따라 보이는 스프라이트까지 포함하고, 업로드는 전투마다 한 번만 소비해야 한다.

캐시 선택은 플레이어·적 선공 같은 전투 상태만으로 정하지 않는다. 현재 카인/가르다병 probe는 번역 원천 선택에서 참가자·병종·장비·지형 집합을 함께 생성하고, 런타임의 각 항목이 이 페이지가 수용하는 집합에 드는지 검사한다. 첫 전투의 지형 `초원/바다`와 뒤 전투의 부분집합 `초원/초원`은 같은 페이지를 써야 하므로 정확한 쌍 일치는 캐시 키가 아니다.

여러 페이지에서 한 전역 글리프 코드를 유지하는 방안은 실제 조합 전의 공존 그래프로 먼저 판정한다. 최초의 임의 병종·장비 모델은 223색으로 활성 슬롯 210을 넘었고, 장별 초기·증원 적 레코드의 원래 병종까지 결속한 모델은 209색으로 줄었다. 그러나 변경 가능한 라이브 병종의 모든 쓰기 지점을 완전하게 열거하는 데 전역 코드북의 안전성을 걸지 않는다. 적의 정체성과 아이템은 원본 레코드에 결속하되 병종은 렌더러가 정의한 24개 전부로 넓히고 원본 장착 판정을 적용한다. 당시 번역 입력의 이 상위집합은 정확히 210색에 들어왔으므로 전역 코드북 경로를 채택했다.

전역 코드북도 `글리프→추상 색`과 `추상 색→물리 타일 코드`를 분리한다. 앞 단계는 번역 글리프끼리의 공존만 판정하고, 뒤 단계는 각 캐시 페이지에 남겨야 하는 원본 배경·스프라이트 코드를 제약으로 누적한다. 한 표본의 안전 코드 수만으로 전체 페이지를 일반화하거나, 물리 코드 충돌을 추상 색 그래프가 해결했다고 간주하지 않는다.

## 15. 완성 페이지 카탈로그 대신 전투 진입 합성으로 바꾼다

참가자 상위집합 10,220×2,132개에 지형 두 칸과 전투 대사까지 곱하면 모델 튜플이 약 1,562억 개다. 이는 실제 도달 수의 증명이 아니지만, 512 KiB PRG에서 기반 자산용 MMC3 8 KiB 두 페이지를 뺀 뒤 최대 56개뿐인 4 KiB 페이지에 조합별 완성본을 미리 두는 설계가 전체 범위를 표현할 수 없음을 보여준다.

따라서 확장 PRG에는 원본 글꼴·그래픽 페이지, 전역 글리프 아틀라스와 원천별 업로드 레시피를 둔다. 전투 진입 때 원본 4,096바이트를 CHR-RAM에 복원하고 현재 이름·병종·장비·지형·대사에 필요한 글리프만 같은 추상 코드로 덮어 완성 페이지를 합성한다. 배경·스프라이트 보호 제약과 물리 코드 매칭은 그대로 유지하며, 합성 전송의 시간 예산과 이탈 복구는 실행 관문으로 남긴다.

## 16. 타일 번호가 아니라 실제 패턴 테이블 소비자를 보호한다

전투 시간 표본의 네임테이블과 OAM 타일 번호를 무조건 한 제약으로 합치면 각 경로는 따로 풀려도 공용 사운드 테스트와 정규 전투를 합친 전역 물리 배정은 실패한다. 32개 표본의 PPU 상태는 배경이 CHR-RAM 대상 `$1000`, 스프라이트가 별도 `$0000`을 일관되게 사용했다. 따라서 보호 코드는 같은 번호의 존재가 아니라 해당 프레임에서 수정할 4 KiB 패턴 테이블을 실제로 소비하는 배경 또는 스프라이트에서만 가져온다. 장래 표본에서 스프라이트가 `$1000`을 쓰면 그 OAM 코드는 자동으로 다시 제약에 들어간다.

대사 레시피도 현재 `$7936`만 읽지 않는다. 원본 생산자 조건이 이미 참이면 후반에 기록될 선택자 `3E`를 미리 투영해, 표시 직전에 글꼴이 바뀌는 시간차를 캐시 입력에 반영한다.

## 17. 공유 고정 표 전체를 전투 범위로 추정하지 않는다

병종·아이템·인물명 표는 전투 밖 메뉴에서도 소비된다. 전투 레시피가 결속한 원천만 전투 물리 코드북으로 재인코딩하며, 레시피 디렉터리의 결측 41개는 단지 작업공간에 번역이 있다는 이유로 전투 ROM에 넣지 않는다. 현재 개발 기반은 전투 원천 231개와 전투 대사 28개를 삽입하고 나머지 고정 원천은 원문 바이트로 유지한다. 이후 비전투 화면은 각 화면 수명과 글꼴 페이지를 별도로 결속한 뒤 같은 번역을 소비한다.

## 18. 부분 프로브와 플레이 가능한 번역판을 구분한다

초벌 번역의 분량과 일부 화면의 한글 표시는 게임 전반의 표시 완성도가 아니다. 목표 화면 밖의 일본어·그래픽이 깨지는 산출물은 구조를 증명하는 개발 프로브로만 남기고, 플레이 가능한 번역판으로 부르지 않는다.

1장 수직 절단면은 번역한 일본어가 한글로 나오고, 아직 번역하지 않은 일본어와 원래 영어·숫자·그래픽이 그대로 남으며, 화면 진입·이탈·재진입 뒤에도 깨진 타일이 하나도 없을 때만 통과한다. 이후 장과 분기에도 같은 기준을 확대한다.

## 19. 검증한 표면은 하나의 누적 패치 계보에 합친다

개별 프로브만 늘리면 각 기능은 따로 통과해도 함께 썼을 때의 코드 동굴, 선택자, CHR 페이지와 화면 복구 충돌을 늦게 발견한다. 이제 기본 개발 산출물은 지원 일본판 원본에서 검증한 단계를 순서대로 다시 적용하는 하나의 누적 ROM이다. 새 표면은 기존 누적 범위의 콜드 회귀를 함께 통과한 뒤 다음 단계가 된다.

전체 대사 번역 입력이 채워진 것과 실제 ROM에 설치·검증된 범위는 분리한다. 입력 완료는 다음 화면 수명을 바로 구현할 수 있다는 뜻이고, 플레이 가능한 번역판은 누적 ROM에서 해당 표면의 진입·시간 위상·이탈과 주변 그래픽까지 통과했다는 뜻이다.

## 20. 공유 번역과 소비자별 물리 인코딩을 분리한다

아군명 하나를 부대 목록·상태·전투·엔딩이 공유하지만 각 화면이 동시에 보존해야 할 문자와 글꼴 수명은 다르다. 전역 이름 표를 한 코드북으로 바로 덮으면 아직 준비되지 않은 소비자에서 글자가 깨진다.

따라서 번역은 인덱스에 결속한 의미 자산 하나로 유지하고, 실제 ROM 바이트와 글꼴 페이지는 검증한 소비자마다 따로 만든다. 준비되지 않은 소비자는 원본 표로 돌아가며, 새 소비자 수명을 열 때 같은 번역을 다시 투영한다.

## 21. 자동 병종 소개는 프로필 구간별 페이지로 공급한다

자동 병종 소개의 한국어 합집합은 216자로 한 페이지 상한 210자를 넘는다. 화면은 입력 없이 프로필 인덱스를 순서대로 소비하므로, 인덱스 `0..10`과 `11..21`을 두 페이지로 나누고 제목 조립 경계에서 선택한다. 원래 영어 능력치·숫자·UI는 두 페이지에 모두 남기며, 첫·경계·마지막 프로필과 자동 이탈 뒤 영어 화면을 같은 빌드에서 검증한다.

## 22. 개별 화면 수가 아니라 전역 최악 조건을 먼저 닫는다

작은 화면을 차례로 고치는 방식은 각 표면의 소비 경로를 배우는 데는 유효했지만, 전체에서 가장 큰 동시 한글 집합이나 가장 까다로운 전환 수명을 감당하지 못하면 앞선 성공만으로 완성을 보장할 수 없다. 화면별 성공 개수도 전체 일본어 잔존량을 대신하지 못한다.

따라서 앞으로는 먼저 모든 도달 가능한 일본어 소비처와 그 화면 수명을 하나의 분모로 확정한다. 그중 최대 동시 글리프 집합, 가장 긴 조판, 가장 복잡한 전환·복구 조건을 전역 구조가 수용하는지 증명한 뒤, 같은 구조로 전체 번역을 설치한다. 개별 실행은 이 전역 판정을 뒷받침하는 표본이며, 완료 조건은 최종 누적 산출물에서 대상 일본어가 0건이고 보호 영어·숫자·그래픽 손상이 0건인 것이다.

## 23. 전역 코드북 크기와 한 화면 수요를 분리한다

전투 공존 그래프의 210색은 모든 캐시에서 같은 글리프 바이트를 유지하기 위한 전역 코드 수다. 이를 한 전투가 210자를 동시에 요구한다는 뜻으로 해석하지 않는다.

실제 전투 수명은 메시지 전체와 예측 라벨 69자, 양측 참가자 각 10자, 지형 둘 6자, 대사 39자를 겹침 공제 없이 더해 최대 134자로 판정한다. 당시에는 관측 활성 코드 68개를 모두 그래픽으로 간주해 202/210으로 계산했고, 전역 최악 수명 후보를 204/210인 턴 경계 게임 오버로 두었다.

## 24. 표 전체가 아니라 실제 선택된 레코드로 수명을 센다

게임 오버의 204칸은 승리·패배 공용 표 11개를 한 화면에 전부 합친 과잉 상한이었다. 실행 표본 전부가 정확한 선택자 `B0:0A`를 유지하므로 실제 게임 오버 수명은 한 레코드의 한국어 30자와 보존 코드 90개, 합계 120칸이다.

따라서 이 시점의 최악 후보는 다시 202/210인 전투가 됐다. 이후에도 큰 표 전체를 한 화면 수요로 간주하지 않고, 생산자와 실행 선택자로 실제 공존 레코드를 먼저 결속한다.

## 25. 화면에 보인 일본어 글꼴은 보존 그래픽이 아니다

전투 네임테이블의 활성 타일 코드를 전부 보존하면 최종적으로 제거해야 할 원본 일본어까지 그래픽 예산으로 이중 계산한다. 원본 글꼴 페이지의 활성 210코드는 일본어 번역 소유 111개와 비일본어 보존 후보 99개로 소스에서 완전 분할한다. 원래 영문·숫자와 제어 코드는 별도 전역 예약을 유지한다.

32개 관측 표본에서 활성 35..68개 중 일본어 11..38개를 회수하면 비일본어 동시 보존은 23..38개다. 텍스트 보수 상한 134개와 합친 관측 최대는 172/210이다. 최상위 32단계뿐 아니라 유닛 패널 12단계와 애니메이션/메시지 41단계를 소스에서 열거했고, 실제 배경 생산 경계는 전투 뱅크 `05/07`의 `$0781` 큐 게시자 17곳으로 좁혀졌다. 직접 `$2007` 우회는 없다. 이 17곳의 동시 코드 수요를 닫은 뒤에만 그래픽 카탈로그 완료와 런타임 튜플 제한 해제를 선언한다. `$0000` 스프라이트 애니메이션은 같은 번호를 쓴다는 이유만으로 `$1000` 캐시 경쟁자로 세지 않는다.

## 26. 전역 합집합은 용량을 닫지만 물리 배정은 위상별로 닫는다

17개 게시자의 코드·보조 루틴·자료 29구간과 큐 템플릿 22개를 전수 해석했다. 속성표와 예약 코드, 최종적으로 번역할 일본어 큐 코드 8개를 제외하면 비일본어 활성 타일의 전역 합집합은 39개다. 실제 동시 집합보다 큰 이 합집합을 텍스트 상한 134개와 모두 겹쳐도 173/210이므로 전투 구조의 원시 슬롯 용량은 충분하다.

하지만 전역 안정 코드북은 210개 추상 색을 고정 바이트에 배정한다. 39개를 모든 추상 색에 일괄 금지하면 실제로 함께 보이지 않는 위상까지 충돌시킨다. 따라서 용량 통과와 물리 배정 완료를 분리한다. 다음 관문은 각 게시자 상태에서 어떤 텍스트 레시피가 공존하는지 소스 위상으로 결속해, 관측 표본이 아닌 전 위상 물리 제약을 만드는 것이다.

## 27. 전역 고정표 대신 전투별 동적 물리 배정을 쓴다

숨은 애니메이션 명령·효과·정리·대사 상태표까지 넓혀 7개 상태군 179엔트리에서 17개 게시자 전부가 도달함을 확인했다. 전역 고정표는 210개 추상 색을 고유하게 배정해야 하지만, 비일본어 39코드를 항상 피우면 안전한 물리 코드는 171개뿐이라 성립하지 않는다.

반면 한 전투에서 선택되는 번역 레시피의 상한 134개와 보호 코드 39개 전부를 동시에 잡아도 173/210이다. 따라서 위상별로 더 작게 줄이는 것을 용량 관문으로 삼지 않고, 전투 진입 때 선택된 레시피만 물리 코드에 배정하며 텍스트도 그 배정으로 투영한다. 관측 고정 배정은 진단 자료일 뿐 배포 구조가 아니다.

## 28. 바이트 일치와 읽을 수 있는 한글을 별도 관문으로 둔다

전투 합성기는 일반 전투·사운드 테스트·정확 최대 모델 입력에서 독립 계산과 CHR-RAM 4,096바이트 일치, 표시 수명과 종료 정리까지 통과했다. 그러나 같은 화면의 문자 영역은 판독 가능한 한국어가 아니었다. 생산된 캐시가 정확하다는 사실만으로 공유 렌더러가 번역 코드와 보존할 영어·숫자 리터럴을 올바르게 구분한다고 볼 수 없다.

당시에는 전체 번역 설치 전에 텍스트 바이트의 소비자별 소유권을 먼저 닫기로 했다. 가족별 최대의 합 `134+39=173/210`은 임의 선택을 수용하는 안전 상한으로 유지하고, 가능한 모델의 정확 최대 `131+39=170/210`은 실행 증인으로 쓴다. 둘 중 어느 수치도 화면에서 한국어·원본 영어·숫자·그래픽이 함께 읽히는 시각 검증을 대신하지 않는다. 후속 동일 상태 A/B에서 이 원인 가설은 기각했으며 실제 원인은 29의 매퍼 선택 순서였다.

## 29. 화면 손상은 생산물보다 소비 페이지를 먼저 대조한다

정상 직전 ROM과 손상 ROM을 같은 전투 상태·입력·합성 시점에서 비교한 결과, 두 CHR-RAM 생산물은 같았고 실제 PPU가 선택한 페이지부터 달랐다. 원인은 사운드 테스트 지원 리팩터링에서 페이지 0 분기가 대상 매퍼 레지스터 선택을 건너뛴 제어 흐름 회귀였다. 번역 바이트 소유권 가설은 기각했다.

앞으로 합성 결과가 정확한데 화면이 깨지면 번역 자료를 다시 손대기 전에 `생산 CHR-RAM → 매퍼 레지스터 쓰기 → PPU 소비 페이지`를 같은 프레임에서 비교한다. 수정은 분기 주소 숫자를 맞추는 데 그치지 않고, 대상 레지스터 선택과 값 쓰기를 별도 역할로 두고 실제 쓰기 순서를 검사한다.

## 30. 동적 명사 뒤 조사는 입력 중립형으로 쓴다

이름·아이템·병종·수량은 실행 중 선택되는 값이라 번역 시점에 받침 유무를 하나로 고정할 수 없다. 런타임 조사 선택기가 없는 동안은 `은(는)`·`이(가)`·`을(를)`·`과(와)`·`(으)로`·`(이)나`를 사용하고, 고정 조사 결합은 검증 단계에서 거부한다.

이 교정으로 공존 그래프의 최소 색 수가 달라져도 번역을 줄여 기존 산출물 크기에 맞추지 않는다. 가족별 레시피는 항상 선택되는 공용 글리프를 중복 저장하지 않고, 런타임의 210칸 코드표는 필요한 색 클래스를 결정적으로 분리해 고정 폭을 유지한다.

## 31. 레코드 최대와 화면 수명을 선택자 없이 합치지 않는다

주 대사의 최대 한글 집합은 175자지만, 이것만으로 어느 화면과 함께 살아 있는지 알 수 없다. 11장 종료 표본은 실제 선택자 `C0:1C`에서 시작하며 최대 레코드 24가 아니었다. 화면 모양과 대사 성격이 비슷하다는 이유로 둘을 합친 233칸 판정은 폐기한다.

앞으로는 `생산자 → 런타임 선택자 → 정확한 레코드·전이 사슬 → 동시 화면 코드`를 모두 결속한 뒤에만 화면 수명을 계산한다. 전투 170칸은 현재까지 가장 큰 결속 완료 수명일 뿐이며, 최대 레코드와 미계수 화면을 닫기 전에는 전역 최대라고 부르지 않는다.

## 32. 같은 엔트리 번호도 선택자가 다르면 별도 대사로 본다

장별 이벤트 표를 위에서부터 조사한 결과, 최대 레코드 24의 실제 생산자는 7장 성 좌표 `(27,10)`의 `C0:18` 경로였다. 11장에도 엔트리 번호 18이 있지만 그 성은 별도 상태기를 거쳐 `30:18`을 선택하므로 같은 소비자로 합치지 않는다.

이제 최대 레코드의 소스 생산자와 선택자는 결속됐다. 다음 판단은 7장 `C0:18`의 실제 화면을 관측해 동시 화면 코드를 붙인 뒤 내리며, 같은 숫자나 비슷한 장면만으로 다른 장의 수명을 대신하지 않는다.

## 33. 최대 대사는 레코드 전체가 아니라 완료 페이지 단위로 공급한다

7장 최대 대사는 15페이지를 한 수명에서 순차 표시한다. 레코드 전체를 한 글꼴 페이지에 상주시키는 수요는 `275/210`으로 불가능하지만, 실제 완료 페이지별 최대 수요는 `135/210`으로 들어간다. 따라서 번역을 줄여 한 페이지에 맞추지 않고, 페이지 묶음마다 글꼴을 나누어 진행 경계에서 다시 공급하는 구조를 채택한다.

초기 진입은 첫 글꼴 묶음을 고르고, 완료 페이지 진행은 다음 페이지가 속한 묶음을 다시 고르며, 마지막 페이지는 한글 글꼴을 강제로 재선택하지 않고 보존 대상 영문 화면으로 이탈한다. 실행 증거는 고정 대기 시간이 아니라 페이지 완료 상태를 확인한 뒤 여러 점멸 위상에서 모은다.

## 34. 새 실행보다 이미 결속된 설치 수명을 전역 비교에 먼저 올린다

전역 수명 표에 전투와 주 대사 계열만 들어가 자동 병종 소개가 빠져 있었다. 그러나 병종 소개는 이미 두 글꼴 묶음의 exact-output 설치와 실행 증거가 있고, 큰 묶음은 한글 161자와 보존 코드 12개로 `173/210`이다. 이는 전투의 정확 최대 `170/210`보다 크다.

앞으로 새 동적 경로를 만들기 전에 현재 빌드 보고서에 결속된 설치 묶음과 보존 코드를 전역 수명 표에 먼저 투영한다. 동적 분석은 그 정적·기존 실행 증거로 닫히지 않는 소비자 경계와 화면 위상을 증명하는 데만 쓴다.

## 35. 유닛 UI 전체 합집합과 실제 화면 수명을 분리한다

번역 입력을 모두 결속하면 유닛 UI 전체 합집합은 229자, 요약·상태 공유군도 218자라 210칸 고정 페이지 하나에는 들어가지 않는다. 그러나 실제 화면은 이름 하나·병종 하나·아이템 최대 네 개와 해당 라벨만 소비하며, 독립 최대를 더한 상한도 요약 36자·상태 30자다. 명령 15개의 합집합은 30자다.

따라서 전체 합집합을 억지로 한 페이지에 넣거나 번역을 줄이지 않는다. 요약 진입에서 현재 내용에 맞춘 페이지를 공급하고 상태 화면은 그 페이지를 상속한다. 명령 메뉴는 자체 공급 경계에서 별도 정적 페이지를 쓴다. 동적 분석은 이 공급·상속 경계와 세 배경 위상을 확인하는 단계에서 사용한다.

## 36. 전 페이지 상한이 넘을 때만 실제 대상 셀 수명으로 좁힌다

맵 메뉴와 저장 질문·전원 종료·중단 문구는 정확히 사라지는 일본어 코드만 회수하고 나머지 활성 코드 210개를 전부 보존하는 상한으로도 들어간다. 이 경우 새 실행 없이 소스 소비자만으로 용량을 닫는다.

저장 완료 선택지는 같은 상한이 `214/210`이라 실패했다. 그래서 이미 확보한 정확한 `B0:00` 저장 상태만 다시 불러오고, 8개 불규칙 프레임의 물리 네임테이블 RAM 2 KiB를 저장했다. 분석기는 대상 대사·선택지가 있는 물리 페이지 0에서만 정확한 셀을 제외하고 페이지 1은 전부 보존하며, 속성표를 제외한 활성 코드 합집합 43개를 원시 덤프에서 다시 계산한다. 동적 분석은 임의 진행이 아니라 이렇게 정적 상한을 막은 하나의 미확정 수치를 닫을 때만 쓴다.

## 37. 제목은 원본 그래픽을 기준으로 다시 제작한다

제목은 일반 문자열이나 기존 글꼴 타일의 단순 치환으로 처리하지 않는다. 원본 제목 그래픽을 편집 기준 이미지로 삼아 ImageGen으로 한글 제목 시안을 만들고, 원래 구도·장식·인상을 보존한 후보를 NES 해상도·색상·타일·CHR 배치 제약에 맞춰 결정적으로 정리한다.

생성된 고해상도 시안 자체를 곧바로 게임 자산으로 간주하지 않는다. 최종 채택은 축소·팔레트화·타일화한 결과가 실제 제목 화면에서 읽히고, 주변 그래픽과 점멸 위상 및 원본 영어·숫자 보호 조건을 함께 통과했을 때만 한다.

## 38. 의미를 보존한 글리프 축소는 구조적 해법 뒤의 최후 수단이다

번역은 원문의 뜻과 정보를 반드시 보존한다. 글꼴 소유권 분리, 화면 수명 분할, 완료 페이지 재적재와 같은 구조적 해법으로도 210칸을 넘는 최악의 경우에만, 같은 뜻을 유지하는 동의어와 문장 재구성으로 고유 글리프 수를 줄일 수 있다.

의미 축약이나 정보 삭제는 허용하지 않으며 이미 구조적으로 수용되는 번역은 이 이유로 바꾸지 않는다. 장 제목과 도입 대사 복합 화면은 페이지 재적재로 최대 `143/210`에 들어가므로 현재 번역문 축소 대상이 아니다.

## 39. 보존 그래픽은 코드 하나가 아니라 실제 가시 셀 전체로 소유한다

제목의 원본 `TM`은 한 코드가 아니라 마지막 행의 `BA+BB` 두 셀에 걸쳐 있었다. 한 셀만 보존한 첫 설치는 실행에서 `TM`을 점처럼 깨뜨렸으므로, 두 셀과 두 패턴을 모두 보존 영역으로 돌리고 한글 로고 폭만 조금 줄였다.

번역 뜻이나 글자를 줄이지 않고도 `117/121` 타일에 들어간다. 앞으로 혼합 그래픽의 소유권은 문자열 추정이나 대표 코드가 아니라 실제 가시 셀과 패턴 전체를 기준으로 정하고, 정적 불변식과 점멸 위상 실행을 함께 통과시킨다.

## 40. 정적 화면 자산은 뒤의 런타임 덮어쓰기까지 한 수명으로 본다

제목 기본 스트림과 CHR만 바꾼 첫 결과는 미리보기와 초기 위상에서는 정상이었지만, 완성 연출이 칼 교차부 11셀을 원작 타일로 다시 써 흰 전경을 깨뜨렸다. 따라서 화면 번역의 소유 범위는 최초 그리기만이 아니라 같은 가시 셀을 바꾸는 후속 전송까지 포함한다.

후속 조사에서 완료 연출이 로고 본체 위 `$2182`의 원작 장식 26셀도 추가로 전송한다는 사실을 확인했다. 현재 설치기는 이 상단 26셀을 빈 타일로 만들고 본체 11셀은 정적 한국어 로고로 다시 고정하되 명령·속성 바이트와 칼·`TM`·저작권 자산을 보존한다. 앞으로 정적 미리보기는 후보 검증으로만 쓰고, 점멸·합성·덮어쓰기 뒤의 실제 완료 프레임을 최종 소비자 증거로 삼는다.

## 41. 남은 번역 소비자는 한 통합 후보에 일괄 설치한다

36개 화면 수명과 전역 최악 용량을 이미 닫았으므로 남은 번역 도메인을 하나씩 설치하고 매번 동적 검증하지 않는다. 남은 13개 도메인의 모든 소비자를 한 후보 ROM에 설치한 뒤 포인터·저장 공간·코드북·글꼴 수명·일본어 잔존·보호 원문을 정적으로 일괄 검사한다.

동적 회귀는 이 정적 관문을 통과한 동일 ROM에서만 수행한다. 실패가 발견되면 번역 입력을 되돌리지 않고 해당 소비자나 렌더러 모듈을 고치며, 작업과 커밋은 역할별로 나누더라도 제품 후보의 설치 범위는 항상 전체를 유지한다.

## 42. 전체 대사는 정적 글꼴 페이지 수에 맞추지 않고 실행 중 합성한다

전체 대사를 정적 글꼴 페이지만으로 미리 만들면 현재 매퍼의 남은 페이지보다 많은 묶음이 필요하다. 이를 번역 축소나 매퍼 재변환의 근거로 삼지 않는다. 글리프 원본은 압축해 프로그램 영역에 두고, 화면에 들어갈 대사 자체를 먼저 읽어 그 화면에 실제로 필요한 글리프만 CHR RAM에 합성한다.

대사 진입에서는 안전한 기준 글꼴을 만들고, 같은 레코드의 다음 페이지에서는 달라진 타일만 갱신한다. 정적 페이지는 필수 기반이 아니라 실행 시간이나 호환성 문제가 실제로 확인될 때 쓸 수 있는 선택적 캐시로 남긴다. 뜻을 줄이는 번역과 매퍼 확장은 이 구조도 성립하지 않을 때 검토하는 후순위 수단이다.

## 43. 글꼴 합성은 ROM 대사보다 완성된 표시 줄을 기준으로 한다

주 대사의 `EC`는 실행 중 이름·아이템·수치 같은 SRAM 문자열을 끼워 넣고, 일부 소비자는 공통 추출기가 머리말로 분리한 바이트도 실제 글자로 표시한다. 따라서 ROM에 저장된 네 줄만 먼저 스캔해서는 화면의 전체 글리프 수요와 일본어 잔존을 알 수 없다.

동적 문자열의 생산자와 가능한 도메인, 소비자별 가시 머리말을 먼저 결속한다. 글꼴 합성은 그 값까지 들어간 완성 줄 버퍼나 의미상 동등한 경계에서 수행하며, 대사 압축은 이 표시 계약을 흐리지 않는 범위의 저장 최적화로만 사용한다.

전수 분류 결과 동적 문자열은 보존 숫자·아이템명·아군명·장소명 네 도메인이며, 가장 큰 페이지도 가능한 이름 합집합과 리터럴을 합쳐 `187/210`에 든다. 번역 동적 문자열과 숫자가 한 페이지에 섞이지 않고 번역 페이지도 두 코드북 그룹뿐이므로, 187개 canonical 이름 코드와 페이지 선택자의 remap 비트, 그룹별 직접 조회표를 사용한다. 전 글리프 상주나 대사 의미 축소는 하지 않는다.

## 44. 대사 압축 전에 실제 이중 진입만 남긴다

같은 대사 저장소라도 직접 진입은 4바이트 머리부를 소비하고 전이 진입은 0바이트 또는 `E8` 6바이트를 소비한다. 전이 대상 139개를 모두 복제하면 전역 저장량에는 들지만 두 PRG 뱅크에서 모자라며, 단일 포인터 보정도 두 델타를 처리하지 못한다.

번역 본문은 하나로 두고, 직접 헤더와 `E8` 효과를 작은 별도 자료에서 모드별로 재생하는 안을 먼저 검증한다. 이 자료는 기존 합성 재료의 PRG 페이지 수를 늘리지 않는다. 직접 생산자와 두 진입 제어 흐름을 결속해 상태 효과 보존을 증명하고, 성립하지 않는 레코드만 국소 분리한다. 해당 뱅크의 부족분이 남을 때만 대사 압축을 적용하며 전면 디코더 재작성과 매퍼 확장은 후순위다.

## 45. 이중 진입은 상태 효과와 보이는 글자를 함께 정규화한다

직접/전이 프리픽스 차이는 상태 효과만 재생하면 끝나지 않는다. `+4` 대상은 전이 진입에서 앞 4바이트가 글자로 보이고, `-2` 대상은 직접 진입에서 5~6번째 바이트가 글자로 보인다. 따라서 공통 번역 본문은 두 소비자 중 더 늦은 본문 경계인 4바이트 또는 6바이트 뒤에서 시작한다.

고정 6바이트 행과 레코드 색인은 그대로 사용하되, 진입 shim은 원래 헤더·`E8` 효과와 소비자별 가시 바이트를 따로 복원한다. 완성 줄 스캔도 이 가시 바이트를 포함해야 하며, 자료를 만들었다는 사실과 본문 인코딩·실행 제어에 실제로 연결했다는 사실은 별도 관문으로 둔다.

## 46. 동적 대사 경로는 부분 완료 목록이 아니라 닫힌 집합으로 증명한다

확인한 `(레코드, 선택자)`를 차례로 완료 목록에 더하면 새 경로를 발견할 때마다 설계와 진척 기준이 흔들린다. 이 목록은 폐기한다.

앞으로 `EC` 소비자가 요구하는 전체 집합과 유한한 게임 흐름 해석기가 만드는 생산자 공급 집합을 `(레코드, 선택자, 문자열 도메인)`으로 비교한다. 누락·불일치·과잉 중 하나라도 있으면 전체 설치가 실패하며 부분 결속은 진척으로 선언하지 않는다. 새 증거는 상위 구조를 바꾸지 않고 해당 흐름 해석기의 원천 결속을 보강한다.

## 47. 이중 진입 원문 자료를 번역 자료로 간주하지 않는다

139개 이중 진입의 6바이트 행을 만들었지만, 모드별로 보이는 480바이트 중 288바이트가 일본어였다. 이를 그대로 재생하는 shim은 일본어 0건 목표를 위반하고, 기존 공통 줄 번역만으로는 어느 한국어 조각을 한 모드에서 제외할지 결정할 수 없다.

따라서 정규화 전략 선택을 취소하고 G4·G5를 다시 연다. 각 모드의 실제 도달성을 증명해 불필요한 변형을 제거하거나, 양쪽을 보수적으로 도달 가능으로 보고 모드별 원문·한국어 조각을 별도 입력으로 만든다. 그 입력이 완전하고 새 글리프 수명까지 통과한 뒤에만 공통 본문과 shim을 설치한다.

## 48. 이중 진입은 고정 바이트가 아니라 처음 공유하는 줄 경계에서 합친다

4바이트 또는 6바이트 뒤를 곧바로 공통 본문으로 보는 안은 실제 레코드에서 깨졌다. 일부 헤더 바이트가 한 모드에서는 빈 줄 제어와 다음 줄의 머리로 소비되고 다른 모드에서는 줄 중간부터 시작하므로, 두 파서는 첫 줄 끝에서도 합류하지 않는다.

139개 레코드마다 직접·전이 선형 구간의 줄 시작 집합을 전수 비교하고 처음 공유하는 줄 경계를 공통 본문 시작으로 삼는다. 그 앞은 직접 선두와 전이 선두를 각각 완전한 번역 단위로 두며, 실행 경로가 제거되기 전까지 두 모드를 모두 필요 입력으로 간주한다. 이 구조는 417개 파트의 닫힌 작업공간으로 검증하고, 미번역 일본어 파트가 하나라도 있으면 전체 설치를 막는다.

## 49. 저장 레코드 수와 실제 표시 경로 수를 분리한다

504개 원천 레코드만으로 코드북을 계산하면 이중 진입에서 서로 다르게 보이는 선두가 빠진다. 반대로 직접·전이 본문을 모두 복제하면 공통 본문의 저장 공유 가능성을 잃는다.

따라서 저장 모델은 504개 원천 레코드와 공통 본문 공유를 유지하고, 표시 모델은 일반 365경로와 이중 진입 직접·전이 278경로, 합계 643경로로 펼친다. 글리프 수명·페이지 코드북·동적 문자열은 표시 모델에서 계산하고, 저장량·포인터·shim은 그 결과를 공통 본문 구조에 결속한 뒤 별도로 통과시킨다.

## 50. 부족한 대사 뱅크는 전용 확장 스크립트 뱅크로 투영한다

두 모드 본문을 복제한 안전 상한은 전체 원천 소유 공간에는 들지만 PRG 뱅크 07·08 안에서는 각각 1,409·227바이트 부족하다. 139개 중 80개는 두 모드의 4줄 페이지 정렬도 달라 공통 본문을 같은 로컬 코드 바이트로 단순 공유할 수 없다.

현재 512 KiB 후보에서 전투 재료 뱅크 10과 고정 뱅크 1F를 제외한 11·12는 각각 16 KiB 전체가 비어 있다. 07·08의 정규화 payload 전체를 이 두 뱅크에 각각 배치하고, 고정 뱅크의 대사 바이트 reader 선택 호출만 새 물리 뱅크로 투영한다. pointer-table 선택과 원래 뱅크 복귀는 유지한다. 이 구조가 성립하는 동안 DTE·10비트 스트림·뜻을 줄이는 번역은 도입하지 않는다.

## 51. 직접·전이는 같은 포인터 주소의 원천/미러 뱅크 쌍으로 나눈다

50번의 두 뱅크 전체 이전안은 저장량을 닫았지만 `E4/E6` 피연산자가 16비트 포인터가 아니라 `selector + entry index`라는 소비자 계약을 충분히 반영하지 못했다. 213개 간선마다 별칭 엔트리를 만들면 테이블 여유와 개별 피연산자 재작성이라는 새 예외가 생긴다.

직접 슬롯은 두 모드 중 긴 길이를 예약해 원천 소유 구간에 두고, 전이 payload는 같은 CPU 주소의 미러 뱅크에 둔다. 전이 대상이 있는 원천 뱅크 `04/07/08/0B/0C`는 확장 뱅크 `11/12/13/14/15`와 일대일 대응한다. 원래 pointer table과 517개 직접 포인터는 주소 하나만 공급하고, 두 전이 resolver 호출이 `$77F2`에 표식 `80`을 붙이면 reader가 대응 미러를 고른다. 따라서 `E4/E6` 피연산자 213개와 일반 직접 읽기·원래 뱅크 복귀는 보존한다. 이 결정은 50번의 전용 확장 저장 원칙을 유지하되 주소 모델을 전역 모드 쌍으로 교체한다.

## 52. 런타임 대사 식별은 화면별 조건이 아니라 원본 상태의 전역 함수로 둔다

특정 장·화면·관측 프레임을 조건으로 페이지 합성을 호출하면 새 경로를 찾을 때마다 hook과 완료 기준이 흔들린다. 그런 국소 조건은 도입하지 않는다.

원본 resolver가 이미 유지하는 디렉터리 선택자 `$77F4`, 엔트리 `$77F1`, 직접·전이 표식을 가진 원천 뱅크 상태 `$77F2`만 입력으로 삼아 643개 표시 경로 중 하나를 고른다. 8개 디렉터리의 523슬롯 전체를 직렬화하고 517개 유효 엔트리와 6개 핸들러 슬롯을 구분하며, 이중 진입 139레코드는 모든 포인터 별칭을 같은 직접·전이 경로 쌍에 귀속한다. 이후 새 실행 증거는 이 전역 함수의 원천 결속을 보강할 수는 있어도 화면별 예외를 추가하거나 상위 설치 전략을 바꾸는 근거가 되지 않는다.

## 53. 휘발 상태는 주소를 영구 점유하지 않고 원본 수명에만 소유한다

모든 화면이 영원히 건드리지 않는 5바이트를 찾는 조건은 실제 게임의 메모리 재사용 방식보다 강하고, 새 화면을 볼 때마다 주소를 옮기는 설계 드리프트를 만든다.

`$07F0..$07F4`는 주 대사 활성 수명에서만 경로·페이지·그룹·상태로 소유한다. 모든 진입은 사용 전에 전체를 초기화하고, 외부 호출·종료·reset·save/load·비활성 선택에서는 내용이 보존된다고 가정하지 않는다. 원본 계산 접근은 주소별 예외가 아니라 큐 1역할과 포인터 10역할로 완전 분할한다. 동시 실행 경계는 고정 NMI와 그 오디오 callee를 별도 추적하고, 직접 접근의 전역 누락은 16개 PRG 뱅크 전체 피연산자 스캔으로 막는다. 이후 새 접근은 기존 역할의 원천 범위를 다시 증명하거나 새 역할을 명시해야 하며, 어느 쪽도 아니면 빌드를 실패시킨다. 발견되는 세부 현실은 이 소유권 계약을 검증하거나 기각할 수 있지만 화면별 조건으로 상위 제어 흐름을 바꾸지는 않는다.

## 54. 전이 미러는 payload 저장소가 아니라 원천 뱅크의 실행 동등 복제본이다

전이 reader가 확장 미러를 선택한 동안에도 NMI는 같은 switchable 뱅크의 코드와 자료를 읽을 수 있다. 전이 대사 payload만 넣고 나머지를 빈 바이트로 두면, 대사 읽기 자체는 맞더라도 인터럽트가 뱅크 로컬 전송 디렉터리를 읽는 순간 그래픽과 제어 흐름이 깨질 수 있다.

따라서 원천 뱅크 `04/07/08/0B/0C`와 대응 미러 `11/12/13/14/15`는 각각 16 KiB 전체를 먼저 복제하고, 그 위에 같은 CPU 주소의 전이 payload만 덮어쓴다. payload 밖 모든 바이트와 NMI 디렉터리 `$BFC0..$BFC1`의 원천 동등성을 설치 전제조건으로 검사한다. 이후 다른 bank-local 소비자가 발견돼도 화면별 보정을 추가하지 않고 이 전체 복제 불변식으로 흡수한다. 또한 NMI의 오디오 호출은 임시 bank `0E` 실행 뒤 활성 PRG 그림자 `$29`를 중앙 선택기에 다시 넘긴다. 전이 전용 reader 선택기만 `$77F2`의 표식이 있는 논리 원천 번호를 받아 물리 미러를 고르고, `$29`에는 그 미러의 첫 페이지를 기록한다. reader 복귀에서만 원래 `0A`로 되돌린다. 따라서 인터럽트가 전이 바이트 읽기 사이에 들어와도 NMI 내부 자료와 NMI 뒤 물리 뱅크 정체성을 모두 보존한다. 상위 비트를 버리는 기존 중앙 선택기는 다른 모든 호출을 위해 그대로 둔다. NMI의 `$29` 복귀 호출 한 곳만 전용 선택기로 보내고, 입력된 물리 페이지가 현재 `$77F2` 전이 ID와 정확히 대응할 때만 확장 경로를 연다. 같은 물리 바이트값이 다른 호출이나 수명에서 들어와도 중앙 선택기의 동작은 바뀌지 않는다.

## 55. 아군명 표는 고정 주소 대신 실측 케이브 안의 계산 배치로 둔다

뱅크 `0B`의 아군명 표 네 구간을 각각 상수 주소로 박아 두었더니 아군명 저장이 `183/184`바이트가 됐다. 용어를 국내 통용 표기로 확정하면서 두 이름이 한 글자씩 길어지자 1바이트가 모자라 빌드가 멈췄다. 앞으로 남은 용어 검토가 계속 이 경계를 건드린다.

경계값만 옮기면 다시 여유가 0이 되므로 배치 방식을 바꾼다. 포인터 표 길이와 문자열 길이에서 다음 구간 주소를 계산해 이어 붙이고, 검사는 케이브 끝 하나로만 한다. 선언한 끝 `0xB940`은 근거가 문서에 없었고 실제 `FF` 구간은 `0xBFA0`까지 1,632바이트가 이어진다. 그 뒤부터 `$9251`로 시작하는 원본 포인터 표와 NMI 뱅크 로컬 디렉터리 `$BFC0`가 있으므로 `0xBFA0`을 실측 끝으로 삼는다.

확장 구간을 세 방향으로 검사했다. 뱅크 `0B`의 대사 저장 최상단은 `$B474`라 케이브 시작 `0xB6D0`보다 604바이트 아래이므로 전이 미러 `0B → 14`의 payload와 겹치지 않는다. 필요한 `0xB940..0xB942`를 가리키는 절대 주소 피연산자는 16개 PRG 뱅크 전체에서 0건이고, 그 주소를 값으로 갖는 포인터 표 항목도 0건이다. 이미 승인했던 `0xB6D0..0xB940` 구간의 유일한 후보는 대사 데이터를 옵코드로 오독한 오탐이었다. 케이브가 원본에서 전부 `FF`인지는 기존 `validate_switchable_cave`가 매 빌드에서 다시 확인한다.

## 56. 수요와 용량을 같은 값으로 단언하지 않는다

전투 합성 로더가 코드북의 충돌 쌍 수를 상수 `8`과 정확히 같은지 검사했다. 아군명 표기를 고쳐 글리프가 하나 줄자 충돌 쌍이 `7`이 되면서 빌드가 멈췄다. 조건이 나아졌는데 실패한 것이다.

`8`은 `$07E0..$07EF` 16바이트가 담을 수 있는 런타임 용량이고 보고서 값은 그때그때의 실제 수요다. 둘은 같아야 할 이유가 없으므로 용량 안에 드는지만 본다. 같은 이유로 아군명 고유 글리프 수를 `72`로 못박은 테스트도 활성 슬롯 예산 안에 드는지 보도록 바꿨다. 번역 표기가 바뀔 때마다 함께 고쳐야 하는 수치는 요구사항이 아니라 현재 입력의 우연한 결과다.

## 57. 고정 4바이트 레코드 헤더 가정을 다시 연다

`inspect_main_record_prefix`는 모든 주 대사 레코드에 4바이트 고정 헤더가 있다고 보고 그만큼을 번역 대상에서 뺀다. 번역 검수 중 이 가정이 일부 레코드에서 실제 표시 내용을 먹는다는 것을 확인했다.

원본 바이트를 디코딩해 확인한 사례다. `shop-and-item-dialogue:036`의 저장은 `0a 07 13 06 | 05 0f | ec 02 …`이고 앞 네 바이트는 `さくてき`(索敵)다. 헤더로 처리하면 표시 문자열이 `が…あがった`가 되어 원본 게임에서도 말이 되지 않는다. 같은 방식으로 `victory-and-defeat-dialogue:001`은 `データ`, `shop-and-item-dialogue:029`는 `たいりょ`, `021`은 `なかなか`, `022`는 `しんじ`가 헤더로 잘려 있었다. `shop-and-item-dialogue:069/070`은 더 나빠서 잘린 네 바이트가 `{EC:01}{SP}を`, 즉 동적 아이템 이름 삽입 지점과 목적격 조사다. 그래서 이 두 레코드만 조사가 `을(를)`이 아니라 `을`로 굳어 있었다.

한국어 초벌은 잘린 부분의 뜻까지 이미 담고 있다. 따라서 이대로 설치하면 화면에 원본 일본어가 남고 그 뒤에 같은 뜻의 한국어가 겹친다. G6의 「대상 일본어 잔존 0건」을 정적 검사로는 잡을 수 없다. 검증기가 번역 대상 범위 안에서만 세기 때문이다. 워크스페이스의 `source_markup`도 같은 범위를 쓰므로 사람이 읽어도 잘린 원문은 보이지 않는다.

전체 조사로 근거를 세 겹으로 세웠다.

첫째, 상태 4 핸들러 `0A:$80E6`을 디코드하면 네 바이트를 무조건 `$7818`~`$781B`에 읽고 마지막 값만 1을 뺀다. 창 기술자다. 상태 3 핸들러 `$81B7`은 일곱 바이트짜리 무분기 코드라 이 소비를 건너뛰지 않는다.

둘째, `E5` 프리픽스가 있어 헤더 위치가 확실한 25개 레코드의 값은 `30 [50|70] 12 05`로 극히 균일하다. `prefix_byte_count`가 4인 레코드 가운데 `byte0∈{30,40}`, `byte2∈{10,12}`, `byte3∈{02..05}`인 것들은 같은 족보이고, `10 01 29 87`이나 `0a 07 13 06` 같은 값은 이 족보 밖이다. 창 파라미터로 읽으면 폭 41, 높이 134 같은 화면 밖 값이 된다.

셋째가 결정적이다. 바이트열 `43 0f 3f 40`은 다른 다섯 레코드의 본문 안에도 나오며, 도구 자신이 그 자리에서는 매번 `データ`로 디코드한다. 같은 바이트열이 `victory-and-defeat-dialogue:001`과 `shop-and-item-dialogue:084`에서만 헤더로 잘려 있다. 코드표를 전제하지 않는 독립 확인이다.

판별은 값 족보가 아니라 프리픽스 직후 바이트로 한다. 진짜 헤더 뒤에는 `E9`처럼 줄이나 창을 여는 제어 코드가 온다. 헤더로 가정한 범위 바로 뒤가 텍스트 코드면 경계를 잘못 잡은 것이다.

이 기준으로 세면 경계 오류는 **63개**다. 처음에 값 족보로 세어 기록한 28개는 과소 집계였다. 프리픽스가 통째로 텍스트인 경우만 봤기 때문인데, 실제로는 프리픽스가 `{EA}`나 `{E8}` 같은 제어 코드로 시작해 그 뒤 텍스트까지 함께 먹은 경우가 더 많다. `shop-and-item-dialogue:002`의 잘린 네 바이트는 `{EA}かねか`이고 뷰에 남은 본문은 `゛たりないよ`다. 합치면 `{EA}かねがたりないよ`이며 이것이 실제 표시 문자열이다. 표에서는 `shop-and-item-dialogue` 52개, `village-and-outro-dialogue`·`victory-and-defeat-dialogue`·`epilogue-dialogue` 각 3개, `recruitment-dialogue` 2개다.

넷째로 실행이 이 판정을 확정했다. 지원 원본을 콜드로 띄워 1장 지도에서 좌표 `08/18`의 아군에게 아이템 `0x4C`(`トオメガネ`, 遠眼鏡)를 넣고 `つかう`를 골랐다. 화면은 `アベル は / トオメガネ をつかった / さくてきが 5 あがった`를 표시했다. 즉 `shop-and-item-dialogue:036`의 잘린 네 바이트 `0a 07 13 06`은 실제로 화면에 나오는 `さくてき`다. 창 기술자로 소비되지 않는다. 이 상태로 한국어를 설치하면 화면에 `さくてき색적이 5 올랐다`가 나온다.

남은 미해결은 런타임 경로다. 잘린 28개가 어떻게 헤더 소비를 피하는지는 아직 모른다. 전이 대상 여부와 직전 레코드의 `E7` 종료 모두 상관이 없었다. 표시가 확정됐으므로 이제 질문은 「이 레코드들이 헤더를 갖는가」가 아니라 「추출기가 어디서 경계를 잘못 잡는가」다. `E7` 재개가 상태 9로 직접 들어간다는 기존 계약이 유력한 후보이므로 외부 디스패처 11곳의 재진입 지점부터 확인한다.

이 수정은 504개 레코드의 줄 분할을 바꾸므로 G4 모집단과 그 위에 선 저장 배치·포인터·글리프 집합이 함께 다시 열린다. 이 항목이 닫히기 전에는 주 대사 설치를 배포 적합으로 세지 않는다.

## 58. 철회한다: 이중 진입 모델 폐기 근거는 측정 오류였다

이 번호는 「57번의 경계 수정으로 전이 대상 139개의 직접·전이 진입 차이가 모두 사라졌으니 47·48·49·51번과 그 위의 구조를 폐기한다」는 결정이었다. 근거가 틀렸으므로 결론을 철회한다. 47·48·49·51번은 그대로 유효하다.

측정이 자기 참조였다. 직접 진입 프리픽스는 추출기가 계산한 값을 읽고, 전이 진입 프리픽스는 같은 자리에서 `E8`인지만 보는 식을 새로 써서 비교했다. 두 값이 같게 나온 것은 자료의 성질이 아니라 같은 규칙을 양쪽에 적용한 결과다. 실제 전이 경로는 `inspect_main_transition_prefix_byte_count`가 따로 계산하며 그 함수와 대조하지 않았다.

직접 확인하면 57번의 수정은 전이 대상을 하나도 바꾸지 않았다. 139개 가운데 프리픽스가 달라진 것은 0개이고 분포도 `0 → 0`이 101개, `6 → 6`이 38개로 그대로다. 경계 오류 63개가 전이 대상과 겹치지 않는다는 사실은 폐기 결정을 쓰기 전에 이미 측정해 둔 것이었는데도 결론에 반영하지 않았다.

이중 진입 작업공간 재추출이 「consumer-entry delta 없음」으로 멈춘 것은 별개 원인이다. 57번이 선형 줄 수를 2,732에서 2,800으로 바꾸었으므로 델타 계산의 입력이 달라졌다. 폐기가 아니라 재계산 대상으로 다룬다.

남기는 교훈은 하나다. 어떤 구조를 폐기하려면 그 구조를 만든 근거를 세운 것과 **다른 경로**로 반증해야 한다. 같은 규칙을 다시 적용해 얻은 일치는 반증이 아니다. 규모가 큰 폐기일수록 실행이나 독립 계산으로 한 겹 더 받친 뒤에 쓴다.

## 59. 이중 진입 모델을 폐기한다

58번에서 같은 결론을 냈다가 근거가 자기 참조여서 철회했다. 이번에는 실행으로 받친다.

레코드 프리픽스는 `E5 → 창 기술자 → E8` 한 가지 순서가 아니었다. 실제 배치는 여덟 가지이고 그중 세 형태에는 창 기술자가 아예 없다. 선두가 `E8`인 39개, 선두가 다른 제어 코드인 129개, 기술자 자리가 표시 텍스트인 38개로 합계 206개다. 직접 진입 파서는 이 셋 모두에 네 바이트를 무조건 빼고 있었고, 전이 진입 파서는 기술자를 아예 세지 않았다. 같은 바이트를 두 규칙으로 읽었으니 두 모드가 다르게 보인 것이다.

실행이 어느 쪽이 맞는지 정했다. 세 형태를 각각 화면으로 확인했고 셋 다 전이 파서와 일치했다. `chapter-intro-dialogue:002`는 `e8 90 30 06 06 26 …`인데 화면은 `※どうしたんだ シーダ`로 시작한다. `chapter-intro-dialogue:004`는 `ed ea 10 0f …`인데 화면은 `※だいじょうぶだよ シーダ`이며 직접 파서대로면 줄 제어와 `だ` 한 글자가 사라진다. `shop-and-item-dialogue:036`은 `0a 07 13 06 …`이고 화면은 `さくてきが 5 あがった`다. 세 표본이 139개 전이 대상의 세 무리를 모두 덮는다.

파서를 실제 배치에 맞추면 139개 전이 대상의 직접·전이 프리픽스가 모두 같아진다. 곁가지 신호도 같은 방향이다. 같은 저장 바이트가 서로 다른 리터럴로 읽히던 구조 충돌 16바이트가 0이 되고, 레코드 겹침이 6쌍에서 5쌍으로, 공유 저장이 217바이트에서 197바이트로 줄며, 재배치 불가 줄 1개가 사라진다. 번역 대상 일본어는 315바이트 늘고 원본 무수정 왕복은 그대로 통과한다.

따라서 47·48·49·51번과 그 위에 세운 구조를 폐기한다. 139레코드 417파트의 이중 진입 작업공간, 직접 선두와 전이 선두를 따로 두는 정규화, 전이 payload를 담던 확장 미러 뱅크 `11`~`15`, 전이 resolver와 reader 선택·복귀 및 NMI 물리 뱅크 복원 routine 네 개, 643개 표시 경로 가운데 이중 진입에서 나온 278개가 대상이다. 최대 대사 수요 `187/210`도 이 경로 집합에서 나온 값이므로 다시 계산한다.

남기는 교훈은 셋이다. 같은 자료가 소비 경로에 따라 다르게 보이면 자료가 아니라 읽는 쪽을 먼저 의심한다. 「보수적으로 두 모드를 모두 필요 입력으로 본다」는 판단은 안전해 보였지만 원인을 덮은 채 구조를 두 배로 키웠다. 그리고 큰 폐기는 그 구조를 세운 것과 다른 경로로 반증해야 한다. 58번의 철회가 그 규칙을 어겨서 나왔다.

## 60. 새로 드러난 EC 소비처 111개를 원본 코드로 결속한다

57번의 프리픽스 수정이 잘린 네 바이트 안에 숨어 있던 `{EC:xx}` 소비처 111개를 드러냈다. 분류표가 이들을 모르면 설치 계획은 「미분류 EC 선택자」로 멈춘다. 세 무리를 각각 원본 코드로 따라갔다.

인물 후일담 105개는 하나의 생산자에서 나온다. `04:$A12C`가 아군 색인 `$773B`를 53에서 시작하고, `$A165`가 색인을 하나 내린 뒤 `$A366`을 불러 그 아군의 이름을 동적 슬롯 0 `$78F2`에 옮긴다. 화면 번호는 `$A195`에서 색인에 하나를 더해 만든다. 생존이면 후일담 표(디렉터리 `0x40`), 전사면 라우팅 표(`0x41`)로 갈리지만 이름 쓰기는 갈림길보다 앞선다. 그래서 두 표의 같은 항목 번호가 같은 아군을 가리키고, 항목 범위는 후일담 1..53, 라우팅 2..53이다. 라우팅에 항목 1이 없는 것은 마르스가 쓰러지면 그 자리에서 게임이 끝나 전사 분기가 없기 때문이다. 105개를 낱낱이 나열하지 않고 이 규칙으로 둔다.

`shop-and-item-dialogue:072`는 여섯 번째 시설이었다. 시설 대사표 `06:$9A99`를 다섯 항목으로 읽고 있었는데 `0B:$A2C2`가 시설 종류 5를 진행 표식 `$05F5`의 최하위 비트로 열어 준다. 종류 5는 비밀 상점이고 표의 여섯 번째 항목이 레코드 72를 가리킨다. 항목 수를 6으로 고친다.

레코드 67·69·70은 소지품이 가득 찼을 때 열리는 맡기기·버리기 흐름이다. 들머리 `06:$B130`이 지금 든 물건의 이름을 슬롯 0에 한 번 쓰고, 맡김(`$B1DE`)과 그대로 버림(`$B221`)은 그 한 번의 쓰기를 다시 읽는다. 인덱스로 고른 물건을 버릴 때(`$B23C`)만 슬롯 1에 따로 쓴다. 생산과 소비가 한 화면 안에 있지 않은 첫 사례라 별도 생산자 갈래로 둔다.

결과로 소비 수요 142개가 공급 142개와 정확히 맞물린다. 미결속·불일치·초과 공급이 모두 0이다.

## 61. 표시 단위를 정규 레코드로 되돌린다

59번이 이중 진입 모델을 폐기했지만 「표시 경로」라는 어휘와 그 자료 구조는 남아 있었다. 런타임 식별표는 엔트리마다 직접·전이 두 색인을 네 바이트로 직렬화했고, 표시 계획은 레코드마다 같은 ID를 두 번 담은 경로 객체를 만들었다. 실체가 없는 이름이 남으면 읽는 사람이 매번 같은 것임을 다시 유도해야 한다. 이름째로 지운다.

같이 정리한 것은 값을 고정하던 단언들이다. 상점 경로 수 2, 실행 코드 시작 주소 `$B8A0`, 재료 payload 22,642바이트, 식별표 2,396바이트는 모두 그때의 결과값이지 지킬 값이 아니었다. 자료가 줄면 실행 코드 자리가 넓어지는 것이 정상인데 등식으로 묶어 두면 개선이 실패로 보인다. 용기 크기 24,576바이트처럼 다른 도메인의 시작점을 고정하려고 정한 값만 정확한 값으로 남기고, 나머지는 하한이나 관계식으로 바꿨다. 56번을 따른다.

재계수 결과는 다음과 같다. 표시 단위 643 → 504, 페이지 작업집합 1,170 → 928, 고유 글리프 715 → 713, 정적 페이지 상한 36 → 35, 직접 저장 30,224 → 29,792바이트, 식별표 2,396 → 1,350바이트, 실행 코드 예약 1,888 → 3,791바이트. 최대 페이지 슬롯 수요는 `188/210`이다.

## 62. 실기 가능성을 설계 불변 조건으로 둔다

실기와 플래시 카트로 검증할 수단이 없다. 그렇다고 실기를 포기하지는 않는다. 검증은 못 하더라도 **실기에서 성립할 수 없는 선택은 하지 않는다**를 불변 조건으로 둔다.

이 조건이 필요한 이유는 검증 수단의 비대칭 때문이다. 에뮬레이터는 여러 규칙 위반을 그냥 넘긴다. 그래서 «에뮬레이터에서 정상»은 «실기에서 정상»의 증거가 되지 못하는데, 우리가 가진 증거는 전부 앞쪽뿐이다. 증거로 못 막으니 설계로 막는다.

당장 이 조건이 하나를 잡아냈다. 대사 런타임 설계 초안이 프레임 예산을 256바이트로 잡았는데, NTSC vblank 2,273사이클에서 바이트당 8사이클이면 2,048사이클로 90%다. 같은 vblank에 OAM DMA 513사이클과 기존 NMI의 입력 스캔·스크롤 복원·전투 합성 판정·PPU 큐 flush가 이미 들어 있으므로 실기에서는 넘친다. vblank를 넘긴 `$2007` 쓰기는 렌더링 중 쓰기가 되어 화면이 깨진다. 에뮬레이터에서는 그대로 돌아갔을 것이다. 예산을 사이클로 유도하도록 고쳤다.

G2 작업 2의 «에뮬레이터와 플래시 카트 호환 범위를 선언한다»가 비어 있었다는 것도 함께 확인했다. G2는 Mesen 동등성만으로 통과했다. 선언이 없으면 G7의 실기 판정에 기준이 없으므로 선언을 따로 닫는다.

빌드 산출물에서 고칠 것은 둘이다. 헤더가 iNES 1.0이라 CHR ROM과 별개인 4 KiB CHR RAM을 표현하지 못하므로 NES 2.0으로 올린다. CHR ROM 216 KiB는 2의 거듭제곱이 아니므로 매퍼 상한과 같은 256 KiB로 정렬한다. 대사를 CHR RAM 합성으로 돌리기로 한 61번 결정이 정적 페이지를 34..63으로 묶으므로 이 정렬은 저절로 맞는다.

매퍼 165 자체의 상한도 다시 확인했다. CHR 뱅크 레지스터가 1 KiB 단위 8비트라 CHR는 256 KiB, PRG는 MMC3식 8 KiB 단위라 512 KiB가 끝이다. 현재 PRG 512 KiB는 상한에 정확히 닿아 있다. 더 늘릴 여지가 없으므로 앞으로 PRG를 늘리는 안은 매퍼 재판정과 같은 무게로 다룬다.

## 63. 대사 합성의 소비자 자리를 다시 찾는다

62번의 실기 불변 조건을 대사 런타임 설계에 적용하려고 기존 NMI의 vblank 여유를 실측했다. 설계가 정한 소비자 자리 `$C191 → $FC20`이 틀렸다.

원본 NMI는 `$C163`에서 시작해 `$C1C3`에서 RTI한다. 사이의 호출 순서는 OAM DMA, `$C3A5`, `$C296`, `$C1EC`, `$D4AD`, `$C733`, `$C36A`, `$C1C4`, `$C1FB`, 그리고 이 프로젝트가 넣은 `$FC20`이다.

고정 뱅크의 PPU 레지스터 쓰기 자리를 전수로 찾으면 데이터 쓰기 `$2007`은 `$C27A`·`$C3DD`·`$D501`에 있다. 각각 `$C296`·`$C3A5`·`$D4AD` 안이다. 스크롤 `$2005`는 `$C36F`·`$C374`로 `$C36A` 안이다. 즉 원본은 «PPU 데이터 → 스크롤» 순서로 vblank를 쓰고 그 뒤에 음악과 논리를 돌린다.

`$FC20`은 스크롤 설정보다 뒤다. 거기서 `$2006`을 건드리면 방금 세운 스크롤 래치가 깨진다. 전투 합성이 이 자리에서 문제없던 것은 전투 전환이 렌더링을 끈 채 합성하기 때문이고, 대사는 화면을 그린 채로 나오므로 같은 면제가 없다.

실측도 같은 결론이다. 1장 맵에서 `$C191` 도달 시점을 두 프레임 재니 하나는 scanline 256(vblank 안, CPU 약 498사이클 남음), 다른 하나는 scanline 16이었다. 뒤쪽은 vblank가 끝난 지 오래고 이미 화면을 그리는 중이다. 같은 화면에서 프레임 간 편차가 37스캔라인, 약 4,200사이클이다.

반면 앞쪽은 여유가 있다. `$C17F`에서 scanline 246·cycle 111로 CPU 약 1,668사이클, `$C185`에서 scanline 246·cycle 231로 약 1,628사이클이 남았다.

따라서 소비자 자리는 원본의 PPU 데이터 작업이 끝나고 스크롤 설정보다 앞인 `$C185`가 후보다. 다만 위 값은 조용한 프레임 표본이고 편차가 4,200사이클이므로 이것으로 예산을 정하지 않는다. 예산은 여러 장면에서 그 자리의 최악값을 모은 뒤에 정한다.

설계 초안의 «프레임당 128바이트»도 근거가 없어졌다. 잠정값조차 두지 않고 측정 결과가 나온 뒤에 적는다.

남기는 교훈은 62번의 되풀이다. 기존 훅이 이미 있고 전투에서 동작한다는 사실이 그 자리가 대사에도 맞는다는 뜻은 아니었다. 두 소비자의 렌더링 조건이 다르기 때문이다. 훅을 재사용할 때는 그 훅이 성립하던 조건까지 같이 물려받는지 확인한다.

## 64. 예산을 재지 말고 조용한 프레임에서만 쓴다

63번이 남긴 «`$C185`의 최악값을 모아 예산을 정한다»를 실행하다가 그 계획 자체가 틀렸다는 것을 알았다. 최악값이 존재하지 않기 때문이다.

`$C3A5`와 `$C296`은 같은 블록 해석기 `$C3E7`을 부른다. 해석기는 0 종료 블록 목록을 끝까지 걷고 블록마다 최대 63바이트를 쓴다. 목록 길이는 게임이 큐에 넣은 만큼이고 코드에 상한이 없다. 내부 루프는 바이트당 18사이클이라 63바이트 블록 하나가 1,134사이클, vblank의 절반이다. 즉 `$C185`에 남는 vblank는 자료가 정하는 값이고, 표본을 아무리 모아도 상한이 증명되지 않는다.

대신 자리를 `$C179`로 옮긴다. `JSR $C3A5`를 소비자 호출로 바꾸고 소비자가 `JMP $C3A5`로 끝낸다. 이 자리 앞에는 NMI 진입 오버헤드와 OAM DMA뿐이고 둘 다 고정 비용이라, **남는 vblank가 표본이 아니라 상수가 된다.** 실측으로 확인했다. `$C179` 진입이 scanline 246 cycle 3, vblank 잔여 CPU 1,704사이클이고, 이는 계산값 2,273 − 566과 3사이클 차이다. 63번이 잰 편차 4,200사이클은 전부 `$C179` 뒤에 있었다.

그리고 소비자는 첫 동작으로 원본의 대기열 표시 `$21`·`$22`·`$89`·`$8A`를 본다. 하나라도 서 있으면 이번 프레임을 건너뛴다. 전부 0이면 원본은 그 프레임 vblank에 PPU 데이터를 쓰지 않는다. 7장 맵·명령 창·이야기 대기 화면 표본에서 표시가 전부 0인 프레임의 `$2007` 쓰기는 0건이었고, 표시가 선 프레임의 쓰기는 전부 `$C3DD` 아니면 `$D501`에서 나왔다.

이 교환이 핵심이다. «남은 예산이 얼마인가»는 6502가 실기에서 답할 수 없는 질문이고, «원본이 이 프레임에 일이 있는가»는 제로 페이지 4바이트로 답할 수 있는 질문이다. 측정으로 상한을 추정하는 대신 상한이 성립하는 조건을 실행 시점에 확인한다.

예산은 이제 유도된다. 1,704 × 0.8 = 1,363, 소비자 고정 비용 63을 빼고 바이트당 8사이클로 나누면 162바이트, 타일 경계로 내려 **프레임당 10타일 160바이트**다.

교훈은 이렇다. 측정이 상한을 주지 않을 때는 표본을 더 모으는 것이 답이 아니다. 상한이 성립하는 자리로 옮기거나, 상한이 성립하는 조건을 코드가 직접 확인하게 만든다.

### 실행 확인

전송 계층만 실은 탐침 ROM(`build-dialogue-transport-probe`)으로 64번의 예산이 실제 ROM에서도 참인지 확인했다.

| 지점 | scanline / cycle | 남은 vblank(CPU) |
|---|---|---|
| `$C179` 진입 | 246 / 3 | 1,704 |
| `$C3A5` 인계 (표본 3회) | 257 / 22, 24, 69 | 447, 446, **431** |

소비자가 쓴 사이클은 최악 1,273이고 정적으로 유도한 상한 1,351(트램폴린 116 + 전송 1,235)보다 작다. 인계 시점은 세 표본 모두 scanline 257로 **vblank 안**이고, 표본 간 편차가 16사이클이다. 편차가 작은 것은 시작과 몸통이 둘 다 고정 비용이기 때문이고, 이것이 `$C185` 대신 `$C179`를 고른 이유 그대로다.

동작도 확인했다. 210타일 콜드 요청이 프레임당 정확히 8타일씩 줄고(포인터 +64, 색인 +8, 잔여 −8), 마지막 타일을 올린 뒤에야 `$07F4`가 `ready(3)`로 바뀌었다. 게이트가 선 프레임은 건너뛰어 210타일이 27프레임이 아니라 38프레임에 끝났다. 굶지 않고 느려지기만 하는 것이 설계가 의도한 실패 모습이다.

새 증거로 이 대전략이 바뀌면 세부 작업 내역이 아니라 바뀐 방향과 이유만 이 문서에 추가한다.

## 65. stateless CHR helper를 상태 생산자로 바꾸지 않는다

대사 전송 뒤 원래 CHR을 복원하려고 `$FA80`에 관측 훅을 달고 `$07EB`에 최근 페이지를 기록한 안을 철회한다. `$07EB`는 기존 전투 런타임의 `$07E0..$07EF` 소유 범위 안이고, mapper165는 직접 CHR 기록기를 의도적으로 stateless로 둔다. helper 관측이 `$5B/$5C`를 갱신하면 중앙 selector 상태와 일시적 직접 기록이 섞인다.

권위 있는 원천은 중앙 FD/FE 기록기가 이미 보존하는 `$5B/$5C`와 상위 비트 `$52`다. 대사 소비자는 이를 읽기만 하고 FD와 FE를 별도 helper로 복원한다. 설치는 중앙 기록기 두 곳과 helper 두 곳의 정확한 후보 바이트에 함께 결속한다. CHR-RAM에 넣을 배경도 한 페이지 번호가 아니라 이 FD/FE 쌍과 화면 수명에서 유도한다.

## 66. 대사 표시에서는 FD만 CHR RAM으로 바꾼다

65번 뒤에는 FD와 FE의 가시 패턴을 한 CHR-RAM 페이지에 합치는 안을 세웠다. 실제 7장 대사 네임테이블을 기존 MMC4 래치 모델로 다시 읽으니 같은 타일 코드가 FD와 FE에서 서로 다른 패턴을 요구했다. 이는 누락된 배경 페이지를 더 복제해서 풀 문제가 아니라, 원본이 두 래치로 분리한 네임스페이스를 표시 selector가 하나로 합친 설계 오류다.

전송과 표시는 역할을 나눈다. 전송 중에는 현재 래치와 관계없이 PPU 쓰기가 RAM에 닿도록 FD와 FE를 모두 잠시 RAM에 걸고, 프레임 이탈에서 중앙 원천 상태로 둘 다 복원한다. 준비 완료 뒤 화면에 보여 줄 때는 원본 대사 글꼴 페이지 `00`과 결속한 FD만 RAM으로 바꾸고 FE는 복원된 원본 CHR ROM에 둔다. 원천 FD가 `00`이 아니면 기존 selector 사슬로 실패 닫힘한다. 앞서 실행 검증한 개별 대사 페이지와 같은 래치 분리를 전역 런타임에 적용하며, FD/FE 한 페이지 합성안은 폐기한다.

## 67. 준비 완료 게시가 FD 하드웨어 선택까지 소유한다

첫 FD-only 탐침에서 전송은 프레임 3269에 `ready(3)`까지 갔지만 화면은 이전 FD 페이지 그대로였다. 중앙 FD selector는 `$29 == 0A`를 주 대사 수명으로 보았는데 실제 완성 화면의 `$29`는 `06`이었다. `$29`는 NMI가 임시 PRG 매핑 뒤 되돌릴 뱅크 그림자이지, 현재 화면이 주 대사인지를 나타내지 않는다. 또한 `ready` 뒤 중앙 FD 공급자가 다시 불린다는 보장도 없다.

따라서 마지막 전송 프레임이 FE를 원본으로 복원한 뒤 FD 레지스터 2를 RAM으로 직접 게시하고, 그 하드웨어 선택 뒤에만 `ready`를 쓴다. 이후 중앙 FD 공급은 `ready`, 원본 대사 상태 `00..0E`, 원천 FD `00`을 확인해 같은 RAM을 다시 고른다. 원천 FD가 다르면 `ready`를 게시하지 않고 요청을 0으로 내려 원본 표시로 실패 닫힘한다. 준비 표식과 실제 래치 선택을 서로 다른 미래 호출에 나누지 않는다.

## 68. 반복 전환 생산자는 완성된 같은 원문 0페이지를 재사용한다

두 번째 FD-only 탐침은 네임테이블 코드가 FD 래치를 실제로 고르고 CHR RAM에도 해당 한글 패턴이 있음을 확인했다. 그런데 `ready(3)` 직후 `0A:$85F8`의 E4 전환 생산자가 같은 `$77F4/$77F1`로 요청 발행기를 다시 불렀다. 요청은 `cold_requested(1)`로 내려가고 커서는 처음부터 다시 시작했다. 완성 페이지를 선택하지 못한 것이 아니라, 선택할 수 있는 수명이 한 프레임도 유지되지 않은 것이다.

요청 발행기는 이제 `ready + 가시 페이지 0 + 게시 원문 selector/index 일치`를 모두 만족할 때만 합성을 건너뛰고 밀어낸 원본 resolver로 바로 넘긴다. 전송 중에만 필요한 항목 커서 두 바이트는 완성 직전에 게시 원문 정체성으로 바꿔 같은 검증된 저장 범위 안에서 phase union으로 쓴다. 다음 페이지, 다른 원문, E7 외부 인계와 수명 재진입은 이 조건을 만족하지 않아 기존처럼 냉합성한다. 이 판정이 커져도 트램폴린과 충돌하지 않도록 CHR 표시 selector는 별도 exact-`FF` 동굴 `$F558..$F700`으로 분리한다.

새 산출물 `A4AE24B8DE40F2930FDC799C48A6D2C3E6E2894D`의 콜드 1장 실행에서 프레임 2929에 `ready(3)`와 게시 정체성 `[80,02]`가 만들어졌다. 이후 `cold_requested(1)` 쓰기 중단점을 건 300프레임이 중단 없이 끝났고 프레임 3230에도 상태와 정체성이 같았다. 매퍼는 FD 레지스터 2를 RAM `00`, FE 레지스터 4를 원본 `68`에 뒀다. 이 증거가 통과시키는 것은 반복 E4 생산자의 멱등성뿐이다. 당시 대사 저장소가 새 런타임 코드북으로 다시 인코딩되지 않았으므로 화면의 한글 정상 표시는 통과하지 않았다.

이 조건의 `가시 페이지 0` 제한은 76번에서 폐기됐고, 원본 resolver까지 생략하던 재사용 복귀는 78번에서 폐기됐다. 이 항목은 그 두 결정을 거치기 전의 전략 단계로만 남긴다.

## 69. 런타임 코드북과 대사 저장소는 같은 설치 단위다

전역 대사 계획은 새 코드북·atlas·그룹 재료를 만들면서도 누적 후보에 들어 있던 국소 코드북 대사 바이트를 그대로 소비했다. 계획은 대사 저장 쓰기 수를 0으로 선언했기 때문에 빌드 자체는 통과했고, 실행에서도 `ready`와 FD/FE 수명은 안정적이었지만 네임테이블 코드가 다른 글리프를 골랐다. 런타임 재료와 본문 인코딩을 별도 단계로 취급한 것이 첫 불일치였다.

따라서 전역 설치는 정규 대사 저장소 11구간과 포인터 517개를 현재 `EncodedMainDialogueBundle`에서 같은 `TrackedImage`에 쓴다. Expected Write는 결속된 누적 후보의 정확한 기존 바이트를 선행조건으로 쓰며, 방출 뒤 최종 이미지의 모든 저장 구간과 포인터를 현재 인코딩과 다시 비교한다. 쓰기 개수만 맞거나 생성기끼리 같은 계산을 공유한다는 사실만으로 설치 성공을 선언하지 않는다.

탐침 `018EDE4D6E6E500D025CBCC5279194BB142161ED`의 콜드 1장 프레임 2937은 `ready`를 쓰는 NMI 내부에서 멈췄다. 그 순간 메모리에 새 코드북이 있어도 프레임버퍼는 직전 완성 프레임이므로 화면 판정에 쓰지 않는다. 한 프레임 뒤 2938에서 대사 네임테이블 코드와 현재 그룹 23 코드북, 참조 CHR 타일 16바이트, PPU 패턴 메모리와 읽히는 한글 본문이 함께 일치했다. 저장소와 런타임 코드북의 설치 단위는 이 표본에서 닫혔다. 남은 것은 `{EA}`가 실행 중 만드는 원본 표식 코드와 장 제목을 같은 화면 수명에 넣는 일이다.

## 70. 준비 상태와 표시 완료 프레임을 구분한다

`ready` 쓰기 중단점은 전송 완료와 FD 하드웨어 게시를 정확히 잡지만, CPU가 아직 NMI 안에 있어 새 CHR 상태가 한 프레임을 그렸다는 뜻은 아니다. 따라서 그 지점의 스크린샷은 메모리·제어 상태 증거로만 쓴다. 표시 정확성은 중단점을 해제한 뒤 최소 한 프레임을 진행하고, 같은 산출물의 네임테이블·CHR·PPU 상태와 화면을 함께 비교한다. 준비 표식과 프레임버퍼를 같은 시점으로 취급하지 않는다.

## 71. 장 제목은 인트로 전이 사슬 전체에서 같은 코드를 쓴다

장 제목 저장소는 장마다 한 번만 인코딩되지만, 화면에 남아 있는 동안 대사 페이지의 CHR 코드북은 바뀐다. 제목 글리프를 첫 페이지에만 더하거나 페이지마다 임의 코드를 주면 다음 페이지에서 이미 그려진 제목 타일이 다른 글리프로 바뀐다. 제목을 페이지마다 다시 쓰는 안도 원본 수명에 없는 부수효과를 만든다.

따라서 원본 `E5` 장 문맥 25개에서 각 인트로의 완전한 `E4/E6` 전이 사슬을 구한다. 장 제목 글리프는 그 사슬의 모든 가시 페이지 작업집합에 더하고, 고유 제목 글리프 88개에는 해당 페이지가 보존하는 코드를 피하는 전역 일대일 배정을 찾는다. 페이지 패커는 고정 글리프-코드가 충돌하는 작업집합을 한 페이지에 합치지 않으며, 제한 해 solver도 같은 비호환 쌍을 제약으로 받는다.

현재 결속은 관련 작업집합 129개, 개별 최대 `188/210`, 합쳐진 페이지 최대 `210/210`, 결정적 정적 그룹 37개다. 장 제목 저장소 25개는 이 배정으로 인코딩해 대사 저장소·런타임 재료와 같은 `TrackedImage`에 쓰고 최종 바이트를 다시 읽는다. 이는 정적 설치 관문의 통과이며, 화면 표시는 새 산출물의 콜드 1장 경로에서 따로 승인한다.

## 72. 레코드 전환과 CHR 상주 그룹 전환을 같은 것으로 보지 않는다

원문 selector/index가 달라져도 새 가시 페이지가 요구하는 정적 그룹은 직전과 같을 수 있다. 이 경우 원문 정체성 비교만으로 매번 `cold_requested`를 게시하면 이미 완성된 CHR-RAM을 화면 위에서 다시 만들고 중간 글리치를 노출한다. resolver가 성공한 뒤 직전 상주 그룹과 새 그룹을 비교하는 공통 발행기를 두고, 같으면 CHR 쓰기 없이 새 원문 정체성과 `ready`만 게시하며 다를 때만 냉합성을 요청한다.

원본 완료 상태 `10`은 대사 수명 종료가 아니라 E6가 선언한 다음 레코드로 넘어가는 짧은 비표시 전이다. selector는 이 상태에서 원본 페이지로 돌아가므로 CHR 상주권을 유지해도 중간 화면에 RAM을 노출하지 않는다. 1장 실행에서 기존 프레임 2991의 불필요한 냉합성이 사라진 것을 확인했다. 반면 E7은 외부 상태기가 사이에 들어오므로 같은 규칙으로 일반화하지 않는다. 관측한 한 호출자가 CHR-RAM 4,096바이트를 보존했다는 사실은 전역 계약이 아니며, 모든 CHR-RAM 작성자가 공유하는 소유권 무효화가 생기기 전까지 E7 재진입은 별도 관문이다.

## 73. 외부 상태 이름이 아니라 실제 CHR-RAM 작성자가 상주권을 끊는다

E7은 제어권을 외부 상태기에 넘기지만 그 사실만으로 CHR-RAM이 바뀌지는 않는다. 호출자 11개를 안전 목록으로 만드는 대신 누적 후보의 직접 CHR-RAM 선택 세 지점과 실제 4 KiB 전투 합성 호출 `$FC49 → $FC99`를 함께 결속한다. 전투 합성 호출은 대사 `ready`를 내리는 소유권 이전 래퍼를 거친 뒤 원래 합성기로 꼬리 호출한다.

E7 인계 중에는 상태 17이 기존 selector를 원본 경로로 돌리므로 대사 RAM을 화면에 고르지 않는다. 따라서 인계 자체는 상주권을 보류하고, 복귀 생산자는 전투 합성기가 그 사이 실제로 상주권을 내리지 않았을 때만 같은 그룹을 재사용한다. 정확 산출물 `EA07D1B7BCBB63590699163AA8AD098D5DCC0F40`의 프레임 3141 E7 인계에서 `ready=03`, 그룹 `15`가 유지됐고 프레임 3261의 이어진 대사는 읽을 수 있었다.

이 결정은 모든 비활성 상태로의 무제한 연장이 아니다. `$07F0..$07FA` 저장소는 주 대사와 결속한 E7 경계 밖에서는 보존이 증명되지 않았으므로 일반 종료는 계속 무효화한다. 수명은 화면 이름이 아니라 «상태 저장소가 보존되고 CHR-RAM 작성자가 없다는 두 증명»이 모두 있을 때만 늘린다.

## 74. 완성 프레임만 읽혀도 전환 중 글리치가 있으면 실패다

같은 산출물에서 서로 다른 그룹의 실제 냉합성이 시작되자 프레임 3666·4444·5025에 기존 한글 타일맵이 준비되지 않은 글꼴로 표시되어 깨졌다. 약 231프레임 뒤 `ready` 화면이 다시 읽힌다는 사실은 이 표시 실패를 상쇄하지 않는다.

따라서 실행 관문은 `ready` 뒤 한 장의 스크린샷이 아니라 요청 시작부터 첫 표시 완료까지의 전 구간이다. 먼저 E6·E7처럼 증명 가능한 불필요한 냉합성을 소유권 재사용으로 없애고, 그래도 남는 실제 그룹 변경은 이전 화면을 깨뜨리지 않는 원자적 표시 또는 오프스크린 준비 구조를 정해야 한다. 이 관문이 닫히기 전에는 다른 번역 도메인을 더 연결해도 전역 대사 런타임 완료로 세지 않는다.

## 75. 필수 냉합성은 미완성 CHR-RAM 대신 전용 빈 표시 페이지를 쓴다

mapper 165가 제공하는 CHR-RAM은 4 KiB 한 장이라 완성 페이지와 작성 중 페이지를 동시에 둘 수 없다. 같은 RAM을 이중 버퍼처럼 다루는 안은 폐기한다. 대신 회수 가능한 CHR-ROM 첫 페이지인 물리 `50`, mapper 값 `C8`을 냉간 요청의 표시 전용으로 예약한다. 원본 FD 글꼴 페이지를 복제해 영어·숫자·제어 43코드와 레이아웃 예약 3코드는 바이트 그대로 두고, 한글 활성 슬롯 210개만 빈 타일로 만든다. 따라서 이전 네임테이블의 한글 코드는 사라지지만 번역 대상이 아닌 원본 영문과 UI는 유지된다.

선택 소유권은 세 곳에 둔다. resolver가 다른 그룹을 게시할 때 NMI를 되살리기 전에 FD를 전용 페이지로 바꾸고, 중앙 FD selector는 `cold_requested` 동안 같은 선택을 유지하며, NMI 전송 소비자는 쓰기를 위해 잠시 CHR-RAM을 건 뒤 원본 FD/FE를 복원하고 렌더링 재개 전에 FD만 전용 페이지로 다시 고른다. `ready`에서는 기존 계약대로 FD만 완성 CHR-RAM을 고르고 FE는 원본 배경 페이지에 남는다. 원천 FD가 대사 기반 페이지 0이 아니면 전용 페이지를 강제로 쓰지 않고 요청을 무효화해 원본 경로로 실패 닫힘한다.

정확 탐침 `30C5406ED6724ADBBCA2B124D626129587C0D22D`에서 cold 게시 중단점 다음 첫 표시 프레임 15154, 복원 단계 15185·15258, 덮기 단계 15289·15336은 모두 빈 대사 슬롯과 보존된 맵·창·초상화·원본 영문/숫자 UI를 보였다. 프레임 16336에는 `$07F4=03`과 장 제목·원본 생성 표식·읽을 수 있는 한글 본문이 함께 나타났다. 중단점 프레임 자체는 요청 전 프레임버퍼이므로 표시 판정에서 제외한다. 이 결정은 글리치를 닫지만 최대 231프레임의 빈 창 대기를 성능상 승인하지는 않는다. 후속 `continuous` 차이 전송은 같은 표시 안전 계약을 유지해야 한다.

## 76. 반복 생산자는 0페이지가 아니라 현재 완성 페이지를 보존한다

한 레코드의 다음 페이지를 합성해 `ready`까지 게시한 뒤에도 원문 생산자는 같은 selector/index로 다시 호출된다. 이때 가시 페이지가 0이 아니라는 이유만으로 새 레코드 해석을 시작하면, 완료 훅이 올린 다음 페이지를 반복 생산자가 즉시 0페이지로 되돌려 대사가 진행되지 않는다.

반복 생산자의 재사용 조건은 이제 `ready + 같은 게시 원문 정체성`뿐이다. 가시 페이지 번호와 상주 그룹은 완료 훅이 이미 확정한 현재 결과로 보존한다. 원문 정체성이 달라질 때만 선행 조회값을 다음 현재 레코드로 승격하며, 수명이 끝나면 상태 무효화가 같은 정체성의 새 진입도 재사용하지 못하게 한다.

실행에서는 다음 페이지가 그룹 `04`로 전환되어 100프레임 뒤 `ready`가 됐지만, 옛 조건이 다시 page 0/group `14`를 합성해 직전 화면으로 돌아가는 반례를 확인했다. 따라서 «글자가 깨지지 않는다»만으로는 통과가 아니며, 입력 뒤 페이지 진행이 유지되는지도 같은 아티팩트에서 검증한다.

## 77. 화면에 함께 남는 대사 전이 사슬은 한 코드북 수명이다

원본 상태 `10`과 `E4/E6` 전이는 논리적 레코드 경계일 뿐 네임테이블을 지우는 경계가 아니다. 이전 대사의 타일이 남아 있는 동안 코드북만 바꾸면 그 타일이 다른 글자로 재해석된다. 따라서 한 레코드의 연속 페이지와 연결된 레코드 전이 사슬 전체를 하나의 코드북 수명으로 묶는다. 현재 전체 그래프는 291개 수명이고, 가장 큰 수명도 활성 슬롯 `198/210`에 들어간다.

이 결정으로 현재 637개 상주 전이는 모두 같은 코드북을 재사용한다. 이후 화면별 예외를 더하는 대신, 새 전이 종류가 생기면 먼저 그 경계가 네임테이블을 실제로 지우는지 증명하고 그래프 수명에 포함한다.

## 78. 한글 재사용 최적화는 원본 상태 처리를 생략하지 않는다

같은 코드북과 현재 페이지를 재사용해도 훅이 가져간 원본 호출은 실행한다. v24는 같은 원문 정체성을 보자 한글 합성뿐 아니라 원본 `$E6B2`까지 생략했고, 새 대사 더블버퍼 길이 `0`이 그대로 소비되어 `$0451..$0550` 256바이트를 덮었다. 그 결과 `$053E=ED`가 잘못된 상태 분기를 만들고 `$8D0F`의 JAM으로 이어졌다.

재사용 경로는 이제 한글 페이지 재합성만 건너뛰고 원본 resolver로 tail-call한다. v25에서는 원본이 보조 버퍼 길이 `06`을 먼저 기록했고, 첫 레코드 전이 뒤 800프레임 동안 메모리 오염·JAM 없이 이어지는 한글 대사를 표시했다. 최적화의 통과 조건은 출력 동일성뿐 아니라 밀어낸 원본 호출의 복귀값·플래그·부수효과 보존이다.
