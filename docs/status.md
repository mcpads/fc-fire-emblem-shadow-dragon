## 검증 결과

- 입력: 지원 일본판 SHA-1 `0179c550d424e0397496078789e7b116601d120c`
- PoC ROM SHA-1: `4529ea8d3724646dc8f4b19e68895b19ad95e2a8`
- 변경 바이트: 119개, 모두 등록된 설정 표·일본어 CHR 타일 쓰기 범위 안
- 영문 패치 ROM 입력: 일본판 원본 SHA-1 불일치로 거부, 산출물 없음
- 빌드 검사: `cargo test --all-targets` 27개 통과, `cargo clippy --all-targets -- -D warnings` 통과
- 글꼴 공급 보고서: CHR 32페이지·8,192타일, 비공백 7,849개, 전부 0인 패턴 343개
- 첫 글꼴 페이지: 보호 코드 42개, 미확정 코드 214개, 사용 가능 판정 0개
- MMC4 공급 보고서: `$B000/$C000/$D000/$E000` 작성 루틴, 직접 `JSR` 후보 12/12/11/7곳, `$E000` 작성 루틴의 직접 `JMP` 후보 2곳
- 텍스트 표 보고서: 포인터 297개, 고유 문자열 296개, 고유 저장 1,788바이트, 원문 보호 45바이트, 비공백 타일 미확정 1,693바이트, `FF` 공백 타일 미확정 50바이트

현재 빌드는 전역 가나 타일 12개를 임시 재사용하므로 설정 화면 밖의 일본어가 깨진다. 이는 한글 표시 소비 경로만 검증하는 PoC 한계이며, 정식 패치에는 허용되지 않는다. 일본판에 원래 존재하는 영어를 번역하거나 손상하는 것도 허용되지 않는다.

## 현재 관문

전체 한글화의 선행 조건은 정식 글꼴 공급 구조다. 원본 CHR 8,192타일 가운데 7,849타일이 비어 있지 않고, 첫 글꼴 페이지에서 전부 0인 타일은 `95`, `FF`뿐이다. 원본 MMC4의 고정 CHR-ROM에 완성형 한글을 상주시키는 안은 채택하지 않는다.

[작업 로드맵](roadmap.md)의 G1 가운데 정적 CHR 목록, 확인된 설정·상태 표의 초기 보호 판정, MMC4 공급 루틴 목록과 1장 초반의 주요 문자 화면 실측을 구현했다. 관측한 모든 문자 화면은 `$5B=00`을 사용하고 화면별 그래픽을 `$5C`에 짝지었다. 문자창이 없는 맵에서는 페이지 00이 빠지고 그래픽 페이지 `15`, `18`, `19`가 교체되므로 동적 글꼴 수명은 화면 전환과 결속해야 한다. 상세 근거는 [렌더 경로 조사](render-paths.md)에 있다.

첫 텍스트 모집단 7개 표는 소비자와 저장 경계를 확인했고, 적 이름·장 제목의 합성 파서에서는 `0F`·`1F`가 출력 폭을 늘리지 않는 결합부호임을 확인했다. 그러나 대사·메뉴·전투 메시지를 포함한 전체 모집단은 아니다. 미분류 1,743바이트는 비공백 타일 대응 1,693바이트와 전부 0인 `FF` 타일 대응 50바이트로 나뉘지만, 다른 다운스트림 표시 의미가 확인되기 전에는 번역 대상으로 계수하지 않는다. 전투·상점·저장·장 전환·엔딩 렌더 경로와 다른 문자열·그래픽 참조자가 남았으므로 214개 미확정 글꼴 코드를 회수 후보로 승격하지 않는다.

## 다음 작업

1. 대사·메뉴·전투 메시지의 포인터·인라인 문자열을 소비자별로 추가한다.
2. 새로 찾은 소비자마다 `ED`·`EF` 동작을 확정하고 `FF`와 비공백 코드가 다운스트림 렌더러에서 갖는 의미를 판정한다.
3. 214개 미확정 코드의 소비 여부를 판정하고 보호 고정 슬롯과 한글 활성 슬롯 예산을 확정한다.
4. 매퍼 후보와 지원할 에뮬레이터·플래시 카트 범위를 결정한다.

동적 한글 글꼴 관문이 통과하기 전에는 설정 PoC의 번역 범위를 늘리지 않는다.
